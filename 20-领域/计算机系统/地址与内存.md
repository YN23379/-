## 地址
计算机系统中，地址的表示直接由系统位宽决定：

- 32位系统使用32位地址，用8位十六进制数表示
    
- 64位系统使用64位地址，用16位十六进制数表示
```
32位系统地址示例：0x12345678 (8位十六进制)
64位系统地址示例：0x00007FFF12345678 (16位十六进制)

每个地址指向1字节的内存位置
```
这是因为地址总线的位数等于系统位宽，每个地址都是系统位宽那么长的二进制数，转换成十六进制就是位数除以4。

计算机内存采用'字节寻址'模型，即每个内存地址对应1字节(8bit)的存储空间，这是硬件层面的约定，与系统位宽无关。

系统位宽(32/64位)决定的是：
- 地址的二进制位数（32位或64位）
    
- 能寻址的内存范围大小（4GB或16EB）
    
- 但每个地址仍然指向1字节的内存单元


当CPU要读取int、long等多字节数据时，会连续访问多个地址的字节然后组合。

地址是内存位置的编号，在32位系统中用8位十六进制数表示。每个地址位置存储1字节数据，用2位十六进制数表示。这是两个不同的概念：

- 地址编号：标识位置（32位系统下是8位十六进制）
    
- 存储内容：该位置的数据（总是2位十六进制，因为1字节=8位）


数据总线和字长
- 32位系统的4字节字长正好匹配32根数据总线，单次传输效率最优
    
- 64位系统同理，8字节字长匹配64根数据总线  
    这种硬件层面的对齐设计确保了内存访问的最高效率。


## 程序内存分布
1. **地址空间布局随机化**：现代操作系统为了安全，每次运行程序时，栈、堆、动态库的起始地址都会随机变化。
    
2. **动态库加载**：不同程序依赖的库不同，加载地址也不同。
    
3. **硬件与架构**：32位与64位系统的地址空间大小完全不同。
由于以上原因内存布局是不确定的




**C语言规范**：定义了变量的**生命周期**和**作用域**的概念（如 `static`, `auto`）。
**编译器和链接器**：根据C语言的规则，决定将不同生命周期的变量放入哪个**逻辑段**（如 `.data`, `.bss`, `.text`）。
**操作系统**：当程序运行时，负责将编译器生成的这些逻辑段**加载到物理内存**中，并管理堆和栈的分配。

### 虚拟地址空间：每个进程"独占"的假象

**为什么需要虚拟地址？** 直接用物理地址有三个致命问题：
① 进程 A 可以写进程 B 的内存（无隔离）；② 两个程序都想用地址 0x1000 就冲突（无法共存）；
③ 内存不够时程序直接跑不了（无扩展）。**虚拟地址一次解决三个**：

1. 每个进程都有**独立的、从 0 开始的连续虚拟地址空间**（隔离）
2. 虚拟地址经**页表映射**到任意物理页（程序间物理地址不重叠也能都用 0x1000 起步）
3. 不常用的页换出到磁盘（扩展），访问时再调入（缺页中断，应用无感）

### 典型的 32/64 位虚拟地址空间布局

```text
32 位（共 4GB）:                      64 位（x86-64 实际用 48 位）:
┌─────────────┐ 高地址                ┌─────────────┐
│ 内核空间 1GB │                       │  内核空间    │
├─────────────┤ 0xC0000000            ├─────────────┤
│ 栈 ↓        │                       │  栈 ↓        │
│   ↓         │                       │    ↓         │
│ 共享库/ mmap │                       │  mmap 区     │
│   ↑         │                       │    ↑         │
│ 堆 ↑        │                       │  堆 ↑        │
├─────────────┤                       ├─────────────┤
│ .bss/.data  │                       │  .bss/.data  │
├─────────────┤ 低地址                ├─────────────┤
│ .text(只读) │                       │  .text(只读) │
└─────────────┘ 0x08048000            └─────────────┘
```

**要点**：

- 32 位系统内核占高地址 1GB，用户态只有 3GB——这就是 32 位系统"大内存利用率低"的原因
- 栈向低地址长、堆向高地址长，**相向生长**——中间的大空隙就是给两者留的余量
- `.text` 只读（防改代码）；`.data` 存已初始化全局量；`.bss` 存未初始化（**不占文件体积，加载时清零**）
- `mmap 区` 是共享库、文件映射和大块 malloc 的家

## 分页机制：虚拟 → 物理怎么翻译

```text
虚拟地址 = 虚拟页号(VPN) + 页内偏移(4KB 页低 12 位不变)
              │
              ▼ 查页表（MMU 硬件自动做）
         页表项 PTE：有效位 + 物理页号 + 读写权限 + 存在位
              │
              ▼
物理地址 = 物理页号(PFN) + 同样的页内偏移
```

- **MMU** 是 CPU 里的硬件单元，**每次访存都做这个翻译**——应用完全无感
- **TLB** 是页表的硬件缓存（几十~几千条）：命中则零开销；不命中要多访存查页表（所以 TLB 命中率对性能极敏感，大页/hugepage 就是为此）
- **多级页表**：x86-64 用 4/5 级页表——只为实际用到的地址范围建表，稀疏地址空间下省内存
- **缺页中断（page fault）**：访问的页不在物理内存（PTE 有效位=0）→ 触发异常 →
  OS 从磁盘调入该页、更新页表 → 重新执行那条指令。**这是虚拟内存"按需加载"的实现机制**
- **页面置换**：物理内存满了，按置换算法（LRU/Clock）淘汰一页（脏页要先写回）

## 物理内存怎么管理（内核视角）

- **伙伴系统（buddy）**：以 2 的幂为粒度分配物理页，**解决外部碎片**（分裂/合并成对操作）
- **Slab/Slub 分配器**：在伙伴系统之上，把常用小对象（`task_struct`、inode）做成对象池，**解决内部碎片**并加速分配
- **页缓存（page cache）**：磁盘文件数据缓存在内存——**同一个文件读写第二次走内存，这是 Linux IO 快的关键**

### 大小端

大小端讨论的是“数据内部字节序”问题 ^6ea824
- **大端模式**：数据的**高位字节**存储在**低地址**处。
    
- **小端模式**：数据的**低位字节**存储在**低地址**处。
对于**一个多字节的数据，最左边的是最高位，最右边的是最低位，这和我们写数字的习惯是一样的。**
**内存地址增长方向从低到高增长**，这是所有现代计算机的共性，**与大小端无关**。

**大端**模式更符合人类阅读习惯，网络协议（如TCP/IP）采用大端作为网络字节序。
**小端**模式对于CPU，从低位开始处理在某些运算（如加法）上更自然。
大小端关注的是：在一个**多字节数据**（如int）的内部，它的各个字节是如何在这片连续地址上排列的。
#### 判断方法
1.联合体判断
可以定义一个包含 `int` 和 `char` 数组的联合体。给 `int` 赋值为 `0x01020304` 后，直接检查 `char` 数组的第一个元素。因为联合体是共享地址的，char数组的第一个元素的内容是如果是高字节的0x01就是大端模式，如果是低字节的0x04就是小端模式

```c
# include <stdio.h>

int main() {
    union {
        int i;
        char c[sizeof(int)];
    } test;
    
    test.i = 0x01020304;
    
    if (test.c[0] == 0x01) {
        printf("大端模式\n");
    } else if (test.c[0] == 0x04) {
        printf("小端模式\n"); 
    }
    
    return 0;
    如果是printf("%x",text.c[0]);
    注意输出就没有0x，只有16进制数了，还要注意整型提升，大端的数据应该是0x00000001然后输出01
}
```

2.指针强制转换
```c
# include <stdio.h>

int main() {
    int num = 0x01020304;   // 一个4字节的整数
    char *p = (char *)&num // 取得num的地址，并用char指针指向它

    // 现在p指向num所占内存的起始地址（即最低地址）
    // 解引用p，查看最低地址处存放的是哪个字节
    if (*p == 0x01) {
        printf("大端模式 (Big-Endian)\n"); // 低地址存的是高位字节0x01
    } else if (*p == 0x04) {
        printf("小端模式 (Little-Endian)\n"); // 低地址存的是低位字节0x04
    }

    // 可选：打印所有字节看看
    for(int i = 0; i < sizeof(int); i++) {
        printf("地址 [%p] 处的字节: 0x%02x\n", (void*)(p + i), *(p + i));
    }
    return 0;
}
```


### 对齐访问，sizeof
**对齐是关于地址的规则，而不是关于数据量的规则。** 它要求数据的地址是数据大小的整数倍，目的是让CPU能用最高效的方式访问内存。

CPU在访问内存时，并不是以字节为单位随意读取的，而是以**字长**为单位。
- 32位CPU通常以4字节为单位访问内存
    
- 64位CPU通常以8字节为单位访问内存

对齐访问：数据在内存中的**起始地址**，必须是其自身**大小**的整数倍，或者更广义地说，是CPU字长的整数倍。
如果数据没有对齐，CPU可能需要进行**两次内存访问**才能读到一个完整的数据，这被称为“不对齐访问”，
不对齐访问的结果**视架构而定，但现代通用CPU通常不会直接‘出错’，而是以‘性能损失’作为代价。**
X86/X64架构(`intel,amd`)：PU硬件支持非对齐访问，但需要付出性能代价，也就是一个本可以一次完成的内存读取，可能被拆分成两次总线操作，然后再在CPU内部拼接。
ARM架构(大多数嵌入式设备，手机)：某些ARM核支持但会损失性能，某些ARM核不支持访问非对齐地址会触发**硬件异常**（CPU fault），可能崩溃。
RISC-V等其他RISC架构：倾向于更严格，很多设计要求对齐访问，否则触发异常。

对齐的目的是**用空间换时间**，提升CPU访问效率
每个数据类型都有其**自然对齐**要求，通常是其自身的大小

- `char`：1字节对齐
    
- `short`：2字节对齐
    
- `int`：4字节对齐
    
- `double`：8字节对齐
    
- 指针：4字节（32位系统）或8字节（64位系统）对齐
#### 对齐规则
1. **数据成员对齐规则**：结构体每个成员相对于结构体首地址的偏移量，必须是 **`min(#pragma pack指定的数值, 这个成员自身的长度)`** 的倍数。
    
    - 如果没有指定 `#pragma pack`，则按成员自身长度对齐。
        
2. **结构体整体对齐规则**：结构体的总大小必须是 **`min(#pragma pack指定的数值, 其最大成员长度)`** 的倍数。
3. 当结构体中有成员长度大于处理器的位数，就以处理器的位数为对齐单位，比如嵌套结构体
**嵌套结构体的对齐 = max(外层结构体对齐要求, 内层结构体对齐要求)**

通过**合理排列结构体成员**，可以显著减少内存浪费
```c
//12字节
struct BadLayout {
    char a;    // 1字节 + 3填充
    int b;     // 4字节  
    char c;    // 1字节 + 3填充
};

// 优化的排列 - 8字节  
struct GoodLayout {
    int b;     // 4字节
    char a;    // 1字节
    char c;    // 1字节 + 2填充（为了4字节对齐）
};
```
**有时会使用 `__attribute__((packed))` 或者 `#pragma pack(1)` 来取消对齐，节省每一字节的内存**
```c
// 使用编译器指令取消对齐（不推荐，影响性能）
# pragma pack(1)
struct PackedStruct {
    char a;
    int b;    // 现在可能不对齐，访问会变慢
    char c;
};
# pragma pack()

// 或者使用属性语法
struct __attribute__((packed)) PackedStruct {
    char a;
    int b;
    char c;
};
```
#### 非对齐应用
1.**网络协议解析**：
```c
// 网络数据包的IP头（共20字节）
struct ip_header {
    unsigned char  ihl:4, version:4;  // 各占4bit
    unsigned char  tos;
    unsigned short tot_len;
    unsigned short id;
    unsigned short frag_off;
    unsigned char  ttl;
    unsigned char  protocol;
    unsigned short check;
    unsigned int   saddr;
    unsigned int   daddr;
} __attribute__((packed));  // 取消对齐，保证结构体大小严格为20字节
```
必须取消对齐
- 网络数据是“扁平”的字节流，没有填充字节。
    
- 如果编译器在字段间插入填充，用指针直接映射报文内容时会错位。
2.**硬件寄存器映射**：
```c
// 映射到内存特定地址的硬件寄存器
struct uart_registers {
    volatile uint32_t data_register;      // 偏移 0x0
    volatile uint32_t interrupt_enable;   // 偏移 0x4  
    volatile uint32_t interrupt_id;       // 偏移 0x8
    volatile uint32_t line_control;       // 偏移 0xC
} __attribute__((packed));
```
硬件寄存器的地址是固定的，不能有“填充”破坏布局。
3.**存储空间极度受限的嵌入式设备**，为节省每一字节的RAM或Flash。
