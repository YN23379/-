# Linux 驱动基础（字符设备驱动完整框架）

> 一句话：写 Linux 驱动就是做"填空题"——内核给好了框架，你按框架填设备号、操作方法和硬件配置。

## 一、驱动是什么、分几类

**驱动是内核里的一段代码，它给用户空间提供一套标准接口（`/dev` 下的设备文件）来操作硬件。**
用户态用统一的 `open/read/write/ioctl`，驱动把这些标准调用"翻译"成对具体硬件寄存器的操作。

按数据读写方式分三类（内核分别用 `struct cdev` / `block_device` / `net_device` 抽象）：

| 类型 | 特征 | 例子 |
|---|---|---|
| **字符设备** | 按字节流顺序访问、一般不缓存、不支持随机存取 | 串口、键盘、LED、I2C/SPI 设备 |
| **块设备** | 按块访问、支持随机寻址、有页缓存 | 硬盘、eMMC、SD 卡 |
| **网络设备** | 不映射到 `/dev`，走套接字接口 | 网卡 |

字符设备最简单、覆盖大多数入门硬件，**是学驱动的起点**。

## 二、加载过程：模块三命令

驱动可以编译进内核（built-in），也可以编成**模块**（.ko）动态加载：

- `insmod xxx.ko`：直接加载，**不解决依赖**（依赖的符号没加载会失败）
- `modprobe xxx`：智能加载，自动加载依赖链（配合 `/etc/modprobe.d` 配置）
- `rmmod xxx`：卸载

模块骨架与 `module_init/module_exit` 见 [[20-领域/Linux/Linux内核.md|Linux内核]] 的"内核模块"一节。

## 三、设备号：驱动在内核里的身份证

应用打开 `/dev/xxx` 时，内核靠**设备号**找到驱动。设备号 `dev_t`（32 位）：

- **高 12 位 = 主设备号**：指向**驱动**（一类设备共用一个驱动）
- **低 20 位 = 次设备号**：指向该驱动下的**具体设备**（同驱动管多个实例）

```c
# define MINORBITS    20
# define MAJOR(dev)   ((unsigned int) ((dev) >> MINORBITS))   /* 从设备号取主设备号 */
# define MINOR(dev)   ((unsigned int) ((dev) & MINORMASK))    /* 取次设备号 */
# define MKDEV(ma,mi) (((ma) << MINORBITS) | (mi))            /* 合成设备号 */
```

`ls -l /dev` 第一列的 `c` = 字符设备、`b` = 块设备；后面的两个数字就是主/次设备号
（如 `loop0` 主 7 次 0）。已占用的主设备号可在内核文档 `devices.txt` 里查。

## 四、三大核心数据结构

### 1. `struct cdev`——字符设备对象

```c
struct cdev {
    struct kobject kobj;                    /* 内嵌内核对象：引用计数/热插拔/设备模型 */
    struct module *owner;                   /* 所属模块（THIS_MODULE） */
    const struct file_operations *ops;      /* 操作方法集（桥梁） */
    struct list_head list;                  /* 同驱动的设备链表 */
    dev_t dev;                              /* 设备号 */
    unsigned int count;                     /* 次设备号个数 */
};
```

内核用**散列表 `cdev_map`** 管理所有字符设备（哈希函数 `major % 255` 分桶，
冲突按次设备号排序）——open 时靠它从设备号反查 cdev。

### 2. `struct file_operations`——操作方法集（驱动的灵魂）

每个成员对应一个系统调用。**应用层调 read，最终就是调这里的 `.read`**：

```c
struct file_operations {
    struct module *owner;                                   /* THIS_MODULE */
    loff_t   (*llseek) (struct file *, loff_t, int);        /* 改读写位置 */
    ssize_t  (*read)  (struct file *, char __user *, size_t, loff_t *);
    ssize_t  (*write) (struct file *, const char __user *, size_t, loff_t *);
    long     (*unlocked_ioctl) (struct file *, unsigned int, unsigned long);
    int      (*open)   (struct inode *, struct file *);
    int      (*release)(struct inode *, struct file *);
    /* 不支持的成员留 NULL：内核对 NULL 的处理各函数不同（如 open=NULL 恒成功） */
};
```

- `read`/`write` 的 `__user` 修饰表示缓冲区在**用户空间**——内核**不能直接解引用**，
  必须用 `copy_to_user()/copy_from_user()`（用户地址可能没映射、也可能是坏指针，直接访问会崩内核）。
  返回"**未能拷贝的字节数**"，0 表示全部成功。
- `unlocked_ioctl`：设备专有控制命令的入口（老 `ioctl` 成员已在 3.0 删除）。
- `open`：驱动第一个被执行的函数，一般做初始化；`release`：文件结构释放时调用。

### 3. `struct file` 与 `struct inode`——别混的两个"文件"

| | `struct inode` | `struct file` |
|---|---|---|
| 表示 | **文件本身**（内核里的文件实体） | **一次打开的实例** |
| 生命周期 | 文件存在期间唯一 | 每次 open 创建一个、close 释放 |
| 驱动关心的成员 | `i_rdev`（设备号）、`i_cdev`（反向指回 cdev） | `f_op`（操作集）、`private_data`（设备私有数据） |

> 同一个设备被 open 三次 → 3 个 `struct file`、1 个 `struct inode`。
> 驱动把描述自己设备的结构体挂在 `file->private_data` 上，后续 read/write 就能拿到。

## 五、驱动程序框架四步法（insmod 时发生什么）

```c
static dev_t devno;                          /* 设备号 */
static struct cdev chr_dev;                  /* 字符设备对象 */
static struct file_operations chr_fops = { .owner = THIS_MODULE, .open = ..., .read = ... };

static int __init chrdev_init(void)
{
    /* 第一步：申请设备号（动态分配，避免冲突） */
    ret = alloc_chrdev_region(&devno, 0, DEV_CNT, DEV_NAME);
    /* 第二步：初始化 cdev，绑定操作方法集 */
    cdev_init(&chr_dev, &chr_fops);
    /* 第三步：把 cdev 注册进内核的 cdev_map 散列表 */
    ret = cdev_add(&chr_dev, devno, DEV_CNT);
    /* 第四步：创建设备节点（class + device，见下） */
}
static void __exit chrdev_exit(void)
{
    cdev_del(&chr_dev);                      /* 注销顺序与申请相反 */
    unregister_chrdev_region(devno, DEV_CNT);
}
```

- `alloc_chrdev_region`（动态）vs `register_chrdev_region`（静态指定）：**优先动态**，避免主设备号冲突。
- **goto 阶梯清理**：申请失败要按反序释放已申请的资源（设备号/cdev）。

### 设备节点：内核与用户的枢纽

- 老办法手动建：`mknod /dev/chrdev c 244 0`（设备名、类型 c/b、主、次）。
  mknod 的本质：创建一个 inode，`i_fop = def_chr_fops`，`i_rdev = 设备号`。
- 现代做法代码自动创建：`class_create()` + `device_create()`，靠 udev/mdev 自动生成 `/dev/节点`。
  卸载时 `device_destroy()` + `class_destroy()` 反序删除。

## 六、open 到底做了什么（一次调用的完整链路）

应用 `open("/dev/chrdev", O_RDWR)` 后内核发生的事——**这是理解驱动的钥匙**：

```text
sys_open → do_sys_open：分配空闲 fd（文件描述符，返回给应用）
  → do_filp_open：解析路径，找到该设备文件的 inode
  → do_dentry_open：file->f_op = inode->i_fop（此刻 = def_chr_fops）
  → def_chr_fops.open = chrdev_open：
       ① 从 inode->i_rdev 取设备号
       ② kobj_lookup(cdev_map, 设备号) 反查到 cdev 对象
       ③ file->f_op = cdev->ops          ← 换成你写的操作方法集！
       ④ 调用你实现的 .open
  → fd_install：fd ↔ file 关联完成
```

**一句话**：open 的本质是"**把该设备的操作方法集挂到这次打开的 file 上**"。
之后 read/write 走 fd → file → f_op，就直接进了你的驱动。

## 七、ioctl 与 procfs/sysfs 的选择

- `read/write` 用于**数据流**传输；`ioctl` 用于**控制命令**（如设置波特率 vs 收发数据）。
  ioctl 更适合不定长、非标准、设备特定的操作。
- ioctl 安全清单（内核态不可信用户指针）：
  1. 唯一幻数（`_IOR/_IOW` 生成）避免命令冲突
  2. 严格检查用户指针（`access_ok` + `copy_from/to_user`）
  3. 验证命令范围和参数大小
  4. 权限控制（`capable()` 检查）
  5. 并发保护（加锁）
- 三种用户态接口的选择：

| 接口 | 特点 | 适用 |
|---|---|---|
| `ioctl` | 同步、即时生效 | 实时控制 |
| `procfs` | 文本、随手可查 | 查看运行时信息（不适合频繁写） |
| `sysfs` | 结构化属性 | 设备属性配置、持久化倾向 |

## 八、下一步：从"填空"到"设备模型"

字符设备框架之后，真实驱动的进阶路线：

1. **并发与竞态**：多任务/多进程同时操作设备的保护（信号量/自旋锁/原子操作）
2. **中断处理**：申请中断、上半部/下半部（见 [[20-领域/Linux/Linux内核.md|Linux内核]]）
3. **阻塞与非阻塞 IO**：等待队列 `wait_queue`，让 read 没数据时睡眠
4. **设备模型 + 设备树**：bus/driver/device 匹配、`platform_driver`、从设备树取资源
5. **pinctrl/gpio、I2C、SPI 子系统**：内核把公共部分抽成子系统，驱动只剩"填差异"

> 这些内容的核心线索是一条：**内核把"共性"抽成框架（子系统），驱动只填"个性"**。
> 与本库 [[20-领域/芯片与平台-i.MX95/i.MX95引脚控制-IOMUXC与RGPIO分工.md|i.MX95 引脚控制]] 对照着看，
> 能体会"同为 ARM，芯片厂怎么在内核框架下实现引脚复用"。
