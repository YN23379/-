## 内存分布
进程运行时大致的内存分布
高地址 0x7fffffffffff
┌─────────────────┐
│   内核空间        │ (用户进程无法访问)
├─────────────────┤
│   栈 (stack)     │ ← 局部变量、函数调用帧，向低地址生长
│                 │
│    ↓↓↓↓↓↓↓      │
├─────────────────┤
│   共享库映射区     │ (动态链接库 .so 文件)
├─────────────────┤
│   堆 (heap)      │ ← malloc/free，向高地址生长
│    ↑↑↑↑↑↑↑      │
├─────────────────┤
│   BSS段         │ ← 未初始化全局变量
├─────────────────┤
│   DATA段        │ ← 已初始化全局变量  
├─────────────────┤
│   .rodata段     │ ← 字符串常量、const全局变量
├─────────────────┤
│   代码段 (.text)  │ ← 程序指令
低地址 0x400000
```text
1、Text（代码区）：二进制，只读
2、Bss（静态区or全局区）：
		未初始化或初始化为0的全局变量、静态变量，具体体现为一个占位符，并不给该段的数据分配空间，只是记录数据所需空间的大小
3、Data（数据段/静态存储区）：存放初始化（普通+静态）全局变量和（全局 + 局部）静态变量
		因为字符串常量很少需要修改，放在静态内存区会提高效率
		//BSS由数据段衍生出去
4、Stack：局部变量
5、Heap：new/delete和malloc/free
		
其中Stack和Heap的内存增长方向是相反的
```

在进程被载入内存中时，基本上被分裂成许多小的节（section）。我们比较关注的是6个主要的节：
 .text 节
.data 节
.bss 节
堆节
栈节
环境/参数节
环境/参数节（environment/arguments section）用来存储系统环境变量的一份复制文件，

**现代Linux进程的内存布局大致从低到高是：代码段、只读数据段、数据段、BSS段、堆、共享库映射区、栈和内核空间。但由于ASLR机制，栈、堆和共享库的具体地址每次运行都会随机化，这是重要的安全特性**。
**地址空间布局随机化 (ASLR)**
实际上，通过`/proc/pid/maps`可以看到真实的内存映射。
现代Linux中，由于ASLR，堆和栈的基地址每次运行都随机化。堆起始于BSS段后的随机偏移处，通过program break指针管理，malloc时可能brk扩展堆或mmap分配大块内存。

ASLR机制是为了避免
- **堆溢出攻击**：难以预测目标地址
    
- **ROP攻击**：代码位置随机化
    
- **信息泄露**：每次运行布局不同

### 栈
栈 (Stack)
- 编译器自动管理，函数调用时分配，返回时释放
- 存放局部变量、函数参数、返回地址
- 空间有限（通常几MB），生长方向从高地址向低地址
- 访问速度快，不会产生内存碎片

### 堆
堆 (Heap)  
- 程序员手动管理(malloc/free, new/delete)
- 存放动态分配的内存
- 空间较大（可达GB级），生长方向从低地址向高地址
- 访问速度较慢，可能产生内存碎片


**栈是由编译器自动管理的后进先出结构，存放函数调用的上下文信息，分配释放速度快但空间小。堆是程序员手动管理的动态内存区，空间大但容易产生内存碎片和泄漏问题。**





## 内存管理
#### 物理内存管理

操作系统如何组织物理内存。

1. **连续分配**
    
    - **块式管理**：将内存划分为固定大小的块，每个块装入一个进程。产生大量**内部碎片**，利用率低，已被淘汰。
        
2. **非连续分配**（现代系统基础）
    
    - **页式管理**：
        
        - 将物理内存与虚拟地址空间均划分为固定大小的**页**。
            
        - 通过**页表**维护虚拟页号到物理页帧号的映射。
            
        - **优点**：有效减少外部碎片，内存利用率高。
            
        - **缺点**：页是物理单位，无逻辑意义。
            
    - **段式管理**：
        
        - 按程序的逻辑结构（如代码段、数据段）划分为大小不等的**段**。
            
        - 通过**段表**维护段地址映射。
            
        - **优点**：段有逻辑含义，易于共享和保护。
            
        - **缺点**：容易产生外部碎片。
            
    - **段页式管理**（现代系统常用）：
        
        - 结合两者优点。先按逻辑分段，每个段内再分页。
            
        - 兼顾了逻辑清晰和物理管理的高效。


#### 虚拟内存

为什么需要以及如何实现虚拟内存。

1. **目的**
    - **安全与隔离**：防止用户进程直接操作物理内存，破坏系统或其他进程。
    - **简化编程**：为每个进程提供统一的、连续的虚拟地址空间。
    - **内存扩容**：利用局部性原理，实现容量大于物理内存的编程空间。

2. **理论基础：局部性原理**
    - **时间局部性**：被访问的内存位置很快可能再次被访问。（源于循环）
    - **空间局部性**：被访问内存的邻近位置很快可能被访问。（源于顺序执行、数组）

3. **硬件支持：MMU 与地址转换**
    - **MMU**：CPU中的内存管理单元，负责虚拟地址到物理地址的实时转换。
    - **转换过程**：CPU发出虚拟地址 -> MMU查询页表 -> 得到物理地址 -> 访问内存。

4. **性能加速**
    - **快表**：一种高速缓存，存放最近使用的页表项。先查快表，命中则无需访问内存中的页表，极大加速地址转换。
    - **多级页表**：解决页表过大、占用过多内存的问题。属于**时间换空间**的典型策略。

#### 虚拟内存的实现

当所需数据不在内存时。

1. **请求分页存储管理**
    - 程序运行时，只需加载部分页至内存。
    - 当访问的页面不在内存时，触发**缺页中断**。

2. **页面置换算法**（缺页中断且物理内存已满时触发）
    - **OPT**：淘汰未来最长时间不再访问的页。理论最优，无法实现，用于衡量算法效率。
    - **FIFO**：淘汰最先进入内存的页。实现简单，但性能差，可能出现Belady异常。
    - **LRU**：淘汰最近最久未使用的页。性能接近OPT，但精确实现开销大。
    - **LFU**：淘汰最不经常使用的页。可能“养懒汉”，早期频繁访问后不再使用的页难以被置换。











#### 补充

- **知识点**：`malloc`/`free`，它们不是系统调用。它们是 **“C库内存分配器”** 提供的函数。
- **核心补充**：理解 **glibc malloc 的行为**。它通过 `brk` 和 `mmap` 系统调用向内核“批发”大块内存，然后自己管理，“零售”给应用程序。
- **面试必问**：“`malloc(1)` 会分配多少内存？” （答案：比1字节多很多，因为有内存对齐和管理开销）
- **如何学习**：搜索“glibc malloc 原理”或“ptmalloc”，了解它如何通过 `chunk` 结构管理内存，以及 `fast bins`、`small bins` 等概念。


**2. 补充：一个至关重要的系统调用 `mmap`**
- **是什么**：一个强大的系统调用，可以将文件、设备、或者一块匿名内存直接映射到进程的虚拟地址空间。
- **为什么重要**：
    - `malloc` 管理大块内存时（比如超过128KB）底层就用 `mmap`。
    - 程序加载动态库（`.so`文件），就是通过 `mmap` 把库文件映射到内存。
    - 这就是 **“内存映射文件”** ，可以用于进程间通信。

- **面试价值**：理解 `mmap`，你就把“进程内存”和“文件系统”这两个核心概念联系起来了。


**3. 补充：嵌入式特有的视角——Swap的不存在**

- **知识点**：在你之前的 `free` 输出里，Swap使用为0。但在许多嵌入式Linux设备上，**根本没有Swap分区**。
- **为什么**：因为嵌入式设备通常使用Flash存储（如eMMC），读写寿命和速度远不如硬盘，频繁的Swap操作会损坏存储且性能极差。
- **后果**：当内存耗尽时，没有Swap可用了，内核的 **OOM Killer** 会被触发，选择一个“坏”进程强制杀掉来释放内存。
- **面试洞察**：你可以说：“在资源受限的嵌入式环境中，我们通常会禁用Swap。这就需要对内存使用更加谨慎，并理解OOM Killer的行为机制。”
    

**4. 补充：理解“缺页中断”的真正代价**

- **概念**：发生缺页中断后，操作系统会从磁盘调入页面。
- **深化**：这称为 **“主缺页”** 或 **“硬缺页”** ，需要磁盘I/O，**代价非常高**（可能使进程睡眠毫秒级）。而如果页面已经在内存池中（比如刚被换出但还没被覆盖），则称为 **“次缺页”** ，代价小很多。
- **联系实际**：这就是为什么程序启动时会有卡顿，因为正在发生大量的主缺页来加载代码和数据。

### Swap
Swap是Linux的**虚拟内存**（Virtual Memory）机制的一部分，用**硬盘空间**模拟内存，当物理内存不足时，将不活跃的页面换出到Swap空间。
**工作流程**：物理内存不足 → 内核选择"冷"页面 → 写入Swap分区 → 释放物理内存
需要访问时 → 从Swap读回 → 可能换出其他页面（页面置换算法）

- **透明性**：应用程序不知道数据在内存还是Swap
- **后备存储**：Swap是RAM的扩展，不是替代
- **性能影响**：硬盘访问比内存慢1000倍以上

实现方式：
Swap分区
```bash
# 创建Swap分区步骤：
1. fdisk /dev/sda  # 创建新分区，类型82 (Linux swap)
2. mkswap /dev/sda3  # 格式化Swap分区
3. swapon /dev/sda3  # 激活Swap
4. /etc/fstab添加：/dev/sda3 swap swap defaults 0 0
```
Swap文件
```bash
# 创建Swap文件步骤：
1. dd if=/dev/zero of=/swapfile bs=1M count=2048  # 创建2GB文件
2. chmod 600 /swapfile  # 设置权限
3. mkswap /swapfile     # 格式化
4. swapon /swapfile     # 激活
5. /etc/fstab添加：/swapfile swap swap defaults 0 0
```

| 特性       | Swap分区   | Swap文件     |
| -------- | -------- | ---------- |
| **性能**   | 稍好（连续空间） | 稍差（文件系统开销） |
| **灵活性**  | 固定大小     | 可动态调整      |
| **创建难度** | 需要分区     | 简单快速       |
| **推荐场景** | 服务器生产环境  | 临时扩展、云环境   |
Swap分区性能稍好，适合生产环境；Swap文件更灵活，适合云环境。  
现代Linux内核对Swap文件优化很好，性能差距不大。

---

Swap主要有三个作用：
1. **内存扩展**：当物理内存不足时，用硬盘空间作为后备
2. **休眠支持**：实现系统休眠（hibernate）功能
3. **内存管理**：让内核能移出不活跃页面，优化内存使用
但Swap不是内存替代品，频繁Swap会导致性能严重下降。


```bash
# 查看当前Swap使用
free -h
swapon --show

# 关键参数：
swappiness = 60        # 默认值，0-100，越高越积极使用Swap
vfs_cache_pressure = 100  # 缓存回收压力
min_free_kbytes        # 最小空闲内存阈值
```
swappiness的详解
```bash
# 值域0-100的含义：
0   ：尽量不用Swap，除非内存耗尽
60  ：平衡模式（默认）
100：积极使用Swap

# 设置方法：
echo 10 > /proc/sys/vm/swappiness
# 或永久：/etc/sysctl.conf添加 vm.swappiness=10
```

### OOM killer
OOM Killer是Linux内核的内存保护机制（全称Out-Of-Memory Killer）。
当系统物理内存和swap空间都耗尽时，内核会选择'牺牲'一个进程强制终止，以此回收内存、防止系统完全崩溃。
它的选择算法基于`oom_score`——每个进程的综合评分。评分主要考虑：内存占用量、运行时间、进程优先级。内核会优先杀死分数高、内存占用大、且不重要的进程。我们可以通过`/proc/[pid]/oom_score_adj`文件调整权重，负值保护关键进程，正值标记可优先牺牲的进程。
实际开发可以核心守护进程设置`oom_score_adj = -1000`确保不被误杀，并且用cgroup限制每个进程的内存上限，超出自动终止而非触发全局OOM
```shell
# OOM Killer的选择算法
oom_score = 占用内存 × oom_score_adj / 1000
# 分数越高，越容易被杀死
```
每个进程都有自己的oom_score_adj，
```shell
# 查看进程OOM分数
cat /proc/[pid]/oom_score

# 调整OOM优先级 (-1000到1000)
echo -100 > /proc/[pid]/oom_score_adj  # 不容易被杀死
echo 1000 > /proc/[pid]/oom_score_adj  # 优先被杀死
```



## 注意
### 进程maps
虽然x86-64是64位架构，但当前实现的虚拟地址只有48位有效位，采用高低半区设计。用户空间地址高16位为0，内核空间高16位为1
这种规范地址设计简化了硬件实现同时提供了足够的地址空间。
**有效地址只有 48 位**，高16位是符号扩展。
即在 x86-64 中，虚拟地址必须满足：
- **用户空间**：高16位全0 → `0x0000...`
    
- **内核空间**：高16位全1 → `0xFFFF...`








## 提问

### 全局变量初始化为0和未初始化有区别吗？
从C语言标准来说，未初始化的全局变量和初始化为0的全局变量都会被置为0，行为完全一致。但在底层实现上，编译器可能对显式初始化为0的变量有特殊处理，不过最终通常都会优化到BSS段。

### 静态和全局变量初始化
在 C 语言中，**全局变量**和**静态变量（包括静态局部变量）** 如果未被显式初始化，编译器会自动将它们初始化为零值。
- **整型**（`int`, `char`, `long` 等）：初始化为 `0`
- **浮点型**（`float`, `double`）：初始化为 `0.0`
- **指针类型**（`int*`, `char*` 等）：初始化为 `NULL`
- **数组/结构体**：所有成员递归地初始化为零值

|变量类型|存储区域|是否自动零初始化|生命周期|
|---|---|---|---|
|**全局变量**|.bss 段|✅ 是|整个程序|
|**静态全局变量**|.bss 段|✅ 是|整个程序|
|**静态局部变量**|.bss 段|✅ 是|整个程序|
|**普通局部变量**|栈(stack)|❌ 否|函数内部|

- **.bss 段**：专门存放未初始化或初始化为0的全局/静态变量
- **操作系统**在加载程序时，会将整个.bss段清零

**在C语言中，全局变量和静态变量（包括静态全局和静态局部变量）如果未被显式初始化，会被编译器自动初始化为零值。这是因为它们存储在程序的.bss段，操作系统在加载时会清零整个段**。
**而普通局部变量存储在栈上，不会自动初始化，其值是未定义的。**


### const变量在哪个段
const变量的存储位置取决于它的作用域。
全局const变量通常放在.rodata只读数据段；
局部const变量在栈上；static const变量也在.rodata段。
这体现了C语言'const'更多是编译期的只读保证，而不是运行时的存储位置约束。



### 堆是如何管理和生长的？

> "堆起始于BSS段之后，通过program break指针标识堆顶。malloc时可能通过brk扩展堆，或mmap分配大内存块。由于ASLR，堆的起始地址每次运行都会随机化。"

### BSS段和堆的关系？

> "BSS段存放未初始化的静态变量，大小在编译时确定。堆紧邻BSS段但地址随机化，用于动态内存分配。两者都是可读写的，但BSS段生命周期随程序，堆内存需要手动管理。"

### malloc(1) 会立即分配物理内存吗？

> "不会。malloc通过brk调整program break，但Linux采用惰性分配，只有在实际访问时才分配物理页。这是基于请求分页的优化机制。"

### 堆内存分配有哪些优化策略？

> "glibc的malloc使用bins管理空闲块：fast bins用于小对象快速分配，unsorted bin用于中等对象，top chunk用于大对象。还有mmap阈值，大块内存直接使用mmap分配。"



### 虚拟内存怎么映射到物理内存
整个系统刚启动的时候还是运行在物理内存上的，内核也被全部加载到了物理内存。内核会记录进程的虚拟内存分配情况，但是并不会马上分配物理内存建立页表映射，而是让进程先运行着。

进程运行的时候，CPU都是通过MMU访问虚拟内存地址的，MMU会用页表去解析虚拟内存，如果找到了其对应的物理地址就直接访问，如果页表项是空的，就会触发缺页异常，在缺页异常中会去分配物理内存并建立页表映射。
然后再重新执行刚才的那条指令，然后CPU还是通过MMU访问内存，页表建立好就可以访问到物理内存了。
当物理内存不足的时候，内核还会把一部分物理内存解除映射，把其内容存放到外存中，等其再次需要的时候再加载回来。
这样，一个进程运行的时候并不需要立马加载其全部内容到物理内存，进程只需要少量的物理内存就能顺利地运行，于是系统运行进程的吞吐量就大大提高了。
