## 基础概念
### 网络类别
**局域网**（LAN）（Local Area Network）：局域网将一定区域内的各种计算机、外部设备和数据库连接起来形成计算机通信的私有网络。在一个建筑或者校园范围内
最流行的局域网技术是以太网（Ethernet），虽然以太网是绝对主流，但Wi-Fi（IEEE 802.11）也是另一种常见的局域网技术。
每个以太网适配器都有一个全球唯一的48位地址，存储在该适配器的非易失性存储器上。就是MAC地址，**媒体存取控制地址**，由IEEE统一分配，烧录在网卡硬件中。

**广域网**：又称广域网、外网、公网。是连接不同地区局域网或城域网计算机通信的远程公共网络。

| 术语        | 定义                               | 比喻                                   |
| --------- | -------------------------------- | ------------------------------------ |
| **局域网**   | 一个小范围（家庭、办公室）内的私有网络。             | **公司内部电话系统**。                        |
| **以太网**   | 实现局域网通信的一套主流技术标准。                | 公司内部电话系统使用的**某种品牌或型号的电话设备和布线规则**。    |
| **MAC地址** | 网络设备（如网卡）的全球唯一硬件地址。在局域网内定位设备。    | 每个电话分机的**唯一物理序列号**（在内部系统里用）。         |
| **路由器**   | 连接两个或多个不同网络的设备，负责在网络间转发数据。       | **公司总机/前台**，负责内部电话与外部网络的转接。          |
| **WAN**   | 覆盖大范围（城市、国家、全球）的网络，用于连接不同位置的局域网。 | **公共电话网络**。                          |
| **互联网**   | 由全球无数网络（LAN, WAN）通过路由器互联而成的网络之网。 | **整个全球电话通信系统**，由无数公司的内部系统和公共电话网共同组成。 |


全球IP因特网，最著名的互联网，每台因特网主机都运行实现TCP/IP协议的软件
因特网的客户端和服务器混合使用套接字接口函数和Unix I/O函数进行通信

`IP（Internet Protocol）`：本质是一个整数，用于表示计算机在网络中的地址。IP协议版本有两个：IPv4和IPv6
- **结构**：由 **网络号** 和 **主机号** 两部分组成。
- **地址分类（历史概念）**：
    - A类：`1.0.0.0` - `126.255.255.255` (大型网络)
    - B类：`128.0.0.0` - `191.255.255.255` (中型网络)
    - C类：`192.0.0.0` - `223.255.255.255` (小型网络)
    - D类：组播地址
    - E类：保留地址
- **CIDR（无类别域间路由）**：现代网络已不再严格按A/B/C类划分，而是采用CIDR，更灵活地分配IP地址空间。

IPv4（Internet Protocol version4）：
使用一个32位的整形数描述一个IP地址，4个字节，int型
也可以使用一个点分十进制字符串描述这个IP地址： 192.168.247.135
分成了4份，每份1字节，8bit（char），最大值为 255
0.0.0.0 是最小的IP地址
255.255.255.255是最大的IP地址
按照IPv4协议计算，可以使用的IP地址共有 2^32 个

IPv6（Internet Protocol version6）：
使用一个128位的整形数描述一个IP地址，16个字节
也可以使用一个字符串描述这个IP地址：2001:0db8:3c4d:0015:0000:0000:1a2f:1a2b
分成了8份，每份2字节，每一部分以16进制的方式表示
按照IPv6协议计算，可以使用的IP地址共有 2^128 个

### 网络通信
网络通信是一个分层结构。当一台主机要访问外网时，它首先通过**子网掩码**判断目标IP是否与自己在同一**子网**。如果在，就直接通过**ARP**协议获取对方MAC地址进行通信；如果不在，则把数据包发往**默认网关**。
**ARP**负责解决同一局域网内**IP地址**到MAC地址的映射问题，是连接**网络层**和**数据链路层**的桥梁。
而**IP协议**作为网络层的核心，通过**IP地址**和**路由**机制，实现了全球互联网的连接。
**划分子网**则是为了解决IP地址浪费、控制广播域和提升网络管理效率的问题。

网关是本地网络的出口，通常是路由器的IP地址。当主机要访问外部网络时，所有数据包都先发给网关，由它进行转发。**网关必须与主机在同一个子网**，否则主机无法通过ARP找到它。
子网掩码的作用是**明确区分IP地址中的网络部分和主机部分**，通过‘按位与’运算计算出网络号。主机通过比较目标IP和自己的网络号是否相同，来判断是直接通信还是发给网关。
子网掩码由网络管理员根据子网规模和数量规划，通过DHCP自动分配或手动配置。而`255.255.255.0` 是家用场景下最常见的一种。



- **发送方**：数据从应用层开始，每向下经过一层，都会被该层协议加上一个**头部**（和可能的尾部）进行封装。
- **接收方**：数据从物理层开始，每向上经过一层，都会拆掉对应的头部，进行解封装，最终将原始数据呈现给应用程序。


IP协议是网络层的核心，是一个**无连接**、**尽最大努力交付**的协议。
- **无连接**：通信前无需建立连接，直接发送数据。
- **不可靠**：不保证数据包一定能到达、不保证顺序、不保证不重复。可靠性由上层协议（如TCP）保障。
- **IP数据包结构**：由**IP头部**和**数据载荷**构成。头部包含关键信息：版本、源IP地址、目的IP地址、生存时间、头部校验和等。
IP地址由网络号和主机号构成

#### 子网
为了优化网络性能和管理，可以将一个大的网络划分为多个小的**子网**。
- **子网掩码**：
    - 一个32位的数字，与IP地址配对使用。
    - **功能**：明确标识IP地址中哪些位代表**网络号**，哪些位代表**主机号**。
    - **规则**：掩码中**连续的“1”对应网络号，连续的“0”对应主机号**。
    - **表示法**：`255.255.255.0` 或 `/24` (表示有24个“1”)。
- **计算网络号**：
    - 操作：将IP地址与子网掩码进行 **“按位与”** 运算。
    - 示例：
        - IP: `192.168.1.10` -> `11000000.10101000.00000001.00001010`
        - Mask: `255.255.255.0` -> `11111111.11111111.11111111.00000000`
        - **按位与结果**：`11000000.10101000.00000001.00000000` -> `192.168.1.0` (网络号)

划分子网的作用：
1. **减少网络广播**：广播域被限制在子网内，提升网络效率。
    
2. **提高安全性**：逻辑上隔离不同部门或用户组。
    
3. **灵活管理**：便于针对不同子网实施不同的管理策略。
子网掩码由**网络管理员**根据网络规模（所需子网数和每个子网的主机数）进行规划。
常通过**DHCP服务**动态分配或**手动静态配置**给终端设备。



#### MAC地址
**MAC地址**是一个48位的全球唯一物理地址，固化在网卡的ROM中。用于在**同一局域网**内标识唯一的网络设备。
格式：`XX:XX:XX:XX:XX:XX` (十六进制表示)。

ARP协议（地址解析协议）是用于把数据链路层的MAC地址和网络层使用的IP地址进行转换，
ARP仅在**同一广播域（同一子网）** 内有效。
对于不同子网的通信，主机通过ARP获取的是**默认网关**的MAC地址。

**工作原理**（假设主机A `(IP_A, MAC_A)` 欲与同子网主机B `(IP_B, ?)` 通信）：
1. **ARP查询广播**：主机A检查本地**ARP缓存表**。若无 `IP_B` 的映射，则构造一个ARP请求包。该包内容为：“我是 `IP_A`，我的MAC是 `MAC_A`，请问 `IP_B` 的MAC地址是什么？” 并以**广播帧**（目标MAC = `FF:FF:FF:FF:FF:FF`）形式发送到局域网。
    
2. **ARP响应单播**：局域网内所有主机都收到该广播，但只有 `IP_B` 的主机会处理。主机B构造一个ARP响应包：“我是 `IP_B`，我的MAC地址是 `MAC_B`”，并**以单播帧**（目标MAC = `MAC_A`）形式直接回复给主机A。
    
3. **更新缓存**：主机A收到响应后，将 `(IP_B -> MAC_B)` 的映射存入本地ARP缓存，后续通信直接使用。缓存条目有生存时间，超时后自动清除。

#### 网关
网关是连接两个不同网络的设备，通常是**路由器**的一个接口。它是本地子网流量的**出入口**
主要是用于**路由转发**。当目标IP地址不在本地子网时，主机会将数据包发送给网关，由网关根据其**路由表**将数据包导向目的地。
网关本身必须有一个IP地址，且该地址必须与它所服务的子网内的所有主机**处于同一子网**。

比如：
- 子网：`192.168.1.0/24`
    
- 合法网关地址通常是该子网的第一个或最后一个可用IP，如 `192.168.1.1` 或 `192.168.1.254`。
注意，主机需要通过ARP获取网关的MAC地址。如果网关IP不在同一子网，ARP请求将无法到达网关，通信也就无法建立。



### 端口
端口的作用是定位到主机上的某一个进程，通过这个端口,进程就可以接受到对应的网络数据。
端口也是一个整型数 （unsigned short） ，一个16位整型数，有效端口的取值范围是：0 ~ 65535(0 ~ 2^16-1)
```text
在电脑上运行了微信和QQ, 小明通过客户端给我的的微信发消息, 电脑上的微信就收到了消息, 为什么?

运行在电脑上的微信和QQ都绑定了不同的端口
通过IP地址可以定位到某一台主机，通过端口就可以定位到主机上的某一个进程
通过指定的IP和端口，发送数据的时候对端就能接受到数据了
```
计算机中所有的进程都需要关联一个端口吗，一个端口可以被重复使用吗?

答：不需要，如果这个进程不需要网络通信，那么这个进程就不需要绑定端口的
一个端口只能给某一个进程使用，多个进程不能同时使用同一个端口
#### 协议默认端口
端口也用于区分主机上的不同网络服务。每个网络服务（如 HTTP、HTTPS、FTP、SSH 等）通常会监听一个特定的端口，以便客户端可以通过该端口与服务进行通信。
- **HTTP 的默认端口是 80**：这是 HTTP 协议的默认端口，被广泛接受和使用。客户端在访问 HTTP 服务时，如果没有指定端口，会默认使用端口 80。
    
- **HTTPS 的默认端口是 443**：这是 HTTPS 协议的默认端口，被广泛接受和使用。客户端在访问 HTTPS 服务时，如果没有指定端口，会默认使用端口 443。

使用默认端口的原因：
- **标准化**：使用固定的默认端口可以简化客户端和服务端的配置。客户端不需要显式指定端口，服务端也不需要额外配置。
    
- **安全性**：HTTPS 使用端口 443，确保了加密通信的安全性，避免了与 HTTP 的端口 80 混淆。
    
- **防火墙和网络策略**：许多网络环境（如公司网络、学校网络等）会根据端口号进行访问控制。使用标准端口可以确保服务的正常访问。

- **FTP**：默认端口是 21。
    
- **SFTP**：默认端口是 22。
    
- **SSH**：默认端口是 22。

## 网络模型
每个网络应用都是基于客户端-服务器模型的，采用这个模型，一个应用是由一个服务器进程和一个或多个客户端进程组成的
服务器管理某种资源，并通过操作这种资源来为它的客户端提供某种服务
在客户端-服务器模型里，基本操作是事务（transaction）：
1）当一个客户端需要服务时，它向服务器发起一个请求，发起一个事务
2）服务器接收到请求后，解释它，以适当的方式操作它的资源
3）服务器给客户端发送一个响应，等待下一个请求
4）客户端受到响应并处理

服务器和客户端通常运行在不同主机上，通过计算机网络的硬件和软件资源来通信。对主机来说，网络只是一种I/O设备，是数据源和接收方
### OSI模型
OSI（Open System Interconnect），即开放式系统互联
OSI七层模型是一种将计算机网络通信协议划分为七个不同层次的标准化框架。每一层都负责不同的功能，从物理连接到应用程序的处理。这种模型有助于不同的系统之间进行通信时，更好地理解和管理网络通信的过程。
OSI定义了网络互连的七层框架（物理层、数据链路层、网络层、传输层、会话层、表示层、应用层），即ISO开放互连系统参考模型。

![[90-附件/OSI七层模型.png]]


应用层（Application Layer）：这是网络体系结构中的最顶层，提供用户接口和应用程序之间的通信服务。在这一层，用户可以访问各种网络应用程序，如电子邮件、文件传输和远程登录。
表示层（Presentation Layer）：该层负责数据的格式化、加密和压缩，以确保数据在不同系统之间的交换是有效的和安全的。它还提供了数据格式转换和语法转换的功能。\
会话层（Session Layer）：会话层管理应用程序之间的通信会话，负责建立、维护和终止会话。它还提供了数据的同步和检查点恢复功能，以确保通信的完整性和持续性。
传输层（Transport Layer）：传输层为应用程序提供端到端的数据传输服务，负责数据的分段、传输控制、错误恢复和流量控制。它主要使用 TCP（传输控制协议）和 UDP（用户数据报协议）来实现这些功能。
网络层（Network Layer）：网络层负责数据包的路由和转发，以及网络中的寻址和拥塞控制。它选择最佳的路径来传输数据包，以确保它们能够从源主机到目标主机进行传输。
数据链路层（Data Link Layer）：数据链路层提供点对点的数据传输服务，负责将原始比特流转换为数据帧，并检测和纠正传输中出现的错误。它还控制访问物理媒介的方式，以及数据帧的传输和接收。
物理层（Physical Layer）：物理层在物理媒介上传输原始比特流，定义了连接主机的硬件设备和传输媒介的规范。它确保比特流能够在网络中准确地传输，例如通过以太网、光纤和无线电波等媒介。

### TCP/IP模型
TCP/IP 四层模型是目前被广泛采用的一种模型，由以下 4 层组成：应用层、传输层、网络层、网络接口层
![[90-附件/TCP IP模型.png]]
应用层（Application Layer）类似于 OSI 模型中的应用层，负责处理用户与网络应用程序之间的通信。它包括诸如 HTTP、FTP、SMTP 等协议，用于实现不同类型的网络服务和应用。
传输层（Transport Layer）：与 OSI 模型中的传输层相对应，提供端到端的数据传输服务。在 TCP/IP 模型中，主要有两个协议：TCP（传输控制协议）和 UDP（用户数据报协议），用于确保可靠的数据传输和简单的数据传输。
网络层（Internet Layer）：相当于 OSI 模型中的网络层，负责数据包的路由和转发。它使用 IP（Internet Protocol）协议来定义数据包的传输路径，并处理不同网络之间的通信。
网络接口层（Link Layer）：与 OSI 模型中的数据链路层和物理层相对应，负责管理网络硬件设备和物理媒介之间的通信。它包括以太网、Wi-Fi、蓝牙等各种物理层和数据链路层协议。


#### 应用层常见协议

**HTTP**（HyperText Transfer Protocol）：用于在客户端和服务器之间传输超文本数据，通常用于 Web 浏览器和 Web 服务器之间的通信。
**FTP**（File Transfer Protocol）：用于在客户端和服务器之间传输文件，支持上传和下载文件的功能。
SMTP（Simple Mail Transfer Protocol）：用于在邮件服务器之间传输电子邮件，负责发送邮件。
**POP3**（Post Office Protocol version 3）：用于从邮件服务器上下载邮件到本地计算机，负责接收邮件。
**IMAP**（Internet Message Access Protocol）：也是用于接收邮件的协议，与 POP3 类似，但提供了更丰富的功能，如在服务器上管理邮件等。
**DNS**（Domain Name System）：用于将域名解析为对应的 IP 地址，从而实现域名和 IP 地址之间的映射。
**HTTPS**（HyperText Transfer Protocol Secure）：是 HTTP 的安全版本，通过 SSL/TLS 加密传输数据，保证通信过程中的安全性。
**SSH**（Secure Shell）：用于远程登录和执行命令，提供了加密的网络连接，保证了通信的安全性。
SNMP（Simple Network Management Protocol）：用于网络设备之间的管理和监控，可以实现对网络设备的远程配置和监控。
Telnet：用于远程登录和执行命令，类似于 SSH，但不提供加密功能，通信数据不安全。

#### 传输层常见协议

TCP（Transmission Control Protocol）：提供可靠的、面向连接的数据传输服务，确保数据的可靠性、顺序性和完整性。TCP适用于对数据传输质量要求较高的场景，如文件传输、网页浏览等。
UDP（User Datagram Protocol）：提供无连接的数据传输服务，不保证数据的可靠性，也不保证数据的顺序性和完整性。UDP适用于实时性要求较高、对数据传输质量要求不那么严格的场景，如音视频传输、在线游戏等。

#### 网络层常见协议

**IP**（Internet Protocol）：是互联网中最基本的协议，用于在网络中传输数据包。IP协议定义了数据包的格式、寻址方式和路由选择等信息，是整个互联网的基础。
**ICMP**（Internet Control Message Protocol）：用于在IP网络中传递控制消息和错误信息。ICMP通常用于网络设备之间的通信，如路由器和主机之间的通信，以及用于检测网络连通性和故障诊断。
**ARP**（Address Resolution Protocol）：用于将IP地址映射为MAC地址（物理地址）。ARP协议在局域网内部使用，通过发送ARP请求获取目标设备的MAC地址，从而实现数据包的传输。
**RARP**（Reverse Address Resolution Protocol）：与ARP相反，用于将MAC地址映射为IP地址。RARP协议通常用于无盘工作站等设备，可以根据MAC地址获取对应的IP地址。
**IPv6**（Internet Protocol version 6）：是IP协议的下一代版本，用于解决IPv4地址空间不足的问题。IPv6采用128位地址长度，提供了更大的地址空间，支持更多的设备连接到互联网。

#### 数据链路层常见协议：
**数据链路层**负责在直接相连的节点间进行无差错的数据帧传输。它通过MAC地址寻址，并提供差错校验。
1. **MAC（媒体访问控制）子层**：解决“谁能用这个信道”的问题。
2. **LLC（逻辑链路控制）子层**：提供帧的封装、差错校验等，对上为网络层提供统一接口。

在局域网中，最常见的是**以太网协议**，它使用MAC地址来寻址。在广域网或点对点链路上，会用到**PPP**或**HDLC**这样的协议。而我们家庭宽带拨号，实际上是使用了**PPPoE**，也就是把PPP协议承载在以太网之上。
#### 物理层常见协议

**物理层**传输原始的比特流。它不关心数据的含义，只定义物理介质和信号的规范。
物理层协议主要是一些电气和物理接口标准，比如常见的**RJ-45网口**、**光纤接口**，以及定义信号频率和编码的 **IEEE 802.3** 系列标准（如1000BASE-T）。它们共同确保了原始的比特流能通过网线、光缆等介质传输出去。

### TCP Socket
TCP是一个面向连接的，安全的，流式传输协议，这个协议是一个传输层协议。
面向连接：是一个双向连接，通过三次握手完成，断开连接需要通过四次挥手完成。
安全：tcp通信过程中，会对发送的每一数据包都会进行校验, 如果发现数据丢失, 会自动重传
流式传输：发送端和接收端处理数据的速度，数据的量都可以不一致


```
客户端 → 服务端：SYN=1, seq=x
    （我要连接，我的序列号从1000开始）

服务端 → 客户端：SYN=1, ACK=1, seq=y, ack=x+1 
    （我同意连接，我的序列号从2000开始，确认收到你的1000）

客户端 → 服务端：ACK=1, seq=x+1, ack=y+1
    （确认收到你的同意，开始通信）
```
TCP三次握手（建立连接）：客户端发送SYN=1同步报文，服务端回复SYN=1，ACK=1确认报文，客户端再发送ACK=1最终确认，通过三次交互确保双方收发能力正常，建立可靠连接。
```c
// TCP头部标志位（6位）
struct tcphdr {
    // ... 其他字段
    u_int8_t flags;
    // 标志位组成：
    // | URG | ACK | PSH | RST | SYN | FIN |
};
// 具体含义：
SYN = 1: 同步序号（建立连接）
ACK = 1: 确认序号有效
FIN = 1: 发送方数据结束（关闭连接）
RST = 1: 重置连接
PSH = 1: 接收方应尽快交给应用层
URG = 1: 紧急指针有效
```
TCP的头部有几个标志位,
三次握手是
客户端发送SYN后进入SYN_SENT状态，
服务端收到后进入SYN_RCVD状态并回复SYN+ACK，
客户端收到后进入ESTABLISHED状态并发送ACK，
服务端收到ACK后也进入ESTABLISHED状态。

1. 交换初始序列号（ISN）防止序列号冲突
2. 协商最大报文段大小（MSS）
3. 确认双方的收发能力都正常
4. 防止历史连接造成的混乱
两次握手无法防止**已失效的连接请求**突然到达服务端，而且无法确保客户端的接收能力正常

四次挥手
1. 主动关闭方发送FIN后进入FIN_WAIT_1状态
2. 被动方收到FIN后进入CLOSE_WAIT状态并回复ACK
3. 被动方处理完数据后发送FIN进入LAST_ACK状态
4. 主动方收到FIN后进入TIME_WAIT状态并回复ACK

TIME_WAIT状态持续2MSL（最大报文生存时间），目的是确保最后一个ACK能被对方收到，
同时让网络中残留的报文自然消失，避免干扰新连接。


```
客户端 → 服务端：FIN=1
    （我数据发完了，要关闭连接）

服务端 → 客户端：ACK=1  
    （收到你的关闭请求，但我可能还有数据要发）

...服务端处理剩余数据...

服务端 → 客户端：FIN=1
    （我数据也发完了，同意关闭）

客户端 → 服务端：ACK=1
    （收到，连接正式关闭）
```
TCP四次挥手（断开连接）：主动方发送FIN=1关闭请求，被动方先回复ACK确认，待数据处理完毕后再发送FIN=1，主动方回复ACK确认，通过四次交互保证数据完整传输后才断开连接。
不是三次：TCP连接是**全双工**的，每个方向需要独立关闭，而且服务端收到FIN后可能还有数据要发送给客户端
#### 服务器-客户端
![[90-附件/TCP socket流程.png]]


```c
1. socket()      // 创建监听套接字，是一个文件描述符
2. bind()        // 将得到的监听的文件描述符绑定IP和端口
3. listen()      // 设置监听(成功之后开始监听, 监听的是客户端的连接)
4. accept()      // 等待并接受客户端的连接请求, 建立新的连接, 会得到一个新的文件描述符(通信的)，没有新连接请求就阻塞
5. recv()/send() // 通信，数据收发读写操作默认都是阻塞的
6. close()       // 断开连接, 关闭套接字
```
监听的文件描述符，只需要有一个
不负责和客户端通信, 负责检测客户端的连接请求, 检测到之后调用accept就建立新的连接
而通信的文件描述符负责和建立连接的客户端通信
如果有N个客户端和服务器建立了新的连接, 通信的文件描述符就有N个，每个客户端和服务器都对应一个通信的文件描述符

文件读取模式：
文本模式是"有状态"的：文件系统需要记住当前是否遇到了\r，以便正确处理后面的\n
二进制模式是"纯净"的：**这就是为什么在进行文件格式解析、网络编程或嵌入式开发时，应该优先使用二进制模式**
#### 拥塞控制
**慢启动**，建立连接后，会先只发1条，然后2条，4条慢慢增加，这个过程称做慢开始，1、2、4递增的数量被称之为 **拥塞窗口** `cwnd`
可以理解为TCP希望刚开始，可以大胆点，不断加数量。但为了保险期间还是从1条还是倍增。
**拥塞窗口会增加到慢启动门限**（ssthreashold）为止，当到达**慢启动门限ssthreshold**时，会变成每次都增加1条。  这个过程叫**拥塞避免过程**， 也有叫他拥塞避免算法的
可以理解为tcp感觉到有风险了，于是开始慢慢地、小心翼翼地1条1条地添加发送条数。

随着每次发送的数量越发越多， 最终会超出带宽限制，于是就会有某条报文发生超时。  
有可能是发的中途丢了， 亦或者是返回的数据全阻塞住了，一条都回不来。
当发送端检测到发生超时时，就会让 **慢启动门限ssthreshold = 当前拥塞窗口cwnd/2**  
接着`cwnd`重新置为1 ，重新开始 慢启动算法。
这样的好处在于可以检测到每次发送的上限，动态调整发送窗口。  
上面的过程叫做 **超时重传**。  
注意发生超时重传时， cwnd会重置成1。

客户端判断超时：每次发送数据包的时候， 都会有一个相应的计时器，一旦超过 RTO(超时时间） 而没有收到 ACK， TCP就会重发该数据包。  
没收到 ACK 的数据包都会存在重传缓冲区里，等到 ACK 后，就从缓冲区里删除。

RTO是通过“每次报文的往返时间样本”和“之前样本的偏差值”**动态计算**出来的。
- RTT ： 报文往返时间（指从发送到收到ack的时间）。每个报文发出后都有个定时器，收到后都会计算出一个RTT样本
- RTTs： 加权平均往返时间，类似于一个估算的往返时间，实时在变。  
    RTTs = （1-a) * RTTs + a * RTT最新样本  
    即每次得到RTT样本后，  都会使用a这个占比去更新RTTs。
- `RTTd`:  RTT偏差加权平均值（就是用来计算超时时间应该比RTT多多少）  
    `RTTd` = (1 - b) *` RTTd` + b*RTTs - RTT最新样本  
    即每次会用新的RTTs以b的占比去更新一下RTTd，并减去RTT样本
- RTO ： 超时重传时间  
    等于平均往返时间 加上 4倍偏差值  
    RTO = RTTs + 4`*RTTd`

如果发生重传，却还是没有收到ack，那么最新的RTT样本会使用karn算法：发生重传时，不更新这次的RTT样。选用后面收到的ack  
修正karn： 为了避免发生重传后，实际RTT都变慢了，导致一下子所有请求都超时， 会在发生重传时，把RTO放大1倍。


接收端冗余确认机制：当接收方收到乱序报文时，重复发送对**最后一个按序到达报文**的ACK。
**快重传**：发送方**连续收到3个重复ACK**，立即重传对应数据，不等超时。这是对丢包的快速响应。
**快速恢复**：触发快重传后，拥塞窗口**减半**而非重置为1，然后进入拥塞避免阶段。避免从慢开始，加速恢复。


##### 注意：
数据发送多了可能会丢失：因为路由器有缓存，IP分组接收过多时就会耗尽空间，丢弃数据。

坚持定时器：当对端**接收缓冲区满**，通告窗口=0，则发送方启动坚持定时器，如**每隔5秒发送1字节探测报文**，小小试探对方是否恢复接收能力。旦收到**通告窗口>0**的ACK，立即恢复数据发送，避免链路闲置。

注意，每一个文件描述符在内核里都对应两块内存，读缓冲区（接收数据），写缓冲区（发送数据）

###### socket()

```c
#include <sys/types.h>
#include <sys/socket.h>
int socket(int domain, int type, int protocol);
```
**参数**：

- `domain`（地址族）：
    - `AF_INET`：IPv4 网络协议（最常用）。
    - `AF_INET6`：IPv6 网络协议。
    - `AF_UNIX`：本地套接字，用于同一台主机上的进程间通信。

- `type`（套接字类型）：
    - `SOCK_STREAM`：提供面向连接的、可靠的、双向的字节流。**对应TCP协议**。
    - `SOCK_DGRAM`：提供无连接的、不可靠的数据报服务。**对应UDP协议**。
- `protocol`：通常设置为 `0`，表示由系统根据 `domain` 和 `type` 自动选择合适的协议（如 `IPPROTO_TCP`）。


**返回值**：
- **成功**：返回一个新的**文件描述符**（一个非负整数）。
- **失败**：返回 `-1`，并设置全局变量 `errno` 以指示错误。
此时套接字还没有与任何地址或端口关联

######  **`bind()`**
将一个套接字与一个特定的IP地址和端口号绑定起来。
```c
#include <sys/types.h>
#include <sys/socket.h>
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```
**参数**：

- `sockfd`：`socket()` 函数返回的文件描述符。
- `addr`：指向一个 `struct sockaddr` 结构的指针，该结构包含了要绑定的地址和端口号。实际使用时，填充的是 `struct sockaddr_in`（用于IPv4），然后强制转换为 `struct sockaddr *`。
- `addrlen`：`addr` 结构体的大小，通常是 `sizeof(struct sockaddr_in)`。


**返回值**：
- **成功**：返回 `0`。
- **失败**：返回 `-1`，并设置 `errno`。

注意：
- **服务器必须调用 `bind()`**，以便客户端知道要连接到哪个地址和端口。
- 如果指定端口号为 `0`，系统会为你随机分配一个可用端口（通常不用于服务器）。
- 如果指定IP地址为 `INADDR_ANY`（即 `0.0.0.0`），表示监听机器上**所有**网络接口（网卡）的连接请求。

###### `struct sockaddr`结构体
使用时常用`struct sockaddr_in`，两种结构体大小一致都是16字节，  但后者更便捷，
```c
// 在写数据的时候不好用
struct sockaddr {
	sa_family_t sa_family;       // 地址族协议, ipv4
	char        sa_data[14];     // 端口(2字节) + IP地址(4字节) + 填充(8字节)
}

typedef unsigned short  uint16_t;
typedef unsigned int    uint32_t;
typedef uint16_t in_port_t;
typedef uint32_t in_addr_t;
typedef unsigned short int sa_family_t;
#define __SOCKADDR_COMMON_SIZE (sizeof (unsigned short int))

struct in_addr
{
    in_addr_t s_addr;
};  

// sizeof(struct sockaddr) == sizeof(struct sockaddr_in)
struct sockaddr_in
{
    sa_family_t sin_family;		/* 地址族协议: AF_INET */
    in_port_t sin_port;         /* 端口, 2字节-> 大端  注意转换成大端！！！*/
    struct in_addr sin_addr;    /* IP地址, 4字节 -> 大端  */
    /* 填充 8字节 */
    unsigned char sin_zero[sizeof (struct sockaddr) - sizeof(sin_family) -
               sizeof (in_port_t) - sizeof (struct in_addr)];
};  

// IPv6 专用地址结构
struct sockaddr_in6 {
    sa_family_t     sin6_family;   // 地址族：AF_INET6
    in_port_t       sin6_port;     // 16位端口号

    struct in6_addr sin6_addr;     // 128位IPv6地址
    uint32_t        sin6_scope_id; // 范围ID

```

###### listen（）
将主动套接字转换为被动套接字，并设置连接请求队列的长度，使其可以接受来自客户端的连接。
```c
#include <sys/types.h>
#include <sys/socket.h>
int listen(int sockfd, int backlog);
```
**参数**：

- `sockfd`：已经绑定地址的套接字文件描述符。
- `backlog`：连接请求队列的最大长度。当多个客户端同时请求连接时，尚未被 `accept()` 处理的连接会在这个队列中排队。这个参数指定了队列的最大长度。

`listen`的backlog参数控制的是已完成连接队列的大小。epoll虽然能高效处理大量连接，但如果应用程序的`accept()`调用跟不上连接建立速度，队列满了之后新连接就会被拒绝。所以backlog大小需要根据应用的处理能力和并发量来合理设置。
如果backlog太小，即使有很多连接完成握手，但不能超过backlog设置的队列大小，多余的连接会让客户端收到RST（连接重置）

`listen()`的backlog参数指定了全连接队列的最大长度。这个队列存放的是已经完成TCP三次握手、等待`accept()`处理的连接。队列大小受应用程序指定的backlog值和系统上限SOMAXCONN的双重限制。当队列满时，新的已完成连接会被内核直接丢弃。


`SOMAXCONN` 宏是系统定义的**全连接队列的最大长度**。
在TCP三次握手过程中有两个队列
1.**半连接队列**:客户端发送SYN，服务器回复SYN-ACK后连接处于`SYN_RCVD`状态（即正在进行TCP三次握手但是未完成的状态）
队列大小由 `net.ipv4.tcp_max_syn_backlog` 控制
```shell
# 半连接队列大小由系统参数控制
cat /proc/sys/net/ipv4/tcp_max_syn_backlog
# 通常为1024或512
```
2.**全连接队列**:三次握手完成，连接处于`ESTABLISHED`状态，等待服务器调用 `accept()` 取出
 **`SOMAXCONN` 控制的是这个队列的大小**，

注意listen设置的是"已完成连接队列"大小，**`accept()` 只是从队列中取出连接**，不是建立连接，**真正的连接建立由内核TCP栈完成**而**epoll监听的是"有新连接到达"这个事件**
```text
客户端SYN → 服务器 → SYN-ACK → 客户端ACK → 
连接建立成功 → 放入accept队列 → epoll通知可读 → 
应用程序accept()取出
```

**返回值**：
- **成功**：返回 `0`。
- **失败**：返回 `-1`，并设置 `errno`。

**注意事项**：

- 调用 `listen()` 之后，套接字就从 **主动套接字** 变成了 **监听套接字**，它不能再用于发起连接，只能用于接受连接。
- `backlog` 的具体含义在不同系统上略有差异，一般设置为 `5` 到 `10` 即可。

###### accept()
从监听套接字的连接请求队列中，取出第一个连接请求，并为这个连接**创建一个新的套接字**用于通信。
就从监听文件描述符对应的读缓存区读取请求，没有就阻塞
```c
#include <sys/types.h>
#include <sys/socket.h>
int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```
**参数**：

- `sockfd`：处于监听状态的套接字文件描述符。
- `addr`：一个指向 `struct sockaddr` 的指针，用于存放**客户端**的地址信息（IP和端口）。如果不需要，可以设为 `NULL`。
- `addrlen`：这是一个**值-结果参数**。调用时，需要将其初始化为 `addr` 指向的缓冲区大小；函数返回时，它会被设置为客户端地址的实际长度。如果 `addr` 为 `NULL`，此参数也应为 `NULL`。


**返回值**：

- **成功**：返回一个**新的套接字文件描述符**。这个新描述符用于与刚刚连接的客户端进行**双向通信**。
    
- **失败**：返回 `-1`，并设置 `errno`。


**注意事项**：
accept()并不会建立连接，他是从全连接队列里取出第一个连接请求并完成创建通信套接字
- **这是最关键的函数之一**。`accept()` 返回的**新套接字**与 `listen()` 用的监听套接字是**两个不同的东西**。
- 默认情况下，`accept()` 是**阻塞**的。如果连接请求队列为空，它将一直等待，直到有新的连接到来。

###### connect()
客户端通过这个函数，主动与指定的服务器建立连接。
```c
#include <sys/types.h>
#include <sys/socket.h>
int connect(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```
**参数**：

- `sockfd`：由 `socket()` 创建出来的套接字文件描述符。
- `addr`：指向一个 `struct sockaddr` 结构的指针，这个结构里包含了**想要连接的服务器的地址信息**（服务器的IP地址和端口号）。和 `bind` 一样，实际填充的是 `struct sockaddr_in`，然后强制转换。
- `addrlen`：`addr` 结构体的大小，即 `sizeof(struct sockaddr_in)`。


**返回值**：

- **成功**：返回 `0`。此时，TCP的三次握手已经完成，连接已经建立。你可以立刻使用 `send()` 和 `recv()` 在这个套接字上进行通信。
- **失败**：返回 `-1`，并设置 `errno`。


**注意事项**：

1. **阻塞行为**：默认情况下，`connect()` 是**阻塞**的。它会发起连接请求，然后一直等待，直到收到服务器的确认（完成TCP三次握手）、超时、或明确被拒绝。
2. **错误处理**：常见的错误 `errno` 有：
    - `ECONNREFUSED`：连接被拒绝。最常见的原因是**服务器没有启动**，或者连接的端口上没有服务在监听。
    - `ETIMEDOUT`：连接超时。可能因为网络不通，或者服务器地址错误。
3. **客户端不需要 `bind`**：通常情况下，客户端不需要调用 `bind()`。操作系统会在调用 `connect()` 时，自动为套接字分配一个临时的本地IP地址和端口号（称为“临时端口”）。

###### `recv()/read()`
在已连接的套接字上进行数据的接收
调用这两个函数会向当前通信的文件描述符对应的读缓冲区读出数据，没有数据就阻塞直到读缓冲区有数据
```c
#include <sys/types.h>
#include <sys/socket.h>
// 接收数据
ssize_t read(int sockfd, void *buf, size_t size);
ssize_t recv(int sockfd, void *buf, size_t size, int flags);


```
参数:
sockfd: 用于通信的文件描述符, accept() 函数的返回值
buf: 指向一块有效内存, 用于存储接收的数据
size: 参数buf指向的内存的容量
flags: 特殊的属性, 一般不使用, 指定为 0
返回值:
大于0：实际接收的字节数
等于0：对方断开了连接
-1：接收数据失败了


默认是**阻塞**的。`recv()` 会阻塞直到有数据到来；

###### send()/write()
调用这两个函数会向当前通信的文件描述符对应的写缓冲区写入数据，内核检测到写缓冲区有数据会自动发送
当写缓存区满了就会被阻塞
```c
// 发送数据的函数
ssize_t write(int fd, const void *buf, size_t len);
ssize_t send(int fd, const void *buf, size_t len, int flags);


```
参数:
fd: 通信的文件描述符, accept() 函数的返回值
buf: 传入参数, 要发送的字符串
len: 要发送的字符串的长度
flags: 特殊的属性, 一般不使用, 指定为 0
返回值：
大于0：实际发送的字节数，和参数len是相等的
-1：发送数据失败了

返回值可能**小于**请求的 `len`！必须检查返回值，并根据实际收发到的字节数来处理数据。这是网络编程中最常见的错误来源之一。
默认`send()` 会阻塞直到内核缓冲区有空间容纳要发送的数据。

###### close()
关闭一个套接字，释放系统资源。
```c
#include <unistd.h>
int close(int sockfd);
```
**参数**：

- `sockfd`：要关闭的套接字文件描述符（可以是监听套接字，也可以是通信套接字）。

**返回值**：
- **成功**：返回 `0`。
- **失败**：返回 `-1`，并设置 `errno`。

**注意事项**：

- 当调用 `close()` 时，如果该套接字仍有数据在发送或接收队列中，系统会尝试在后台完成这些操作，但最安全的方式是，在关闭前确保所有数据都已处理完毕。
- 对于面向连接的协议（如TCP），`close()` 会触发TCP的断开连接流程（发送FIN包）。


###### `setsockopt`()
用于任意类型、任意状态套接口的设置选项值。
```c
#include <sys/socket.h>
int setsockopt(int sockfd, int level, int optname, 
               const void *optval, socklen_t optlen);
```
- **`sockfd`**：要设置的套接字文件描述符
- **level**：选项的协议层，常用：
    - `SOL_SOCKET`：套接字通用选项
    - `IPPROTO_TCP`：TCP协议选项
    - `IPPROTO_IP`：IP协议选项
- **`optname`**：具体选项名，如：
    - `SO_REUSEADDR`：地址重用
    - `SO_KEEPALIVE`：保持连接
    - `SO_RCVTIMEO`：接收超时
- **`optval`**：选项值指针
- **`optlen`**：选项值长度

成功为1，失败为-1.设置errno

eg：
```c
setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
```
**`SO_REUSEADDR`的作用**：允许立即重用处于 `TIME_WAIT` 状态的端口。
用于服务器崩溃后快速重启,开发调试时频繁重启服务.避免"Address already in use"错误

**TIME_WAIT状态**：TCP连接关闭后，端口会等待2MSL（60-120秒）才完全释放。`SO_REUSEADDR` 跳过这个等待。

### 注意

#### **TCP三次握手过程**

**三次**：防止已失效的连接请求突然传到服务器，造成资源浪费

#### **TCP vs UDP**

|特性|TCP|UDP|
|---|---|---|
|**连接性**|面向连接（三次握手）|无连接|
|**可靠性**|可靠（确认、重传、排序）|不可靠（可能丢包、乱序）|
|**传输方式**|字节流（可能粘包）|数据报（保持边界）|
|**速度**|较慢（有控制机制）|很快（直接发送）|
|**头部大小**|20-60字节|8字节|
|**流量控制**|有（滑动窗口）|无|
|**拥塞控制**|有（四大算法）|无|
|**应用场景**|Web(HTTP)、邮件、文件传输|视频流、DNS、游戏|

## **三、关键概念详解**

|特性|TCP|UDP|
|---|---|---|
|连接性|面向连接|无连接|
|可靠性|可靠传输|不可靠传输|
|速度|慢|快|
|数据顺序|保证顺序|不保证顺序|
|适用场景|文件传输、网页浏览|视频流、DNS查询|
**TCP通过建立连接、确认、重传、排序、流量和拥塞控制，确保数据最终能完整、有序地送达。** 
过程复杂，开销大，速度慢，但可靠。

**UDP 不建立连接、不确认、不重传、不排序、不控速。**
过程简单，开销极小，速度快，但不可靠。
#### MQTT VS Socket

MQTT是应用层协议，在Socket基础上封装了订阅发布、QoS质量等级、遗嘱消息等物联网专用

#### TCP粘包
TCP粘包和拆包问题，本质上是因为TCP是面向字节流的协议，它不关心应用层消息的边界，只保证数据的有序可靠传输。这会导致以下三种情况：

1. **粘包**：发送端的多个小数据包被合并成一个大数据包接收
2. **拆包**：一个大数据包被拆分成多个小包接收
3. **混合情况**：粘包和拆包同时发生

##### 解决方案：
1.固定长度协议：每个应用层消息都采用相同的固定长度。
- 定义固定的消息长度，比如1024字节
- 不足的部分用特定字符（如`\0`）填充
- 接收方每次读取固定长度的数据
实现简单，解析高效
空间浪费严重，不够灵活
**适用场景**：协议字段固定的场景，如某些金融、物联网协议"

2.长度前缀协议（最常用）：在消息头中定义长度字段，指明消息体的长度。
1. 定义消息结构：`[消息头(4字节)][消息体]`
2. 消息头存储消息体的长度（通常用4字节整数，网络字节序）
3. 接收方先读4字节获取长度，再读取对应长度的消息体

空间利用率高，解析明确，业界标准做法
需要两次系统调用，需要处理字节序
**适用场景**：**绝大多数网络通信场景**，如HTTP、gRPC、自定义TCP协议等

3.分隔符协议：使用特殊字符或字符串作为消息边界。
- 选择不会在正常数据中出现的分隔符，如`\r\n`、`\0`等
- 发送方在每个消息末尾添加分隔符
- 接收方基于分隔符来拆分消息
可读，调试方便
需要扫描整个消息，性能稍差；分隔符需要转义处理
**适用场景**：文本协议，如Redis协议、SMTP、FTP等

### I/O模型

- **阻塞IO**：调用函数后进程一直等待操作完成
- **非阻塞IO**：调用立即返回，需要轮询检查状态
- **IO多路复用**：select/poll/epoll同时监控多个套接字

**操作系统为支持高并发网络应用提供的底层机制**，主要用于实现同时检查多个文件描述符，确认I/O系统调用是否可以非阻塞地执行

#### 通知模式
文件描述符准备就绪的通知模式：
水平触发通知：如果文件描述符上可以非阻塞地执行I/O系统调用则说明就绪
边缘触发通知：如果文件描述符自上次状态检查之后有了新的I/O活动则说明就绪

采用水平触发通知可以在任意时刻检查文件描述符的就绪状态，不需要每次当文件描述符就绪之后尽可能多地执行I/O操作

采用边缘触发通知时只有当I/O事件发生时才通知，所以需要：
1.在接收到一个I/O事件通知之后让程序在某时刻尽可能多地在对应的文件描述符上执行I/O，不这么做可能导致数据丢失或者程序阻塞，但采用之后可能会让其他文件描述符处于饥饿状态
2.每个被检查的文件描述符应当是非阻塞的，因为程序如果采用循环来执行对文件描述符尽可能多的I/O操作，且文件描述符是阻塞的，当没有更多I/O可执行时会I/O系统调用会被阻塞
#### 多路复用I/O
- 多路: 指的是多个socket网络连接;
- 复用: 指的是复用一个线程、使用一个线程来检查多个文件描述符（Socket）的就绪状态
- 多路复用主要有三种技术：select，poll，epoll。epoll是最新的, 也是目前最好的多路复用技术；

可以在普通文件，终端，伪终端，管道，FIFO，套机子以及一些其他类型的字符型设备上使用select()和poll()来检查文件描述符
与多进程和多线程技术相比，I/O多路复用技术的最大优势是系统开销小，系统不必创建进程或者线程，也不必维护这些进程/线程，从而大大减小了系统的开销。
##### select
系统调用select()会一直阻塞，直到一个或多个文件描述符集合成为就绪状态
```c
#include <sys/select.h>

int select(int nfds, fd_set *readfds, fd_set *writefds, 
           fd_set *exceptfds, struct timeval *timeout);



// 相关宏
FD_ZERO(&set);      // 清空集合
FD_SET(fd, &set);   // 添加fd到集合  
FD_CLR(fd, &set);   // 从集合移除
FD_ISSET(fd, &set); // 检查fd是否在集合
```
- readfds：内核检测该集合中的IO是否可读。如果想让内核帮忙检测某个IO是否可读，需要手动把文件描述符加入该集合。
- writefds：内核检测该集合中的IO是否可写。同readfds，需要手动把文件描述符加入该集合。
- exceptfds：内核检测该集合中的IO是否异常。同readfds，需要手动把文件描述符加入该集合。
- nfds：以上三个集合中最大的文件描述符数值 + 1，例如集合是{0,1,5,10}，那么 maxfd 就是 11
- timeout：用户线程调用select的超时时长。

- 设置成NULL，表示如果没有 I/O 事件发生，则 select 一直等待下去。
- 设置为非0的值，这个表示等待固定的一段时间后从 select 阻塞调用中返回。
- 设置成 0，表示根本不等待，检测完毕立即返回。

函数返回值：

- 大于0：成功，返回集合中已就绪的IO总个数
- 等于-1：调用失败
- 等于0：没有就绪的IO

fd_set本质是一个数组，为了方便我们操作该数组，操作系统提供了以下函数：
```c
// 将文件描述符fd从set集合中删除 
void FD_CLR(int fd, fd_set *set); 

// 判断文件描述符fd是否在set集合中 
int  FD_ISSET(int fd, fd_set *set); 

// 将文件描述符fd添加到set集合中 
void FD_SET(int fd, fd_set *set); 

// 将set集合中, 所有文件描述符对应的标志位设置为0
void FD_ZERO(fd_set *set);
```


##### poll
poll的实现和select非常相似，只是描述fd集合的方式不同。针对select遗留的三个问题中（问题(2)是fd限制问题，问题(1)和(3)则是性能问题），poll只是使用pollfd结构而不是select的fd_set结构，这就解决了select的问题(2)fds集合大小1024限制问题。但poll和select同样存在一个性能缺点就是包含大量文件描述符的数组被整体复制于用户态和内核的地址空间之间，而不论这些文件描述符是否就绪，它的开销随着文件描述符数量的增加而线性增大。
```c

struct pollfd {
　　 int fd;           /*文件描述符*/
　　 short events;     /*监控的事件*/
　　 short revents;    /*监控事件中满足条件返回的事件*/
};
int poll(struct pollfd *fds, unsigned long nfds, int timeout);   
```
- fds：struct pollfd类型的数组, 存储了待检测的文件描述符，struct pollfd有三个成员：
- fd：委托内核检测的文件描述符
- events：委托内核检测的fd事件（输入、输出、错误），每一个事件有多个取值
- revents：这是一个传出参数，数据由内核写入，存储内核检测之后的结果
- nfds：描述的是数组 fds 的大小
- timeout: 指定poll函数的阻塞时长

- -1：一直阻塞，直到检测的集合中有就绪的IO事件，然后解除阻塞函数返回
- 0：不阻塞，不管检测集合中有没有已就绪的IO事件，函数马上返回
- 大于0：表示 poll 调用方等待指定的毫秒数后返回


函数返回值：

- -1：失败
- 大于0：表示检测的集合中已就绪的文件描述符的总个数


#### epoll
epoll 全称 eventpoll，是 linux 内核实现IO多路转接/复用（IO multiplexing）的一个实现。IO多路转接的意思是在一个操作里同时监听多个输入输出源，在其中一个或多个输入输出源可用的时候返回，然后对其的进行读写操作。epoll是select和poll的升级版，相较于这两个前辈，epoll改进了工作方式，因此它更加高效。

**epoll实现高并发的核心是通过事件驱动和内核事件表，避免了传统多线程模型的上下文切换开销。它并不直接处理TCP连接建立，而是监听`accept`队列中是否有新连接到达**。

- 对于待检测集合select和poll是基于线性方式处理的，epoll是基于红黑树来管理待检测集合的。
- select和poll每次都会线性扫描整个待检测集合，集合越大速度越慢，epoll使用的是回调机制，效率高，处理效率也不会随着检测集合的变大而下降
- select和poll工作过程中存在内核/用户空间数据的频繁拷贝问题，在epoll中内核和用户区使用的是共享内存（基于mmap内存映射区实现），省去了不必要的内存拷贝。
- 程序猿需要对select和poll返回的集合进行判断才能知道哪些文件描述符是就绪的，通过epoll可以直接得到已就绪的文件描述符集合，无需再次检测
- 使用epoll没有最大文件描述符的限制，仅受系统中进程能打开的最大文件数目限制
- 当多路复用的文件数量庞大、IO流量频繁的时候，一般不太适合使用select()和poll()，这种情况下select()和poll()表现较差，推荐使用epoll()。
##### 触发模式
| 特性       | 水平触发（LT，默认）             | 边缘触发（ET）                      |
| -------- | ----------------------- | ----------------------------- |
| **触发条件** | 只要事件状态满足（如可读/可写），就会一直触发 | 只在事件状态**从不满足变为满足**时触发一次       |
| **重复触发** | 只要事件持续存在，就会**不断触发**     | 事件持续存在时，**只触发一次**，需手动处理完才能再触发 |
| **适用场景** | 简单应用、新手友好               | 高并发服务器、性能敏感场景                 |

水平触发 （LT，默认）
```c
struct epoll_event ev;
ev.events = EPOLLIN; // 可读事件
ev.data.fd = listenfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listenfd, &ev);

// 等待事件
int nfds = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (int n = 0; n < nfds; ++n) {
    if (events[n].data.fd == listenfd) {
        // 接收新连接
        int connfd = accept(listenfd, NULL, NULL);
        ev.events = EPOLLIN | EPOLLET; // 添加新连接到监听
        ev.data.fd = connfd;
        epoll_ctl(epfd, EPOLL_CTL_ADD, connfd, &ev);
    } else {
        // 处理数据
        char buf[1024];
        int len = read(events[n].data.fd, buf, sizeof(buf));
        if (len > 0) {
            write(events[n].data.fd, buf, len); // 回显数据
        }
    }
}
```

边缘触发（ET）
```c
struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET; // 边缘触发
ev.data.fd = listenfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listenfd, &ev);

// 等待事件
int nfds = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (int n = 0; n < nfds; ++n) {
    if (events[n].data.fd == listenfd) {
        // 接收新连接
        int connfd = accept(listenfd, NULL, NULL);
        ev.events = EPOLLIN | EPOLLET; // 添加新连接到监听
        ev.data.fd = connfd;
        epoll_ctl(epfd, EPOLL_CTL_ADD, connfd, &ev);
    } else {
        // 处理数据
        char buf[1024];
        while (1) { // 关键：循环读取，直到无数据
            int len = read(events[n].data.fd, buf, sizeof(buf));
            if (len <= 0) break; // 无数据或出错
            write(events[n].data.fd, buf, len); // 回显数据
        }
    }
}
```

> **关键差异**：ET 模式下，必须**循环读取**，直到无数据可读，否则可能错过后续数据。

|特性|水平触发（LT）|边缘触发（ET）|
|:--|:--|:--|
|**CPU 使用率**|可能较高，因为事件持续触发|较低，事件只触发一次|
|**数据处理效率**|简单，适合小数据量|高效，适合大数据量和高并发|
|**适用场景**|简单应用、新手友好|高并发服务器、性能敏感场景|

水平触发只要事件状态满足就会一直触发，边缘触发只在事件状态从不满足变为满足时触发一次。
边缘触发只触发一次，减少了 CPU 的重复处理，提高了处理效率，适合高并发场景。
在边缘触发模式下，必须循环读取数据，直到无数据可读，否则可能错过后续数据。

EPOLLIN表示socket有数据可读，包括新连接到达、客户端发送数据、对端关闭连接等。EPOLLERR表示连接发生错误如RST复位，EPOLLHUP表示连接被挂断如正常关闭。一个epoll实例可以同时监控成百上千个socket，epoll_wait返回时只报告那些有事件发生的socket，通过events数组中的掩码位来区分具体是什么事件。

EPOLLIN、EPOLLOUT这些是位掩码常量，不是信号。它们与open的O_RDONLY类似，都是通过按位或组合、按位与检查的方式来使用。区别在于open标志在创建文件时一次性设置，而epoll事件标志会随着socket状态变化被内核动态更新。

eg：
```c
#define MAX_EVENTS 1024
struct epoll_event events[MAX_EVENTS];

while (1) {
    int nfds = epoll_wait(epoll_fd, events, MAX_EVENTS, -1);
    
    for (int i = 0; i < nfds; i++) {
        int fd = events[i].data.fd;
        
        // 1. 检查错误或挂断（优先级最高）
        if (events[i].events & (EPOLLERR | EPOLLHUP)) {
            printf("连接异常，清理fd=%d\n", fd);
            close(fd);
            continue;
        }
        
        // 2. 如果是监听socket，接受新连接
        if (fd == server_fd) {
            accept_new_connection(server_fd, epoll_fd);
        }
        // 3. 如果是客户端socket，读取数据
        else if (events[i].events & EPOLLIN) {
            handle_client_data(fd);
        }
        // 4. 可写事件（通常用于发送缓冲区满后恢复）
        else if (events[i].events & EPOLLOUT) {
            handle_write_ready(fd);
        }
    }
}
```

###### epoll_create1()
`epoll_create1` 比 `epoll_create` 多一个 flags 参数，可传` EPOLL_CLOEXEC` 让 `fd` 自动 `O_CLOEXEC`，避免` fork-exec` 后泄漏；size 参数被忽略，两者内核都用同样哈希表实现

```c
int epoll_create1(int flags)
```
flags 可为 0 或 `EPOLL_CLOEXEC`
- **EPOLL_CLOEXEC**：设置 `FD_CLOEXEC` 标志，**fork 后 exec 族函数自动关闭 fd**，防止句柄泄漏（线程池、守护进程必备）。
    
- 无其他 flag，**传非 0 非 EPOLL_CLOEXEC 返回 -EINVAL**。
**epoll_create1的1表示 单 flags 参数** 版本，内核后续可扩展新 flag，保持 ABI 兼容。
`EPOLL_CLOEXEC` 防止 fork-exec 后子进程继承 epoll fd，避免句柄泄漏，是线程池/守护进程标配。


```c
// 老代码
int epfd = epoll_create(256);          // size 无用
fcntl(epfd, F_SETFD, FD_CLOEXEC);      //还得再调一次

// 新代码
int epfd = epoll_create1(EPOLL_CLOEXEC); // 自动带 CLOEXEC
```
###### `epoll_create`()
`epoll_create(`)函数的作用是创建一个红黑树模型的实例，用于管理待检测的文件描述符的集合。
```c
int epoll_create(int size);
```
函数参数 size：在Linux内核2.6.8版本以后，这个参数是被忽略的，只需要指定一个大于0的数值就可以了。
函数返回值：
失败：返回-1
成功：返回一个有效的文件描述符，通过这个文件描述符就可以访问创建的epoll实例了

###### `epoll_ctl`()
管理红黑树实例上的节点，可以进行添加、删除、修改操作。
```c
// 联合体, 多个变量共用同一块内存        
typedef union epoll_data {
 	void        *ptr;
	int          fd;	// 通常情况下使用这个成员, 和epoll_ctl的第三个参数相同即可
	uint32_t     u32;
	uint64_t     u64;
} epoll_data_t;

struct epoll_event {
	uint32_t     events;      /* Epoll events */
	epoll_data_t data;        /* User data variable */
};
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);

```

函数参数：
- epfd：epoll_create() 函数的返回值，通过这个参数找到epoll实例

- op：这是一个枚举值，控制通过该函数执行什么操作
- EPOLL_CTL_ADD：往epoll模型中添加新的节点
- EPOLL_CTL_MOD：修改epoll模型中已经存在的节点
- EPOLL_CTL_DEL：删除epoll模型中的指定的节点

- fd：文件描述符，即要添加/修改/删除的文件描述符

- event：epoll事件，有两个成员`events`和`data`用来修饰第三个参数对应的文件描述符的，指定检测这个文件描述符的什么事件
- events：委托epoll检测的事件
- EPOLLIN：读事件, 接收数据, 检测读缓冲区，如果有数据该文件描述符就绪
- EPOLLOUT：写事件, 发送数据, 检测写缓冲区，如果可写该文件描述符就绪
- EPOLLERR：异常事件
- data：用户数据变量，这是一个联合体类型，通常情况下使用里边的fd成员，用于存储待检测的文件描述符的值，在调用epoll_wait()函数的时候这个值会被传出。

函数返回值：
 失败：返回-1
 成功：返回0

###### `epoll_wait()`
检测创建的epoll实例中有没有就绪的文件描述符。
```c
int epoll_wait(int epfd, struct epoll_event * events, int maxevents, int timeout);

```
函数参数：
- `epfd`：`epoll_create`() 函数的返回值, 通过这个参数找到epoll实例
- events：传出参数, 这是一个结构体数组的地址, 里边存储了已就绪的文件描述符的信息
- maxevents：修饰第二个参数, 结构体数组的容量（元素个数）
- timeout：如果检测的epoll实例中没有已就绪的文件描述符，该函数阻塞的时长, 单位ms 毫秒
0：函数不阻塞，不管epoll实例中有没有就绪的文件描述符，函数被调用后都直接返回
大于0：如果epoll实例中没有已就绪的文件描述符，函数阻塞对应的毫秒数再返回
-1：函数一直阻塞，直到epoll实例中有已就绪的文件描述符之后才解除阻塞

函数返回值：
成功：
- 等于0：函数是阻塞被强制解除了, 没有检测到满足条件的文件描述符
- 大于0：检测到的已就绪的文件描述符的总个数
失败：返回-1

### JSON
**JSON（JavaScript Object Notation）** 是一种轻量级的**数据交换格式**。
1. **易于人阅读和编写**：采用纯文本形式，结构清晰。
2. **易于机器解析和生成**：基于键值对集合，可以被各种编程语言轻松处理。
3. **独立于语言**：虽然源自 JavaScript，但 C, C++, Python, Java 等几乎所有现代语言都有其解析库。

JSON作为一种轻量级的数据交换格式，有三个核心优势：**结构化、可扩展、语言无关**。相比XML，它没有冗余标签，体积更小，解析更快；相比二进制协议，它具备可读性，调试方便。


JSON的基本数据类型：

- 数值：十进制数，不能有前导0，可以为负数，可以有小数部分。还可以用e或者E表示指数部分。不能包含非数，如NaN。不区分整数与浮点数。JavaScript用双精度浮点数表示所有数值。
- 字符串：以双引号""括起来的零个或多个Unicode码位。支持反斜杠开始的转义字符序列。
- 布尔值：表示为true或者false。
- 值的有序列表（array）：有序的零个或者多个值。每个值可以为任意类型。序列表使用方括号`[]`括起来。元素之间用逗号,分割。形如：`[value, value]`
- 对象（object）：若干无序的“键-值对”(key-value pairs)，其中键是数值或字符串。建议但不强制要求对象中的键是独一无二的。对象以花括号{开始，并以}结束。键-值对之间使用逗号分隔。键与值之间用冒号:分割。
- null类型：值写为null。

- 失败（内存不足）：返回 `NULL`

**注意事项：**
- 创建的对象初始为空对象 `{}`
- **必须最终调用 `cJSON_Delete()` 来释放内存**
- 如果创建失败返回 NULL，后续操作会导致段错误





##### `cJSON_AddNumberToObject`

```c
cJSON_bool cJSON_AddNumberToObject(cJSON * const object, 
                                  const char * const name, 
                                  const double number);
```
**参数：**

- `object`：要向其中添加数值的 cJSON 对象（必须是通过 `cJSON_CreateObject` 创建的对象）
- `name`：键名（字符串）
- `number`：要添加的数值（double 类型）

**返回值：**
- 成功：返回 `cJSON_True`
- 失败：返回 `cJSON_False`（通常是因为内存分配失败）
**注意事项：**

- **会复制键名字符串**，所以可以传递栈上的字符串或字面量
- 数值以 `double` 存储，但 cJSON 会自动区分数值和整数表示
- 如果键名已存在，**会覆盖**原有的值
- 必须确保 `object` 参数是有效的 cJSON 对象指针



### HTTP
`libcurl`库是最常用的用于实现HTTP协议的库
HTTP协议是Hyper Text Transfer Protocol(超文本传输协议）的缩写，是用于从万
维网（WWW:WorldWideWeb）服务器传输超文本到本地浏览器的传送协议。
HTTP是一个基于TCP/IP通信协议来传递数据（HTML文件，图片文件，查询结果
等）。
**HTTP 是一种请求/响应式的协议**。一个客户机与服务器建立连接后，发送一个请求给服务器；服务器接到请求后，给予相应的响应信息。

- 基于请求/应答模式，客户端发送一个请求，服务器返回一个应答；
- HTTP协议是一个无状态协议，无状态意味着对服务器而言，每次请求都是独立无关联的，服务器不用存储记忆上次请求的数据和状态，处理速度会比较快

#### HTTP方法
HTTP 方法（也称为 HTTP 动词）是 HTTP 协议的核心概念。
`HTTP`定义了多种请求方法，来满足各种需求。`HTTP/1.0`定义了三种请求方法：`GET`、`POST` 和 `HEAD`，到了`HTTP/1.1`，新增了五种请求方法：`OPTIONS`、`PUT`、`DELETE`、`TRACE` 和 `CONNECT`。

##### HEAD
可以看做是只拿响应头不返回 body主体的GET方法
- **幂等**：多次 HEAD 与一次效果相同
- **安全**：不修改服务器状态
常用于探测资源是否存在，获取响应头作缓存校验，常配合OPTION方法探测服务器所允许的方法
```http

### HEAD 请求
HEAD /index.html HTTP/1.1
Host: example.com

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234
Date: ...
（**无 body，0 字节**）
```


##### **GET**
检索资源，不应改变服务器状态
```http
GET /api/users/123 HTTP/1.1
Host: example.com
```
**特点**：
- 参数在 URL 中（查询字符串）
- 可缓存
- 幂等（多次请求结果相同）
- 安全（不修改数据）

```c
// libcurl GET 请求
curl_easy_setopt(curl, CURLOPT_URL, "http://api.com/users/123");
// 或者带参数
curl_easy_setopt(curl, CURLOPT_URL, "http://api.com/users?id=123&type=admin");
```
在libcurl里默认就是GET方法，不需要其他额外处理
- `CURLOPT_URL`：请求的完整 URL
- `CURLOPT_HTTPGET`：显式设置为 GET 方法（通常不需要，因为 GET 是默认值）
```c
CURL *curl = curl_easy_init();
if(curl) {
    // 1. 设置 URL
    curl_easy_setopt(curl, CURLOPT_URL, "https://api.example.com/users");
    
    // 2. (可选) 设置查询参数 - 方法1：直接拼接到 URL
    curl_easy_setopt(curl, CURLOPT_URL, "https://api.example.com/users?id=123&name=john");
    
    // 3. (可选) 设置查询参数 - 方法2：使用自定义请求
    curl_easy_setopt(curl, CURLOPT_CUSTOMREQUEST, "GET");
    
    // 4. 执行请求
    CURLcode res = curl_easy_perform(curl);
    
    curl_easy_cleanup(curl);
}
```
##### **POST**
创建新资源，提交数据
```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json

{"name": "John", "email": "john@example.com"}
```
**特点**：
- 参数在请求体中
- 不可缓存
- 非幂等（多次请求可能产生不同结果）
- 不安全
```c
// libcurl POST 请求
const char *data = "name=John&email=john@example.com";
curl_easy_setopt(curl, CURLOPT_URL, "http://api.com/users");
curl_easy_setopt(curl, CURLOPT_POSTFIELDS, data);
```
```c
CURL *curl = curl_easy_init();
if(curl) {
    // 1. 设置 URL
    curl_easy_setopt(curl, CURLOPT_URL, "https://api.example.com/users");
    // 2. 设置为 POST 方法
    curl_easy_setopt(curl, CURLOPT_POST, 1L);
    
    // 3. 设置 POST 数据
    const char *post_data = "name=john&email=john@example.com";
    curl_easy_setopt(curl, CURLOPT_POSTFIELDS, post_data);
    
    // 4. (可选) 设置数据长度
    curl_easy_setopt(curl, CURLOPT_POSTFIELDSIZE, strlen(post_data));
    
    // 5. (可选) 设置 Content-Type
    struct curl_slist *headers = NULL;
    headers = curl_slist_append(headers, "Content-Type: application/x-www-form-urlencoded");
    curl_easy_setopt(curl, CURLOPT_HTTPHEADER, headers);
    
    // 6. 执行请求
    CURLcode res = curl_easy_perform(curl);
    
    curl_slist_free_all(headers);
    curl_easy_cleanup(curl);
}
```
`json`

##### **PUT**

{"name": "John Updated", "email": "john_new@example.com"}

**特点**：

- 幂等（多次请求结果相同）
    
- 需要指定完整资源

##### **PATCH**
部分更新资源（只修改指定字段）
```http

Host: example.com
Content-Type: application/json

{"email": "john_updated@example.com"}
```
**特点**：
- 非幂等（取决于实现）
    
- 只发送需要修改的字段

##### **DELETE**
删除指定资源
```http
DELETE /api/users/123 HTTP/1.1
Host: example.com
```
**特点**：

- 幂等
    
- 不安全


##### 方法特性

|方法|幂等性|安全性|缓存|请求体|典型应用|
|---|---|---|---|---|---|
|GET|✅|✅|✅|❌|获取资源|
|POST|❌|❌|❌|✅|创建资源|
|PUT|✅|❌|❌|✅|完整更新|
|PATCH|❌|❌|❌|✅|部分更新|
|DELETE|✅|❌|❌|❌|删除资源|
幂等性理解
```text
// 幂等：多次执行效果相同
// GET /users/1      → 总是返回用户1的信息
// PUT /users/1      → 总是把用户1更新为指定状态
// DELETE /users/1   → 第一次删除成功，后续返回404

// 非幂等：每次执行可能产生不同结果  
// POST /users       → 第一次创建用户1，第二次创建用户2
// PATCH /users/1    → 可能依赖当前状态，结果不同
```

##### HTTP头
**HTTP 头**是在 HTTP 请求和响应中传递的元数据，采用 `键: 值` 格式。它们出现在请求/响应的起始行之后，空行之前。
```http
GET /api/data HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer xyz123
User-Agent: MyApp/1.0
```
设置HTTP头，是为了确认通信协议
- 客户端通过声明HTTP头确定服务器接收响应的格式类型
- 同时告诉服务器发送的数据格式以便完整解析
- 确认客户端的身份
- 控制缓存行为
根据数据格式和服务器要求决定最后需不需要设置HTTP头，对应来看对于POST，PUT都需要设置以方便数据的传输，而简单的GET，测试则可以不需要HTTP头

![[90-附件/HTTP协议格式.png]]

HTTP消息头是在，客户端请求（Request）或服务器响应（Response）时传递的，位请求或响应的第一行， HTTP消息体（请求或响应的内容）是其后传输。`HTTP消息头`，以明文的字符串格式传送，是以冒号分隔的键/值对，如： Accept-Charset: utf-8，每一个消息头最后以回车符( CR)和换行符( LF)结尾。`HTTP消息头`结束后，会用一个空白的字段来标识，这样就会出现两个连续的`CR-LF`。
HTTP协议规定请求头和请求体之间用两个CRLF分隔（`\r\n\r\n`）。

`HTTP消息头`支持自定义， 自定义的专用消息头一般会添加`'X-'`前缀。
###### 请求头

客户端发送给服务器的元数据

| **Authorization**     | 身份验证凭证        | `Authorization: Bearer eyJhbGciOiJ...`             | API 认证、用户登录           |

| **Accept-Language**   | 客户端接受的语言      | `Accept-Language: zh-CN, en;q=0.9`                 | 国际化、多语言网站             |
| **Connection**        | 控制连接行为        | `Connection: keep-alive`                           | 连接复用，提高性能             |
| **Cache-Control**     | 缓存指令          | `Cache-Control: no-cache`                          | 控制缓存行为                |
| **If-Modified-Since** | 条件请求：时间       | `If-Modified-Since: Mon, 27 Nov 2023 00:00:00 GMT` | 节省带宽，304 Not Modified |
| **If-None-Match**     | 条件请求：ETag     | `If-None-Match: "abc123"`                          | 实体标签验证                |
| **Referer**           | 来源页面 URL      | `Referer: https://example.com/page`                | 统计分析、防盗链              |

| **Cookie**            | 客户端存储的 Cookie | `Cookie: sessionid=abc123; user=john`              | 会话管理、用户状态             |

##### 状态码
`HTTP`协议的状态码由`3`位数字组成，第一个数字定义了响应的类别，共有`5`中类别：

1.`1xx`: 指示信息–表示请求已接收，继续处理
2.`2xx`: 成功–表示请求已被成功接收、理解、接受
3.`3xx`: 重定向–要完成请求必须进行更进一步的操作
4.`4xx`: 客户端错误–请求有语法错误或请求无法实现
5.`5xx`: 服务器端错误–服务器未能实现合法的请求
```text
200 OK                        //客户端请求成功
400 Bad Request               //客户端请求有语法错误，不能被服务器所理解
401 Unauthorized              //请求未经授权，这个状态代码必须和WWW-Authenticate报头域一起使用 
403 Forbidden                 //服务器收到请求，但是拒绝提供服务
404 Not Found                 //请求资源不存在，eg：输入了错误的URL
500 Internal Server Error     //服务器发生不可预期的错误
503 Server Unavailable        //服务器当前不能处理客户端的请求，一段时间后可能恢复正常
```
###### HTTPS
`HTTPS`是安全的`HTTP`通道，即在HTTP通信中加入了`SSL`层（当前版本是`TLS1.2`），通信的数据被加密了，防止被窃取。
HTTPS使用的加密方式结合了对称加密和不对称加密的特点，在保证安全的情况下，又提高了传输效率。HTTP和HTTPS的区别如下：
1. https协议需要到ca申请证书，一般免费证书很少，需要交费。
    
2. http的信息是明文传输，https 则是具有安全性的ssl加密传输协议。
    
3. http和https用的端口不一样，前者是80，后者是443。
    
4. http的连接很简单，是无状态的；HTTPS协议是由SSL+HTTP协议构建的可进行加密传输、身份认证的网络协议，比http协议安全


#### 过程
`HTTP`协议采用请求/响应模式，客户端向服务器发送一个请求报文，然后服务器响应请求。
一次`HTTP`请求的过程：
1. 在浏览器中输入`URL`，并按下回车键
2. 浏览器向`DNS`服务器请求解析该`URL`中的域名对应的`IP`地址(如果是`IP`请求，则不需要该步骤)
3. 解析出`IP`后，根据`IP`和端口号，和服务器建立[TCP](https://www.jianshu.com/p/ef892323e68f)连接
4. 浏览器向服务器发送请求，该请求报文作为`TCP`三次握手的第三个报文发送给服务器
5. 服务器做出响应，把数据发送给浏览器
6. 通信完成，断开`TCP`连接
7. 浏览器解析收到的数据并显示



#### `curl_global_init()`
初始化` libcurl` 的**全局资源**（SSL库、WinSock等）,是 `libcurl `库的**全局初始化函数**，在使用任何其他` libcurl `功能之前必须调用。
```c
CURLcode curl_global_init(long flags);
```
`flags`是要指定初始化的全局功能，可以是以下值的**按位或**组合：
```c
// 初始化所有可能的模块（推荐默认值）
CURL_GLOBAL_ALL

// 安全相关的初始化（SSL、WinIDN）
CURL_GLOBAL_SSL          // 初始化 SSL 层
CURL_GLOBAL_WIN32        // 在 Windows 上初始化 Win32 套接字

// 备选便捷值
CURL_GLOBAL_DEFAULT      // = CURL_GLOBAL_ALL（最常用）
CURL_GLOBAL_NOTHING      // 不初始化任何东西（测试用途）
CURL_GLOBAL_ACK_EINTR    // 在 7.24.0 后已废弃
```
返回值：
- **`CURLE_OK` (0)**：初始化成功
- **`CURLE_OUT_OF_MEMORY` (27)**：内存不足
- **`CURLE_FAILED_INIT` (2)**：底层库初始化失败（如 OpenSSL）
- **其他错误码**：特定模块初始化失败
注意：
**程序生命周期内只调用一次**，通常在 main 函数开始处；
**必须与 `curl_global_cleanup` 配对使用**，防止资源泄漏；
**在多线程环境中需要同步保护**。
实践中需要检查其返回值，因为 SSL 库初始化失败会导致后续所有 HTTPS 请求失败。
这个函数体现了库设计的'初始化-使用-清理'经典模式。

#### `curl_easy_init()`
```c
CURL *curl_easy_init(void);
```
初始化一个CURL会话，创建句柄
**返回值**：成功返回CURL指针，失败返回NULL  
**注意**：每个传输都需要单独的句柄


#### `curl_easy_setopt()`

```c
CURLcode curl_easy_setopt(CURL *handle, CURLoption option, parameter);
```
设置CURL选项（最重要的函数）  
handle就是创建的CURL句柄，必须是有效的、未清理的句柄

**CURLoption常用选项**
指定要设置哪个选项，超过 250 个可选参数，是枚举类型
```c
CURLOPT_URL          // 设置请求URL
CURLOPT_POSTFIELDS   // 设置POST数据
CURLOPT_HTTPHEADER   // 设置HTTP头
CURLOPT_WRITEFUNCTION // 设置响应回调
CURLOPT_TIMEOUT      // 设置超时时间
```
`parameter`是选项的具体值，类型**根据 option 不同而变化**
**注意**：
- 选项类型必须与参数类型匹配
- 使用字符串作为参数注意生命周期，应该使用字面量替代栈上的字符数组
- 回调函数的命名必须准确
```c
size_t write_function(char *ptr, size_t size, size_t nmemb, void *userdata);
```
- 最好为每一个配置作单独检查
该函数的关键在于**参数类型根据选项动态变化**——比如 `CURLOPT_URL` 需要字符串，`CURLOPT_TIMEOUT` 需要长整型。使用时必须注意类型精确匹配、字符串生命周期管理，以及像 HTTP 头链表这类需要手动清理的资源。
`libcurl `设置 HTTP 方法的核心是：
GET 用默认设置
POST 用 `CURLOPT_POST`
其他方法用 `CURLOPT_CUSTOMREQUEST`
关键要配套设置 `CURLOPT_POSTFIELDS` 传递数据，用 `CURLOPT_HTTPHEADER` 设置正确的 Content-Type，特别是 JSON 数据需要 `application/json` 类型。


用于设置非标准的 HTTP 方法，但是会覆盖默认的方法检测
```c
// 设置自定义 HTTP 方法
curl_easy_setopt(curl, CURLOPT_CUSTOMREQUEST, "PUT");
curl_easy_setopt(curl, CURLOPT_CUSTOMREQUEST, "DELETE");
curl_easy_setopt(curl, CURLOPT_CUSTOMREQUEST, "PATCH");
```

设置HTTP头，注意**必须手动清理** `curl_slist_free_all(headers)`
```c
// 设置 HTTP 头部
struct curl_slist *headers = NULL;
headers = curl_slist_append(headers, "Content-Type: application/json");
headers = curl_slist_append(headers, "Authorization: Bearer token123");
curl_easy_setopt(curl, CURLOPT_HTTPHEADER, headers);
```

#### `curl_easy_perform()`

```c
CURLcode curl_easy_perform(CURL *handle);
```
执行传输操作（阻塞式）  
**返回值**：`CURLE_OK`表示成功，其他为错误码  
**注意**：会阻塞直到传输完成或超时

该函数会自动打印相关信息到终端里
```c
curl_easy_setopt(g_curl, CURLOPT_WRITEFUNCTION, NULL);  // 禁用默认输出处理
curl_easy_setopt(g_curl, CURLOPT_WRITEDATA, NULL);     // 不输出到stdout
```

#### `curl_easy_cleanup()`

```c
void curl_easy_cleanup(CURL *handle);
```

清理CURL会话，释放资源
**注意**：必须调用，否则内存泄漏

#### HTTP头部管理

##### `curl_slist_append()`

```c
struct curl_slist *curl_slist_append(struct curl_slist *list, const char *string);
```
向链表添加HTTP头部
```c
struct curl_slist *headers = NULL;
headers = curl_slist_append(headers, "Content-Type: application/json");
headers = curl_slist_append(headers, "User-Agent: MyMonitor/1.0");
```
**返回值**：新的链表头  
**注意**：必须保存返回值，因为可能重新分配


##### `curl_slist_free_all()`
```c
void curl_slist_free_all(struct curl_slist *list);
```
**功能**：释放整个HTTP头部链表  
**注意**：必须调用，否则内存泄漏


##### `curl_easy_strerror()`
```c
const char *curl_easy_strerror(CURLcode errornum);
```
将错误码转换为可读字符串
```c
CURLcode res = curl_easy_perform(curl);
if(res != CURLE_OK) {
    fprintf(stderr, "curl_easy_perform() failed: %s\n",
            curl_easy_strerror(res));
}
```



#### 注意
**`libcurl` 在底层封装了 Socket 编程的所有细节**。它内部创建了 Socket、处理了 TCP 三次握手、管理连接池，向开发者暴露了简单的 `setopt_perform` 接口。
创建` Socket、TCP` 三次握手、数据收发都在 `curl_easy_perform()` 内部完成。
`libcurl` 自动处理 `SYN → SYN-ACK → ACK` 流程，可以通过选项控制超时、重试等行为
