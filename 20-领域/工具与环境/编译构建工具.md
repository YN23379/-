## 一、编译器核心

- **GCC**：最传统的 C/C++ 编译器套件（`gcc`、`g++`、`gfortran`），跨平台、优化成熟。
    
- **Clang/LLVM**：现代化替代，模块化、错误提示友好、编译更快，是 iOS/Android 主流。
    
- **其他**：`rustc` (Rust)、`go build` (Go)、方舟编译器（OpenHarmony 应用层）。
    

> **作用**：把源码翻译成目标文件；性能与兼容性取决于编译器优化和架构支持。

### GCC 编译四阶段（必背）

一条 `gcc hello.c -o hello` 背后其实是**四步**，每一步都能单独停：

| 阶段 | 做什么 | 产物 | 命令 |
|---|---|---|---|
| 预处理 | **宏替换、条件编译、头文件展开、去注释** | `.i` | `gcc -E hello.c -o hello.i` |
| 编译 | 检查语法合法性，**翻译成汇编** | `.s` | `gcc -S hello.i -o hello.s` |
| 汇编 | 汇编转二进制目标代码 | `.o` | `gcc -c hello.s -o hello.o` |
| 链接 | 多个 `.o` + 库 → 可执行文件 | 可执行 | `gcc hello.o -o hello` |

> **为什么中间非要过一道汇编？** ①汇编是机器码的可读形式，便于检查与调试；
> ②编译器在此做寄存器分配、指令重排等优化；③汇编与架构相关，改这一层就能适配多平台。

### 静态库与动态库（面试必问）

`printf` 的实现在哪？——在库里。你 `#include <stdio.h>` 只拿到**声明**，真正的实现在 `libc` 里，
链接器负责把它接上。这分两种接法：

| | 静态库 | 动态库 |
|---|---|---|
| 后缀 | `.a`（Linux）/ `.lib`（Windows） | `.so`（Linux）/ `.dll`（Windows） |
| 链接时机 | **编译链接时**把库代码拷进可执行文件 | **运行时**由加载器载入库 |
| 体积 | 大（每个程序都带一份副本） | 小（多程序共享一份） |
| 运行依赖 | 无，单文件可直接跑 | **缺 .so 就跑不起来** |
| 更新库 | 要**重新编译所有相关程序** | 换 .so 即可，不用重编 |
| 速度 | 略快（不用运行时解析） | 略慢（有动态解析开销） |

```bash
# 生成静态链接（体积大、独立）
gcc -static hello.o -o hello

# 默认就是动态链接（体积小、依赖 .so）
gcc hello.o -o hello

# 查看可执行文件依赖哪些动态库
ldd hello
#   libc.so.6 => /lib64/libc.so.6 (0x00007ff7...)
```

**记忆锚点**：静态 = "把库抄进自己家"（肥但独立）；动态 = "全楼共用一间库房"（瘦但依赖）。

**嵌入式的取舍**：交叉编译 toolchain 默认动态链接 glibc，但烧到板子上若 rootfs 里没有对应 .so
就起不来——所以做**最小 rootfs** 时常用 `gcc -static`，或者用 musl/uClibc 这类轻量 libc。

### GCC 常用选项速查

| 类别 | 选项 | 含义 |
|---|---|---|
| 控制 stage | `-E` `-S` `-c` | 只预处理 / 只编译 / 只汇编 |
| 输出 | `-o 名字` | 指定输出文件名 |
| 链接 | `-static` `-shared` | 静态链接 / 生成 .so |
| 优化 | `-O0` `-O1` `-O2` `-O3` | 从不优化到最高优化（`-O0` 默认，调试用） |
| 调试 | `-g` | 生成调试信息，供 gdb 用 |
| 警告 | `-Wall` `-w` | 全部警告 / 关闭警告（开发建议开 -Wall） |

> 条件编译（`#ifdef`/`#ifndef`）最典型两个用法：**多平台兼容**（按 `_WIN32`/`__linux__` 选代码）
> 和**调试/发布分离**（`#define DEBUG` 时才编进日志）。详细展开见

## 二、构建系统演化

- **Make**：最早的依赖构建工具，基于时间戳判断更新；语法晦涩但轻量。
    
- **CMake**：生成 Makefile 的“构建生成器”，跨平台，C++ 项目主流。
    
- **GN + Ninja**：现代高效组合。
    
    - **GN**：元构建系统，解析 `BUILD.gn` 生成 Ninja 文件。
        
    - **Ninja**：极快的执行器，支持并行与增量编译。
        
    - 应用：Chromium、OpenHarmony 等大型项目。

### GN与Ninja
**Ninja**是指一种高效的构建工具，用于调用各种工具（如编译器、链接器等）来编译大型项目。**它与传统的构建工具如cmake或make不同**，ninja在设计时就注重避免模糊和不确定性，通过元构建系统（如cmake）生成的具体编译命令来执行。ninja具有并行编译和增量编译两大特点，前者允许没有依赖关系的命令并行执行，后者根据文件的时间戳变化来决定哪些命令需要重新执行，从而提高构建效率。ninja的安装简单，支持系统级、用户级和自定义安装，广泛应用于大型项目如PyTorch的构建过程中。此外，ninja与GN构建工具结合，形成了一个强大的构建系统，广泛应用于如Chromium等开源项目中。
**GN**是指Google的构建系统GN，它是一个元构建工具，用于生成Ninja构建系统所需的配置文件。具体来说，GN的主要功能包括：

- **生成配置文件**：根据构建配置文件（如.gn和BUILD.gn）生成Ninja可以使用的构建配置文件（build.ninja）。
- **定义构建规则**：在构建配置文件中，开发者可以定义各种构建规则，如编译目标、依赖关系、编译选项等。
- **支持模块化构建**：GN允许将构建过程拆分为多个模块，每个模块可以独立配置，便于管理复杂的构建流程。
- **增强内建模块**：在OpenHarmony中，GN对内建模块进行了功能增强，使其更适合于OpenHarmony的编译需求。
- **扩展业务模块**：GN也支持对业务模块进行功能扩展，以满足特定应用或系统的构建需求。
- **部件化抽象**：GN将构建过程抽象为部件级别，使得产品可以以最小粒度进行拼装和独立编译。
- **解决方案级版本构建**：支持轻量、小型、标准三种系统的解决方案级版本构建，适应不同场景的构建需求。
- **SDK开发套件构建**：用于支撑应用开发者使用IDE进行开发，提供SDK开发套件的构建支持。

## 三、OpenHarmony 生态构建链

- **hb（OHOS Build）**：OpenHarmony 封装构建入口。
    
    - 命令：`hb set` 选择产品 → `hb build` 执行编译。
        
    - 流程：**hb → GN → Ninja → Clang/GCC**。
        
    - 作用：屏蔽底层复杂度，实现“一键构建”。
        
- **BUILD.gn** 定义模块与依赖，统一管理目标、源码、库。

## 四、IDE 与命令行对比

|方式|优点|缺点|
|---|---|---|
|命令行|灵活、可脚本化|学习曲线高|
|IDE（DevEco、VS Code、CLion）|集成编译、烧录、调试，开箱即用|占资源|

> **DevEco Device Tool** = 集成 hb + 交叉编译链 + 调试器 (GDB/J-Link)，是 Hi3861 开发主力。
