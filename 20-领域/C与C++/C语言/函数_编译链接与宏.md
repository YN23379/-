## 函数调用
当函数A调用函数B时，系统会为B创建一个新的**栈帧**并压入栈顶。这个栈帧里包含了B的局部变量、参数以及**返回地址**。虽然B的栈帧是独立的，但它们都在同一个调用栈上，地址空间是连续的。A的局部变量存储在A的栈帧里。因为栈指针的移动，B**不能直接通过变量名**访问A的变量。但如果A将某个变量的**地址**（指针）传递给B，B就可以通过这个指针来间接访问和修改A栈帧里的那个变量。这就是‘访问’的本质。

大多数CPU上的程序实现使用栈来支持函数调用操作，栈被用来传递函数参数、存储
返回信息、临时保存寄存器原有的值以备恢复以及用来存储局部变量。
函数调用操作所使用的栈部分叫做栈帧结构，每个函数调用都有属于自己的栈帧结
构，栈帧结构由两个指针指定，帧指针（指向起始），栈指针（指向栈顶），函数对
大多数数据的访问都是基于帧指针

栈指针和帧指针一般都有专门的寄存器，通常使用ebp寄存器作为帧指针，使用esp
寄存器做栈指针。
帧指针指向栈帧结构的头，存放着上一个栈帧的头部地址，栈指针指向栈顶。

### 重定义
**指在同一个程序（例如链接多个源文件时）中，同一个变量或函数名被多次提供实现或初始化，导致链接器报错。**
原因主要有：
一.将普通全局变量或函数的定义直接写在了头文件里，这个头文件被多个源文件包含后，每个源文件都生成了一份自己的定义，链接时就冲突了
二.是在不同的源文件中，各自定义了两个完全相同的全局变量或函数。

解决：在头文件中使用 `extern` 关键字进行变量和函数的声明，而将它们的唯一定义放在一个源文件中。
对于需要在头文件中实现的小型函数，则必须使用 `inline` 关键字来修饰，这样才能安全地在多个编译单元中使用而不会引发重定义错误。

## 宏定义
在 C 语言中，可以采用命令` #define `来定义宏,该命令允许把一个名称指定成任何所需的文本,在定义了宏之后，无论宏名称出现在源代码的何处，预处理器都会把它用定义时指定的文本替换掉。

宏定义是什么，有几点：带不带参数，注意副作用参数和多语句，还有条件编译，特殊符号和预定义宏，取消宏定义，宏的优缺点


`#define `宏名称 替换文本

用于替代程序中重复出现的常量，提升可读性和维护性

宏可以接受参数并生成表达式，但需注意运算符优先级问题：

### 特殊符号
#### **​`#`​** ​ **运算符（字符串化运算符）**  
将宏参数转换为字符串：
`# `的操作数必须是宏替换文本中的形参。将宏定义的传入参数转换成用一对双引号括起来的参数名的字符串，只能用于有传入参数的宏定义，而且必须放在宏定义体的参数前面。
```text

printf("%s", STR(Hello));  // 输出 "Hello"

适用于调试时打印变量名。
```
#### **`##`​** ​ **运算符（连接符）**  
拼接标识符生成新变量或函数名，即将宏定义的多个形参转换成一个实际参数名
运算符##连接两个记号，它必须有两个操作数
通常,使用 ## 运算符时，至少有一个操作数是宏的形参。在这种情况下，实参值会先替换形参，然后等记号粘贴完成后，才进行宏展开。
```text

int VAR_NAME(1) = 10;  // 展开为 int var_1 = 10;
常用于代码模板化生成。 
没有 `##` 时，`var_n` 中的 `n` 不会被参数替换，它就是一个字面文本
```

### 宏展开
#### 字符串与宏
宏展开只发生在代码的“结构”部分，而被双引号包裹起来的字符串内容，预处理器会将其视为一个不可分割的、纯粹的文本块，不会去检查里面是否有宏。
用于保证字符串内容的稳定性和可预测性。
```

printf("NAME says HELLO");//最终不会展开HELLO
```

如果想在字符串里使用宏的值，可以**将宏放在字符串外，利用字符串自动连接的特性进行连接**，或者是**使用参数化宏**：
`#define GREET(name) printf("Hello, " #name "\n")` 通过

#### 阶段处理
无法通过宏展开的方式创建预处理器命令
在替换实参，以及执行完 # 和 ## 运算之后，预处理器会检查操作所得的替换文本，并展开其中包含的所有宏。
预处理器的工作是分阶段的。**首先**会寻找所有以 `#` 开头的预处理指令（如 `#define`, `#ifdef` 等），并执行它们。在所有这些指令都处理完后，它才会进行宏展开。
这也说明宏不可以递归地展开：如果预处理器在 A 宏的替换文本中又遇到了 A 宏的名称，或者从嵌套在 A 宏内的 B 宏内又遇到了 A 宏的名称，那么 A 宏的名称就会无法展开。

```
#define DEFINE_INT int x = 5;
#define INCLUDE_STDIO #include <stdio.h>

DEFINE_INT
INCLUDE_STDIO

展开结果
int x = 5;
#include <stdio.h>//这一行虽然成功替换但是已经错过了预处理指令阶段
这一行虽然以 `#` 开头，但是是不合法的代码，会导致编译错误。
```




### 注意

#### 副作用参数问题
宏参数可能被多次求值，导致意外结果
带多条语句的（必须用 do { ... } while(0) 包裹！）
```c
#define MAX(a, b) ((a) > (b) ? (a) : (b))
int x = 5, y = 10;
int z = MAX(x++, y++);  // 展开后 x 和 y 被递增两次
 
输出结果：`x=6, y=12, z=10`（而非预期的 11）。

#define SWAP_INT(a, b) do { \
    int temp = (a); \
    (a) = (b); \
    (b) = temp; \
} while(0)
```
**不要在宏的参数中使用有副作用的表达式（比如函数调用）**，因为宏是简单的文本替换，会导致重复计算。

如计算二叉树的深度，用fmax就可以，但如果是下面就不行，会超时
```c
#define MAX(a,b) ((a>b)?(a):(b)) 
int maxDepth(struct TreeNode* root) 
{
	 if(!root) return 0; 
	return MAX(maxDepth(root->left),maxDepth(root->right))+1; 
}
```

​`#define`​ 是文本替换，`typedef`​ 是类型别名
```text
#define INT_PTR int*     // 可能导致错误：INT_PTR a, b;（a是指针，b是int）
typedef int* IntPtr;     // 正确：IntPtr a, b;（均为指针）

建议复杂类型使用 `typedef`。
```

### `#ifdef` 和 `#if defined()`
`#ifdef MACRO` 是 `#if defined(MACRO)` 的简写形式，两者功能相同。但 `#if defined()` 可以处理更复杂的条件判断

宏是由**预处理器**处理的，发生在编译之前。它进行的是简单的**文本替换**。
#### 无类型检查
宏参数没有类型概念。预处理器只是机械地将文本替换过去。这很容易导致类型不匹配的错误，而这些错误只有在编译阶段甚至运行时才会暴露。

#### **多次参数求值**
如果参数是一个带有副作用的表达式（如 `x++`），它会被替换多次，导致意想不到的结果。

#### **运算符优先级问题**
即使给参数加了括号，如果外部表达式的优先级不高，仍然可能出错。
需要给**每个参数和整个表达式加括号**，

#### 无法调试，没有作用域
宏在编译前就已经被替换掉了。在调试器中无法跟踪到宏的“内部”，因为它根本不存在于编译后的代码中，只能看到替换后的复杂表达式。
宏是全局的，从定义点开始到文件末尾（或 `#undef`）都有效。它不遵守C/C++的作用域规则（如命名空间、类、函数作用域），容易造成命名污染和冲突。

优点：
- **泛型性**：正因为没有类型检查，一个宏可以用于任何类型，只要该类型支持宏体内的操作（如比较大小）。
    
- **生成代码**：宏可以做一些函数做不到的事情，比如用 `#`（字符串化）和 `##`（连接）运算符在预处理期生成代码。
    
- **编译期常量**：用宏定义常量（如 `#define PI 3.14159`）在旧的C代码中很常见。
### `#ifndef`
优点：
1. **防止重复包含**：同一个头文件被多次`#include`时只生效一次
    
2. **避免重复定义**：防止结构体、函数声明等被重复定义
    
3. **提高编译速度**：避免重复编译相同内容
注意结束加上`#endif`


### 作用：

**定义常量和简化重复代码**。用 `#define` 进行简单的文本替换，代替常用到的一些常数，封装常用代码片段，在预处理阶段直接进行文本替换，减少硬编码和代码重复。


**条件编译，让同一份代码能适应不同环境**。通过`#ifdef`、`#if defined()`等条件编译指令，我们可以在编译阶段根据预定义宏来包含或排除特定代码段。：
**平台移植**，根据编译器预定义的宏（如 `__linux__`, `_WIN32`）编译特定平台的代码。
**调试管理**，通过自定义宏（如 `DEBUG`）控制调试日志、断言等代码在发布（Release）版本中的存在与否。
**防止头文件被重复包含**，通过 `#ifndef` - `#define` - `#endif` 组合，确保同一个头文件只被包含一次，这是因为宏文本替换的一个特性，也就是第一次包含时定义宏，后续包含遇到已定义的宏就直接跳过

**高级应用**。通过宏的字符串化和连接操作符，实现编译期反射、自动化代码生成等高级特性，比如Linux内核中的`container_of`宏就是通过地址计算实现从成员指针获取容器结构的经典案例。

**本质上，宏是预处理器在编译前进行的文本替换工具，它让我们能够在编译阶段根据不同条件塑造最终的源代码，实现跨平台兼容、调试控制、性能优化等多种目标。**


## 内联函数 (Inline Functions)
内联函数是由**编译器**处理的，它是真正的函数，只是编译器收到“内联”的建议后，会尝试将函数调用展开为函数体本身的代码，从而避免函数调用的开销（压栈、跳转、返回等）。

使用原因：
**使用内联函数首要目的是为了更安全地替代宏定义**。因为宏是简单的文本替换，没有类型检查，而且参数如果是表达式可能会被多次计算导致难以发现的错误。内联函数则具备完整的函数特性，编译器会进行类型安全检查，参数也只计算一次，从根本上避免了宏的这些缺陷。

**另一个核心目的是为了提升程序运行效率**。对于代码量小且频繁调用的函数，它调用的压栈、跳转、返回等开销会累积成显著的性能损失。而内联函数通过将函数体代码直接展开到调用处，消除了这部分开销，以空间换时间。


联函数的定义与普通函数基本相同,只是在函数定义前加上关键字 inline。
### 实现
C语言通过 **结构体 + 函数指针** 来模拟类的封装，而内联则通过 **`static inline` 修饰函数** 来实现。

用结构体模拟类，将数据封装起来，然后将对结构体操作的、代码量小而且频繁调用的函数，用 **`static inline`** 在头文件中实现。但这只是给编译器的优化建议，最终是否内联由编译器决定。

而**C++在类里定义的所有函数都会自动称为内联函数（隐式内联）**

内联函数本身也是一个真正的函数，具有普通函数的所有行为，唯一不同之处在于内联函数会在适当地方像预定义宏一样展开，在程序运行时不再进行函数调用和返回，从而消除函数调用和返回的系统开销,提高了程序执行效率。
### 注意
**内联函数的展开最终由编译器决定，`inline`关键字只是一个建议，甚至在类里定义的函数无需该关键字也可能被隐式内联。**
`inline` 关键字更像是一个给编译器的**建议**，而非命令。编译器会根据函数的复杂程度、调用频率等因素进行综合判断，最终**决定权在编译器手中**。因此，即使函数被声明为 `inline`，也不保证一定会被展开。
此外也存在**隐式内联**的情况。在 C++ 中，可以**直接在类内部定义的成员函数**，即使没有 `inline` 关键字，也通常会被编译器视为内联函数。

虽然无法强制要求编译器展开内联函数，但可以通过一些方法**强烈建议**它这么做。最关键的是**开启编译器优化选项**，比如GCC使用 `-O2` 或 `-O3`，因为在最低优化级别下编译器通常不会处理内联。
然后可以使用编译器的**扩展属性**来增加建议的权重，
如GCC的 `__attribute__((always_inline))`。
但是编译器仍会基于自身的启发式算法做决定，通常会**拒绝内联过于复杂的函数**，比如包含循环或递归的函数。



内联展开是在编译时进行的，只有链接的时候源文件之间才有关系。所以内联要想跨源文件必须把实现写在头文件里。如果一个内联函数会在多个源文件中被用到，那么必须把它定义在头文件中
内联函数的定义不一定要跟声明放在一个头文件里面：定义可以放在一个单独的头文件中，里面需要给函数定义前加上inline 关键字



### 强弱符号
在C语言中，编译器默认函数和初始化的全局变量为**强符号**（Strong Symbol），未初始化的全局变量为**弱符号**（Weak Symbol）。强符号之所以强，是因为它们拥有确切的数据，变量有值，函数有函数体；弱符号之所以弱，是因为它们还未被初始化，没有确切的数据。

内联函数能放在头文件而不报重定义错误，是因为编译器将其处理为**弱符号**。
普通函数是强符号，重复定义会导致链接错误。而所有目标文件中的同名内联函数都是弱符号，链接器按规则（如选择最先遇到或最大的）合并为一个，因此允许存在多个定义。

但这有风险。如果某处定义了同名强符号函数（即使实现不同），链接时会优先选择强符号，可能导致内联函数被意外替换，引发逻辑错误，尤其在未开启编译器优化时。
### 与宏定义区别

| 方面       | **内联函数 (Inline Function)** | **宏定义 (Macro)**      |
| -------- | -------------------------- | -------------------- |
| **处理阶段** | **编译器**                    | **预处理器**             |
| **本质**   | 有类型的**函数**                 | 纯粹的**文本替换**          |
| **类型安全** | ✅**有严格类型检查**，更安全           | ❌ **无类型检查**，容易出错     |
| **参数求值** | 参数**只计算一次**                | 参数可能**被多次求值**，导致副作用  |
| **调试**   | ✅ **支持调试**（尽管可能因内联而复杂）     | ❌ **难以调试**，只看到替换后的代码 |
| **作用域**  | 遵守C语言的**作用域规则**            | **全局替换**，不受作用域约束     |
### 应用

**应当使用内联的场景：**

- 函数代码亮很小（通常1-5行）。
    
- 函数被频繁调用，性能至关重要。
    
- 想要定义一个函数式的功能，但又想避免宏的安全风险。

**不应使用内联的场景：**
- 函数体内包含循环或复杂的条件判断。
    
- 函数体代码较长。
    
- 函数是递归函数或虚函数（绝大多数情况下编译器会忽略其内联建议）。
#### 内联与static
- **`inline` 函数默认是外部链接**。这意味着整个程序中只有一个相同的定义。为了保证这一点，**必须将内联函数的定义放在头文件中**，这样所有包含该头文件的源文件看到的都是同一个定义，链接器会正确处理，不会报重定义错误。
    
- **`static` 函数是内部链接**。每个源文件中的同名`static`函数都是独立的实体，互不干扰。这会导致代码冗余。
- 
在 C 语言中，处理头文件内的内联函数时，最稳妥和常见的做法是使用 `static inline`。
虽然单纯的 `inline` 函数在理论上是外部链接的，是为了让整个程序共享一个定义，但容易引发链接错误，需要额外的技巧来保证"一个定义规则"。
所以为了**编译安全性和简化开发**，通常使用的是 `static inline`。它确保每个编译单元拥有自己的副本，避免了链接问题，并且编译器能更好地进行内联优化。
这在 Linux 内核和大量嵌入式代码中是非常普遍和推荐的模式

### 缺陷

1. **代码膨胀**：每一处内联调用都会复制一份函数体代码。如果函数体很大或调用极其频繁，会显著增加最终程序的大小，可能反而因缓存命中率下降而降低效率。
    
2. **编译器决策权**：`inline` 关键字仅是**建议**，编译器有权拒绝。通常，包含循环、递归或过于复杂的函数不会被内联。
    
3. **对构造/析构函数的误解**：看似简单的构造函数和析构函数，实际上可能“悄无声息”地调用了基类或成员对象的构造/析构函数，导致其真实代码量很大，不适合内联。

## 宏与内联总结
**宏**和**内联函数**是平衡**性能**与**安全性**的关键工具。
1. **宏**在预处理阶段进行文本替换。优点是**没有函数调用的开销**、能实现**泛型编程**和**条件编译**。但缺点是**缺乏类型检查**、**调试困难**，使用时必须注意**参数括号**，**多语句封装**和副参数作用的问题。
    
2. **内联函数**在编译阶段处理，它提供了类似宏的性能，同时具备**完整的类型检查和作用域**，更安全、易于调试。
    
3. **选择策略是**：对于简单的、类型无关的或需要预处理器特性（如字符串化）的操作，用宏；对于需要类型安全、逻辑稍复杂的操作，优先使用内联函数。但在寄存器操作、调试断言、跨平台代码中，宏是不可替代的。”


内联函数用 `inline` 关键字声明，它的主要作用是**消除函数调用的开销**。编译器会尝试将函数调用直接替换为函数体的代码，类似于宏展开，但它是类型安全的。

区别：
内联函数有完整的类型检查，宏只是文本替换。
内联函数参数只求值一次，而宏的参数可能导致多次求值，产生副作用。
内联函数可以调试，宏在预处理后就不存在了。
内联函数本质是函数，可以取地址；宏不行。
static与内联
- 单纯的 `inline` 是外部链接，需要保证全项目只有一个定义，否则可能链接错误，管理起来更复杂。
- 而 `static inline` 是内部链接，每个 `.c` 文件包含头文件后都会得到一份自己的副本，绝对不会有链接问题。这是 Linux 内核和很多大型项目的首选方式，虽然可能有点代码冗余，但换来了编译的确定性和简便性。

注意：
内联只对小型且频繁调用的函数使用。对大函数内联会急剧膨胀代码尺寸，反而可能降低性能。
而且递归函数无法内联。
如果通过函数指针调用内联函数，或者函数太大，编译器可能会忽略 `inline` 建议，把它当作普通函数编译。


## 断言
**断言**是一种在代码中插入的检查点，用于在**开发阶段**捕获“绝对不应该发生”的情况。
```c
#include <assert.h>

void divide(int a, int b) {
    assert(b != 0);  // 我断言除数b不为0
    int result = a / b;
    // ... 其他代码
}
```

### 模式

### 调试模式
```c
在Debug构建中，assert是激活的
#define NDEBUG  // 如果定义了这个，assert就会被禁用
#include <assert.h>

// 如果没有定义NDEBUG，assert正常工作
assert(pointer != NULL); // 如果pointer为NULL，程序中止
```
### 发布模式

```c
在Release构建中，通常通过定义NDEBUG来禁用assert
#define NDEBUG  // 禁用所有assert
#include <assert.h>

assert(pointer != NULL); // 这行代码在编译时会被移除，没有任何效果
```

### 断言和错误处理
**用断言检查不可能的事，用错误处理处理可能的事**。

|特性|断言|错误处理|
|---|---|---|
|**目标**|捕获程序员错误（bug）|处理预期的运行时错误|
|**使用场景**|“这绝对不该发生”的情况|“这可能会发生”的情况|
|**例子**|空指针、数组越界、逻辑错误|文件不存在、网络断开、用户输入错误|
|**处理方式**|立即终止程序|返回错误码、抛出异常、恢复操作|
|**发布版本**|通常被禁用|必须保留|

## c行为

### UB
**UB = Undefined Behavior（未定义行为）**
C/C++标准**没有定义**这种情况下程序应该做什么，最终结果取决于编译器，编译器可以做任何事情，包括崩溃、输出错误结果、甚至看似“正常”运行。

常见的UB有：
内存相关：数组越界，解引用空指针
类型相关：类型双关（type punning）
运算相关：溢出，除以0
序列点相关：
多线程未同步，函数返回局部变量指针

```c
int i = 5;
i = i++ + ++i;
printf("%d", i);
```
这是UB，同一表达式内对i多次修改无序列点。实际输出依赖编译器，应该避免这种写法。

类型双关
通过不同类型的指针**重新解释同一块内存**，不同于类型转换（创建新值）。
因为**严格别名规则**——只能通过对象的声明类型或兼容类型访问内存。
正确做法是用`union`或`memcpy`,也有例外，联合体和`char *`就允许类型双关。
```c
int a = 10;
float* fp = (float*)&a;  // 说"把这块内存当作float来看"
printf("%f", *fp);       // UB！用float类型读取int的内存位模式
// 没有创建新值，只是重新解释同一块内存
```

### 序列点
序列点（Sequence Point）是程序中所有副作用（如修改变量）必须完成的时间点。
`printf` 的参数计算顺序没有序列点分隔。

```c
int a = 10;
printf("%d %d", a++, ++a);//未定义行为
```
使用上述代码在不同编译器，或者同一编译器的不同优化级别下都可能会有不同的输出结果
改正
```c
int a = 10;
int b = a++;  // 序列点：分号
int c = ++a;  // 序列点：分号
printf("%d %d", b, c);  // 输出：10 12
或者
int a = 10;
printf("%d ", a++);  // 序列点：函数调用后
printf("%d", ++a);   // 输出：10 12
```

因为 **C标准规定：在两个序列点之间对同一个变量进行多次修改是未定义行为（UB）**


两个参数 `a++` 和 `++a`：都修改 `a`，都读取 `a` 的值且他们之间没有序列点

C标准说（C11 6.5§2）：
> 如果标量对象上的副作用相对于同一标量对象上的不同副作用或使用同一标量对象的值进行的值计算是无序的，则行为未定义。
   也就是**不能又读又写同一个变量，且顺序不确定**。
