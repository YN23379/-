# 基于 OpenHarmony 的智慧安防报警系统（IoT 边缘应用）
老师要求：
智能安防报警系统主要实现遭遇窃贼时报警的功能。当家中发生非正常紧急情况（有人接近）时，通过一系列传感器的感应，及时将测量数据反馈给设备端，判断事故后立即进行声光报警。

具体任务分设备端和小程序端

1.设备端，功能包括：
①NFC配网功能；
②利用红外传感器检测是否有人闯入，有人并超时则判断为异常；
③发布和订阅 MQTT 的消息；
④保存红外传感器的阈值信息到 Hi3861 模块中的 Flash 存储中；
⑤屏幕显示传感器及控制等关键信息。

2.开发微信小程序，功能包括：①将配网信息数据写入 NFC 标签中；②手动控制蜂鸣器的开关；③设置红外传感器的阈值范围；④开启自动控制功能；⑤显示当前红外传感器的数据和蜂鸣器当前的状态。

3.其他自由发挥内容。

解决了内存泄漏问题，
**`cJSON_PrintUnformatted(json_root)`**： 这一行，cJSON库在**堆内存上动态分配**了一块空间，并将格式化后的JSON字符串的指针`payload`返回
使用下面的free
```
 char *payload = cJSON_PrintUnformatted(json_root);
    if (payload != NULL) {

        cJSON_free(payload); // 或者使用 free(payload); 取决于cJSON的配置
    }
    cJSON_Delete(json_root);
```

项目本质上是一个**物联网边缘设备控制系统（智能安防报警系统）**。它运行在嵌入式 Linux / OpenHarmony 平台上，完成了从传感器数据采集 → 状态判定 → MQTT 通信 → 云端同步 → 显示与报警 的完整闭环。

**NFC（NDEF）→ Wi-Fi（Hi3861 内置 2.4 GHz）→ MQTT（Paho/lwIP）→ 云/小程序**；
**AP3216C@I²C 采样 → 状态机判定 → AW2013@I²C 控灯、蜂鸣器 GPIO → SSD1306@I²C 显示**。  
**开发**：DevEco（集成 hb/GN+Ninja）+ riscv32 交叉链；**OS**：OpenHarmony LiteOS-M。

#### AP3216C
是一颗三合一（环境光/红外/接近） I²C 数字传感器，提供 ALS（环境光）、IR、Proximity，走 I²C，寄存器配置简单，适合做人靠近检测。[知乎专栏](https://zhuanlan.zhihu.com/p/677091825?utm_source=chatgpt.com)
只用接近通道（PS），阈值（`ps_threshold`）+ 超时（`timeout_threshold`）配合状态机判断“有人且持续超时 → 报警”。
    
- 注意点：
    
    - 上电初始化顺序：复位→开通道→设增益/积分时间（影响噪声与延迟）。
        
    - 采样频率与去抖：PS 读值抖动，用移动平均或时间窗确认“连续 N 次超阈”再触发。
        
    - 在强光/反射面前如何避免误报？——PS 饱和时做软钳位+短时降低积分时间；再辅以阈值自适应或环境校准。


#### AW2013
RGB LED 恒流**驱动**
是AWINIC 出的 3 通道 RGB LED 驱动，I²C 配置，带电流与 PWM 控制，常用于状态灯/告警灯。[51CTO](https://ost.51cto.com/posts/7898?utm_source=chatgpt.com)
红灯通道显示三种状态：**常亮**（手动）、**闪烁**（自动告警）、**熄灭**（正常）。

- 注意点：
    
    - 典型步骤：`enable → set current → set PWM/呼吸`，先开稳流再设占空比。
        
    - 冲突仲裁：人为常亮优先级最高，其次是自动闪烁；避免“手动长鸣时误闪”的状态竞争（我们后来做了清晰的优先级+去抖）。
        
    - 为什么”按一次长鸣“灯会闪一下？——状态边沿导致分支条件瞬时满足，需加**状态去抖/延迟仲裁**。
        

#### SSD1306
0.96" 128×64 OLED 控制器
Solomon Systech 的常见 OLED 控制器，I²C/SPI 皆可，页寻址显示。[百度开发者中心](https://developer.baidu.com/article/details/3275590?utm_source=chatgpt.com)
显示**是否有人、是否报警、PS 实时值/阈值**与模式。
    
- 注意点：
    
    - 显示缓存（framebuffer）→ 分页刷屏，注意**缓冲清零**和**越界写**会导致“半行残影/错色”。
        
    - `printf`/`sprintf` 的类型匹配（比如 `difftime` 是 double，别用 `%d`）和长度控制，避免随机字符。
        
    - 为何会出现“上一帧字符残留”？——没清缓冲或写入长度小于上次，需覆盖/清空对应区域。
        

#### NFC 模块
用于「NFC 配网 / NDEF」
- **是板载一颗 I²C 接口的 NFC 动态标签/读写器**（课程板通常集成 NDEF 支持），用手机写入 Wi-Fi SSID/密码；设备上电读取 NDEF 完成配网。华清的板卡说明明确“带 NFC RFID 通信芯片”。[HarmonyOS 设备开发官网](https://device.harmonyos.com/cn/develop/ide?utm_source=chatgpt.com)
- 
**联网路径**：NFC 取 SSID/密码 → Wi-Fi 上网 → MQTT（Paho）建连 → 订阅/发布；
- 注意点：
    
    - **数据留存**：这类 NFC 动态标签自带非易失存储，掉电不丢；实际配网流程是**手机→NFC 标签（NDEF）→ 板端 I²C 读取 → Wi-Fi 连接**。
        
    - 生产注意：NDEF 分区、容量限制、写保护/密码、防止把敏感信息回传到云端日志。
        
    - 手机贴一下就能连网的关键是什么？——答：**NDEF 数据模型**与设备侧对 NDEF 解析+Wi-Fi 驱动的衔接。

1. **定义模块 ([BUILD.gn](https://build.gn/))**：在`BUILD.gn`中声明源码、编译选项及**依赖的其他模块**，这是构建系统工作的输入和依据。

## 问题
"1.5行显示"和"颜色分割"说明：

- 数据写入了**显示缓冲区的相邻内存**
    
- 上半部黄色：写到了第一行缓冲区末尾
    
- 下半部蓝色：写到了第二行缓冲区开头
  
直接把difftime(current, last) 作为参数传到sprintf的格式化输出里，格式都是对的，对应的是%2d,但是显示的是-21？
`difftime()` 函数返回的是 **`double` 类型**（表示秒数，可能带小数），但你用 `%2d` 来格式化，`%d` 是用于 `int` 类型的。

**类型不匹配导致内存解释错误，所以显示奇怪的负数。**


现在的问题是刚开始显示的还是负数，一行最多显示16个字符，而且显示的两位数后面那一位和刚开始的负数都是随机的，只有左边那位数是差不多正常的，就是-7 0 1 2 3 4 5，最大就是5后面那一位是从那个负数显示到最后就不会变

**缓冲区没有初始化/清零**导致的显示残留。
1. `difftime(current_time, 0)` 计算的是从1970年到现在的时间差，结果是巨大的正数
    
2. **强制转换为 `int`**：巨大的 `double` 转 `int` 发生溢出，变成负数

### 追问回答

- **Q1：为什么做线程池？**  
    A：多条永循环线程各自 `sleep` 的节拍漂移难控，栈占用也高。线程池用一个工作线程按“间隔时间”调度 MQTT 发送/接收/心跳，**统一时基 + 省内存**，也便于后续加任务（如重连退避）。
    
- **Q2：你怎么定位并修复 MQTT 上报崩溃？**  
    A：长跑后崩溃、堆增长 → 检查每个上报路径，发现 `cJSON_PrintUnformatted` 返回堆内存未 `cJSON_free`。补齐释放后复测稳定，并在异常路径加保护与日志。
    
- **Q3：状态机比 if-else 好在哪？**  
    A：把“检测/计时/报警”抽成 **状态与转换**，更清晰也更易加“去抖/最小驻留时间”。灯与警铃冲突用“**优先级表**”（手动常亮＞自动闪烁＞仅长鸣灭灯）解决。
    
- **Q4：NV 持久化怎么做的？**  
    A：定义含 `ps_threshold/timeout_threshold` 的 NV 结构体，启动时 `read→校验→回填运行变量`；命令设置后 `write` 写回。这样参数掉电不丢，链路“云命令→本地生效→落盘”闭环。
    
- **Q5：如果继续优化？**  
    A：MQTT 重连用 **指数退避**；上报加 **QoS1** 与小型发送缓冲；线程池支持**漂移校正**；把 NV 封成 `load/save` API 并统一错误码与日志级别。

“我们用的是 **HiSpark Wi-Fi IoT（Hi3861V100）** 板，OpenHarmony 的 **LiteOS-M** 形态，用 **DevEco + hb（GN/Ninja）** 构建。硬件这边通过 **AP3216C** 做接近检测，**AW2013** 驱动 RGB 灯提示，**SSD1306** 做页面显示，配合 **NFC NDEF** 做一贴即配网。软件侧我负责 **MQTT 通信、采集状态机和任务并发**：用阈值+时间窗判定入侵，红灯做常亮/闪烁的优先级仲裁，MQTT 上报属性并支持阈值下发写到 Flash 防掉电。”

 这个项目是跑在 **Hi3861 + OpenHarmony** 的边缘端安防应用。我负责 **采集+状态机、MQTT 通信和并发模型**。系统从 AP3216C 周期采集接近值，进入三态状态机：进入→计时→超时触发报警，联动蜂鸣器/红灯，并通过 **MQTT** 上报到云端；小程序下发命令后设备解析 JSON 即时生效。

### 问答
1. **这块板是什么架构？为什么看到 RISC-V？**

> **答**：Hi3861V100 IoT SoC，OpenHarmony 的 Hi3861 方案配的是 **RISC-V 32（RV32IMAC）** 工具链与 LiteOS-M 运行时；我这套工程的编译参数里就有 `-march=rv32imac`，IDE 也是走 riscv32 交叉链。[Alldatasheet](https://www.alldatasheet.com/datasheet-pdf/view/1179026/ETC2/SSD1306.html?utm_source=chatgpt.com)

2. **OpenHarmony 的构建链路是怎样的？IDE 点“编译”发生了什么？**

> **答**：DevEco 调用 **hb**；hb 基于 **GN 生成 Ninja**，再用交叉编译器（`riscv32-unknown-elf-gcc`）编、链出固件；失败看 `build.log`，`target.elf` 缺失多半是前一阶段报错导致未产物。[CSDN博客](https://blog.csdn.net/gitblog_06698/article/details/142571786?utm_source=chatgpt.com)

3. **I²C 外设你怎么用？需要注意什么？**

> **答**：都走 I²C：AP3216C（ALS/PS/IR）、AW2013（RGB 驱动）、SSD1306（OLED）。我遵循**上电顺序**、**地址配置**与**读写时序**；遇到总线忙/抖动，用**超时+软复位**清状态；显示异常一般是 **GDDRAM 未清/缓冲区残留**（我遇到过，先清屏再写）。[中源液晶+2WatElectronics.com+2](https://sino-lcd.com/icDetails/SSD1306.html?utm_source=chatgpt.com)

4. **Wi-Fi/ MQTT 在这块板上怎么跑？**

> **答**：SoC 内置射频，系统用 OpenHarmony 的 Wi-Fi Service 建链；上层用 Paho Embedded-C 建 MQTT 客户端；我设计了 **主题命名**（如 `device/{id}/props`）、**QoS1** 上报、**心跳/重连**与 **内存释放（如 cJSON_print 的 payload 释放）**，避免内存泄漏。

5. **课程框架里封装很多，你到底做了什么？**

> **答**：我负责三件“应用层可衡量”的事：

- **采集与状态机**：把 AP3216C 的 PS 值做“有人/超时=报警”的状态机（`ALARM_OFF → TRIGGERED → ALARM_ON`），并把 **灯光/蜂鸣** 的“手动/自动/冲突优先级”明确化；
    
- **MQTT 通信**：属性上报 JSON、命令下行解析、**内存释放**与重连；
    
- **参数持久化**（按你现在进度）：PS 阈值/超时阈值与运行态同步 + Flash/NV 保存（调用厂商 `hi_factory_nv_read/write` 一类 API）。

6. **如果我拔电再上电，设备还记得阈值吗？**
    

> **答**：记得。阈值同步到 **NV/Flash**，启动先 `nv_read` → 同步到运行变量；收命令更新则 `nv_write` 持久化（配网信息同理，NFC 模块的 NDEF 数据也会掉电不丢）。

7. **这类项目最大的坑是什么？**

> **答**：两类：

- **构建/环境坑**：工具链版本、hb 根目录识别、预编库缺失导致链接阶段不产物；
    
- **运行时坑**：**内存管理**（cJSON、MQTT payload）、**并发与状态冲突**（手动灯/自动灯/长鸣的优先级），以及 **I²C 设备未清屏/残帧** 导致显示脏数据。


你写“统一时基、避免漂移”，面试官下一句话肯定是：  
**“漂移到底有多大？你怎么量的？”**

- 现成钩子：线程池主循环里已经 10 ms 检查一次，把 `hi_get_us()` 采样值塞进一个 **环形缓冲**（64 点即可），上电跑 1 h 后回读；
    
- 指标：最大 **jitter = (maxΔt – 10 ms)**，**< 500 µs** 算合格（LiteOS-M 时钟节拍的典型值）；
    
- 结果：你现在就能跑，**今晚把 jitter 值写在简历括号里**——  
    “线程池定时抖动 ≤ 380 µs（1 h 统计，n=360 000）”  
    **一句话，秒掉 90% 候选人。**
    

2. NV 持久化 → 把“掉电不丢”变成“量化寿命”
面试官常追问：  
**“Flash 能写多少次？你这条命令多久写一次？会不会写穿？”**

- Hi3861 内置 SPI Flash，**典型寿命 10 000 次擦除**（查规格书《Hi3861V100 数据手册》表 4-4）；
    
- 你目前做法：命令一下发就 `nv_write`，假设用户每 10 s 调一次阈值，**理论寿命只有 10 000×10 s ≈ 1.16 天**——明显不合理；
    
- 现成补丁：  
    ① 内存变量与 NV 值**异或比较**，只有**真变**才写；  
    ② 加 **5 min 定时合并写**（容忍掉电丢失 5 min）；  
    ③ 简历里给结论：  
    “NV 写放大系数 0.02，**全生命周期可承受 57 年连续参数调整**。”

# 笔记

> 结构 = 架构 → 启动/并发 → 数据流 → 状态机 → MQTT → NV(Flash) → 显示 → 关键问题与修复 → 构建与联调 → 测试与验收 → 可扩展点 → 文件导览


## 1. 系统架构（文字版图）

- **硬件**：Hi3861，AP3216C（IR/接近），AW2013（RGB），SSD1306（OLED），NFC
    
- **系统**：OpenHarmony（LiteOS-M）
    
- **链路**：传感器采集 → 状态机判定 → 声光（蜂鸣器/红灯） → MQTT 上报/命令下发 → 小程序
    
- **存储**：NV(Flash) 保存 `ps_threshold / timeout_threshold`（掉电不丢）
    
- **并发**：线程池（MQTT 任务/心跳等）+ 采集独立线程

## 2. 启动与并发模型

- **启动顺序**：外设初始化 → NFC 配网 → Wi-Fi → MQTT 连接/订阅 → 线程池启动 MQTT 发送/接收 → 启动采集线程
    
- **线程池**（自研，单工人线程）
    
    - 控制结构：任务数组（函数指针 + interval + last_run），互斥保护
        
    - 工作循环：每 10ms 检查是否到期 → 调用；防忙等
        
    - 好处：统一节拍、减少线程数与栈占用，便于新增心跳/重连任务
        
- **采集线程**：独立 while 循环（保证实时性），与线程池互不阻塞

## 3. 数据流与主题

- **上报数据（属性）**：`ps`（接近值）、`ps_threshold`、`timeout_threshold`、`alarm_state`、`isBody`、设备模式等
    
- **下发命令**：设置阈值、开关自动模式、手动蜂鸣（长鸣）、手动灯常亮等
    
- **主题**：遵循华为云设备规范（命令/属性主题模板集中在 `sys_config.h`），避免魔法字符串

## 4. 状态机

- **三态**：
    
    - `ALARM_OFF`：无人或未触发
        
    - `ALARM_TRIGGERED`：有人→进入计时，计时未达阈值
        
    - `ALARM_ON`：超过超时阈值，进入报警（滴滴/长鸣方案）
        
- **关键变量**：`psData`（接近值）、`ps_threshold`、`timeout_threshold`、`is_Body`（是否有人）、手动按钮状态、自动模式开关
    
- **灯/铃优先级**：手动常亮 ＞ 自动闪烁（自动模式 + 自动灯开 + 报警）＞ 仅长鸣可灭灯 ＞ 默认灭灯
    
- **为什么是状态机**：时序清晰、可插入去抖/驻留，易测试和回溯（日志映射状态变化）
    

## 5. MQTT 实现要点

- **客户端生命周期**：初始化 → 连接 → 订阅（命令主题） → 上报属性 → 断线重连
    
- **JSON 处理**：`cJSON` 序列化（上报）/反序列化（命令）；**发布后释放 payload**，异常路径也要释放
    
- **失败策略**：连接失败循环重试（可演进为指数退避）；发布失败记录并可选缓冲重发（后续优化）
    

## 6. NV(Flash) 持久化

- **NV 结构体**：包含 `ps_threshold` 与 `timeout_threshold`（以及扩展字段）
    
- **启动加载**：`read → 校验 → 回填运行变量`，异常时落默认值并 `write` 修复
    
- **命令变更**：设置阈值后 `write` 写回，立即生效并上报
    
- **一致性**：上报 JSON 同步带上当前阈值，云端与设备状态可对照
    

## 7. 显示（OLED）与调试

- **页面**：报警图标/无报警图标、左/右侧“有人/无人与报警状态 Yes/No”、顶部运行信息
    
- **注意点**：每帧前**清空缓冲/区域重绘**，避免“1.5 行显示”和颜色残影
    
- **串口日志**：模块前缀、关键信息（状态切换、参数变更、连接重试、错误码）
    

## 8. 关键问题与修复

- **内存泄漏**：`cJSON_PrintUnformatted` 返回堆内存 → 发布后 `cJSON_free(payload)`；对异常分支同样释放
    
- **类型/显示异常**：`difftime` 返回 `double`，格式化用 `%f` 或先 `int elapsed = (int)difftime(...)` 再 `%d`；并在写屏前清零缓冲
    
- **灯/铃冲突**：统一优先级表，分离“手动常亮”和“自动闪烁”的决策；对“长鸣+自动报警”的过渡态加入去抖或最小驻留
    
- **并发抖动**：改造为线程池统一时基，避免各线程独睡造成的节拍漂移
    
- **构建与环境**：DevEco + hb 工具链与 SDK 版本匹配；缺库/链接错误逐项补齐；容器与本机路径一致性


| 问题                         | 可能原因              | 快速解决                                         |
| -------------------------- | ----------------- | -------------------------------------------- |
| `target.elf` 找不到           | 构建中断 / Ninja 缓存损坏 | `hb clean && hb build -f`                    |
| 编译卡住                       | 缺少交叉编译工具链         | 检查 `device/hisilicon/hi3861/sdk_liteos` 是否完整 |
| hb 报错 “set product failed” | 没有选择产品配置          | 重新执行 `hb set`                                |
| 烧录失败                       | 未连接 J-Link / 串口占用 | 检查设备连接并重启 IDE                                |
|                            |                   |                                              |



## 9. 构建与联调

- **工具**：DevEco Device Tool（含 hb 工具链）
    
- **流程**：清理 → 构建 → 烧录 → 串口观察（初始化 → NFC 配网 → Wi-Fi → MQTT 连接/订阅 → 上报/下发）

    - 连接失败：AP/密码/NFC 配网检查、热点频段、Broker 可达性
