 并发设计 (软件层面) → 调度机制 (OS层面) → 并行执行 (硬件层面)
## 进程与线程：
*进程是一个具有一定独立功能的程序在一个数据集合上依次动态执行的**过程***
**进程是资源分配的基本单位**，每个进程有独立的地址空间,地址空间包括代码区、数据区和堆栈区，进程之间的地址空间是隔离的，互不影响。
**多进程是指操作系统中同时存在多个进程并发执行的模型**。每个进程是程序的一次执行实例，是系统**资源分配和保护**的基本单位，拥有独立的虚拟地址空间、文件描述符、信号处理等资源。进程间的执行和资源相互隔离，通过进程间通信（IPC）机制进行数据交换。多进程通过时间片轮转或并行处理，实现了宏观上的并发执行。

**线程是CPU调度的基本单位**，它是进程内部的一个执行流，同一进程内多个线程共享进程的地址空间和资源（如打开的文件、全局变量）。
**多线程是指在一个进程内部存在多个线程并发执行的模型**。线程作为系统**CPU调度和执行**的基本单位，共享其所属进程的全部资源，如代码段、数据段、打开的文件等，但每个线程拥有独立的线程ID、程序计数器、寄存器集合和栈空间。多线程旨在将一个进程的任务分解为多个可并行执行的子任务，以提高程序的执行效率和响应能力。

[[进程控制#进程间通信IPC]]
进程间通信（IPC）：管道是最基本的IPC，共享内存是最快的IPC
信号（异步机制），套接字（功能最强大，可用于网络通信），消息队列（内核的一个链表）。主要成本是上下文切换和数据拷贝
线程间通信：通过共享内存和同步机制实现，进程内的所有线程共享相同的地址空间（全局变量、堆空间等），所以各线程之间可以直接读写另一线程看到的数据，主要成本是同步开销
同步机制：
- **互斥锁**：保证同一时间只有一个线程能进入临界区。
    
- **条件变量**：让线程在某个条件不满足时主动等待，条件满足时被唤醒。
    
- **信号量**：控制同时访问资源的线程数量。
    
- **读写锁**：允许多个读，但只允许一个写。


进程与程序：程序是用适当形式描述的算法，是一个存储在磁盘上的**静态实体**，而进程是cpu读取各种输入，运行这个算法的事件本身，也就是一个正在执行的程序的**动态实例**。

多进程更健壮，进程崩溃不影响其他进程；线程崩溃会导致整个进程崩溃。

**线程运行的本质就是函数运行**，函数运行时信息是保存在栈帧中的，因此每个线程都有自己独立的、私有的栈区。而**所属线程的栈区、程序计数器、栈指针以及函数运行使用的寄存器是线程私有的**，**统称为线程上下文**。
**进程上下文**，就是一个进程在执行的时候，CPU中所有寄存器的值、进程的状态以及内核堆栈上的内容，
当内核需要切换到另一个进程时，它需要保存当前进程的进程上下文，以便再次执行该进程时，能够恢复切换时的状态继续执行。

进程强调**隔离与安全**，线程强调**共享与效率**。


## 并行与并发

在（应用层）：使用**多进程/多线程来创建出多个可执行的任务单元。这是实现并发能力的设计手段。
操作系统（内核层）：通过调度算法来管理和切换这些任务单元，让它们共享CPU。这是实现并发执行的支撑机制。
并发设计其他方法：
- **异步编程（协程）**：在单个线程内，通过任务调度在IO等待时切换执行其他任务，从而实现高并发。这是现代高并发服务（如Nginx、Redis）的核心技术，在嵌入式Linux开发中也会遇到。
    
- **事件驱动**：基于事件循环，当某个事件（如文件描述符可读）触发时，执行相应的回调函数。
    多进程/多线程是 **“抢占式”** 并发，由操作系统内核进行调度；而协程等是 **“协作式”** 并发，由程序自身主动让出执行权。两者都是为了解决并发问题。

**多进程和多线程** 是实现并发设计的两种主要技术手段。多进程资源隔离好但开销大，多线程共享数据高效但需要处理同步问题。


**并发** 指的是**逻辑上**同时处理多任务的能力。这些任务在**一段时间内**都在向前推进，但在**单核CPU的任一时刻，实际上只有一个任务在执行**。
操作系统通过调度技术实现并发（软件策略），比如时间片轮转让任务交替执行，优先级调度确保关键任务及时响应，以及更复杂的多级反馈队列来平衡效率和响应时间。
**并发解决的是‘等待’的问题**
调度技术：
先到先服务（FCFS），短作业优先（SJF）
**时间片轮转调度**：每个任务被分配一个固定的时间片，时间用完就被挂起换上另一个任务。
**优先级调度**：给不同任务分配不同优先级。高优先级任务先运行。如操作系统的中断处理
**多级反馈队列**：综合了时间片和优先级。任务会在不同优先级的队列间移动



**并行** 指的是**物理上**同时执行多任务的能力。这要求**必须有多个计算单元（如多核CPU）**，使得多个任务能在**同一时刻**分别在不同的核心上执行。
**并行依赖于硬件提供多个计算单元**（硬件基础），**解决的是‘速度’的问题。
多计算单元：
多核处理器**（最常见1. 每个核心可以同时执行一个线程），**多个CPU**（服务器）
**众核架构**（GPU），**分布式系统**（多个计算机通过网络组成）

并发关乎**任务结构**，并行关乎**执行效率**。**并行通常是并发设计在硬件上的理想体现**，因为需要并发实现之后再在可能的被多计算单元上同时处理



多线程优点：
- **提高响应性**：主线程保持响应，后台线程处理耗时任务
- **提高资源利用率**：充分利用多核CPU的计算能力
- **经济高效**：创建线程比创建进程开销小
- **简化复杂任务**：将复杂任务分解为多个线程协同处理

## POSIX线程与函数
POSIX线程（pthread）是C/C++中实现多线程的标准API，在Linux/Unix系统中广泛使用。使用时需包含头文件`<pthread.h>`
==编译时需添加`-pthread`选项，较老版本是加上 -lpthread==可在末尾
该选项保证程序在多线程环境下正确编译和链接
忘记添加会导致"未定义的引用"链接错误
### 创建线程 - pthread_create

```c
int pthread_create(pthread_t *thread, 
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *), 
                   void *arg);
```
- `thread`：指向线程标识符的指针
- `attr`：设置线程属性，通常设为NULL
- `start_routine`：线程运行的函数指针
就是子线程运行的函数 ，是一个回调函数
- `arg`：传递给线程函数的参数
返回值：成功为0，否则为错误码

### 等待线程结束 - pthread_join
回收子线程

```c
int pthread_join(pthread_t thread, void **retval);
```
- `thread`：要等待的线程ID
- `retval`：存储线程返回值的指针，可为NULL

**返回值：** 成功返回0，失败返回错误码

**注意事项：**

- 调用该函数的线程将阻塞，直到目标线程结束
- 每个线程只能被一个线程join一次
- 未join的线程会产生"僵尸线程"，浪费系统资源


### 分离线程 - pthread_detach

```c
int pthread_detach(pthread_t thread);
```

**功能：** 将线程设置为分离状态，线程结束后自动回收资源

**使用场景：** 不需要获取线程返回值，也不关心线程何时结束时使用

**注意事项：**

- 分离状态的线程不能被join
- 如果线程已结束，分离操作可能失败
- 主线程退出后，分离线程也会终止

### 取消线程 - pthread_cancel

```c
int pthread_cancel(pthread_t thread);
```

**功能：** 向指定线程发送取消请求

**使用场景：** 需要强制终止另一个线程的执行时使用

**注意事项：**

- 成功只表示取消请求已发送，不保证线程立即终止
    
- 线程需要在取消点才能响应取消请求
    
- 被取消的线程需要使用清理函数释放资源
    
- 分离状态的线程也可以被取消

### 线程终止 - pthread_exit

```c
void pthread_exit(void *retval);
```
**`retval` 是一个 `void*` 类型的指针**
它是在线程间传递数据的一种机制，而不是简单的函数返回值
它允许线程在退出时**传递一个值**给它的“回收者”（即调用 `pthread_join` 的线程）。

**功能：** 显式终止当前线程，并返回一个值
**返回值**：0表示成功，非0为对应的错误码
**注意事项：**

- 主线程调用pthread_exit不会导致进程退出
- 线程函数执行return语句也会隐式调用pthread_exit

### 读写锁
读写锁是互斥锁的升级版, 在做读操作的时候可以提高程序的执行效率，如果所有的线程都是做读操作, 那么读是并行的，但是使用互斥锁，读操作也是串行的。

读写锁是一把锁，锁的类型为pthread_rwlock_t，有了类型之后就可以创建一把互斥锁了：


读写锁既可以锁定读操作，也可以锁定写操作。
锁的状态: 锁定/打开
锁定的是什么操作: 读操作/写操作，使用读写锁锁定了读操作，需要先解锁才能去锁定写操作，反之亦然。
读写锁的使用方式与互斥锁的使用方式是完全相同的：找共享资源, 确定临界区，在临界区的开始位置加锁（读锁/写锁），临界区的结束位置解锁。

**注意**：
使用读写锁的读锁锁定了临界区，线程对临界区的访问是并行的，读锁是共享的。
使用读写锁的写锁锁定了临界区，线程对临界区的访问是串行的，写锁是独占的。
使用读写锁分别对两个临界区加了读锁和写锁，两个线程要同时访问这两个临界区，访问写锁临界区的线程继续运行，访问读锁临界区的线程阻塞，因为写锁比读锁的优先级高。
如果说程序中所有的线程都对共享资源做写操作，使用读写锁没有优势，和互斥锁是一样的，如果说程序中所有的线程都对共享资源有写也有读操作，并且对共享资源读的操作越多，读写锁更有优势。

由于读写锁允许多个读线程同时持有锁，如果一直有新的读线程到来，写线程可能**永远无法获得锁**（因为要等所有读线程释放）。
**解决方案**：很多读写锁实现提供了偏向写的策略：
- 当有写线程在等待时，阻止新的读线程获取锁。
    
- 这样在现有的读线程完成后，写线程就能获得锁。

**读写锁不保证先来先服务**：即使写操作先访问，但会被当前读锁阻塞，这时候在写操作之后加入的读操作会比写操作先被服务，因为写操作要等待所有读锁解锁才进行。
**读锁的作用是**：**保护读操作不被写操作干扰**，**同时允许其他读操作并行进行**。
**写锁**保护的是：**写操作不被读操作和其他写操作干扰**，**写锁的约束条件是为读操作的正确性服务的**。
- **读锁模式**：允许新的读操作加入，阻止写操作进入
    
- **写锁模式**：阻止所有读操作和写操作进入
    
- **无锁模式**：第一个到来的读操作或写操作决定进入哪种模式

```c
// 线程A（读）获取了读锁
pthread_rwlock_rdlock(&rwlock);
// 开始读取...

// 线程B（写）尝试获取写锁
pthread_rwlock_wrlock(&rwlock); 
// 线程B会在这里阻塞！等待线程A释放读锁

// 线程A安全地读完数据后...
pthread_rwlock_unlock(&rwlock);
// 现在线程B才获得写锁，开始修改数据
```

多个读可以并行，有读的时候不能写，写是互斥的，有写的时候不能读


#### 读写锁函数
Linux提供的读写锁操作函数原型如下，如果函数调用成功返回0，失败返回对应的错误号：
```c

#include <pthread.h>
pthread_rwlock_t rwlock;
// 初始化读写锁
int pthread_rwlock_init(pthread_rwlock_t *restrict rwlock,
           const pthread_rwlockattr_t *restrict attr);
// 释放读写锁占用的系统资源
int pthread_rwlock_destroy(pthread_rwlock_t *rwlock);

```
rwlock: 读写锁的地址，传出参数
attr: 读写锁属性，一般使用默认属性，指定为NULL

```c
// 在程序中对读写锁加读锁, 锁定的是读操作
int pthread_rwlock_rdlock(pthread_rwlock_t *rwlock);
```
调用这个函数，如果读写锁是打开的，那么加锁成功；如果读写锁已经锁定了读操作，调用这个函数依然可以加锁成功，因为读锁是共享的；如果读写锁已经锁定了写操作，调用这个函数的线程会被阻塞。


```c
// 这个函数可以有效的避免死锁
// 如果加读锁失败, 不会阻塞当前线程, 直接返回错误号
int pthread_rwlock_tryrdlock(pthread_rwlock_t *rwlock);
```
调用这个函数，如果读写锁是打开的，那么加锁成功；如果读写锁已经锁定了读操作，调用这个函数依然可以加锁成功，因为读锁是共享的；如果读写锁已经锁定了写操作，调用这个函数加锁失败，对应的线程不会被阻塞，可以在程序中对函数返回值进行判断，添加加锁失败之后的处理动作。


```c
// 在程序中对读写锁加写锁, 锁定的是写操作
int pthread_rwlock_wrlock(pthread_rwlock_t *rwlock);
```
调用这个函数，如果读写锁是打开的，那么加锁成功；如果读写锁已经锁定了读操作或者锁定了写操作，调用这个函数的线程会被阻塞。


```c
// 这个函数可以有效的避免死锁
// 如果加写锁失败, 不会阻塞当前线程, 直接返回错误号
int pthread_rwlock_trywrlock(pthread_rwlock_t *rwlock);
```
调用这个函数，如果读写锁是打开的，那么加锁成功；如果读写锁已经锁定了读操作或者锁定了写操作，调用这个函数加锁失败，但是线程不会阻塞，可以在程序中对函数返回值进行判断，添加加锁失败之后的处理动作。


```c
// 解锁, 不管锁定了读还是写都可用解锁
int pthread_rwlock_unlock(pthread_rwlock_t *rwlock);

```

### 条件变量（Condition Variable）
严格意义上来说，条件变量的主要作用不是处理线程同步, 而是进行线程的阻塞。
在多线程程序中只使用条件变量无法实现线程的同步, 必须要配合互斥锁来使用。
虽然条件变量和互斥锁都能阻塞线程，但是二者的效果是不一样的，二者的区别如下：

1.假设有A-Z 26个线程，这26个线程共同访问同一把互斥锁，如果线程A加锁成功，那么其余B-Z线程访问互斥锁都阻塞，所有的线程只能顺序访问临界区
2.条件变量只有在满足指定条件下才会阻塞线程，如果条件不满足，多个线程可以同时进入临界区，同时读写临界资源，这种情况下还是会出现共享资源中数据的混乱。

**一般情况下条件变量用于处理生产者和消费者模型，并且和互斥锁配合使用**。条件变量类型对应的类型为pthread_cond_t，这样就可以定义一个条件变量类型的变量了：



初始化与销毁

```c
// 静态初始化
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

// 动态初始化
int pthread_cond_init(pthread_cond_t *cond, 
                     const pthread_condattr_t *attr);
cond: 条件变量的地址

attr: 条件变量属性, 一般使用默认属性, 指定为NULL
// 销毁条件变量
int pthread_cond_destroy(pthread_cond_t *cond);
```

等待与通知

```c
int pthread_cond_wait(pthread_cond_t *cond, 
                      pthread_mutex_t *mutex);
                      
int pthread_cond_signal(pthread_cond_t *cond);   // 唤醒一个等待线程
int pthread_cond_broadcast(pthread_cond_t *cond); // 唤醒所有等待线程
```
pthread_cond_signal是唤醒至少一个被阻塞的线程（总个数不定），pthread_cond_broadcast是唤醒所有被阻塞的线程。


```c
// 线程阻塞函数, 哪个线程调用这个函数, 哪个线程就会被阻塞
int pthread_cond_wait(pthread_cond_t *restrict cond, pthread_mutex_t *restrict mutex);

```
- `pthread_cond_wait`：主动**让出CPU**，线程进入睡眠状态
    
- `pthread_mutex_lock`：尝试获取锁，如果锁被占用，线程**阻塞等待**


pthread_cond_wait函数在阻塞线程的时候，需要一个互斥锁参数，让线程顺序进入临界区，避免出现数共享资源的数据混乱。
在阻塞线程时候，如果线程已经对互斥锁mutex上锁，那么会将这把锁打开，这样做是为了避免死锁
当线程解除阻塞的时候，函数内部会帮助这个线程再次将这个mutex互斥锁锁上，继续向下访问临界区


```c
// 等待方的标准模式
pthread_mutex_lock(&mutex);
while (condition_is_false) {
    pthread_cond_wait(&cond, &mutex);
}
// 执行操作...
pthread_mutex_unlock(&mutex);
```

```c
// 通知方的标准模式  
pthread_mutex_lock(&mutex);
// 改变条件
condition = true;
pthread_cond_signal(&cond); // 或 pthread_cond_broadcast
pthread_mutex_unlock(&mutex);
```

使用循环是为了让可能不止一个线程陷入循环里然后被condwait函数阻塞，直到条件成立，只有一个也是一样的，因为即使condwait不阻塞了，还需要条件达到能够释放该线程时才可以释放，也就是除了其他线程唤醒并且当前条件能够释放时才释放

**条件变量只是阻塞/唤醒机制，真正的同步逻辑是通过"条件判断+互斥锁"共同完成的**。这种设计给了程序员最大的灵活性来控制线程间的协作。



### 信号量（semaphore）
信号量用在多线程多任务同步的，一个线程完成了某一个事件就通过信号量告诉别的线程，别的线程再进行某些动作。
信号量不一定是锁定某一个资源，而是流程上的概念，比如：有A，B两个线程，B线程要等A线程完成某一任务以后再进行自己下面的步骤，这个任务并不一定是锁定某一资源，还可以是进行一些计算或者数据处理之类。

信号量（信号灯）与互斥锁和条件变量的主要不同在于”灯”的概念，灯亮则意味着资源可用，灯灭则意味着不可用。信号量主要阻塞线程, 不能完全保证线程安全，如果要保证线程安全, 需要信号量和互斥锁一起使用。

信号量和条件变量一样用于处理生产者和消费者模型，用于阻塞生产者线程或者消费者线程的运行。信号的类型为sem_t对应的头文件为<semaphore.h>：


```c
#include <semaphore.h>
// 初始化信号量/信号灯
int sem_init(sem_t *sem, int pshared, unsigned int value);
// 资源释放, 线程销毁之后调用这个函数
// 参数 sem 就是 sem_init() 的第一个参数            
int sem_destroy(sem_t *sem);


sem：信号量变量地址
pshared：
0：线程同步
非0：进程同步
value：初始化当前信号量拥有的资源数（>=0），如果资源数为0，线程就会被阻塞了。
```


```c
// 参数 sem 就是 sem_init() 的第一个参数  
// 函数被调用sem中的资源就会被消耗1个, 资源数-1
int sem_wait(sem_t *sem);
```
当线程调用这个函数，并且sem中的资源数>0，线程不会阻塞，线程会占用sem中的一个资源，因此资源数-1，直到sem中的资源数减为0时，资源被耗尽，因此线程也就被阻塞了。


```c
// 参数 sem 就是 sem_init() 的第一个参数  
// 函数被调用sem中的资源就会被消耗1个, 资源数-1
int sem_trywait(sem_t *sem);
```
当线程调用这个函数，并且sem中的资源数>0，线程不会阻塞，线程会占用sem中的一个资源，因此资源数-1，直到sem中的资源数减为0时，资源被耗尽，线程也不会被阻塞，直接返回错误号，因此可以在程序中添加判断分支，用于处理获取资源失败之后的情况。

```c
// 表示的时间是从1971.1.1到某个时间点的时间, 总长度使用秒/纳秒表示
struct timespec {
	time_t tv_sec;      /* Seconds */
	long   tv_nsec;     /* Nanoseconds [0 .. 999999999] */
};
// 调用该函数线程获取sem中的一个资源，当资源数为0时，线程阻塞，在阻塞abs_timeout对应的时长之后，解除阻塞。
// abs_timeout: 阻塞的时间长度, 单位是s, 是从1970.1.1开始计算的
int sem_timedwait(sem_t *sem, const struct timespec *abs_timeout);
```
该函数的参数abs_timeout和pthread_cond_timedwait的最后一个参数是一样的
当线程调用这个函数，并且sem中的资源数>0，线程不会阻塞，线程会占用sem中的一个资源，因此资源数-1，直到sem中的资源数减为0时，资源被耗尽，线程被阻塞，当阻塞指定的时长之后，线程解除阻塞。

```c
// 调用该函数给sem中的资源数+1
int sem_post(sem_t *sem);
```
调用该函数会将sem中的资源数+1，如果有线程在调用sem_wait、sem_trywait、sem_timedwait时因为sem中的资源数为0被阻塞了，这时这些线程会解除阻塞，获取到资源之后继续向下运行。


```c
// 查看信号量 sem 中的整形数的当前值, 这个值会被写入到sval指针对应的内存中
// sval是一个传出参数
int sem_getvalue(sem_t *sem, int *sval);
```
通过这个函数可以查看sem中现在拥有的资源个数，通过第二个参数sval将数据传出，而该函数的返回值表示函数执行是否成功（0=成功，-1=失败，其他就是错误码）

## 线程池
指在应用程序启动时创建一定数量的线程，并将它们保存在线程池中。当需要执行任务时，从线程池中获取一个空闲的线程，将任务分配给该线程执行。当任务执行完毕后，线程将返回到线程池，可以被其他任务复用。
目的是避免频繁地创建和销毁线程的开销，以及控制并发执行的线程数量，从而提高系统的性能和资源利用率。

**任务队列，存储需要处理的任务，由工作的线程来处理这些任务**
通过线程池提供的API函数，将一个待处理的任务添加到任务队列，或者从任务队列中删除
已处理的任务会被从任务队列中删除
线程池的使用者，也就是调用线程池函数往任务队列中添加任务的线程就是生产者线程

**工作的线程（任务队列任务的消费者）** ，N个
线程池中维护了一定数量的工作线程, 他们的作用是是不停的读任务队列, 从里边取出任务并处理
工作的线程相当于是任务队列的消费者角色
如果任务队列为空, 工作的线程将会被阻塞 (使用条件变量/信号量阻塞)
如果阻塞之后有了新的任务, 由生产者将阻塞解除, 工作线程开始工作

**管理者线程（不处理任务队列中的任务）**，1个
它的任务是周期性的对任务队列中的任务数量以及处于忙状态的工作线程个数进行检测
当任务过多的时候, 可以适当的创建一些新的工作线程
当任务过少的时候, 可以适当的销毁一些工作的线程

线程池适用于：
- **高并发**：需要同时处理大量任务
    
- **波动负载**：任务数量时多时少
    
- **短任务**：任务执行时间较短，创建线程的开销相对较大


## 注意

- **`pthread_join`**：用于**线程生命周期管理**，等待线程结束并回收资源
    
- **互斥锁/条件变量**：用于**线程间同步**，控制并发线程的执行顺序
因为`pthread_join` 会阻塞调用线程，看要求是需要**线程间的同步还是主线程等待**，并且`pthread_join` 通常由创建线程的调用者来使用，



## **CMSIS-RTOS**
这是 ARM 为 Cortex-M 系列处理器定义的实时操作系统通用接口，它在底层可能是 FreeRTOS、RTX 或其他 RTOS。


```c
typedef struct {
  const char                   *name;       // 线程名字符串，用于调试和追踪
  uint32_t                 attr_bits;       // 保留位，通常设为0
  void                      *cb_mem;        // 自定义控制块内存（通常为NULL，让系统自动分配）
  uint32_t                   cb_size;       // 自定义控制块大小
  void                  *stack_mem;         // 自定义栈内存（通常为NULL，让系统自动分配）
  uint32_t                stack_size;       // 栈大小 - 关键参数，防止栈溢出
  osPriority_t             priority;        // 线程优先级 - 关键参数
  TZ_ModuleId_t        tz_module;           // TrustZone 模块ID（安全扩展）
  uint32_t                  reserved;       // 保留位
} osThreadAttr_t;
操作状态
- `osOK`: 操作成功
    
- `osError`: 未指定的错误
    
- `osErrorTimeout`: 操作超时
    
- `osErrorResource`: 资源不可用
    
- `osErrorParameter`: 参数错误
    
- `osErrorNoMemory`: 内存不足
    
- `osErrorISR`: 在中断服务程序中调用
```
`osThreadAttr_t`**不是线程标识符**，而是线程的**属性配置集**，用于在创建线程时指定其特性。
- `pthread_attr_t` 需要调用一系列函数来设置属性（如 `pthread_attr_setstacksize`）
    
- `osThreadAttr_t` 直接赋值，更直观，更适合资源受限的嵌入式系统

### 创建线程
`ososThreadNew`
```c
osThreadId_t osThreadNew(osThreadFunc_t func, void *argument, const osThreadAttr_t *attr)
```

|CMSIS-RTOS `osThreadNew`|POSIX `pthread_create`|说明|
|---|---|---|
|`func`|`start_routine`|线程入口函数，完全对应|
|`argument`|`arg`|传递给线程的参数，完全对应|
|`attr`|`attr`|线程属性，概念对应但实现不同|
|**返回值** `osThreadId_t`|`pthread_t *thread`|**关键区别：CMSIS返回ID，POSIX通过参数返回**|
- **CMSIS-RTOS (`osThreadNew`)**：为**资源受限的嵌入式系统**设计，API 简单直接，静态配置为主。
    
- **POSIX (`pthread_create`)**：为**通用计算系统**设计，API 更灵活，动态配置能力强。
### 线程等待
```c
osStatus_t osThreadJoin(osThreadId_t thread_id);
- `thread_id`: 要等待的线程ID
返回值：操作状态（osOK表示成功）
```
- 只能等待可连接（joinable）的线程
    
- 等待的线程必须处于运行状态
    
- 超时设置可防止永久阻塞
### 线程分离
```c
osStatus_t osThreadDetach(osThreadId_t thread_id);
```
- `thread_id`: 要分离的线程ID
    

**返回值：** 操作状态（osOK表示成功）

**注意事项：**

- 分离状态的线程不能被join
    
- 如果线程已结束，分离操作可能失败
    
- 分离后线程资源在线程结束时自动释放


### 线程退出
```c
void osThreadExit(void);、
```
- 线程可以调用此函数主动退出
    
- 线程函数返回时也会自动调用
    
- 退出前会执行线程的清理工作

### POSIX pthread vs. CMSIS-RTOS osThread 

| 特性        | POSIX `pthread`                                                            | CMSIS-RTOS `osThread`                                 | **区别                                                                |
| --------- | -------------------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------- |
| **线程标识符** | 作为**输出参数**传入：`pthread_t *thread`                                           | 作为**返回值**：`osThreadId_t`                              | **设计哲学**：POSIX倾向于将资源句柄作为参数输出；CMSIS风格更类似面向对象，将新创建的对象句柄直接返回。          |
| **属性设置**  | 使用**不透明对象**：`pthread_attr_t`，需调用`pthread_attr_init`及一系列set函数。**允许默认NULL**。 | 使用**透明结构体**：`osThreadAttr_t`，**直接赋值成员**。**允许默认NULL**。 | **灵活性与简便性**：POSIX属性对象可复用，更灵活但更复杂。CMSIS结构体直观赋值，更适合资源受限、追求代码简洁的嵌入式开发。 |
| **栈管理**   | 属性中设置，通常依赖系统默认值，在PC/服务器上足够。                                                | **必须显式指定**`stack_size`，是嵌入式开发的关键步骤。                   | **目标平台**：嵌入式系统内存寸土寸金，且没有虚拟内存兜底，**必须精确控制栈大小**以防溢出。通用系统内存充裕，有MMU保护。   |
| **优先级**   | 通过属性设置，策略复杂（如`SCHED_FIFO`, `SCHED_RR`）。                                    | 直接赋值一个`osPriority_t`枚举值，简单直观。                         | **系统复杂度**：Linux/Unix是通用分时系统，调度策略复杂。大多数RTOS是实时系统，优先级调度是核心，API因此简化。   |
| **错误处理**  | 返回**int错误码**，需手动检查。                                                        | 返回**NULL句柄**表示失败，判断更直接。                               | **惯例与清晰度**：POSIX C库函数惯例。CMSIS返回NULL非常直观，符合嵌入式开发中“资源分配失败”的常见检查模式。    |
| **设计目标**  | **通用性、可移植性、灵活性**。                                                          | **确定性、低开销、代码体积小**。                                    | **根源**：POSIX为跨Unix系统设计；CMSIS为ARM Cortex-M这类资源紧俏的微控制器设计。             |
