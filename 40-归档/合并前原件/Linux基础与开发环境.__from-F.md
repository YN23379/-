## 开发环境

### 环境变量
"环境变量是操作系统提供的键值对，用于：
1. **配置程序行为**：如`PATH`定义命令搜索路径
2. **传递信息**：进程间通过环境变量共享配置
3. **控制特性**：如`LD_LIBRARY_PATH`控制库加载

继承规则：
1. **父子继承**：子进程继承父进程的环境变量
2. **exec保持**：`exec()`系列函数默认保持环境变量
3. **修改隔离**：子进程修改不影响父进程
4. **Shell特殊**：Shell脚本中的export影响后续命令

环境变量的生命周期：
- 临时变量：`export VAR=value` （进程结束就消失）
- 用户级：`~/.bashrc`, `~/.bash_profile` （登录时加载） 
- 系统级：`/etc/profile`, `/etc/environment` （所有用户共享）

**Linux的环境变量加载遵循用户→系统的优先级，分为两个层次：**
**用户级配置**（优先级高）：
- **`~/.bashrc`**：每次打开bash终端时加载，适合设置别名、函数等交互配置
- **`~/.bash_profile`** 或 **`~/.profile`**：用户登录时加载一次，适合设置PATH等环境变量
**系统级配置**（优先级低）：
- **`/etc/profile`**：所有用户登录时加载，设置全局环境变量
	- **`/etc/environment`**：系统最早加载，设置最2基础的环境变量

**加载顺序**：`/etc/environment` → `/etc/profile` → `~/.bash_profile` → `~/.bashrc`，后者覆盖前者。

### 程序里获取环境变量
```c
#include <stdio.h>
#include <stdlib.h>

void env_demo() {
    // 1. 获取环境变量
    char *path = getenv("PATH");
    if (path) {
        printf("PATH: %s\n", path);
    }
    
    // 2. 设置环境变量（当前进程及子进程）
    setenv("MY_APP_DEBUG", "1", 1);  // 1=覆盖已存在
    
    // 3. 设置环境变量（仅当前进程）
    putenv("MY_VAR=value");
    // 4. 删除环境变量
    unsetenv("MY_VAR");
}
```

### Shell

Shell是一个**命令解释器**，它用于接收并执行用户输入的命令。
执行脚本（一系列命令的集合）。
提供编程功能，如变量、循环、条件判断。
常见：Bash, Zsh, Ksh, Csh等。
#### shell脚本

shell 是一种脚本语言  而脚本 本质是一个文件（.sh结尾，也可以不写），文件里面存放的是 特定格式的指令，系统可以使用脚本解析器 翻译或解析 指令 并执行（它不需要编译）  
**shell 既是应用程序 又是一种脚本语言**，查看自己linux系统的默认解析：
echo $SHELL $SHELL是环境变量
脚本的调用：打开终端时系统自动调用：/etc/profile 或 ~/.bashrc
**/etc/profile**
此文件为系统的每个用户设置环境信息,当用户第一次登录时,该文件被执行，系统的公共环境变量在这里设置
开机自启动的程序，一般也在这里设置
**~/.bashrc**
用户自己的家目录中的.bashrc
登录时会自动调用，打开任意终端时也会自动调用
这个文件一般设置与个人用户有关的环境变量，如交叉编译器的路径等等
用户手动调用：用户实现的脚本

##### shell语法
在脚本文件.sh中：
定义开头：#!/bin/bash。**#!用来声明脚本由什么类型的shell解释，否则使用默认shell**
加上可执行权限：在终端上，chmod +x xxxx.sh
运行方式：./xxx.sh bash  xxx.sh . xxx.sh
./xxx.sh 按脚本文件里#!指定类型的shell解析脚本
bash xxx.sh 优先用bash解析，没有就文件指定的
. xxx.sh 直接使用默认解析器解析（不会执行第一行的#！指定的解析器）但是第一行还是要写的

变量：
变量名=变量值  ，**等号两边不能有空格！**
$： 引用变量，
echo $变量名,等价于 echo ${变量名}  打印变量的值
unset  变量名  （用于清除变量值）
传递参数：脚本内通过 `$1`, `$2` ... 获取执行脚本时传入的参数。
`$0`是当前执行脚本的名称，$SHELL是当前系统默认使用的Shell路径
read 变量名  变量获取键盘输入的值，可多个读取，变量名直接空格隔开
readonly 变量名 声明只读变量

终端上输入env查看环境变量，
导出环境变量 作用：（让其他shell脚本识别该变量，设为全局变量）

该命令通常用命令“.”来替代：. FileName

![[Shell变量生命周期.png]]
1. **`source`（或`.`）** 是在**当前Shell进程**内部执行脚本，所以脚本里定义的**所有变量（无论是否export）** 在当前终端都有效。
    
2. **`./script.sh`** 是启动一个**新的子Shell进程**来执行脚本。脚本结束时，这个子进程就被销毁了，它里面定义的**所有变量也随之销毁**，所以在父Shell（终端）里看不到。
    
3. **`export`** 的关键作用是：**将一个变量标记为“环境变量”，使其可以被子进程继承。** 如果不用`export`，子进程根本无法从父进程那里知道这个变量的存在。
想让脚本的变量**影响你的当前终端环境**，用 **`source`**。
想让脚本内部的变量**被它自己启动的程序（子进程）使用**，用 **`export`**。
若需要让变量永久有效则需要写在bashrc文件，或者是bash_profile中，shell会在启动时读取这两个配置文件，最好是在末尾添加，而根目录下的etc目录里的profile和bashrc文件则是对所有用户都有效
**注意事项**：
1、变量名只能包含英文字母下划线和数字，不能以数字开头
1_num=10 错误
num_1=20 正确
2、等号两边不能直接接空格符，若变量中本身就包含了空格，则整个字符串都要用双引号、或单引号括起来
3、双引号 单引号的区别
双引号：可以解析变量的值
单引号：不能解析变量的值
4.**空格就是生命线**：
- `if` 和 `[[` 之间要有空格
- `[[` 和变量之间要有空格
- 变量和运算符（如 `-eq`）之间要有空格
- 运算符和变量之间要有空格
- `]]` 和前一个变量之间要有空格

```shell
$0    # 脚本名称
$1, $2, $3...    # 第1、2、3...个参数
$#    # 参数个数
$@    # 所有参数（每个参数独立）
$*    # 所有参数（作为一个整体）
"$@"  # 推荐！保持参数原样传递
"$*"  # 所有参数合并为一个字符串

# 示例：遍历所有参数
for arg in "$@"; do
    echo "参数: $arg"
done


$$    # 当前脚本的PID
$!    # 最后一个后台进程的PID
$?    # 上一个命令的退出状态

# 示例：
sleep 5 &
echo "后台进程PID: $!"
echo "脚本自身PID: $$"

```

### GCC编译
**GCC (GNU Compiler Collection)**
![[GCC编译过程.png]]
1. **预处理**：处理源代码中的`#`开头的指令，完成**宏替换、头文件包含和条件编译**，删除注释，输出一个纯粹的`.i`文本文件。
    
2. **编译**：进行**词法、语法、语义分析**，在确认代码逻辑正确后，进行**代码优化**，最终将预处理后的文件**翻译成对应的汇编代码**，生成`.s`文件。
    
3. **汇编**：将人类可读的汇编代码.s文件翻译成机器语言指令，把这些指令打包成**可重定位目标程序**的格式，并将结果保存在目标文件.o中。这个文件包含了机器码，但其中函数和全局变量的**内存地址尚未确定**。
    
4. **链接**：这是生成最终可执行文件的关键一步。链接器（ld）将多个`.o`目标文件和所需的库文件**合并**在一起，完成**地址和空间分配**以及**符号解析与重定位**，解决所有跨文件的函数调用和变量访问问题，生成一个可以加载到内存中运行的可执行文件，最后可执行文件加载到储存器后由系统负责执行

链接主要解决：
**符号解析**：将目标文件中每个符号（静态变量、函数、全局变量）和其定义进行关联。即确保所有被引用的函数和变量都能找到定义
**重定位**：将每个符号的定义与具体在虚拟内存中的位置进行关联

`.o`文件虽然是二进制机器码，但它是**可重定位的**，其内部地址是从零开始的临时地址，需要链接器最终绑定到进程虚拟地址空间的实际地址。
#### 动态静态链接
**动态链接和静态链接是程序构建（编译和链接）的最后一步，
是链接过程中的两种不同策略，它们决定了如何将代码和它依赖的库代码组合成一个可执行文件。

##### 动态链接（默认链接方式）：

在编译时，链接器只在可执行文件中记录下所需的库（如 `libc.so`），**不拷贝**库的代码。到==**程序运行时**==，由操作系统的动态链接器（如 `ld-linux.so`）去查找并加载所需的共享库（通常是 `.so` 文件 Linux, `.dll`  Windows）到内存中，并将程序与库函数“连接”起来。
gcc命令编译时末尾位置加上-dynamic
生成的可执行文件**很小**，但它**在运行时必须能找到它依赖的动态库**，否则会启动失败
ldd查看依赖，objdump分析二进制文件。

编译器在链接时，会把**动态库的SONAME**（而不是绝对路径）写入可执行文件的头部。
可以用 `readelf` 命令查看依赖动态库
`readelf -d your_program | grep NEEDED`
动态库的查找是一个由动态链接器主导的、有明确优先级的过程。它首先读取编译时记录在可执行文件中的库名，然后按固定顺序搜索：**优先使用编译时嵌入的`RPATH`或`RUNPATH`路径，接着是运行时环境变量`LD_LIBRARY_PATH`，再然后是系统缓存`/etc/ld.so.cache`，最后回退到`/lib`、`/usr/lib`等标准目录。**

###### 动态库依赖
动态库的查找遵循一个明确的优先级流程，主要基于以下几个路径：
动态库查找遵循四级优先级：

1. **编译时RPATH** → 2. **环境变量LD_LIBRARY_PATH** → 3. **系统缓存/etc/ld.so.cache** → 4. **标准系统路径**
查找过程是短路式的，一旦找到就立即返回。

**第一级**：检查可执行文件内嵌的`RPATH`，链接器会优先尝试这些路径，可以用`readelf -d`查看  
**第二级**：环境变量`LD_LIBRARY_PATH`允许用户在运行时临时指定库路径，用于临时覆盖  
**第三级**：链接器读取系统库缓存`/etc/ld.so.cache`，这是**最常用的查找路径**  这个文件由 `ldconfig` 命令根据 `/etc/ld.so.conf` 配置生成
**第四级**：如果以上都找不到，会回退到标准路径：`/lib`、`/usr/lib`、`/lib64`、`/usr/lib64` 等

有些库还支持 `LD_PRELOAD` 环境变量，可以强制优先加载特定库，常用于调试或函数劫持

| 工具/指令                 | 应用场景与作用                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------- |
| **`ldd <可执行文件>`**     | **诊断依赖**：快速列出该程序运行所需的所有动态库及其系统找到的路径。这是最常用的检查命令。                                               |
| **`readelf -d <文件>`** | **探查内部信息**：查看编译时写入可执行文件内部的动态库信息（如`NEEDED`库名、`RPATH`等），比`ldd`更底层。                              |
| **`LD_LIBRARY_PATH`** | **临时指定路径**：通过`export LD_LIBRARY_PATH=/path:$LD_LIBRARY_PATH`，临时添加一个运行时库搜索路径，常用于开发和调试。         |
| **`ldconfig`**        | **更新系统缓存**：在安装新库到系统目录（如`/usr/local/lib`）后，需要以root身份运行此命令来更新`/etc/ld.so.cache`，使系统能立即找到它。      |
| **`LD_DEBUG=libs`**   | **高级调试**：在程序运行时开启调试输出，**详细展示**链接器搜索库的每一步过程，是解决复杂库依赖问题的终极利器。用法：`LD_DEBUG=libs ./your_program`。 |

## APT
**`A`**`dvanced` **`P`**`ackage `**`T`**`ool`（高级包管理工具）
是Debian/Ubuntu的**软件包管理系统**，相当于：
- Windows的：应用商店/安装程序
- macOS的：Homebrew
- Android的：Google Play
- iOS的：App Store
常用命令
```shell
sudo apt-get update
# 执行后，系统会：
1. 读取 /etc/apt/sources.list 中的软件源地址
2. 连接这些源服务器下载最新的软件包列表信息
3. 更新本地的 /var/lib/apt/lists/ 目录下的索引文件
4. 但不会安装或更新任何实际软件
```

|命令|作用|比喻|
|---|---|---|
|`apt-get update`|**更新软件包列表**|刷新商品目录|
|`apt-get upgrade`|**升级已安装的软件**|更新已安装的APP|
|`apt-get install`|**安装新软件**|安装新APP|
|`apt-get remove`|**卸载软件**|删除APP|
|`apt-cache search`|**搜索软件包**|在商店中搜索|
注意：
update和upgrade：
`update` 是更新本地的软件包索引信息，相当于刷新商品目录；而 `upgrade` 是实际升级已安装的软件到最新版本。通常我们应该先 `update` 再 `upgrade`，确保基于最新的信息进行升级。

安装软件之前最好先update
因为软件源每天都在更新，本地的软件包列表可能已经过时。先 `update` 可以确保
获取到软件的最新版本信息，避免因版本冲突导致的安装失败，确保依赖关系解析的正确性


apt与apt-get
`apt` 是较新的命令行工具，提供了更友好的用户界面和进度显示；`apt-get` 是较旧的底层工具。功能上基本等价，但在脚本中为了兼容性通常还是用 `apt-get`。

## Linux系统

### Linux系统组成
标准架构：Bootloader->Kernel->Rootfs->Application

#### **Bootloader**：
Bootloader 是一段在操作系统内核运行之前执行的小程序。它负责初始化硬件设备、建立内存空间映射，配置好正确的环境，从ROM中加载内核映像到内存，将控制权转交给内核。
Bootloader存储在ROM中。
分为两部分：FSBL和SSBL，first stage 和 second stage
常见类型：
- **U-Boot**：嵌入式 Linux 领域事实上的标准，功能强大，支持多种架构。
- **GRUB**：主要用于 x86 PC 的 Linux 系统。
- **RedBoot**：基于 eCos 的 Bootloader。

**核心工作流程：**

1. **硬件初始化**：初始化 CPU 时钟、SDRAM 控制器、串口等关键硬件。
2. **环境建立**：为操作系统内核设置好运行时环境，尤其是内存布局。
3. **内核加载**：从存储设备（如 eMMC、Flash）将内核映像和设备树文件加载到指定的内存地址。
4. **传递参数**：根据约定，向内核传递启动参数，如内存大小、控制台设备、设备树在内存中的地址。
5. **跳转执行**：跳转到内核的入口地址，将系统的控制权永久移交给内核。

主要关注设备树
##### 设备树
一种描述硬件系统组件和数据结构的语言。它是一个与平台无关的、树状结构的数据文件，用于将系统的硬件配置信息从 Linux 内核源码中分离出来。由Bootloader 传递给内核，内核通过解析它来动态识别系统中的硬件，并加载对应的驱动程序。
主要用于实现**驱动代码与硬件配置的分离**，同一份内核与驱动搭配不同的设备树就可以支持不同的硬件平台。

设备树是节点和属性的简单树结构。属性是键值对,节点可以包含属性和子节点树的节点，描述了linux内核或其他软件系统(如u-boot)用于初始化硬件的参数。
一些优点包括:无需重新编译任何源代码即可轻松更改系统配置、可以轻松添加对新硬件的支持、可以使用include语句重用现有的.dts文件,并可以覆盖以前定义的功能。

设备树源文件扩展名为 **`.dts`** 或 `.dtsi`（包含文件），编译后生成 **`.dtb`** 二进制文件。
设备树配置错误，会导致内核无法识别硬件，当系统无法启动时，通过串口查看Bootloader和内核的打印信息，可以初步判断问题是出在硬件初始化阶段还是内核加载阶段。
设备树的核心结构是 **“节点”** 和 **“属性”，
节点描述一个总线或设备
属性描述该设备的特性，如地址、中断号、兼容性字符串。
可以使用dtc命令，设备树编译器，可以将 .dtb 反编译成可读的 .dts。
#### Kernel：Linux内核
是操作系统核心，硬件和应用程序之间的中间层**。负责管理系统的**进程、内存、设备、文件和网络**等资源。


- **内核空间**：内核运行的特权模式（Ring 0），可以执行任何CPU指令，访问所有内存。
- **用户空间**：应用程序运行的非特权模式（Ring 3），访问资源受限。
- **系统调用**：是用户空间程序**主动**进入内核空间的唯一合法方式。
  
  
- **用户态**：进程正在用户空间运行。
- **内核态**：进程通过系统调用或中断，正在内核空间执行代码。

##### 内核架构
1. **宏内核**
    - **特点**：所有核心功能（进程调度、内存管理、文件系统、设备驱动等）都作为一个**整体**运行在内核空间。
    - **代表**：**Linux**。
    - **优点**：性能高，组件间调用效率高。
    - **缺点**：稳定性差，一个驱动崩溃可能导致整个内核崩溃。
2. **微内核**
    - **特点**：只将最核心的功能（进程通信、调度）放在内核，其他功能作为“服务”运行在用户空间。
    - **代表**：GNU Hurd, `Minix`。
    - **优点**：稳定性高，模块化好，一个服务崩溃不影响内核。
    - **缺点**：性能开销大，因为需要频繁在用户态和内核态间切换。

进程管理
- **进程 vs 线程**：
    
    - 进程：资源分配的**单位**（拥有独立的地址空间）。
        
    - 线程：CPU调度的**单位**（共享进程的地址空间）。
        
    - **Linux线程实现**：通过 `clone()` 系统调用实现，线程被视为“轻量级进程”，与进程一样用 `task_struct` 表示。
        
- **调度器**：
    
    - **CFS**：完全公平调度器，为普通进程设计，基于**虚拟运行时间**进行调度。
        
    - **实时调度策略**：`SCHED_FIFO`（先进先出）, `SCHED_RR`（时间片轮转），优先级高于普通进程。

内存管理
- **虚拟内存**：为每个进程提供独立的、连续的虚拟地址空间。
    
- **分页**：将虚拟内存和物理内存划分为固定大小的页（通常4KB），通过页表进行映射。
    
- **页缓存**：将磁盘文件数据缓存在内存中，减少I/O，**这是Linux性能的关键**。
    
- **伙伴系统**：解决**外部碎片**，负责管理物理页的分配和释放。
    
- **Slab分配器**：解决**内部碎片**，在伙伴系统之上，为内核中小对象（如 `task_struct`）提供快速分配。

文件系统
- **VFS**：虚拟文件系统，为上层的应用程序和底层的具体文件系统（如ext4, XFS, Btrfs）提供统一的抽象接口。
    
- **inode**：索引节点，记录文件的**元数据**（权限、所有者、大小、时间戳、数据块位置等）。**打开文件就是inode被载入内存**。
    
- **dentry**：目录项，记录文件名和inode的映射关系，用于路径查找和目录树缓存。
设备驱动
- **一切皆文件**：设备在 `/dev` 下以文件形式呈现，通过 `open`, `read`, `write`, `ioctl` 等文件操作接口来访问。
    
- **字符设备**：以字节流方式访问，无缓冲（如键盘、鼠标）。
    
- **块设备**：以数据块为单位访问，有缓存（如硬盘、U盘）。
    
- **网络设备**：特殊，不映射到文件，通过套接字接口访问。

网络栈
- 处理网络协议（TCP/IP）的实现。
    
- **套接字**：是网络通信的端点，为应用程序提供网络编程接口。

关键数据结构：
1. **`task_struct`**：**进程描述符**，内核用它来代表一个进程/线程，包含了进程的所有信息（状态、PID、优先级、内存映射、打开文件等）。
    
2. **`mm_struct`**：描述一个进程的**整个虚拟地址空间**。
    
3. **`vm_area_struct`**：描述进程虚拟地址空间中的一段**连续区域**（如代码段、数据段、堆、栈、共享库）。
    
4. **`file`**：代表一个**已打开的文件**。
    
5. **`inode`**：代表文件系统上的一个文件（已打开或未打开）。
    
6. **`dentry`**：代表一个路径的组成部分，用于缓存，加速路径解析。

### 重定向
重定向就是通过操作文件描述符来控制程序的输入输出流。
文件描述符：0(stdin)、1(stdout)、2(stderr)
- `>` 是**双目操作符**，左边是文件描述符（默认1），右边是目标
- 每次 `>` 或 `&>` 只能处理**一个重定向**
- 多个重定向需要分开写
```shell
> /var/log/monitor.log      # 完全等价于
1> /var/log/monitor.log     # 1是默认的，可以省略
```
**Shell是`从左到右`扫描整个命令字符串来解析语法，但在`设置重定向`时，效果是`从右到左`累积的。**

**`>` 的两边可以是：**
- **左边**：文件描述符数字（0,1,2,3...）
- **右边**：
    - **文件名**（如 `/var/log/file`）
    - **文件描述符**（如 `&1`, `&2`）
    - **设备文件**（如 `/dev/null`）


`2>&1`
表示将**标准错误（文件描述符2）重定向到标准输出（文件描述符1）当前指向的地方**。这样做的效果是把程序的正常输出和错误输出合并到同一个流中。强调"当前指向"这个概念

**&** 表示**复制 fd 表项**，不是复制文件名。

`1>&2`
把 **标准输出（fd 1）** 重定向到 **标准错误（fd 2）** 当前指向的文件

1>&2 把 stdout 塞进 stderr，2>&1 把 stderr 塞进 stdout，底层都是 **dup2 原子复制 fd 表项**



**`cmd > log 2>&1` 和 `cmd 2>&1 > log`**
- `cmd > log 2>&1`：先让标准输出指向`log`文件，再把标准错误指向标准输出（此时已经是`log`文件）。结果是**两者都进入log**。
    
- `cmd 2>&1 > log`：先让标准错误指向标准输出（此时是终端屏幕），再让标准输出指向`log`文件。结果是**错误输出还在屏幕，只有标准输出进入log**。"


#### 底层实现
Shell在解析这些符号后，会调用 `dup2()` 系统调用来原子性地完成文件描述符的复制。
比如 `2>&1` 就是 `dup2(1, 2)`，把fd 1指向的文件表项复制给fd 2。
```c
// 以 2>&1 为例：先 1>log，再 2>&1
int fd1 = open("log", O_WRONLY|O_CREAT|O_TRUNC, 0644); // fd=3
dup2(fd1, 1);               // stdout → log
dup2(1, 2);                 // stderr → stdout（当前指向 log）
close(fd1);                 // 关闭多余副本


int main(void)
{
    int logfd = open("app.log", O_WRONLY|O_CREAT|O_TRUNC, 0644);
    if (logfd < 0) exit(1);

    /* 原子实现：2>&1 */
    dup2(logfd, 1);          // 1>app.log
    dup2(1, 2);              // 2>&1（复制 fd=1 到 fd=2）

    close(logfd);            // 关闭多余副本

    printf("stdout message\n");   // 写 app.log
    fprintf(stderr, "stderr message\n"); // 也写 app.log
    return 0;
}
```

注意：
**`&` 有两种完全不同的含义**，取决于它的位置：

- **在重定向中 (`2>&1`)**：`&` 表示 **“文件描述符”** 而不是普通文件。
    
    - `> file`：输出到名为 `file` 的文件
        
    - `> &1`：输出到 **文件描述符1** 指向的地方
        
- **在命令末尾 (`cmd &`)**：`&` 表示 **“在后台运行”**。
    
    - `./program`：在前台运行，占用当前终端
        
    - `./program &`：在**后台运行**，立即返回终端提示符，不阻塞当前终端

### stat 文件查看
`stat` 命令提供了关于一个文件的、来自文件的 `inode` 的完整元数据的具体信息，涵盖了文件大小、物理磁盘占用、权限、所有权以及三个关键的时间戳。
```
  File: ‘file.txt’
  Size: 305 Blocks: 8 IO Block: 4096 regular file
Device: 801h/2049d Inode: 260672 Links: 1
Access: (0644/-rw-r--r--) Uid: ( 1000/ user) Gid: ( 1000/ group)
Access: 2023-10-11 15:30:00.000000000 +0800
Modify: 2023-10-11 15:20:00.000000000 +0800
Change: 2023-10-11 15:25:00.000000000 +0800
 Birth: 2025-11-27 18:35:03.069215931 +0800

```

| 字段                 | 核心含义与作用                                                                                               |
| ------------------ | ----------------------------------------------------------------------------------------------------- |
| **File / Size**    | **文件逻辑大小**：文件内容的实际字节数，是用户最关心的尺寸。                                                                      |
| **Blocks**         | **文件物理占用**：文件在磁盘上实际占用的 512 B 块数。**Size ≠ Blocks*512**，因存在尾部碎片。                                        |
| **IO Block**       | **文件系统块大小**：文件系统读写该文件时使用的基本单位，通常是 4096 字节。                                                            |
| **Device / Inode** | **存储身份标识**：文件存储在哪个设备上及其 inode 编号。**inode 是文件系统的核心元数据**。                                               |
| **Links**          | **硬链接计数**：指向此 inode 的目录条目数量。为 0 时文件数据才被真正删除。                                                          |
| **Access**         | **最后访问时间**：文件内容最后一次被**读取**的时间（例如 `cat`）。                                                              |
| **Modify**         | **最后修改时间**：文件**内容**最后一次被**更改**的时间（例如 `vi` 编辑保存）。                                                      |
| **Change**         | **最后改变时间**：文件**元数据**（如权限、所有者）最后一次被**更改**的时间（例如 `chmod`）。**关键区别：改内容会变 Modify 和 Change，改元数据只变 Change。** |
| **Birth**          | **文件创建时间**                                                                                            |

### free
```shell
$ free
               total        used        free      shared   buff/cache   available
Mem:         8091444     2977084      702572       40224     4411788     4769216
Swap:        8787964           0     8787964
```

| 字段         | 物理内存视角               |                                           |
| ---------- | -------------------- | ----------------------------------------- |
| total      | 总物理内存                | “单板插了多少 RAM？”——看 total                    |
| used       | 已被使用的页               | 包含用户进程+内核数据结构，**不含**完全空闲页                 |
| free       | 完全未使用的页              | 紧急备用，越小不代表越卡（缓存可回收）                       |
| shared     | 多个进程共享的页（tmpfs/shm）  | 嵌入式常为零；若 >0 说明用了 /dev/shm 或共享库            |
| buff/cache | 页缓存 + slab 可回收部分     | “缓存占这么多，系统会卡吗？”——答“不会，available 已算进可回收部分” |
| available  | 估算“无需 swap 即可立即用”的内存 | 内核算法 = free + 大部分缓存；**看可用内存只看这一列**        |
| Swap:total | 交换区总大小               | 嵌入式通常关 swap；若不为 0 说明启用磁盘交换                |
| Swap:used  | 已用交换区                | **≠0 即代表内存曾耗尽过**，性能已下降                    |
available把可回收缓存算进去了，而free 只统计完全未用的页。
free:**完全未使用**,**紧急情况专用**
used - available:**已被使用且不可回收**，用户进程、内核数据结构、页表、驱动缓冲区…
**buff/cache** 的主体：**已被使用但**随时**可回收**，

### ls
```
ls -l
-rwxr-xr-x 1 user group 16432 Oct 11 15:20 my_program
drwxr-xr-x 2 user group 4096 Oct 11 14:00 my_dir
lrwxrwxrwx 1 user group 7 Oct 11 13:00 link_test -> my_program
```

| 列               | 核心含义与作用                                                           |
| --------------- | ----------------------------------------------------------------- |
| **第1列 (权限)**    | **文件类型与权限**：首字符表示类型（`-`：文件，`d`：目录，`l`：链接）。后续9字符为三组权限（属主/属组/其他用户）。 |

| **第6-8列 (时间戳)** | **最后修改时间**：显示的是文件**内容**最后一次被修改的时间（即 `stat` 命令中的 **Modify** 时间）。   |
| **第9列 (文件名)**   | **文件名**：文件或目录的名称。如果是符号链接，会以 `->` 指向目标路径。                          |

### du
du 只显示目录或者文件的磁盘使用情况，不针对整个文件系统
不是文件字节数；能递归、能排除、人类可读

|概念|du 行为|面试易混点|
|:--|:--|:--|
|**block size**|默认 **1024 B** 为单位（`-k` 显式）；空洞文件向上取整|与 `ls -l` 字节数可能差 4 KB|
|**sparse file**|默认按**实际占用块**算；加 `--apparent-size` 才看逻辑字节|“为什么 du < ls 大小？”——稀疏文件|
|**目录本身**|仅统计 **目录项+inode** 时 4 KB；默认**递归子目录**|`stat %s` 只给 inode 块，du 给总和|


| 选项                  | 记忆键         | 作用                               | 嵌入式典型场景            |
| :------------------ | :---------- | :------------------------------- | :----------------- |
| `-s`                | **s**ummary | 只给目录总计，不展开子目录                    | 快速看 `/var/log` 总占用 |
| `-h`                | **h**uman   | 自动 K/M/G 单位                      | 更方便读               |
| `-b`                | **b**ytes   | 以字节为单位（等价 `--apparent-size -B1`） | 脚本算比例              |
| `--apparent-size`   | 逻辑大小        | 忽略空洞，与 ls 字节一致                   | 检测稀疏日志             |
| `--max-depth=N`     | 深度裁剪        | 只看 N 层子目录                        | 定位哪一级日志爆炸          |
| `--exclude=PATTERN` | 排除          | 跳过 `*.tmp`、`*core*`              | 量产镜像瘦身             |

#### du ls stat区别
du 按块算，不含空洞时比 ls 小；加 `--apparent-size` 后与 ls 字节一致。
`-sh` 快速看总大小，`--apparent-size` 对比逻辑字节，`-exclude` 和 `--max-depth` 定位哪级目录爆炸，

| 命令      | 统计粒度          | 是否含空洞                     | 典型用途       |
| ------- | ------------- | ------------------------- | ---------- |
| `du`    | **块**         | 默认不含（可 `--apparent-size`） | 看“磁盘吃了多少”  |
| `ls -l` | **字节**        | 含空洞                       | 看“文件逻辑大小”  |
| `stat`  | **inode 元数据** | 仅 inode 块                 | 看权限/时间/设备号 |

### ip
`ip a` 命令展示了系统所有的网络接口。典型的输出包括：

1. **`lo`**：环回接口，用于本机内部通信，地址是 `127.0.0.1`。
    
2. **`ens33`/`eth0`**：物理以太网卡，拥有局域网的IP地址（如 `192.168.x.x`），是系统访问外部网络的主要通道。
    
3. **`virbr0`**：由libvirt创建的虚拟网桥，为KVM虚拟机提供网络连接，当没有虚拟机运行时，它会显示 `NO-CARRIER`。
    
4. **`docker0`**：由Docker创建的虚拟网桥，是Docker容器的默认网络网关，没有容器运行时同样显示 `DOWN`。
    

最常用的是物理网卡（如 `ens33`），因为它连接着真实的网络。而虚拟网桥只有在相应的虚拟化技术（KVM/Docker）被使用时才会激活。

### ps查看进程
- **ps** = Process Status (进程状态)
    
- **a** = all users (所有用户的进程)

- **R (Running)**：运行中或可运行

- **Z (Zombie)**：僵尸进程（已终止但未被父进程回收）

pstree（树状结构显示进程关系）结尾加-p就是带PID

### 文件权限
通过 ls -l查看文件权限
```shell
-rw-r--r-- 1 user group 1234 Jan 1 12:34 filename
```

    - `o`：其他用户
    - `a`：所有用户（等同于 `ugo`）
- **operator**：
    - `+`：添加权限
    - `-`：移除权限
    - `=`：设置权限
- **permission**：
    - `r`：读权限
    - `w`：写权限
    - `x`：执行权限

## 工具

### **读图工具：`readelf` / `objdump`**
查看编译出的程序二进制文件，它的各个段（section）到底有多大，理想布局是什么样。

```
readelf -S your_program    # 查看所有段头信息，了解.text, .data, .bss的大小
size your_program          # 快速查看程序文本、数据、bss段的总大小
```

### **运行时诊断工具：`gdb` / `core dump`**
程序崩溃后，用gdb加载核心转储文件，通过`bt`命令查看调用栈，理解崩溃时栈的状态。
```
gdb your_program core      # 调试核心转储
(gdb) bt                   # 查看崩溃时的栈回溯
```

### **内存分析工具：`valgrind` / `mtrace`**
检测内存泄漏、越界访问。虽然在目标板上运行可能性能开销大，但在交叉编译后的仿真环境中极有价值。
`valgrind`是一个工具集，最常用的是内存监测工具`memcheck`，
需要下载
```shell
# 最基本用法
valgrind --leak-check=full ./your_program

# 如果程序需要参数
valgrind --leak-check=full ./your_program arg1 arg2
```
- `--leak-check=full`：详细显示每个泄漏的位置。
    
- `--show-leak-kinds=all`：显示所有类型的泄漏（明确的、间接的等）。
    
- `--track-origins=yes`：追踪未初始化值的来源，对检测未初始化内存问题非常有用。
    
- `--log-file=valgrind.log`：将输出重定向到文件。

也可以使用`-fsanitize=address`选项在编译的时候加上，编译成功之后就可以直接运行，运行结束会和valgrind一样出现结果
```shell
aarch64-linux-gnu-gcc -g -fsanitize=address -fno-omit-frame-pointer \
    main.c thread_pool.c -o app
```

`mtrace`是glibc自带的一种简单内存泄漏检测机制。它的原理是记录所有的 `malloc` 和 `free` 操作，然后检查是否匹配。

1.在代码里穿插追踪函数，
2.运行程序前，设置 `MALLOC_TRACE` 环境变量，指定日志文件路径。
```shell
export MALLOC_TRACE=./mtrace.log
./your_program
```
3.分析
```shell
mtrace ./your_program $MALLOC_TRACE
```

### perf
`perf stat ./your_program`
- **`task-clock (msec)`**：程序真正消耗的CPU时间。如果这个值远小于 `seconds elapsed`（墙上的钟表时间），说明大量时间花在了等待I/O或被其他进程抢占了。
    
- **`context-switches`**：上下文切换次数。如果这个数字巨大，说明程序可能因为系统调用或锁竞争，被频繁地挂起/唤醒。
    
- **`cache-misses`**：缓存未命中数。这是嵌入式程序最常见的性能杀手！如果这个比例很高，说明数据访问模式不友好，CPU经常在空等内存。
```text
61.82 msec task-clock:u     # 实际CPU时间很少
33.57 seconds time elapsed  # 总运行时间长
0.32 insn per cycle         # 指令效率较低（但没关系）
```
- IPC（每周期指令数）：理想值0.8-1.2，低于0.5表示效率低下
    
- 分支预测失败率：正常应＜5%，超过10%需优化分支逻辑
    
- 任务时钟vs实际时间：差距大说明程序存在大量I/O等待或睡眠




1.采样`perf record -g ./your_program`
- `-g` 选项至关重要，它会记录调用图信息，这能看到完整的函数调用链。
2.生成报告
`perf report`
第一行：
- **Children**：该函数及其**调用的所有子函数**的CPU时间占比
    
- **Self**：该函数**自身**（不含子函数）的CPU时间占比
    
- **Command**：进程名
    
- **Shared Object**：所属的库或可执行文件
    
- **Symbol**：函数名
最后一列：
1. **`_start`
    
    - 程序的**入口点**，由操作系统调用
        
    - 设置初始环境，然后调用 `__libc_start_main`
        
2. **`__libc_start_main@@GLIBC_2.34` 
    
    - C库的启动函数，初始化标准I/O、环境变量等
        
    - 然后调用 `__libc_start_call_main`
        
3. **`__libc_start_call_main` 
    
    - 实际调用你的 `main` 函数
        
    - 处理main的返回值和退出
        
4. **`main` 
    
    - 主函数
- 这是调用关系的体现：A调用B，B调用C，所以时间会"累积"到调用链顶端
    
- 实际消耗时间的是它们调用的子函数



- **第一列 `Overhead`**：这是**最重要的指标**！它直观地说明每个函数在总采样中所占的**百分比**排在第一位的，就是头号优化目标。
    
- **展开调用链**：按**回车键**可以展开一个函数的调用链。这能让你看到是这个函数本身耗时，还是它调用的子函数耗时。
    
- **注解汇编代码**：
    
    1. 在 `perf report` 界面中，用方向键选中函数。
        
    2. 按 **`a`** 键。
        
    3. **效果**：`perf` 会**将源代码（或汇编指令）与采样事件并排显示**，直接在代码行级别说明每条指令的开销占比


### `strace`
`strace` 是 Linux 系统下强大的诊断和调试工具，用于追踪程序执行期间的系统调用(system calls)和接收到的信号(signals)。系统调用是应用程序与操作系统内核交互的接口，通过 `strace` 可以深入了解程序的底层行为。

`strace` 适用于以下场景：
- 调试程序异常行为
- 分析程序性能瓶颈
- 理解程序如何与操作系统交互
- 诊断权限相关问题
- 排查文件/网络访问问题

```shell
strace [选项] 命令 [命令参数]

```
常用选项参数

| 选项              | 说明                |
| --------------- | ----------------- |
| `-c`            | 统计系统调用次数和时间       |
| `-f`            | 跟踪子进程             |
| `-e trace=系统调用` | 只跟踪特定系统调用         |
| `-o 文件`         | 将输出写入文件           |
| `-p PID`        | 附加到正在运行的进程        |
| `-t`            | 显示时间戳             |
| `-T`            | 显示系统调用耗时          |
| `-s 大小`         | 设置字符串最大显示长度(默认32) |
| `-v`            | 显示更详细的信息          |
