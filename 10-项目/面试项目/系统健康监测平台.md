 项目实现：项目实际上实现的是几个常见工具的部分功能比如top，free，还实现了日志功能，top是系统级和进程级别的工具，我实现的这个项目更偏向于对系统的监测，对系统层次的相关数据进行采集和处理，判断当前系统的一个健康程度

这个项目主要是由于在我刚开始接触Linux系统的时候想查看程序，cpu，系统的状态，就了解到了top和htop指令，使用之后就萌发了想要自己实现简单的top指令的想法
一开始就只是采集系统的关键指标输出到终端，后续才不断改善添加了新的功能。
项目整体的架构是基于线程池和异步循环队列的设计，在主线程采集数据之后增添任务到任务队列里，创建的工作线程就会取出任务进行任务处理，整体数据流就是采集，然后日志和网络异步输出。

采集主要是对/proc和/sys里的文件进行访问采集，这两个文件都是动态生成的。而/proc是虚拟文件系统，不占用磁盘空间

日志主要实现的是在采集完之后，对数据结构体进行等级判定并输出一条日志到日志文件，判断文件需不需要轮转保证文件大小不超过阈值，然后实现日志文件的逆序打印

客户端主要是在采集完成后由线程池创建HTTP发送任务，通过cJSON库的API函数构建JSON字符串用于发送HTTP信息到服务器

服务器则基于epoll实现的简易的HTTP服务器，通过socket-bind-listen创建监听套接字，并转变成epoll事件加入到epoll的监听队列里，选用的是水平触发模式，然后创建epoll的事件数组，进入while循环，调用epoll_wait持续监听，然后对应判断当前socket套接字是需要accept还是处理客户端请求。

线程池则是先初始化线程池，我采用的是链式的环形队列，这样更方便修改任务队列的长度，然后在主函数对应创建任务加入任务队列，由工作线程组进行任务处理。

## 数据采集
/proc是Linux内核提供的虚拟文件系统，包含了系统运行时的各种信息，访问简单高效，不需要安装额外依赖，非常适合嵌入式环境。

- **CPU使用率**：通过两次采样`/proc/stat`，用差值算法计算真实利用率
- **系统负载**：直接读取`/proc/loadavg`第一项（1分钟平均负载）
- **内存信息**：解析`/proc/meminfo`中的MemAvailable字段
- **CPU温度**：从`/sys/class/thermal`虚拟文件系统读取

### CPU使用率
**核心**：`/proc/stat`是系统启动以来累计值，用差值计算得出真实瞬时使用率。
这里的时间片的单位是`jiffies`即内核的时间单位，取决于系统的HZ值（定时器中断频率，相当于软件时钟，反映内核调度和统计的节奏），为HZ值的倒数

实现：
先在main函数的循环之前进行第一次的cpu时间片的基准采集（记录总时间片和总空闲时间片），因为需要差值计算得到使用率，然后在采集函数里再次采集然后与上一次的作差，通过计算得到最后cpu使用率

头文件实现：在头文件里定义关于cpu时间片的结构体变量，里面有两个成员total_time和idle_time，用这个结构体数据类型在全局结构体里定义prev_time和curr_time用于计算差值

读取函数实现：打开/proc/stat文件，一次性读取到buffer里，缓冲区设置成512字节，当然缓冲区最后一位会设置成'\0'防止溢出读取失败，通过strstr函数在buffer里找"cpu “行，其实就是第一行，但如果后续想看具体哪一个核就可以改，注意比较字符串最后的是空格，因为strstr是严格按照每一位字符寻找的，当然也可以直接fgets读一行。我的开发板是4核的，下面就是cpu0到cpu3，第一行是总和，然后如果strstr查找成功就声明cpu时间片的对应的变量，我这里考虑到最后两个时间片的使用很少很少就没有记录，然后用sscanf格式化输入，计算输出我需要的总时间和空闲时间到处理函数


**CPU使用率 = (所有时间 - idle - iowait) / 所有时间**
```
// 关键公式
总时间差 = curr.total_time - prev.total_time;
空闲时间差 = curr.idle_time - prev.idle_time;  
CPU使用率 = (1 - 空闲时间差/总时间差) × 100%

```

**nice时间**：统计优先级较低（nice值>0）进程的用户态运行时间，反映系统如何调度低优先级任务
```text
-20 (最高优先级) 到 19 (最低优先级)
普通用户只能调高nice值(0→19)，root可以调低(-20→19)
```

Linux中nice值从-20到19影响的是普通进程的权重分配。在CFS调度器下，不是给高优先级进程更多的时间片，而是通过虚拟运行时间来保证公平性——高优先级进程的实际运行时间会被'打折'计算，这样调度器就会更频繁地选择它运行。

#### top与stat
**`/proc/stat` 提供的是系统级、累积的CPU时间分布，而 `top` 提供的是实时、进程级的CPU使用情况。它们互为补充，共同构成完整的性能监控体系。**
**`top` 命令本身就是通过读取 `/proc/stat` 和 `/proc/[pid]/stat` 来生成显示的。**
top中的CPU使用率也是用的差值计算，但它对每一个字段的时间差分别做了统计，最后处理得到了8个对应的cpu占用率，而我则是更关注cpu的非空闲率，也就是具体的使用率

注意：
1. **时间间隔**：通常 1-3 秒间隔，太短会不准确，太长会不实时
2. **差值计算**：使用无符号长整型避免溢出

### 可用内存
在`/proc/meminfo`中用`strstr`快速定位`MemAvailable`行。  
**直接来源：**  
MemAvailable数据直接来源于`/proc/meminfo`，直接读取这个虚拟文件获取该值。
**内核计算原理：**  
MemAvailable是估算值，计算逻辑是：MemFree + 可回收的页面缓存(Active/Inactive file) + 可回收slab缓存(SReclaimable) - 水位线保护值。它比简单的free + buff/cache更准确，反映了系统真实的可用内存余量。
**设计哲学：**  
Linux内存管理的核心是“不用白不用”——内核会充分利用空闲内存做磁盘缓存提升性能。MemAvailable指标的出现，正是为了纠正“只看free内存”的认知误区，为系统管理员提供真正有参考价值的“安全水位”指示。

free命令的一部分,free就是解析的`/proc/meminfo`文件
[[Linux基础与开发环境#free]]

**Swap** 是一块**磁盘空间**，当**物理内存（RAM）不够用**时，Linux 内核会把内存中暂时不用的数据“换出”到这块磁盘空间，从而释放出物理内存给急需的程序使用。当程序再次需要那些数据时，内核再把它们从 Swap “换入”到内存。 ^a288aa
- **`free` 命令的 `available` 列**：其数据**直接来源于** `/proc/meminfo` 中的 `MemAvailable` 字段。
- **它是内存的“应急后备仓库”，但访问速度比物理内存慢成千上万倍**。
- **工作时机**：不是物理内存用完才开始用，内核有预判机制，会提前将一些不活跃的页面换出，以保持物理内存的空闲余量。
- **MemTotal**: 总物理内存
- **MemFree**: 完全未使用的内存
- **MemAvailable**: **真正可用的内存**（包含可回收的缓存）
- **Buffers**: 块设备缓存
- **Cached**: 页面缓存
- **SwapCached**: 交换区缓存

### 系统负载
系统负载表示系统中**可运行**和**不可中断**状态进程的平均数量，而CPU使用率是CPU忙碌时间的百分比。
top指令显示的是文件里的三个浮点数，我这里显示第一个，当然这个文件后面还有当前运行进程数和总进程数，最后的是最近运行进程的pid

读取`/proc/loadavg`第一个值（1分钟平均负载）。
1分钟，5分钟，15分钟 系统平均负载，   当前运行进程数/总进程数  最近运行进程的PID

正确处理字符串解析，确保`sscanf`准确匹配浮点数。
- **负载 < CPU 核心数**：系统较空闲。
- **负载 ≈ CPU 核心数**：系统满负荷
- **负载 > CPU 核心数**：系统过载，有进程在等待

**负载计算原理**：统计处于以下状态的进程数：
- **R (Running/Runnable)**：正在运行或等待运行的进程
- **D (Uninterruptible Sleep)**：不可中断睡眠的进程（通常是等待I/O）
内核每5秒采样一次，然后用指数衰减公式计算移动平均

高负载直接影响：
- **程序响应时间**：进程需要排队等待调度
- **吞吐量**：系统处理能力下降
- **用户体验**：交互式应用卡
"系统负载的统计是在Linux内核调度器中实现的：
每次时钟中断都会采样，记录所有CPU运行队列中的R状态和D状态进程数  
用指数衰减算移动平均，每5秒更新一次  

- **CPU使用率**：衡量 **CPU 时间的繁忙程度**（“干活的时间占比”）
- **系统负载**：衡量 **系统任务队列的长度**（“排队等待的任务数”）
Linux 通过内核计算一个**指数衰减移动平均**值，来平滑瞬时队列长度的峰值。我们通过 `cat /proc/loadavg` 或 `uptime` 命令查看：
```
$ uptime
 16:30:00 up 10 days,  1:00,  1 user,  load average: 1.20, 0.80, 0.50
```

若epoll事件结构体数组有事件，则分别进行处理

如果是其他方法就直接响应。

服务器对客户端的响应：检查状态码是否是200，对应构建响应的正确错误状态，构建响应格式的字符串然后`send(fd, header, len, MSG_NOSIGNAL);`
`MSG_NOSIGNAL`防止在连接断开时触发 SIGPIPE 信号，让 send 返回 EPIPE 错误而不是终止进程。

- 每个子网是一个**广播域**，设备在同一个子网内可以通过**ARP协议**发现对方的MAC地址，直接通信。
- 如果两个设备**不在同一个子网**，它们会认为对方在“远程网络”，**不会尝试直接发ARP请求**，而是**把数据包发给默认网关（路由器）**，由路由器转发。
HTTP是基于TCP的，TCP又依赖IP层。IP层不通，TCP就建立不了连接，HTTP自然失败。

**“为什么每 1MB 就要 `fclose→fopen`？句柄抖动的代价你量化过吗？”**

|现问题|现象|10 行修复|
|:--|:--|:--|

```c
static int log_rotate(void) {
    fflush(log_fp);
    long size = ftell(log_fp);
    if (size < LOG_ROTATE_SIZE) return 1;

    // 原地快速清空，不关闭文件
    if (ftruncate(fileno(log_fp), 0) == 0) {
        rewind(log_fp);
        return 1;
    }
    // 失败再回退到旧逻辑
    ... /* 你原来的 rename 逻辑 */
}
```

**“tail 用 `popen` 起新进程，云原生场景能接受吗？”**

|现问题|现象|10 行修复|
|:--|:--|:--|
|`popen("tail")`|fork+exec 20 ms，内存暴涨 2 MB|直接 mmap 文件，**倒序找换行符**，零拷贝、零进程|

```c
void log_print_recent(int lines) {
    if (!log_fp) return;
    fflush(log_fp);
    int fd = fileno(log_fp);
    off_t size = lseek(fd, 0, SEEK_END);
    if (size <= 0) return;

    char *map = mmap(NULL, size, PROT_READ, MAP_SHARED, fd, 0);
    if (map == MAP_FAILED) return;

    int cnt = 0;
    for (off_t i = size - 1; i >= 0 && cnt < lines; --i) {
        if (map[i] == '\n') ++cnt;
    }
    off_t start = (cnt == lines) ? i + 1 : 0;
    fwrite(map + start, 1, size - start, stdout);
    munmap(map, size);
}
```

> commit 消息：`feat: zero-copy tail, no fork/execl`
