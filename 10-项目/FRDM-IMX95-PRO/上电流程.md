# FRDM-IMX95-PRO 上电流程

看两个串口，**同时开**，参数 115200-8-N-1。COM 号不固定，按输出内容认。

| 标记 | 串口 | 谁在输出 | 什么时候有字 |
|---|---|---|---|
| **[COM19]** | M33 | DDR 固件、System Manager | 最先 |
| **[COM17]** | A55 | SPL、BL31、U-Boot、Linux | 晚几秒，一直到登录提示符 |

---

## 总结

按下电源后，PMIC 先按顺序建立各路电压并释放复位，**但上电瞬间只有 AON 域有电**——它的电源轨 VAON 是常开的，而供 A55 的 VDD_ARM 要等之后才打开，所以整个 SoC 里**只有 AON 域里的 Cortex-M33 能执行**。M33 复位后从片内 Boot ROM 取第一条指令，由 Boot ROM 读启动模式引脚选定启动设备、启动 ELE 做签名校验，然后按启动容器里写死的装载地址和入口地址，把固件逐个装进内存并运行：先是 DDR 训练固件（OEI）把主内存准备好，再是 System Manager（SM）把资源隔离规则写进硬件、按顺序放开其它核。**A55 被放开后按 SPL → BL31 → U-Boot → Linux 接力启动**：SPL 读下一级镜像，BL31 在最高异常级 EL3 建好安全环境并决定 U-Boot 的异常级，U-Boot 做板级初始化、把内核和设备树读进内存，最后 Linux 接管 A55、用 PSCI 把其余 5 个核叫醒，启动 systemd 并给出登录提示符。

全过程不需要人工干预，只有 U-Boot 阶段留了 2 秒可以中断。

---

## 具体阶段

每个阶段先给"屏幕上看到什么"，再讲"这一步在做什么"，最后列**来源**——本项目自己的配置、源码或实机日志，用来佐证前面的说法。

### 阶段 1 · 硬件上电

**屏幕上看到**：两个串口都没有任何输出。

**这一步在做什么**：

PMIC 按 i.MX95 要求的顺序逐路建立电压，然后释放复位信号。板上的电源方案是 **PF09（PPF0900AMBA1ES）加两片 PF5301/PF5302**，六路主要电源轨：

| 电源轨         | 电压          | 谁供       | 供什么                   |
| ----------- | ----------- | -------- | --------------------- |
| **VAON**    | 1.8 V       | PF09     | **常开电源，供低功耗域和 RTC 域** |
| VDD_SOC     | 0.61–0.95 V | PF5302   | SoC 核心逻辑              |
| **VDD_ARM** | 0.76–1.05 V | PF5301   | **Arm Cortex-A55 内核** |
| VDD_1V8     | 1.8 V       | PF09 LDO | IO 和外设域               |

**VAON 和 VDD_ARM 是两条不同的轨**：前者上电就有电，后者要等 SM 建立。这就是"上电后只有 M33 能跑"的原因——AON 域由 VAON 供，A55 由 VDD_ARM 供。

手动复位走的是另一条路：按 K1 会在 PF09 的 FCCU1 引脚上产生下降沿，PMIC 据此执行整板冷复位，**但 NVCC_BBSM_1P8 这一路不断电**，因为它供的是 BBNSM（RTC 与部分电源状态）。所以冷复位不丢时间，断电才丢。

**来源**：

| 证据 | 位置 | 说明 |
|---|---|---|
| 六路电源轨表 | `UM12527` §2.2 Table 6 | 官方资料明确说明。VAON 一行原文是 "Always-on supply for low-power and RTC domains" |
| K1 复位链路与 NVCC_BBSM_1P8 | `UM12527` Table 4 | 官方资料明确说明 |
| AON 是常开域 | `imx-sm/devices/MIMX95/sm/dev_sm_power.h:72`：`#define DEV_SM_PD_AON PWR_MIX_SLICE_IDX_AON /*!< 1: Always-on domain */` | 源码可以确认 |
| AON "不可切换"的实现 | `imx-sm/devices/MIMX95/drivers/fsl_power.c`：AON slice 的 `.flags = 0U`，其它 mix 是 `PWR_MIX_FLAG_SWITCHABLE` | 源码可以确认 |
| A55 的 ARM 电压是后来建立的 | `mx95frdm-pro.cfg` 的 A55 启动序列第一步是 `VOLT_ARM start=1` | 源码可以确认，旁证 |

**更深一层（知道有就行）**：PMIC 内部的上下电时序表、BBNSM 的后备电池切换逻辑、各路电压的斜率要求。

### 阶段 2 · Boot ROM

**屏幕上看到**：COM19 仍然没有输出。

**这一步在做什么**：

M33 复位后，硬件把 PC 指向片内 Boot ROM 的复位入口。**这是硬件行为，不是软件跳转。** Boot ROM 是一段用掩膜工艺固化的代码，**改不了**，它做四件事：

**① 读启动模式引脚。** 板子上的 4 根 BOOT_MODE 引脚接在 SW4 拨码开关上，Boot ROM 采样它们的电平决定去哪个设备找启动容器：

| SW4[1:4] | 启动设备                  |
| -------- | --------------------- |
| `x010`   | uSDHC1 8-bit eMMC（默认） |
| `x011`   | uSDHC2 4-bit SD       |
| `x001`   | USB 串行下载              |
| `x100`   | FlexSPI Serial NOR    |

读引脚是 ROM 代码在做，引脚本身只是拨码开关的静态电平。而且**只在复位瞬间采样一次**，改了拨码必须重新上电。

**② 启动 ELE。** ELE 是 SoC 内部一个独立的安全子系统，有自己的核和 ROM。**启动容器里的第一个部件就是 ELE 的固件**，Boot ROM 把它交给 ELE 运行，之后由 ELE 对容器里其余镜像做 AHAB 签名校验，校验通过才继续。

**③ 按容器描述装载镜像。** 容器里每个镜像描述都带：类型、核心编号、装载地址、入口地址、大小、SHA384 哈希。**所以"谁装到哪"是容器里写死的字段，不是约定。**

**④ 把控制权交出去。** 给 SM 的那段跳转代码是这样的：

```asm
/* Load PC and SP */
ldr r0, =0x1FFC0000
ldr r13, [r0, #0]      ; SP ← 0x1FFC0000 处第 1 个字
ldr r1,  [r0, #4]      ; PC ← 0x1FFC0004 处第 2 个字
bx  r1
```

也就是把 `0x1FFC0000` 当作 Cortex-M 的向量表来读，取栈顶和复位入口后跳过去。**为什么用这种"约定地址 + 读向量表"的方式**：ROM 和 SM 是分别编译的两段固件，ROM 是掩膜的、改不了，两者之间没有共同的调用约定，也不能靠链接器解析符号，只能约定一个地址、各自按同一格式解释。

除跳转外，Boot ROM 还在固定地址留了两张信息表给 SM 读：

| 结构 | 地址 | 魔数（tag） |
|---|---|---|
| Handover | `0x2003DC00` | `0xC0FFEE16` |
| Passover | `0x2003DE00` | 同族 tag |

魔数用来确认"这块内存确实是上一级留给我的"，而不是读到的随机数据。

### 阶段 3 · DDR 训练

**屏幕上看到**（COM19 的第一行字）：

```text
DDR OEI: (Build 193, Commit fa9e9a29, Mar 10 2026 10:11:00)

DDR OEI: SOC MIMX95(B0), Board mx95lp5
DDR OEI: IMEM + DMEM load in 2388 us
DDR OEI: Quickboot FW run complete in 1038 us
DDR OEI: ACSM SRAM restore in 217 us
DDR OEI: done, err = 0
```

**这一步在做什么**：

OEI 固件初始化并**训练 LPDDR5**。

为什么需要训练：DDR 上电后时序参数是不确定的——芯片和内存颗粒之间的走线长度每块板不同，温度和电压会影响信号完整性，颗粒出厂给的是典型值而不是**这一块板子**的实测值。所以必须写入一组已知的测试图案、再读回来比对，反复调整延迟参数直到读写稳定。

**训练不通过，后面所有代码都没有可用的主内存**，所以这一步失败整个启动就到此为止。判据只有一条：`err = 0`。

**为什么 OEI 要先跑**：DDR 训练之前只有 M33 的片内 TCM 可用，容量小；SM 自己也跑在内存里，所以必须先有主内存。

**来源**：

| 证据 | 位置 | 说明 |
|---|---|---|
| OEI 是容器里的镜像 | `imx-mkimage/iMX95/soc.mak`：`OEI_M33_LOAD_ADDR ?= 0x1ffc0000` | 源码可以确认 |
| **入口地址那个 `+1`** | 同上：`OEI_M33_ENTR_ADDR ?= 0x1ffc0001`，注释原文 `# = real entry address (0x1ffc0000) + 1` | 源码可以确认。这是 Cortex-M 的约定，入口地址最低位表示 Thumb 状态 |
| OEI 和 SM 都装到 `0x1FFC0000` | 容器解析报告 `build/pro-gpio/flash-m7-gpio.parse.txt`：OEI `@ load 0x1FFC0000, entry 0x1FFC0001`；SM `@ load 0x1FFC0000, entry 0x1FFC0000` | 实机验证得到 |
| 两者在容器里靠偏移排开 | 同上：OEI 在 `0x22C00`，中间 64 KB 保留区，SM 在 `0x82000` | 实机验证得到 |
| 训练结果 | 实机 COM19 日志 `DDR OEI: done, err = 0` | 实机验证得到 |
| 容量在 U-Boot 阶段被报出 | 实机 COM17 日志 `DRAM: 15.8 GiB` | 实机验证得到。U-Boot 只是读结果，不负责训练 |

> `待验证`：OEI 和 SM 的装载地址都写作 `0x1FFC0000`，是"先后复用同一段内存"还是"报告里地址字段含义有差别"，没有找到官方说明。从启动顺序看应该是前者，但没有直接证据。

**更深一层（知道有就行）**：训练的具体项目（写均衡、读均衡、门训练、命令地址训练）各自的算法、LPDDR5 的时序参数表、Quickboot 的加速原理。

### 阶段 4 · System Manager

**屏幕上看到**：

```text
Hello from SM (Build 819, Commit c450f539, Mar 10 2026 10:11:02)

Press key to enter monitor mode.
```

**这一步在做什么**：

SM 启动后按顺序做四件事：

1. **武装看门狗。** 这是 SM 执行的第一条有实质意义的操作，用的是 AON 域的 32.768 kHz 低功耗时钟——它复位后立刻可用，不依赖任何后续初始化。SM 要在自己还没初始化完的这段危险期里有个兜底：初始化卡死就硬件复位重来。
2. **写 TRDC/RDC 隔离规则。** 把"哪个核能用哪些外设和内存"写进硬件。**这件事必须在任何其它核启动之前完成**，因为规则一旦定好，后面的核一睁眼就在被限制好的环境里；反过来的话，核会先用上即将被收走的资源。
3. **按启动顺序表放开 M7 和 A55。**
4. **进入服务模式**，长期响应 SCMI 请求。

`Press key to enter monitor mode.` 是 SM 调试监视器的入口，正常启动不要按键。

**来源**：

| 证据 | 位置 | 说明 |
|---|---|---|
| SM 复位后第一件事是配看门狗 | `imx-sm/devices/MIMX95/gcc/startup_MIMX95_cm33.S:439` 起：`_WDOGBASE = 0x442E0000`（WDOG2），写解锁键 `0xD928C520`，`TOVAL = 32768`（1000 ms × 32768 Hz），`WDOGCS = 0x21E2` | 源码可以确认 |
| WDOG2 确实归 SM | `mx95frdm-pro.cfg`：`WDOG1 OWNER` / `WDOG2 OWNER` 在 LM0(SM) 段 | 源码可以确认。与上一行互相印证 |
| 必须先写隔离再放核 | `arch.md` 原文："loading their configuration **before starting any other cores**" | 官方资料明确说明 |
| TRDC 配置怎么写进去 | `devices/MIMX95/sm/dev_sm_rdc.c:97-190`：先 `ELE_RdcRelease()` 向 ELE 申请所有权，再 `CONFIG_Load()` 直接写 TRDC 寄存器 | 源码可以确认 |
| 启动顺序 | `mx95frdm-pro.cfg`：`LM0 SM boot=1`、`LM1 M7 boot=2`、`LM2 AP boot=3` | 源码可以确认 |
| 固件版本 | 实机 COM19 `Build 819`，与 U-Boot 打印的 `SM firmware Build 819` 一致 | 实机验证得到 |

**更深一层（知道有就行）**：TRDC 的寄存器布局与域格式（DFMT）、看门狗的窗口模式、SM 的 SCMI 协议栈实现。

### 阶段 5 · SPL

**屏幕上看到**（COM17 的第一行字）：

```text
U-Boot SPL 2025.04-g99518e6b6f20 (Feb 02 2026 - 05:52:54 +0000)
SYS Boot reason: por, origin: -1, errid: -1
Normal Boot
Trying to boot from MMC1
Boot stage: Primary
Image set: 0, offset: 0x8000
```

**这一步在做什么**：

SPL 是 A55 上跑的第一段可见代码。它初始化串口（所以从这行开始 COM17 才有输出），然后从启动设备读下一级镜像。

`Trying to boot from MMC1` 里的 MMC1 是 eMMC——本板 `mmc 0` 是 eMMC，`mmc 1` 是 SD。`Boot stage: Primary` 说明用的是主镜像区而不是备份区。

### 阶段 6 · BL31（ATF）

**屏幕上看到**：

```text
NOTICE:  BL31: v2.12.0(release):lf-6.18.2-1.0.0
NOTICE:  BL31: Built : 07:53:18, Feb 10 2026
```

**这一步在做什么**：

BL31 是 ARM Trusted Firmware，跑在 A55 的最高异常级 **EL3**。它在这一步做四件事：

1. 注册串口控制台（就是这两行 `NOTICE`）
2. 把 GPIO2~5 划给非安全世界，建 MMU 页表
3. 建立 SCMI 通信通道
4. **决定 U-Boot 跑在哪个异常级**：读 A55 的能力寄存器，实现了 EL2 就用 EL2，否则退回 EL1

**BL31 常驻不退场**，是唯一一段启动完还留在原地的固件，之后长期在 EL3 提供 PSCI 服务。

**来源**：

| 证据 | 位置 | 说明 |
|---|---|---|
| BL31 直接在 EL3 运行 | `tools/imx-atf-source/plat/imx/imx9/imx95/platform.mk`：`RESET_TO_BL31 := 1` | 源码可以确认。说明不需要 BL1/BL2 两级 |
| 决定 U-Boot 异常级 | `plat/imx/imx9/imx95/imx95_bl31_setup.c:51-65`：读 `ID_AA64PFR0_EL1`，`mode = (el_status) ? MODE_EL2 : MODE_EL1` | 源码可以确认。A55 有 EL2，所以 U-Boot 在 EL2 |
| BL31 把 GPIO2~5 划给非安全世界 | 同上 `bl31_plat_arch_setup()`，109–146 行 | 源码可以确认。**这是项目里 M7 读 GPIO 得 0 的根因** |
| 冷启动只放一个核 | `platform.mk`：`COLD_BOOT_SINGLE_CPU := 1` | 源码可以确认 |
| U-Boot 入口地址 | `imx95_bl31_setup.c` 填 `bl33_image_ep_info.pc = PLAT_NS_IMAGE_OFFSET`，值为 `0x90200000` | 源码可以确认 |

**更深一层（知道有就行）**：ATF 的 BL 阶段编号体系、异常级切换的汇编细节、PSCI 状态机。

### 阶段 7 · U-Boot

**屏幕上看到**：

```text
U-Boot 2025.04-g99518e6b6f20 (Feb 02 2026 - 05:52:54 +0000)

CPU:   i.MX9596 rev2.0 at 1800MHz
Model: NXP FRDM-IMX95-PRO board
DRAM:  15.8 GiB
Loading Environment from MMC... *** Warning - bad CRC, using default environment
...
Scanning for bootflows in all bootdevs
Running BSP bootcmd ...
...
Hit any key to stop autoboot:  2  1  0
```

**这一步在做什么**：

U-Boot 跑在 EL2，做板级识别和初始化：报芯片型号、主频、板型、内存容量，读环境变量，扫描启动设备，然后给出 2 秒的倒计时。

`DRAM: 15.8 GiB` 的容量是阶段 3 报出来的，U-Boot 只是读结果。`bad CRC` 说明本板环境区损坏、每次用编译进镜像的默认环境。

**这 2 秒是唯一能改变启动参数的时机。** 有些参数（比如给 Jailhouse 腾内存用的 `jh_root_mem`）必须在 Linux 启动**之前**设置，因为 Linux 一旦启动就把内存全认领了，运行期再抽走的代价极高。这就是 Jailhouse 那套流程要"重启一次、在 U-Boot 里设参数"的原因。

要抢提示符必须**先开始按回车再上电**，且**只用 CR，不要用 Ctrl-C**——项目踩过坑：连续 Ctrl-C 会杀死串口登录服务，之后提示符永久消失，看起来像板子挂了。

**来源**：

| 证据 | 位置 | 说明 |
|---|---|---|
| U-Boot 装载地址 | 容器解析报告：`U-Boot 1215488 B @ 0x90200000`；与 BL31 填的入口一致 | 实机验证得到 + 源码可以确认 |

### 阶段 8 · 加载内核和 DTB，交给内核

**屏幕上看到**：

```text
36211200 bytes read in 109 ms (316.8 MiB/s)
95378 bytes read in 2 ms (45.5 MiB/s)
## Flattened Device Tree blob at 93000000
   Loading Device Tree to 000000009ffe5000, end 000000009ffff491 ... OK
Starting kernel ...
```

**这一步在做什么**：

U-Boot 从 eMMC 启动分区读出两个文件放进内存：内核 Image 36 MB，设备树 95 KB。设备树先放在 `0x93000000`，然后被搬到内存高端 `0x9ffe5000`，腾出低端给内核。最后执行 `booti` 跳转。

`Starting kernel ...` 是分界线：这行之前串口上说话的是 U-Boot，之后是 Linux 内核。

**来源**：

| 证据 | 位置 | 说明 |
|---|---|---|
| 内核大小 | 实机日志 `36211200 bytes read` | 实机验证得到 |
| DTB 大小可以互相验证 | 实机日志 `95378 bytes read`，与 `bsp/LF_v6.18.2-1.0.0_IMX95/imx95-19x19-frdm-pro.dtb` 的文件大小一致 | 实机验证得到 |
| 内核装载地址 | `imx-mkimage/iMX95/soc.mak:73`：`KERNEL_ADDR ?= 0x90400000` | 源码可以确认 |
| DTB 装载地址 | 同上：`KERNEL_DTB_ADDR ?= 0x93000000` | 源码可以确认 |

**更深一层（知道有就行）**：`booti` 的传参约定、设备树从 U-Boot 传给内核的过程。

### 阶段 9 · 内核起来

**屏幕上看到**：

```text
[    0.000000] Booting Linux on physical CPU 0x0000000000 [0x412fd050]
[    0.000000] Linux version 6.18.2-1.0.0-gf49f45233f7b ...
[    0.000000] Machine model: NXP FRDM-IMX95-PRO
[    0.000000] earlycon: lpuart32 at MMIO32 0x0000000044380000
[    0.079401] smp: Brought up 1 node, 6 CPUs
[    0.211427] CPU: All CPU(s) started at EL2
[    0.288095] Memory: 15106208K/16515072K available
[    5.649821] Freeing unused kernel memory: 2112K
```

**这一步在做什么**：

内核在 CPU0 上初始化，然后用 **PSCI 接口**把 CPU1~5 逐个叫醒。PSCI 调用会陷入 EL3 交给 BL31，BL31 再通过 SCMI 请求 SM 打开对应核的电源和时钟——**和阶段 4 里 SM 放开 CPU0 是同一套操作，只是这次是运行期发起的**。

方括号里是内核启动后的秒数。几个关键点：

| 行 | 意义 |
|---|---|
| `earlycon ... 0x44380000` | 控制台绑定到 LPUART1，就是 COM17 |
| `smp: Brought up 1 node, 6 CPUs` | 6 个 A55 全部上线 |
| `CPU: All CPU(s) started at EL2` | **EL2 是空着的**，Jailhouse 才有地方入驻 |
| `Memory: 15106208K/16515072K` | 约 15.75 GB，**没做 Jailhouse 设置时的数值** |
| `Freeing unused kernel memory` | 内核初始化完成 |

| 控制台是 LPUART1 | 实机日志 `earlycon: lpuart32 at MMIO32 0x44380000` | 实机验证得到 |
| 6 核上线、EL2 | 实机日志 | 实机验证得到 |

## 为什么是这个顺序

**需要有主体先分配资源。** A55 如果先跑，会默认自己能用全部外设和内存，等占满了再收回来就晚了。所以 M33 上的 SM 先上岗，把隔离规则写进硬件，再放开 A55。

**隔离是 SM 做的，不是 Linux 做的。** Linux 里的 root 只是 A55 内部的超级用户，越不过 SM 定的规则。项目里 `remoteproc` 报 `lmm(1) not under Linux Control`、U-Boot 往 M7 TCM 写数据触发异常、把 GPIO2 整个从 A55 拿走导致 WDOG3 反复复位，根因都在这里。

**EL2 是空着的**，所以 Jailhouse 有地方入驻。

### 阶段之间靠什么衔接

| 从 → 到 | 靠什么 |
|---|---|
| 1 → 2 | 纯硬件。复位释放后 M33 从 Boot ROM 取指 |
| 2 → 3 | 容器描述里写死的装载地址和入口地址 |
| 3 → 4 | 同上。另外 Boot ROM 在 `0x2003DC00` 留了带魔数 `0xC0FFEE16` 的结构给 SM 读启动参数 |
| 4 → 5 | SM 放开 CPU0。SPL 镜像早已由 Boot ROM 装到 `0x20480000` |
| 5 → 6 | SPL 把 BL31 装到 `0x8A200000` 并跳转 |
| 6 → 7 | BL31 填好 U-Boot 入口 `0x90200000` |
| 7 → 8 | U-Boot 内部：找启动设备、读内核和 DTB |
| 8 → 9 | U-Boot 执行 `booti` 跳转 |
| 9 → 10 | 内核内部：用 PSCI 叫醒其它核、启动第一个用户态程序 |

**越靠前越依赖"固定地址 + 魔数"，越靠后越依赖标准协议。**
