# 进度汇报：FRDM-IMX95-PRO 上跑 FreeRTOS（2026-09-17）

## 0. 一句话

前期按板卡默认分工在 M7 上把 FreeRTOS 端到端跑通，并打通了 i.MX95 的启动、烧录、System Manager 权限整条链；现已确认为 A55 目标，属于换 CPU 端口层（M7 成果作为平台底座与参照）。

## 1. 资料怎么找、找到了什么

- 顺序：开发板用户手册/快速入门 → 芯片与 SDK 资料 → 应用笔记 → BSP。来源为本机 `C:\Users\chen\Desktop\资料\IMX95` 与工程内 SDK。
- 关键资料：`UM12527` 板级用户手册（接口、启动模式 SW4）、`FRDMIMX95PROQSG` 快速上手、原理图 `SPF-95794_B1`（引脚与外设连接）、`UUU.pdf`（USB 串行下载）、`AN14120/AN14478/AN14748`（M7 应用构建与启动）、`UM12022`。
- 用途：确认“哪个口下载、哪个口是串口、怎么进下载模式、镜像包含哪些组件、M7 怎么被启动”。它们是后面所有判断的依据，不靠猜。

## 2. 上电验证 Linux，以及为什么先做 M7

- 按手册上电，COM17 看到 SPL→ATF(BL31)→U-Boot→Linux，确认板卡正常、eMMC 出厂系统可用。
- 登录 Linux 查看 `/lib/firmware`，发现板载固件里有 `imx95-19x19-evk_m7_TCM_*.bin`（含 FreeRTOS 示例），**因此判断“板载 FreeRTOS 是跑在 M7 上的”，于是先按 M7 推进**。
- 这就是后来方向调整的来源：早期资料与 SDK 示例都指向 M7；目标改成 A55 是产品分工变化，不是技术路线错误。

## 3. 烧录方式：官方做法与推进过程

i.MX95 不能像 STM32 那样用调试器往 Flash 写一个 bin，它是“多核 + Boot ROM + 安全启动容器”的模型。官方正常烧录是：把启动容器 `flash.bin` 写入 SD/eMMC，Boot ROM 从介质读取并启动各核。

三条备选路径都试过，各自卡点不同：

| 路径 | 结果 | 原因 |
|---|---|---|
| Linux remoteproc 加载 M7 | `lmm(1) not under Linux Control` | SM 没把 M7 逻辑机交给 Linux；是硬件级权限，换 root/chmod 都没用 |
| U-Boot `prepaux/bootaux` 搬 M7 到 TCM | 同步异常复位 | A55 默认没有 M7 TCM 的写权限，被访问控制挡住 |
| JTAG/SWD 调试器 | 放弃 | 板上只有裸露焊点、无调试座，且无 J-Link |
| **USB + UUU（SDPS）** | **采用** | 整个容器经 J7 交给 Boot ROM，载入内存运行，不写 Flash |

结论：必须自己组装一个合法的启动容器，并让 System Manager 在启动时拉起目标核。

补充：板载 `/lib/firmware` 的 M7 固件是给 Linux remoteproc 用的**裸镜像**（无容器头、无装载地址等元数据），**不能 `UUU boot -f` 直接发**。它“在 Linux 里用不了”正是上表第一行的权限问题，与文件无关；要让 Boot ROM 启动 M7，必须把它作为 M7 载荷打进 `flash.bin`。（另：`_linux_remote` 是 RPMsg 从机端、需 Linux 主机配合；`15x15` 与 `19x19` 板型不能混用。）

## 4. 怎么熟悉板子

- **SW4 启动模式**：`x001`=USB 串行下载（J7，本方案用）、`x010`=eMMC（Linux）、`x011`=microSD、`x100`=QSPI NOR。SW4 只是复位时给 Boot ROM 的启动源选择，不代表“选 Linux 还是选 FreeRTOS”。
- **关键接口**：J11 供电（USB-C PD）、J22 调试串口（板载 CH9114F，转出 4 个 COM）、J7 芯片 USB1 下载口、SW1 电源使能、K1/K2 复位与 SD 强制启动。
- **串口映射**（实测）：COM17=A55、COM18=M7、COM19=M33 System Manager、COM16 备用；波特率 115200-8-N-1。
- **外设**：J15 排针上 GPIO_IO14=J15-8、GPIO_IO15=J15-10、GND=J15-39（J15-9 是 IO，不是地）。

## 5. 烧到 TCM 之后：串口和 GPIO 怎么测

- **串口**：M7 的调试串口从 SDK 示例默认的 LPUART3 改为板上实际接出的 **LPUART7**（引脚 GPIO_IO36=TX、GPIO_IO37=RX），对应 COM18，能打印、能回显。
- **GPIO**：用 GPIO2 的 bit14（J15-8，输出）和 bit15（J15-10，输入）。输出用 LED 模块/逻辑分析仪看约 1 Hz 方波，输入用“输出回接输入”的杜邦线，COM18 上 `OUT` 与 `IN` 同步翻转。

## 6. FreeRTOS 从哪来、烧录文件怎么生成、怎么烧

烧录文件不是单独一个 bin，而是一个“启动容器”，来源分四步：

**① 我们自己生成两个核镜像**

- M7 FreeRTOS：IAR 9.70.4 编译 MCUXpresso SDK `SDK_26_06_00_IMX95LPD5EVK-19` 里的 `freertos_hello`（`cm7`）示例 → `freertos_hello.bin`。
- M33 System Manager：源码**不在 SDK 里**，来自 NXP `imx-sm` 仓库（`tools/imx-sm`）；改 `mx95frdm-pro-m7gpio.cfg` → 用 `configtool.pl` 生成配置头文件 → Arm GNU Toolchain 14.2.rel1 编译成 `m33_image.bin`。

**② 从 Linux BSP 原厂启动镜像里“拆”出 NXP 组件**

- 来源：`LF_v6.18.2-1.0.0_IMX95` 里的原厂镜像 `imx-boot-imx95-19x19-lpddr5-frdm-pro-sd.bin-flash_a55`。
- 工具：`imx-mkimage` 的 `make SOC=iMX95 extract`，拆到 `extracted_imgs/`：ELE/AHAB 容器与 V2X 固件、DDR OEI+LPDDR5、原厂 M33 SM（被我们自己的替换）、A55 SPL、BL31(ATF)、U-Boot、TEE；另有一段 64 KB Quick Boot 数据（不在镜像列表里，用 dd 按偏移取出）。
- 坑：ELE/AHAB 版本必须与 BSP 匹配，否则 SM 起不来。

**③ 在 WSL 里用 `imx-mkimage` 组装（它是打包工具，不是编译器）**

- 先做 A55 子容器（BL31 + U-Boot + TEE）→ 再拼主 ROM 容器（`-append ahab… -oei … -m33 … -m7 … -ap spl …`）→ 按 1 KB 对齐追加子容器 → 得 `flash.bin`；用 `mkimage_imx8 -parse` 核对每个镜像的核心与装载地址。

**④ 交给 UUU**

- 把 `flash.bin` 复制成 uuu 脚本引用的文件名（如 `flash-m7-preempt.bin`）；uuu 文件内容只有一行 `SDPS: boot -f flash-m7-preempt.bin`。
- “改名”不是格式转换，只是让文件名对上 uuu 脚本。
- 板子进 USB 下载模式并冷复位 → `uuu -lsusb` 看到 `SDPS` → 运行 `uuu.exe xxx.uuu` → Boot ROM 收容器、ELE 校验、DDR OEI 初始化内存、SM 启动并拉起 M7 与 A55 链。
- 关键点：**SDPS 只下载到内存运行，不写 eMMC**；容器布局、SM 位置、AHAB(ELE) 版本必须对齐（踩过版本/64 KB 保留区的坑）。

## 7. 串口初始化与收发验证

主链：

```text
BOARD_InitPins() 复用 GPIO_IO36/37 -> LPUART7_TX/RX（经 SM/SCMI 写 IOMUXC）
BOARD_InitDebugConsole() 设 LPUART7 根时钟(24 MHz)并初始化 PRINTF
main() LPUART_Init(115200) + 开接收中断
LPUART7_IRQHandler 收到字节 -> xQueueSendFromISR
echo_task xQueueReceive -> LPUART_WriteBlocking 原样发回
```

验证：COM18 能收到启动打印（输出），在终端输入字符能被原样返回（输入），证明中断、队列、任务切换、串口收发全通。

## 8. GPIO 初始化与输入输出验证，以及 M7 的 GPIO 控制权

**初始化分三层**（这是 i.MX95 与 STM32 最大的不同）：

1. **引脚复用/电气（IOMUXC，归 M33 SM 管）**：M7 不直接写，`BOARD_InitPins()` 通过 `HAL_PinctrlSetPinMux/SetPinCfg` 发 SCMI 请求，由 SM 代写 IOMUXC，把 IO14/15 复用成 GPIO2 的 bit14/15。
2. **资源访问权限（SM 配置 + TRDC）**：需要让 M7 所在逻辑机拥有 GPIO2。
3. **GPIO 方向/数据（RGPIO，M7 直接写）**：`RGPIO_PinInit/Write/Read`。

**控制权怎么改的（核心）**：

- 改 SM 配置 `mx95frdm-pro-m7gpio.cfg`：`LM1/M7: GPIO2 OWNER`，同时 `LM2/A55: GPIO2 ACCESS` 和 `PERLPI_GPIO2 ALL`（保留给 A55 启动用）。
- 用官方工具链把 cfg 编译成 `m33_image.bin`，替换进启动容器；SM 启动时据此配置逻辑机与 TRDC。
- 踩坑：最初把 GPIO2 整块从 A55 拿走，A55 起不来，触发 WDOG3→FCCU 复位 LM2；保留 A55 的 API 与访问权后恢复。
- 还有一层：A55 启动链里的 BL31 会把 GPIO2 的安全域 `PCNS/PCNP` 全置 1，M7（安全态）就被“读 0、写无效”。解法是 M7 只按位清回自己两根脚（`PCNS/PCNP &= ~bit14|bit15`）。

**验证**：输出脚有约 1 Hz 方波（逻辑分析仪），把输出回接输入后 COM18 的 `OUT` 与 `IN` 同步，证明复用、权限、安全域、方向、物理引脚全通。

## 9. 实时性、任务创建与任务间通信

- **实时性**：核心不是“快”，而是“结果在时限内产生”。关键指标：响应时间（重点看最大值）、抖动 jitter、截止期 deadline、WCET（最坏执行时间）。分硬/软/firm 实时。
- **任务创建**：`xTaskCreate(函数, 名字, 栈深度, 参数, 优先级, 句柄)`；每个任务独立栈；优先级数字越大越高；`configUSE_PREEMPTION=1` 开启抢占。
- **任务间通信**：本例用**队列**——中断里 `xQueueSendFromISR` 送数据，任务里 `xQueueReceive` 取数据，实现“中断生产、任务消费”。
- **实测**：M7 @800 MHz，`vTaskDelayUntil` 500 ms 周期任务，周期抖动约 0~7.5 ns；另做了抢占实验（高优先级忙等 600 ms 时，低优先级任务打印间隔从 100 ms 跳到 700 ms），并发现本工程默认 `configUSE_TIME_SLICING=0`（同级不轮转）。
