## LED任务

在现有M7 FreeRTOS串口工程中新增独立的`led_task`：

```text
任务名：led_task
优先级：configMAX_PRIORITIES - 2，即3
任务栈：configMINIMAL_STACK_SIZE + 100，即190个StackType_t
输出：GPIO2_IO14，J15-8
阻塞时间：500 ms
```

任务先调用`RGPIO_PinInit()`把GPIO2_IO14设为数字输出，然后每500 ms翻转一次状态并调用`RGPIO_PinWrite()`。IAR编译、重新打包和启动后，8位LED模块对应灯按照预期间隔闪烁，说明任务创建、调度、阻塞延时和GPIO输出均正常。

## FreeRTOS配置

打开以下配置：

```c
#define configUSE_IDLE_HOOK 1
#define configCHECK_FOR_STACK_OVERFLOW 2
```

新增`vApplicationIdleHook()`，用于观察没有其他就绪任务时空闲任务是否得到运行；新增`vApplicationStackOverflowHook()`，任务栈检查发现异常时进入该函数并停止继续运行。当前只建立基础框架，后续再增加任务列表和剩余栈输出。

## 当前任务关系

- `echo_task`：优先级4，等待串口接收队列；没有数据时阻塞。
- `led_task`：优先级3，每500 ms唤醒一次，翻转LED后再次阻塞。
- Idle任务：优先级0，前两个任务都阻塞时运行。

串口中断收到字符后把数据写入队列，并唤醒高优先级的`echo_task`。由于FreeRTOS开启抢占调度，`echo_task`一旦就绪会抢占正在运行的低优先级任务；处理完字符后再次等待队列，CPU继续运行LED任务或Idle任务。

## 双LED不同优先级：验证抢占

目标：把单个LED任务改成两个LED、两个不同优先级任务，验证“高优先级就绪会抢占低优先级”，并观察低优先级LED的闪烁节奏如何随高优先级任务的忙等/阻塞变化。

实现（`freertos_hello.c`）：

```text
echo_task : 优先级4，LPUART7回显（不变）
task_high : 优先级3，GPIO2_IO14/J15-8，忙等600ms -> 翻转 -> vTaskDelay(400ms)
task_low  : 优先级2，GPIO2_IO15/J15-10，翻转 -> 打印tick和dt -> vTaskDelay(100ms)
```

关键点：

- 忙等用DWT周期计数器（`main()`里`MSDK_EnableCpuCycleCounter()`使能），内部不调用任何FreeRTOS API，所以真正占住CPU。
- `dt`单位是tick；`configTICK_RATE_HZ=200`，1 tick=5ms，100ms=20 ticks。
- 接线：LED1接J15-8，LED2接J15-10，各自经限流电阻到GND(J15-39)；原来的J15-8↔J15-10回环线要拔掉。

COM18实测（节选）：

```text
task_high ready (GPIO2_IO14, prio 3) busy=600ms block=400ms
task_low ready (GPIO2_IO15, prio 2) period=100ms
LOW t=122 dt=1
LOW t=142 dt=20
LOW t=162 dt=20
LOW t=182 dt=20
LOW t=321 dt=139
LOW t=341 dt=20
...
```

结论：

- 规律为`20,20,20,140`循环，合计200 ticks=1000ms，等于task_high周期。
- `140 ticks = 700ms = 600ms忙等 + 100ms正常周期`；说明task_low已就绪却被推迟约600ms，直到task_high忙等结束——**抢占成立**。
- 第一行`dt=1`为任务刚启动的残段，可忽略。
- LED15肉眼可见每秒停顿约0.6s，LED14每1s翻转。

## 对照实验：task_low与task_high同级（SAME-PRIO）

目的：排除“死机/其它阻塞”，证明正常实验里的长停顿来自“两个任务优先级不同”。

改动（`freertos_hello.c`增加开关）：

```c
#define CONTROL_SAME_PRIORITY (1)   /* 1=对照(同级)，0=正常(低优先级) */
#if CONTROL_SAME_PRIORITY
#define low_task_PRIORITY  (configMAX_PRIORITIES - 2) /* 优先级 3，与 task_high 同级 */
#else
#define low_task_PRIORITY  (configMAX_PRIORITIES - 3) /* 优先级 2 */
#endif
```

### 第一次对照（同级，时间片关闭）——结果与预期不符

镜像：

```text

容器  : build/pro-gpio/flash-m7-preempt-sameprio.bin (2855936B)

UUU   : build/pro-gpio/preempt-sameprio-ram.uuu
```

实测（COM18）：

```text
task_high ready (GPIO2_IO14, prio 3) busy=600ms block=400ms
task_low ready (GPIO2_IO15, prio 3) period=100ms mode=SAME-PRIO
LOW t=122 dt=1
LOW t=142 dt=20
LOW t=162 dt=20
LOW t=182 dt=20
LOW t=321 dt=139
...
```

结果与正常实验完全一样（`20,20,20,14x`循环）：同级也没有让另一个任务在忙等期间得到运行。

### 根因（已查证）

本工程实际**未开启时间片轮转**。工程用的是`rtos/freertos/freertos-kernel/template/FreeRTOSConfig.h`（`.ewp`包含路径含`.../freertos-kernel/template`），该文件：

```c
#include "FreeRTOSConfig_Gen.h"
...
#if !defined(configUSE_TIME_SLICING)
#define configUSE_TIME_SLICING  0
#endif
```

而项目`FreeRTOSConfig_Gen.h`第13行是`// #define configUSE_TIME_SLICING 0`（注释掉），未定义 → 被模板设为**0**。因此同级任务不轮转，忙等任务仍独占CPU，同级的另一个任务同样被饿死。这不是实验做错，是配置如此。
