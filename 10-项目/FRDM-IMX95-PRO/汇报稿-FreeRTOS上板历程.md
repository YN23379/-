# 汇报稿：FreeRTOS 从选板到上板验证

> 类型：口头汇报稿。配套知识梳理见《汇报稿-FreeRTOS上板历程-知识梳理.md》。
> 撰写规范见 `Work/AGENTS.md` 的演讲稿写作规范。

我先从官网找资料，找到快速入门指南，按上面的步骤把 A55 的 Linux 启动起来，确认板子正常，然后下载原理图和引脚图，对照板子上的接口和引脚。

接着登录 Linux 看板载固件，里面有一批 FreeRTOS 的 bin 和 elf，名字都是 M7 的，我就以为这块板子跑 FreeRTOS 是在 M7 核上。于是找烧录方法，查资料也问了 AI，说可以用 Linux 的 remoteproc 驱动把固件加载到 M7 的 TCM 里启动。TCM 是直接连在 M7 核上的紧耦合内存，速度稳定，适合放实时程序。实际试不行，Linux 报 M7 这个逻辑机不归 Linux 控制，也就是 System Manager 没把 M7 的控制权给 Linux，不是文件权限的问题。我又在 U-Boot 里直接把程序搬到 TCM，结果触发异常复位，因为 A55 默认没有写 M7 TCM 的权限。也想过用调试器下载，但原理图上 JTAG 和 SWD 的引脚只引到裸露焊点，要自己焊，手头也没有 J-Link，就放弃了。最后看到官方是用 USB 加 UUU 下载，我先去找烧录文件。

我去官网下了 SDK。这里没有 Pro 版本，就下了普通的 i.MX95 19x19 的 SDK，里面有针对 IAR 的 FreeRTOS 示例，用 IAR 编译得到一个 M7 的 bin。

但这个 bin 不能直接烧。i.MX95 的 Boot ROM 要的是一个启动容器，里面要有每个镜像的核心和装载地址。我去看官方原厂的启动镜像，用 imx-mkimage 拆开，拆出来有 ELE 安全固件，V2X 平台固件，DDR 初始化，原厂的 M33 SM，A55 的 SPL，BL31，U-Boot 和 TEE。ELE 是芯片的安全子系统固件，负责安全启动校验。SM 就是 System Manager，是运行在 M33 上的系统管理固件。BL31 是 A55 的安全监控层。SPL 是 A55 的第一阶段引导。DDR 初始化负责把内存训练起来。TEE 是可信执行环境固件。另外还有一段 Quick Boot 数据，是原厂启动镜像里的一段数据，不在普通镜像列表里，我们一开始没保留，设备在早期启动就停了，后来按偏移从原厂镜像里取出来补上。我要做的就是把自己编的 M7 程序和这些组件按同样格式重新打成 flash.bin。这里有个坑，ELE 版本必须和 BSP 匹配，一开始用旧版本 SM 起不来，换成匹配的 2.0.5 才正常。

打包在笔记本的 WSL 里做。M7 用 IAR 编，M33 的 System Manager 用官方的 Arm GNU 工具链 14.2.rel1 编，这个工具链从 ARM 官网下载，打包用的 imx-mkimage 在 WSL 里用 make 编出来。齐了之后打包，再用官方 uuu 通过 USB 把容器发给 Boot ROM。这里调整了很多次，除了 ELE 版本和 Quick Boot 数据，原厂镜像里 DDR 初始化和 SM 之间还有一段 64KB 的保留区，少了它 SM 也不启动。USB 偶尔报错，要冷复位重试。全部对齐之后才烧进去，看到 hello world。

跑起来先测串口，用 J22 引出来的 LPUART7，对应电脑的 COM18，打印和回显正常。再测 GPIO，用 GPIO2 的 14 和 15 做输出和输入。输出接 LED 或逻辑分析仪能看到方波，输入用杜邦线把输出回接过来，串口上输出和输入同步翻转。

但 GPIO 一开始问题很多。M7 没有直接使用 GPIO 的权限，我查资料发现 GPIO2 默认分给 A55，M7 要用就得改 M33 上的 System Manager。这个源码不在 SDK 里，是单独一个仓库，我去官网找到它。板子的配置在 configs 目录下有一份 Pro 板对应的 cfg，我在它基础上改，把 GPIO2 的 OWNER 给 M7，同时保留 A55 需要的访问权限和 API 权限。因为 A55 启动阶段也要用 GPIO2，整块拿走它就会起不来，触发看门狗复位。改完用配置工具生成配置头文件，再用 Arm GNU 工具链编成 M33 镜像，替换进启动容器。

后来发现 USB 烧录是烧到 TCM 也就是 RAM 里，掉电就没了，要掉电保持得写 SD 卡。为了不动 eMMC 里官方的系统，我写 SD 卡，结果又有新问题。A55 完整启动会经过 BL31，BL31 会把 GPIO2 所有引脚的安全属性设成非安全，M7 是安全态，读写自己那两根脚就变成读 0 写无效。最后的办法是 M7 把自己那两根脚按位设回安全域。

这里有两层，一层是 SM 里对引脚的归属和 TRDC 的访问权限，另一层是 GPIO 控制器内部按引脚的安全属性。顺便理一下整体隔离。芯片的电源，时钟，复位，引脚和各核启动都由 M33 上的 System Manager 管。它把芯片分成几个逻辑机，LM0 是它自己，LM1 是 M7，LM2 是 A55，每个逻辑机有自己的内存，外设，引脚和 API 权限。TRDC 是硬件访问控制，总线访问会带发起方的域 ID，TRDC 根据域 ID 和目标地址判断能不能访问。各核向 SM 申请服务，比如时钟和引脚，走 SCMI 协议，通过 MU 邮箱发。主链是，Boot ROM 收到启动容器，ELE 校验，DDR 初始化，然后启动 SM，SM 配好逻辑机和 TRDC，再按配置把 M7 和 A55 拉起来。所以 M7 用一个外设要过两道，一道是 TRDC 允不允许访问寄存器，一道是通过 SCMI 请 SM 配引脚。

然后这两天我了解实时性。我觉得实时性就是在规定时间内完成指定操作，分硬实时和软实时。硬实时要求很高，必须在规定时间内完成，不允许超时，超时可能造成严重后果，主要是保证系统不出错。软实时要求没那么严，超时一般只是影响质量。我理解实时性不能只看平均值，还要看最坏情况，比如抖动和最大响应时间。

我简单测了一下，用 M7 内部的周期计数器计时，测一个 500 毫秒的周期任务，看实际周期，抖动和任务执行时间，结果周期很稳，抖动也小。但这肯定不够，我打算先把多任务做起来再测，任务多了，CPU 负载上来，实时性的数据才更有说服力。

所以先做了 LED 任务。用 GPIO2_IO14 接一个 LED，创建任务，先设成输出，然后每 500 毫秒翻转一次，翻转完就阻塞让出 CPU。为了验证优先级抢占，我改成两个 LED 两个任务，一个高优先级一个低优先级。高优先级任务每周期先忙等一段时间占住 CPU，再翻转自己的 LED，然后阻塞，低优先级任务周期更短。这样高优先级忙等时，低优先级任务已经到点却拿不到 CPU，打印的间隔明显变大，LED 也停顿一下。改忙等或者阻塞的时间，低优先级 LED 的节奏就跟着变。这就说明高优先级会抢占低优先级。

我对 FreeRTOS 的理解是，它是一个抢占式的实时操作系统，任务是固定优先级，高优先级就绪了可以抢占低优先级。用任务创建把不同功能拆成不同任务，就不用像裸机那样靠一堆标志位在一个大循环里切来切去，代码不会越来越乱。任务之间通信我现在用队列，就是生产者消费者模型，先创建队列，一个任务把数据发进队列，另一个任务取出来处理。我们的串口就是中断收到数据放进队列，任务再取出来回发。任务同步还有信号量和互斥量这些，后面继续补。
