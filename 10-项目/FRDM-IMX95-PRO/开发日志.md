### GPIO权限修改

原始Pro配置：

```text
F:\project\Learning\RTOS\tools\imx-sm\configs\other\mx95frdm-pro.cfg
```

测试配置：

```text
F:\project\Learning\RTOS\tools\imx-sm\configs\other\mx95frdm-pro-m7gpio.cfg
```

相对原始配置只改变GPIO2的归属：

- 将`PERLPI_GPIO2 ALL`从LM2/A55的API权限移到LM1/M7。
- 将`GPIO2 OWNER`从LM2/A55资源列表移到LM1/M7。
- 保留M7已有的GPIO_IO14、GPIO_IO15、LPUART7及其引脚权限。
- GPIO3、GPIO4、GPIO5不变。

这不是只开放两个引脚，而是把整个GPIO2寄存器控制器交给M7。TRDC按资源块控制访问；只改IOMUX引脚复用而不改变GPIO2控制器归属，M7仍会在访问GPIO2寄存器时被拒绝。

### FreeRTOS GPIO程序

- GPIO2_IO14配置为输出，对应J15-8。
- GPIO2_IO15配置为输入，对应J15-10。
- FreeRTOS任务每500 ms翻转一次输出并读取输入。
- COM18持续打印输出状态和输入状态。
- 正确地线为J15-39。J15-9是GPIO_IO04，不是GND。

### 实际接线

```text

逻辑分析仪CH0         -> J15-8
逻辑分析仪CH1         -> J15-10
逻辑分析仪GND         -> J15-39
```

不接外部3.3 V或5 V。输入电平直接由GPIO2_IO14提供，避免输入悬空。

### 同时出现的问题

COM19反复输出：

```text
Reset LM 2, reason=fccu, errId=19
```

COM17没有A55 SPL、U-Boot或Linux持续输出。官方SM源码给出：

```c
#define DEV_SM_FAULT_WDOG3 19U
```

注释为`WDOG3 timeout (Watchdog reset request)`。Pro配置中LM2名为`AP`，拥有WDOG3，并配置`FAULT_WDOG3 OWNER, reaction=lm_reset`。因此该信息的含义是：LM2/A55启动后没有在规定时间内维护WDOG3，FCCU收到19号故障，M33上的System Manager按配置关闭并重新启动LM2。LM2再次超时后过程重复，所以COM19持续打印。

这个错误不是GPIO2的TRDC拒绝信息，也不表示M7 GPIO验证失败。M7属于LM1，实测仍持续运行。

### 已确认与未确认

已确认：

- `errId=19`是WDOG3超时。
- 发生故障的是LM2/AP/A55逻辑机。
- `reaction=lm_reset`导致System Manager反复复位LM2。
- M7 FreeRTOS、GPIO输出和GPIO输入均正常运行。
- 当前是USB RAM启动，eMMC中的原Linux没有被覆盖，也没有自动运行。

尚未确认：

- A55停在启动链的具体位置。
- A55未喂WDOG3是否由GPIO2整体转交给M7造成。
- 新编译SM与原始可运行SM的其他二进制差异是否影响A55启动。

### 后续排查方法

不关闭WDOG3，不屏蔽FCCU，也不删除LM复位状态机。用单变量对照定位：

1. 使用同一版本SM源码和原始`mx95frdm-pro.cfg`，搭配已验证的M7 UART程序生成对照容器，确认A55链路是否恢复。
2. 使用GPIO权限版SM，搭配不访问GPIO的旧M7程序，确认LM2复位是否只由SM资源配置触发。
3. 对比COM17、COM19和UUU结果，确定故障随“GPIO2归属”还是随“SM重编二进制”变化。
4. 若确认A55早期启动依赖GPIO2，工程方案应改为选择A55启动阶段不依赖的GPIO资源、调整A55 SPL，或由唯一所有者控制GPIO并通过RPMsg提供服务。
5. GPIO专用测试也可制作不启动LM2的M7-only镜像，但必须先核对官方构建目标和Pro配置，不能把它当成Linux与M7共存方案。

### 当前结论

GPIO输入输出验证已经完成。`Reset LM 2`是另一个A55启动链问题，不应修改M7 GPIO程序来规避。下一阶段是通过受控对照找出WDOG3超时的上游原因，然后再进行SD卡持久化；暂不写eMMC。

### 2026-09-15 WDOG3问题解决结果

先构建并运行“官方原始Pro SM配置 + 相同GPIO M7程序”的严格对照镜像。对照结果为：COM17恢复A55 SPL输出，COM19正常进入SM Debug Monitor且不再出现`errId=19`；由于原始配置不允许M7访问GPIO2，COM18没有GPIO输出。这个单变量对照证明SM重新编译和容器构建本身可以正常启动A55，WDOG3循环由“把整个GPIO2从A55转交给M7”触发。

根据官方SM配置文档，API权限和TRDC访问权限是两套控制。TRDC为每个DID设置独立权限，同一外设可以允许多个DID访问。因此最终配置不再转移GPIO2所有权，而是：

```text
LM2/A55：保留PERLPI_GPIO2 ALL和GPIO2 OWNER
LM1/M7：增加ACCESS: perm=rw, api=none
LM1/M7：增加GPIO2 ACCESS
```

该配置使A55继续拥有GPIO2及其SCMI管理权限，M7只获得直接访问GPIO2寄存器所需的TRDC读写权限。生成的`config_trdc.h`相对官方原始Pro配置只增加一条TRDC寄存器写入；M7的SCMI表中GPIO2仍为`NONE`，A55仍为`ALL`。

重新构建并通过UUU RAM启动后，实机结果为：

```text
COM17：U-Boot SPL正常启动并进入USB SDP等待后续A55镜像
COM18：M7 FreeRTOS UART和GPIO任务持续运行
COM19：DDR OEI完成，System Manager进入Debug Monitor，无WDOG3/FCCU循环
```

由此确认WDOG3问题已解决。COM17最后出现`SPL: failed to boot from all boot devices`，是因为当前`.uuu`脚本只执行一次`SDPS: boot`，没有继续向SPL的SDPV阶段发送完整A55系统，并非WDOG3故障。GPIO日志中`OUT`翻转而`IN`始终为0表示GPIO输入端没有接到输出电平；重新连接J15-8和J15-10后才能进行回环比较，这也不是权限错误。

### 三、SD 启动问题与排查

#### 1. 初始现象

- USB SDPS 临时启动时，M7 FreeRTOS 串口和 GPIO 均正常。
- 同一类镜像写入 SD 卡并完整启动后，M7 串口任务仍在运行，但 GPIO14 无波形，GPIO15读回始终为0。
- M7诊断值由正常状态变为：`PCNS=FFFFFFFF`、`PCNP=FFFFFFFF`、`PDOR/PDIR/PDDR`访问异常。
- 在 U-Boot 中直接写 GPIO2 的 PSOR/PCOR 可以改变实际引脚电平，因此没有先判定为硬件损坏。

#### 2. 关键判断

USB SDPS 流程停留在 SPL 阶段，不能代表完整 A55 启动链已经执行。SD 启动会继续经过 BL31 和 U-Boot，启动阶段不同是两种结果的关键差异。

匹配板载版本的 TF-A 源码为：

```text
F:\project\Learning\RTOS\tools\imx-atf-source
branch: lf_v2.12
commit: 4a2e9ef5f9f185bda68470b46365add008903b8c
```

文件 `plat/imx/imx9/imx95/imx95_bl31_setup.c` 中明确有：

```c
mmio_write_32(GPIO2_BASE + 0x10, 0xffffffff); /* PCNS */
mmio_write_32(GPIO2_BASE + 0x18, 0xffffffff); /* PCNP */
```

因此，SD 启动时 BL31 会把 GPIO2 的按引脚安全/特权属性重新设置为全1。M7虽然已经启动，但随后访问被改变属性的 GPIO14/15时读为0、写入无效。问题不是 M7 没启动，也不是 FreeRTOS 没调度。

### 四、修复方案

#### 1. SM 配置

最终使用：

```text
F:\project\Learning\RTOS\tools\imx-sm\configs\other\mx95frdm-pro-m7gpio.cfg
```

保留以下关系：

```text
LM1/M7: GPIO2 OWNER
LM2/A55: GPIO2 ACCESS
LM2/A55: PERLPI_GPIO2 ALL
M7: PIN_GPIO_IO14/15 OWNER
```

不能把 GPIO2 和 A55 所需 API 全部移走，否则 A55 启动过程会出现 `WDOG3 -> FCCU errId=19 -> Reset LM2`。

#### 2. M7 代码

文件：

```text
F:\project\Learning\RTOS\SDK_26_06_00_IMX95LPD5EVK-19\boards\imx95lpd5evk19\freertos_examples\freertos_hello\cm7\freertos_hello.c
```

只清除 GPIO2 bit14/15：

```c
#define GPIO_PIN_MASK ((1UL << 14U) | (1UL << 15U))
GPIO2->PCNS &= ~GPIO_PIN_MASK;
GPIO2->PCNP &= ~GPIO_PIN_MASK;
```

当前稳定实现为：初始化前清除一次；任务循环中先检查 bit14/15，只有被重新设置时才调用 `gpio_reclaim_pins()`。实测表明，单次清零或只在进入循环前清零受启动时序影响，不能作为稳定结论。按位清除后全寄存器预期为 `0xFFFF3FFF`，不会影响 GPIO2 其他引脚。

### LED任务

在现有M7 FreeRTOS串口工程中新增独立的`led_task`：

```text
任务名：led_task
优先级：configMAX_PRIORITIES - 2，即3
任务栈：configMINIMAL_STACK_SIZE + 100，即190个StackType_t
输出：GPIO2_IO14，J15-8
阻塞时间：500 ms
```

任务先调用`RGPIO_PinInit()`把GPIO2_IO14设为数字输出，然后每500 ms翻转一次状态并调用`RGPIO_PinWrite()`。IAR编译、重新打包和启动后，8位LED模块对应灯按照预期间隔闪烁，说明任务创建、调度、阻塞延时和GPIO输出均正常。

### FreeRTOS配置

打开以下配置：

```c
#define configUSE_IDLE_HOOK 1
#define configCHECK_FOR_STACK_OVERFLOW 2
```

新增`vApplicationIdleHook()`，用于观察没有其他就绪任务时空闲任务是否得到运行；新增`vApplicationStackOverflowHook()`，任务栈检查发现异常时进入该函数并停止继续运行。当前只建立基础框架，后续再增加任务列表和剩余栈输出。

### 当前任务关系

- `echo_task`：优先级4，等待串口接收队列；没有数据时阻塞。
- `led_task`：优先级3，每500 ms唤醒一次，翻转LED后再次阻塞。
- Idle任务：优先级0，前两个任务都阻塞时运行。

串口中断收到字符后把数据写入队列，并唤醒高优先级的`echo_task`。由于FreeRTOS开启抢占调度，`echo_task`一旦就绪会抢占正在运行的低优先级任务；处理完字符后再次等待队列，CPU继续运行LED任务或Idle任务。

### 双LED不同优先级：验证抢占

目标：把单个LED任务改成两个LED、两个不同优先级任务，验证“高优先级就绪会抢占低优先级”，并观察低优先级LED的闪烁节奏如何随高优先级任务的忙等/阻塞变化。

实现（`freertos_hello.c`）：

```text
echo_task : 优先级4，LPUART7回显（不变）
task_high : 优先级3，GPIO2_IO14/J15-8，忙等600ms -> 翻转 -> vTaskDelay(400ms)
task_low  : 优先级2，GPIO2_IO15/J15-10，翻转 -> 打印tick和dt -> vTaskDelay(100ms)
```

关键点：

- 忙等用DWT周期计数器（`main()`里`MSDK_EnableCpuCycleCounter()`使能），内部不调用任何FreeRTOS API，所以真正占住CPU。
- `dt`单位是tick；`configTICK_RATE_HZ=200`，1 tick=5ms，100ms=20 ticks。
- 接线：LED1接J15-8，LED2接J15-10，各自经限流电阻到GND(J15-39)；原来的J15-8↔J15-10回环线要拔掉。

COM18实测（节选）：

```text
task_high ready (GPIO2_IO14, prio 3) busy=600ms block=400ms
task_low ready (GPIO2_IO15, prio 2) period=100ms
LOW t=122 dt=1
LOW t=142 dt=20
LOW t=162 dt=20
LOW t=182 dt=20
LOW t=321 dt=139
LOW t=341 dt=20
...
```

结论：

- 规律为`20,20,20,140`循环，合计200 ticks=1000ms，等于task_high周期。
- `140 ticks = 700ms = 600ms忙等 + 100ms正常周期`；说明task_low已就绪却被推迟约600ms，直到task_high忙等结束——**抢占成立**。

### 四、遇到的问题：现象 → 排查 → 根因 → 解决

#### 问题 1：串口打不开，`Access to the port 'COMxx' is denied`

- **现象**：PowerShell/.NET 打开 COM16–19 全部报 `Access to the port 'COMxx' is denied`。
- **排查**：先怀疑沙箱拦截；但沙箱拦截会带 `[sandbox: ...]` 标记，这里没有，只有 .NET 异常。列进程发现 `MobaXterm`（PID 27856）在跑。
- **根因**：MobaXterm 打开着串口会话，Windows 串口是独占资源。
- **解决**：关闭 MobaXterm 的串口标签页（保留 SSH 页），四个口立即可打开。
- **验证**：关闭后逐个 `Open()` 全部成功。

#### 问题 2：沙箱拒绝执行外部程序

- **现象**：`uuu.exe`、`tar.exe`、`python.exe`、`git.exe`、`cmd.exe` 一律 `Access is denied` / `[sandbox: file access denied under workspace-write mode]`。
- **排查**：逐个试，发现规律——**新进程创建被拦，进程内的 PowerShell/.NET 代码不受影响**。
- **根因**：当前 DSH 文件策略为 `workspace-write`，工作区外的可执行文件/设备访问被拒。
- **解决**：需要跑 uuu 时按沙箱规则单次提权；本次的串口读写、二进制字符串提取全部改用纯 PowerShell/.NET 实现，不需要提权。
- **附带收获**：写了 `serial-probe.ps1`（单口交互）与 `serial-capture.ps1`（多口并发抓取），后续一直用。

#### 问题 3：抢 U-Boot autoboot 失败（命令落在了错误的时刻）

- **现象**：第一次尝试时，`printenv` 命令的回显出现在 **BL31 之后、U-Boot banner 之前**，说明命令在 ATF 阶段就发出去了；板子随后正常自启。
- **排查**：读脚本逻辑，发现提前退出条件是 `$all -match '=>\s*$'`——用"累积输出里是否出现 `=>`"来判断是否到了 U-Boot 提示符。
- **根因**：Linux 关机日志里出现了能匹配该正则的字符组合，脚本**误判提前结束发送**；而 i.MX95 的 autoboot 只有 2 秒，发送窗口一旦错过就必然失败。
- **解决**：改为"整个窗口内持续轮发 Ctrl-C/空格/回车，不做提前判断"，并且必须在**上电之前**就开始发键。
- **教训**：用文本匹配当状态机很脆；抢 autoboot 这种一次性窗口，宁可多打也不要提前收手。

#### 问题 4（今天最值钱的坑）：A55 控制台彻底静默，看起来像"板子挂了"

- **现象**：COM17 发什么都不回（CR、`version`、`root` 全部无响应），持续几分钟。
- **排查路径（逐步排除）**：
  1. 怀疑内核 panic / 板子复位 → 但没有新的启动日志，M33 侧也没有复位迹象；
  2. 怀疑 USB 串口重新枚举、COM 号变了 → 读注册表 `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM`，映射**未变**：`\Device\Serial2 = COM17`，四个口都还在，也都能打开；
  3. 怀疑板子掉电 → 探测 COM19（M33 SM 控制台），此时**还能进 `*** SM Debug Monitor ***`**，说明 SoC 有电、M33 正常；
  4. 结论收敛到"只有 A55 的串口登录会话出了问题"。
- **根因**：上一轮我连续 28 秒轮发 Ctrl-C（每 120 ms 一个），把 `serial-getty@ttyLP0` 反复杀死并重启。systemd 默认 `StartLimitBurst=5` / `StartLimitIntervalSec=10s`，超过后**放弃重启该单元** → 登录提示符永久消失 → 串口一个字都不再输出。**内核和系统是活的。**
- **解决/规避**：
  - 抢 autoboot 的发送时长限制在启动窗口内（脚本加了 `-BlastSec`，默认 90 秒），抢不到就停手，不再继续砸 getty；
  - 需要重新拿到控制台时，断电重启即可（今天结束时板子已断电）；
  - 判断"板子是否活着"必须用**独立通道交叉验证**（M33 SM 控制台、网络、串口端口映射），不能只看一个串口有没有回显。
- **验证**：后来 COM19 也静默，是因为用户把板子断电了；这条时间线对得上。

#### 问题 5：PowerShell 脚本里中文注释把下一行"吃掉"

- **现象**：改完 `uboot-run.ps1` 后运行报 `Attempted to divide by zero`，原因是 `$keys` 变成了 `$null`（`$null.Count` 在 PS 3+ 返回 0，取模即除零）。
- **排查**：读回文件，行内容本身是正确的。
- **根因**：文件是无 BOM 的 UTF-8，Windows PowerShell 5.1 按 ANSI（CP936）解码，中文注释的字节序列在行尾被解成续行/转义，把紧随其后的赋值行吞掉了。
- **解决**：交互脚本改成**纯 ASCII**（注释也用英文），中文说明放到 Markdown 笔记里。
- **教训**：给 Windows PowerShell 5.1 写的 .ps1 一律用 ASCII，或显式带 BOM 保存。

### 九、当日补充：Jailhouse 在 Pro 板上实机跑通（当天下午后半段）

前面第八节写的都还成立，但**当天下班前把实机链路打通了**，这是今天最重要的结果。

#### 9.1 可复现步骤

1. 用脚本在上电前开始轮发回车抢 U-Boot（CR 能打断 autoboot，但不会像 Ctrl-C 那样打死 getty），拿到 `u-boot=>` 后**在同一个进程里立刻**下发：

#### 9.2 这一步暴露的新问题（都要记）

1. **U-Boot 变量不持久**：原厂环境区 CRC 损坏，U-Boot 每次都用编译进镜像的默认环境。断电后 `jh_root_mem`/`jh_clk` 全部丢失，必须重做；板载也没有 `fw_printenv`/`fw_setenv`，无法从 Linux 写 U-Boot 环境。
2. **U-Boot 提示符不是"安全停车位"**：停在 `u-boot=>` 不操作，一分多钟后会被看门狗复位并自启回 Linux（上一轮的 `setenv` 就是这样失效的）。所以必须"抢到提示符→立刻 setenv→立刻启动"，全在一个进程内完成。
3. **inmate 会抢走调试串口**：`uart-demo.bin` 占用 LPUART1 及其中断后，**Linux 控制台彻底失去输入**（回车、Ctrl-C 都无效），只能靠复位板子收回控制权。这正是 Harpoon 给 inmate 单独分配一路 UART 的原因。
4. **我的串口读取函数在持续数据流下会无限等待**：`Read-UntilQuiet` 只按"多久没有新数据"退出，遇到 inmate 每秒上百行刷屏就永远等不到安静，表现为脚本挂死、看起来像板子卡死。已加绝对超时上限（`maxMs`）并截断输出。**这几次"板子挂了"的假象，根因都在工具侧，不在板子。**
5. **抢 autoboot 的按键选择很关键**：Ctrl-C 会杀死 `serial-getty@ttyLP0`，连续打会触发 systemd 的 `StartLimitBurst=5/StartLimitIntervalSec=10s`，导致 getty 永久不再启动（表现为串口彻底静默，但内核正常）。**只用回车（CR）轮发即可打断 autoboot，且不会打死 getty。**

#### 9.3 对下一步的影响

- 底座已验证 → 不再需要"赌 EVK 容器能不能在 Pro 上启动"。路径 A（UUU 送 EVK 容器）可以降级为备选。
- 剩下要解决的是 **inmate 侧**：把演示 inmate 换成 Harpoon 的 FreeRTOS 应用，并解决三件事：
  1. 拿到 `imx95-harpoon-freertos.cell`（或等价 cell 配置）、FreeRTOS inmate 二进制、inmate 设备树；
  2. 给 inmate 指定**独立于 Linux 控制台**的串口（否则又会失去 Linux 控制权）；
  3. `jh_root_mem`/`jh_clk` 每次启动都要重设，后续要么固化进 U-Boot 环境区，要么写进启动脚本/自制容器。
