# 2026-09-14 FRDM-IMX95-PRO开发日志

## 本日目标

- 在M7 FreeRTOS程序中验证GPIO输出和输入。
- 解决M7访问GPIO2时的TRDC权限问题。
- 分析GPIO镜像运行时COM19反复报告LM2复位的问题。

## 使用环境

- 开发板：NXP FRDM-IMX95-PRO，i.MX95 B0，19x19封装，LPDDR5。
- M7工程：SDK 26.06.00中的FreeRTOS工程，IAR编译。
- 下载接口：J7，i.MX95 USB Serial Downloader。
- 下载工具：UUU 1.5.243。
- 调试串口：J22提供四路UART；本次COM18为M7，COM19为M33 System Manager，COM17为A55启动串口。
- 启动开关：SW4[1:4]为`ON、OFF、OFF、ON`，对应官方表中的`x001` USB Serial Downloader模式。
- 启动方式：UUU RAM临时启动，未写入eMMC。

## 官方依据

- `UM12527`第2.3节给出SW4启动模式：`x001`为USB Serial Downloader，`x010`为eMMC，`x011`为microSD，`x100`为FlexSPI NOR。
- `AN14748`说明M7 BIN通过`imx-mkimage`加入i.MX95启动容器，再通过UUU运行或写入启动介质。
- SDK `driver_examples/rgpio/led_output/cm7/example_board_readme.md`说明官方GPIO示例使用`GPIO2`、`RGPIO_PinInit()`、`RGPIO_PortToggle()`和`GPIO2->PCNS = 0`，并明确该示例不能与默认Linux BSP直接共存。
- `imx-sm`官方README及配置文件表明，System Manager通过Logical Machine和TRDC配置分配核心、外设、内存和访问权限。

## GPIO权限修改

原始Pro配置：

```text
F:\project\Learning\RTOS\tools\imx-sm\configs\other\mx95frdm-pro.cfg
```

测试配置：

```text
F:\project\Learning\RTOS\tools\imx-sm\configs\other\mx95frdm-pro-m7gpio.cfg
```

相对原始配置只改变GPIO2的归属：

- 将`PERLPI_GPIO2 ALL`从LM2/A55的API权限移到LM1/M7。
- 将`GPIO2 OWNER`从LM2/A55资源列表移到LM1/M7。
- 保留M7已有的GPIO_IO14、GPIO_IO15、LPUART7及其引脚权限。
- GPIO3、GPIO4、GPIO5不变。

这不是只开放两个引脚，而是把整个GPIO2寄存器控制器交给M7。TRDC按资源块控制访问；只改IOMUX引脚复用而不改变GPIO2控制器归属，M7仍会在访问GPIO2寄存器时被拒绝。

## FreeRTOS GPIO程序

- GPIO2_IO14配置为输出，对应J15-8。
- GPIO2_IO15配置为输入，对应J15-10。
- FreeRTOS任务每500 ms翻转一次输出并读取输入。
- COM18持续打印输出状态和输入状态。
- 正确地线为J15-39。J15-9是GPIO_IO04，不是GND。

## 实际接线

```text
J15-8  GPIO2_IO14输出 -> J15-10 GPIO2_IO15输入
逻辑分析仪CH0         -> J15-8
逻辑分析仪CH1         -> J15-10
逻辑分析仪GND         -> J15-39
```

不接外部3.3 V或5 V。输入电平直接由GPIO2_IO14提供，避免输入悬空。

## 同时出现的问题

COM19反复输出：

```text
Reset LM 2, reason=fccu, errId=19
```

COM17没有A55 SPL、U-Boot或Linux持续输出。官方SM源码给出：

```c
#define DEV_SM_FAULT_WDOG3 19U
```

注释为`WDOG3 timeout (Watchdog reset request)`。Pro配置中LM2名为`AP`，拥有WDOG3，并配置`FAULT_WDOG3 OWNER, reaction=lm_reset`。因此该信息的含义是：LM2/A55启动后没有在规定时间内维护WDOG3，FCCU收到19号故障，M33上的System Manager按配置关闭并重新启动LM2。LM2再次超时后过程重复，所以COM19持续打印。

这个错误不是GPIO2的TRDC拒绝信息，也不表示M7 GPIO验证失败。M7属于LM1，实测仍持续运行。

## 已确认与未确认

已确认：

- `errId=19`是WDOG3超时。
- 发生故障的是LM2/AP/A55逻辑机。
- `reaction=lm_reset`导致System Manager反复复位LM2。
- M7 FreeRTOS、GPIO输出和GPIO输入均正常运行。
- 当前是USB RAM启动，eMMC中的原Linux没有被覆盖，也没有自动运行。

尚未确认：

- A55停在启动链的具体位置。
- A55未喂WDOG3是否由GPIO2整体转交给M7造成。
- 新编译SM与原始可运行SM的其他二进制差异是否影响A55启动。

## 后续排查方法

不关闭WDOG3，不屏蔽FCCU，也不删除LM复位状态机。用单变量对照定位：

1. 使用同一版本SM源码和原始`mx95frdm-pro.cfg`，搭配已验证的M7 UART程序生成对照容器，确认A55链路是否恢复。
2. 使用GPIO权限版SM，搭配不访问GPIO的旧M7程序，确认LM2复位是否只由SM资源配置触发。
3. 对比COM17、COM19和UUU结果，确定故障随“GPIO2归属”还是随“SM重编二进制”变化。
4. 若确认A55早期启动依赖GPIO2，工程方案应改为选择A55启动阶段不依赖的GPIO资源、调整A55 SPL，或由唯一所有者控制GPIO并通过RPMsg提供服务。
5. GPIO专用测试也可制作不启动LM2的M7-only镜像，但必须先核对官方构建目标和Pro配置，不能把它当成Linux与M7共存方案。

## 当前结论

GPIO输入输出验证已经完成。`Reset LM 2`是另一个A55启动链问题，不应修改M7 GPIO程序来规避。下一阶段是通过受控对照找出WDOG3超时的上游原因，然后再进行SD卡持久化；暂不写eMMC。

## 2026-09-15 WDOG3问题解决结果

先构建并运行“官方原始Pro SM配置 + 相同GPIO M7程序”的严格对照镜像。对照结果为：COM17恢复A55 SPL输出，COM19正常进入SM Debug Monitor且不再出现`errId=19`；由于原始配置不允许M7访问GPIO2，COM18没有GPIO输出。这个单变量对照证明SM重新编译和容器构建本身可以正常启动A55，WDOG3循环由“把整个GPIO2从A55转交给M7”触发。

根据官方SM配置文档，API权限和TRDC访问权限是两套控制。TRDC为每个DID设置独立权限，同一外设可以允许多个DID访问。因此最终配置不再转移GPIO2所有权，而是：

```text
LM2/A55：保留PERLPI_GPIO2 ALL和GPIO2 OWNER
LM1/M7：增加ACCESS: perm=rw, api=none
LM1/M7：增加GPIO2 ACCESS
```

该配置使A55继续拥有GPIO2及其SCMI管理权限，M7只获得直接访问GPIO2寄存器所需的TRDC读写权限。生成的`config_trdc.h`相对官方原始Pro配置只增加一条TRDC寄存器写入；M7的SCMI表中GPIO2仍为`NONE`，A55仍为`ALL`。

重新构建并通过UUU RAM启动后，实机结果为：

```text
COM17：U-Boot SPL正常启动并进入USB SDP等待后续A55镜像
COM18：M7 FreeRTOS UART和GPIO任务持续运行
COM19：DDR OEI完成，System Manager进入Debug Monitor，无WDOG3/FCCU循环
```

由此确认WDOG3问题已解决。COM17最后出现`SPL: failed to boot from all boot devices`，是因为当前`.uuu`脚本只执行一次`SDPS: boot`，没有继续向SPL的SDPV阶段发送完整A55系统，并非WDOG3故障。GPIO日志中`OUT`翻转而`IN`始终为0表示GPIO输入端没有接到输出电平；重新连接J15-8和J15-10后才能进行回环比较，这也不是权限错误。
