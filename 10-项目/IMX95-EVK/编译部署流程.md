# A55 侧编译与部署流程

> **这一篇是给汇报用的**：一条能从头讲到尾的流程，加上必须知道的边界条件。
> 操作细节（七层代码、六条改动路线）见 [[10-项目/IMX95-EVK/开发流程-改代码到上板.md|开发流程：改代码到上板]]。

---

## 一、五步流程

```text
①  改代码
    └─ harpoon-apps/<应用>/freertos/main.c

②  编译（在 WSL 里）
    └─ ./build_ddr_release.sh
    └─ 工具链：arm-gnu-toolchain-13.2.Rel1（aarch64-none-elf，裸机版）
    └─ 产物：ddr_release/<应用>.bin       ← 单个文件，94 KB 量级

③  拷到板子
    └─ scp <应用>.bin  root@<板子IP>:/tmp/

④  板上加载
    └─ jailhouse cell create /usr/share/jailhouse/cells/imx95-harpoon-freertos.cell
    └─ jailhouse cell load freertos /tmp/<应用>.bin -a 0xf0000000
    └─ jailhouse cell start freertos

⑤  看输出
    └─ COM9（LPUART3，inmate 控制台）
```

**这五步就是全部。** 不需要 imx-mkimage 打包、不需要 UUU 重烧、不需要重新上电。

---

## 二、逐步说明

### 第 1 步：改代码

**只有一个文件：**

```text
~/hww/harpoon-apps/hello_world/freertos/main.c
```

在 WSL 里（VSCode 用 WSL Remote 打开 `~/hww/harpoon-apps`）。

**为什么只有一个**：`CMakeLists.txt` 里的源文件列表是写死的，应用入口固定是 `main.c`。

```cmake
set(MCUX_SDK_SRCS
    "${AppPath}/freertos/main.c"        ← 应用入口
    "${BoardPath}/board.c"              ← 板级（所有应用共用）
    "${BoardPath}/mmu.c"                ← 一级页表（所有应用共用）
)
```

**新建 `.c` 文件必须同步改这个列表**，否则不会被编译。

### 第 2 步：编译

```bash
export ARMGCC_DIR=/opt/arm-gnu-toolchain-13.2.Rel1-x86_64-aarch64-none-elf
export PATH=$ARMGCC_DIR/bin:$PATH

cd ~/hww/harpoon-apps/hello_world/freertos/boards/imx95lpd5evk19/armgcc_aarch64
./build_ddr_release.sh
```

或者用封装脚本（一条命令，编完自动拷到 Windows 侧）：

```bash
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh hello_world
```

**`build_ddr_release.sh` 内部就三行**：

```sh
rm -rf CMakeFiles Makefile cmake_install.cmake CMakeCache.txt   # 清掉旧配置
cmake -DCMAKE_TOOLCHAIN_FILE=".../armgcc_aarch64.cmake" \
      -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=ddr_release .      # 生成 Makefile
make -j $(nproc)                                                 # 编译
```

**产物目录里只有两个文件**：

| 文件 | 大小 | 用途 |
|---|---|---|
| `hello_world.elf` | 277,584 B | 完整 ELF，**带符号**，查地址/反汇编用 |
| **`hello_world.bin`** | **94,680 B** | **★ 要 scp 的就是它** |

`make` 编完自动跑一条 `objcopy -O binary`（`CMakeLists.txt` 第 146–147 行），**没有别的后处理**。

**核对入口地址**（建议每次做）：

```bash
aarch64-none-elf-readelf -h ddr_release/hello_world.elf | grep "Entry point"
# 必须输出：Entry point address: 0xf0000000
```

### 第 3 步：拷到板子

```powershell
# Windows PowerShell 里
scp F:\project\Learning\RTOS\build\a55-bin\hello_world.bin root@<板子IP>:/tmp/
```

**板子 IP**：在板子上敲 `ip -brief addr`。

> ⚠️ **`/tmp` 是 tmpfs，断电清空。** 板子重启后必须重新传。

### 第 4 步：板上加载

```bash
jailhouse cell shutdown freertos        # 先停旧的
jailhouse cell destroy  freertos
jailhouse cell create /usr/share/jailhouse/cells/imx95-harpoon-freertos.cell
jailhouse cell load freertos /tmp/hello_world.bin -a 0xf0000000
jailhouse cell start freertos
```

> ⚠️ **`cell load` 必须看到 `can be loaded` 再 `start`。**
> `load` 失败时 `start` 照样会执行，CPU 会从地址 0 取指，
> 报 `instruction abort at 0x200`。

**或者走官方的 systemd 方式**：

```bash
harpoon_set_configuration.sh freertos hello
systemctl start harpoon
```

systemd 方式读 `/etc/harpoon/harpoon.conf` 决定加载哪个 cell、哪个 bin；手工方式可以随时指定任意 bin 和地址。**日常调代码用手工更快。**

### 第 5 步：看输出

**COM9**（LPUART3，FT4232H 通道 A）。

**串口分工**（容易搞混）：

| 串口 | 是什么 |
|---|---|
| COM7 | Linux 控制台（UART1） |
| **COM9** | **inmate 控制台（UART3）** |
| COM8 | SM 调试监视器（UART2） |
| COM6 | FT4232H 的 I2C 通道，**不是串口** |

## 三、核心：为什么只有五步

### 3.1 这段代码不在启动链里

**这是整件事的关键。**

| | 启动链上的东西 | **inmate（我们的代码）** |
|---|---|---|
| 谁加载 | **Boot ROM** | **Linux 侧的 jailhouse** |
| 什么时候 | 上电那一下 | **系统跑起来之后** |
| 从哪读 | 分区表之前的**裸区** | **文件系统**（root 分区） |
| 怎么换 | 只能重写裸区（UUU） | **scp 拷个文件** |
| 生效 | 重新上电 | 重启一个 cell |

**启动链是**：`Boot ROM → SPL → ATF(BL31) → U-Boot → 内核 → Linux`。

这条链上唯一的"容器"是那个 `imx-boot`，里面装 SPL + DDR训练 + ATF + U-Boot + SM 固件。

**inmate 不在里面。**

所以：

- **不需要 imx-mkimage 打包** —— 打包是为了把几个独立编译的东西按 Boot ROM 规定的偏移拼起来，inmate 没这个约束
- **不需要 UUU 重烧** —— 只改文件系统里的一个文件，和写裸区没关系
- **不需要重新上电** —— jailhouse 在运行期把代码放进 cell 的物理地址，然后放 CPU 出去跑

### 3.2 一个 bin 就够，因为链接脚本已经安排好一切

`MIMX9596xxxxx_ca55_ddr_ram.ld` 把 inmate 所有东西安排在一段连续地址空间：

| 段 | 运行地址 | 大小 | 是什么 |
|---|---|---|---|
| `.interrupts` | `0xf0000000` | 6 KB | 异常向量表 + 启动代码 |
| `.text` | `0xf0002000` | 84 KB | 代码 + 只读数据 |
| `.data` | `0xf0600000` | 472 B | 已初始化变量 |
| `.bss` | `0xf0601000` | ~1.7 MB | 未初始化变量（**不占 bin 体积**）|
| 栈 | `0xf0bfe000` | 8 KB | |

**一个 ELF → 一条 `objcopy -O binary` → 一个 bin。没有任何其他输入。**

> **`.data` 有个细节**：它的运行地址是 `0xf0600000`，但在 bin 里紧跟在 `.text` 后面。
> 链接脚本写的是 `> m_data AT > m_text` —— **加载地址和运行地址分离**，
> 启动代码负责把它搬到运行地址。**所以 bin 只有 94 KB，而不是 6 MB 多。**

### 3.3 资源划分是三层，不是一层

新手最容易以为"改了 cell 就行"。**实际是三层，缺任何一层现象都是"程序直接没了"。**

```text
① SM 层（TRDC / RDC）      ← 硬件访问权。由 SM 在启动时按 .cfg 配置
        ↓
② jailhouse cell 层         ← hypervisor 的 stage-2 页表 + 中断表
        ↓
③ inmate 一级页表           ← 应用自己的 stage-1 页表（mmu.c / app_mmu.h）
```

| 层 | 谁在管 | 改哪里 | 改完怎么生效 |
|---|---|---|---|
| ① SM | AON Cortex-M33 上的 SM 固件 | `imx-sm/configs/*.cfg` | **重编 SM + 重烧启动容器** |
| ② cell | jailhouse | `.cell` 文件 | **scp 新 cell + 重建 cell** |
| ③ 一级页表 | inmate 自己 | `mmu.c` 或应用自己的 `app_mmu.h` | 重编应用 |

**实测过的例子**：给 inmate 加 GPIO 时，cell 里没有 RGPIO 段、一级页表里也没有 GPIO2 —— **两处都要加**，只加一处就是"程序一读就死"。

## 四、什么改动要动什么（★ 汇报重点）

| 改动内容 | 改哪个文件 | 编译/重烧 | 部署动作 |
|---|---|---|---|
| **改应用逻辑** | `<应用>/freertos/main.c` | 重编应用 | scp bin + 重建 cell |
| 用**新外设** | 1. `.cell` 加 MMIO 段 + 中断<br>2. 应用加 `app_mmu.h` | 重编应用 | **scp bin + scp 新 cell** |
| 改**链接地址** | 链接脚本 `m_memory` 段 | 重编应用 | scp bin；**`cell load -a` 参数和 cell 的 LOAD 区同步改** |
| 改**板级代码** | `common/freertos/boards/.../board.c` / `mmu.c` | 重编**所有应用** | scp bin |
| 改**设备树** | 内核源码 `.dts` | 编 dtbs | **拷进 boot 分区 + 重新上电** |
| 改**内核** | 内核源码 | 编 `Image` | **拷进 boot 分区 + 重新上电** |
| 改 **SM 配置** | `imx-sm/configs/*.cfg` | **重编 SM** | **重编启动容器 + UUU 重烧** |
| 改 **U-Boot / ATF** | 各自源码 | **重编** | **重编启动容器 + UUU 重烧** |
| 改**内存让出量** | `imx95_evk.env` 的 `jh_root_mem` | **重编 U-Boot** | **重编启动容器 + UUU 重烧** |

**规律很清晰**：

- **前半段（应用、外设、cell、DTB、内核）都是"运行期加载"的** → 拷文件就行
- **后半段（SM、U-Boot、ATF、内存参数）在启动容器里** → 必须走 UUU 重烧裸区

### 一个具体的例子：以后要改成两颗核

老大三阶段可能要求多核（比如 RTOS 用 2 个核）：

| 要改 | 具体改什么 |
|---|---|
| **cell 文件** | 内存段里加第二个 CPU（现在只给了 CPU5） |
| **SM 配置** | `CPU_A55C4` / `CPU_A55C5` 之类的归属 —— **要看 SM 把哪个核分给了谁** |
| **应用** | FreeRTOS 开 SMP（`configNUMBER_OF_CORES = 2`），两个核的启动地址 |
| **部署** | **scp 新 cell** + scp 新 bin，然后重建 cell |

**这几项里只有 SM 那一层要重烧**，其它还是拷文件。

### 改代码 + 编译（WSL）

```bash
# 1. 改 main.c（用 VSCode WSL Remote 打开 ~/hww/harpoon-apps）

# 2. 编译（封装脚本，编完自动拷到 F:\...\build\a55-bin\）
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh hello_world

# 或者手动
export ARMGCC_DIR=/opt/arm-gnu-toolchain-13.2.Rel1-x86_64-aarch64-none-elf
export PATH=$ARMGCC_DIR/bin:$PATH
cd ~/hww/harpoon-apps/hello_world/freertos/boards/imx95lpd5evk19/armgcc_aarch64
./build_ddr_release.sh

# 3. 核对入口地址
aarch64-none-elf-readelf -h ddr_release/hello_world.elf | grep "Entry point"
```

### 部署（Windows → 板子）

```powershell
scp F:\project\Learning\RTOS\build\a55-bin\hello_world.bin root@<板子IP>:/tmp/
```

### 板上加载

```bash
jailhouse cell shutdown freertos
jailhouse cell destroy  freertos
jailhouse cell create /usr/share/jailhouse/cells/imx95-harpoon-freertos.cell
jailhouse cell load freertos /tmp/hello_world.bin -a 0xf0000000
jailhouse cell start freertos
```

### 只换 cell 时（比如以后加了新外设）

```powershell
scp F:\project\Learning\RTOS\build\a55-bin\imx95-harpoon-freertos-gpio.cell root@<板子IP>:/tmp/
```

```bash
# 板上：把新 cell 放到 jailhouse 的目录
cp /tmp/imx95-harpoon-freertos-gpio.cell /usr/share/jailhouse/cells/
# 然后用它建 cell（cell 名从文件里读，不一定是 freertos）
jailhouse cell create /usr/share/jailhouse/cells/imx95-harpoon-freertos-gpio.cell
jailhouse cell load freertos-gpio /tmp/hello_world.bin -a 0xf0000000
jailhouse cell start freertos-gpio
```

## 六、验证点（每次部署后按顺序看）

| # | 验证什么 | 怎么看 | 不对的话说明什么 |
|---|---|---|---|
| 1 | 入口地址对 | `readelf -h \| grep Entry` → `0xf0000000` | 链接脚本被改过 |
| 2 | 文件传到了 | 板上 `ls -l /tmp/*.bin` | scp 失败，或 `/tmp` 被清空 |
| 3 | cell 建起来了 | `jailhouse cell list` | cell 文件路径错，或旧 cell 占着 CPU |
| 4 | 装载成功 | `cell load` 输出含 **`can be loaded`** | bin 地址不对 / 文件没传 |
| 5 | 启动成功 | `cell start` 输出 `Started cell` | — |
| 6 | **有输出** | **COM9 上出现预期打印** | 串口选错 / 外设权限 / 页表缺项 |

## 七、汇报要点

**如果只讲三句话**：

1. **A55 侧的开发闭环是"改一个文件、跑一次编译、拷一个 bin"** —— 因为 RTOS 应用不在启动链里，由 Linux 侧的 jailhouse 在运行期加载，**不需要 imx-mkimage 打包、不需要 UUU 重烧**。
2. **资源划分是三层**（SM 的硬件访问权 → jailhouse cell → inmate 一级页表），**改外设要同时动后两层**；只动 SM 那一层才需要重烧启动容器。
3. **改动越靠下，代价越大**：应用和 cell 是拷文件，设备树和内核要重启，SM / U-Boot / ATF 要重烧。

**如果讲一张图**，就是第一节那张五步流程图。

**要强调的对比**（和以前 M7 那套相比）：

| | 以前（M7 裸机） | **现在（Harpoon / A55）** |
|---|---|---|
| 改一行代码 | 重编 → **imx-mkimage 打包** → **UUU 烧 eMMC** → 重新上电 | 重编 → scp → 重启一个 cell |
| 单次迭代时间 | 几分钟到十几分钟 | **十几秒** |
| 风险 | 烧坏启动区要重新恢复 | 只动文件系统里一个文件 |

**这个对比本身就是汇报的一个亮点 —— 开发效率的提升是 Harpoon 方案的实际收益之一。**
