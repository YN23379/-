# 性能参数是什么、为什么测它们

> **这一篇讲概念**：14 个指标各自是什么、体现系统的什么能力、什么时候会变差。
> 怎么测、代码怎么写见 [[10-项目/IMX95-EVK/性能测试详解.md|性能测试详解]]；
> 实测数据见 [[10-项目/IMX95-EVK/性能与实时性测试方案.md|性能与实时性测试方案]]。

---

## 零、先分清两类东西

老大要的四项（CPU 性能、实时性、任务调度延时、中断延时）**其实是两类完全不同的指标**：

| | **延时（latency）** | **吞吐（throughput）** |
|---|---|---|
| 量纲 | **时间**（ns、μs） | **速率**（次/秒、字节/秒） |
| 问的问题 | "**一件事**要多久办完？" | "**单位时间**能办多少件？" |
| 例子 | 中断延时 791 ns | 整数吞吐 1798 MOPS |
| 谁关心 | **实时系统** —— 要在截止时间前响应 | 数据密集型系统 —— 要处理得完 |

**两者不是一回事，而且经常互相矛盾。**

举个直观的例子：一条洗车流水线。**吞吐**可以是"每小时 60 辆车"，但**单辆车的延时**是"从进去到出来 20 分钟"。**吞吐高不代表延时低。**

反过来说，一个系统响应很快（延时低）也可能效率不高（吞吐低）。

**所以两类指标必须分开测、分开报。**

| 类 | 项目 | 谁提供 |
|---|---|---|
| **A 类：延时** | 中断延时、任务调度延时 | **rt_latency**（NXP 现成，TPM 计时） |
| **B 类：吞吐** | CPU 吞吐、内存带宽、RTOS 开销 | **自己写的程序**（generic timer + 大量平均） |

## 一、实时性 —— 延时类参数

### 1.1 中断延时（irq delay）

**是什么**：

**从"硬件产生中断信号"到"CPU 开始执行中断服务程序（ISR）的第一条指令"。**

```text
  ① 硬件发出中断信号        ② CPU 开始执行 ISR
        │                          │
        │◄────── irq delay ───────►│
```

**这一段里发生了什么**：

| 环节 | 说明 |
|---|---|
| 中断控制器仲裁 | GIC（Generic Interrupt Controller）判断这个中断的优先级、决定要不要送 |
| CPU 完成当前指令 | 处理器不能半路停下，要等当前指令执行完 |
| **异常入口** | 保存现场、跳到异常向量表对应的入口 |
| **hypervisor 处理** | **这一层是虚拟化特有的** |
| 进入 RTOS 的中断处理入口 | 从异常向量跳到 FreeRTOS 的 IRQ handler |

> **UG10170 原文把这一段的开销定义为**"hardware + hypervisor + IRQ vector latency"——
> 也就是说，NXP 自己也是按这个口径算的。

**体现什么**：

**这是系统响应能力的下限。** 不管你的任务优先级多高、调度器多快，
**中断来了至少也要等这么久，CPU 才开始处理。**

**什么时候会变差**：

| 情况 | 为什么 |
|---|---|
| 中断被屏蔽（临界区里关了中断） | 要等临界区结束 |
| 有更高优先级的中断在跑 | 要等它跑完 |
| 中断嵌套 | 新中断要等正在处理的中断让路 |
| hypervisor 开销 | 每个中断都要过一层 |

**实测量级**：**791 ns**（无负载时）。

### 1.2 任务调度延时（irq to sched）

**是什么**：

**从"ISR 里唤醒了某个任务"到"那个任务真的开始跑"。**

```text
  ① 硬件中断          ② 进 ISR          ③ 任务开始跑
        │                 │                  │
        │◄─ irq delay ───►│                  │
        │◄────────── irq to sched ──────────►│
```

**注意**：`irq to sched` 是**从①开始算**的，不是从②开始算 —— 也就是说它**包含** `irq delay`。

所以：

```text
irq to sched  =  irq delay  +  （ISR 到任务的时间）
```

**"ISR 到任务"这一段里发生了什么**：

| 环节 | 说明 |
|---|---|
| ISR 里的处理 | 读硬件、清中断标志 |
| **调用 RTOS API** | 比如 `xSemaphoreGiveFromISR()`，把某个任务从"等待"移到"就绪" |
| **调度决策** | `vTaskSwitchContext()` —— 找出当前优先级最高的就绪任务 |
| **上下文切换** | 保存当前任务的寄存器，恢复目标任务 的寄存器 |
| **恢复正常运行** | 从异常返回，目标任务的 PC 被装入 |

**体现什么**：

**这是 RTOS 的"调度能力"。** 中断已经处理完了，任务多久能被叫起来干活 —— 直接决定系统能不能满足实时性要求。

**什么时候会变差**：

| 情况 | 为什么 |
|---|---|
| 有更高优先级任务在跑 | 得等它让出 CPU |
| 中断持续嵌套 | 调度器插不进去 |
| 调度器本身慢 | 上下文切换开销大 |

**实测量级**：**2005 ns**（无负载时）。

### 1.3 为什么要拆成两段（★ 方法论）

**只测"中断发生 → 任务开始跑"的总时间，出问题时你不知道该怪谁。**

拆开之后，**故障定位一目了然**：

| 现象 | 说明什么 |
|---|---|
| `irq delay` 变大 | **底层问题** —— 中断被屏蔽了、有高优先级中断在跑、hypervisor 开销大 |
| `irq delay` 正常、`irq to sched` 变大 | **RTOS 层问题** —— 调度器慢、有高优先级任务占着 CPU、中断嵌套 |

**这就是为什么 NXP 的 rt_latency 要分开报这两个数。**

### 1.4 中断嵌套下会怎样（TC3）

**什么是中断嵌套**：**高优先级的中断可以打断正在处理的低优先级中断。**

```text
低优先级中断开始处理
    ├── 高优先级中断来了 ──► 插进去先处理
    │       ├── 又来一个 ──► 再插
    │       └── 处理完
    └── 才轮到低优先级中断继续
```

**为什么它专门拖慢 `irq to sched`**：

`irq delay` 测的是"进 ISR 之前"——**只要 CPU 能响应，高优先级中断反而响应得更快**（优先级就是干这个的）。所以这一段受影响小。

但 `irq to sched` 测的是"ISR 到任务" —— **低优先级中断在跑的时候，RTOS 调度器根本插不进去**。中断一个接一个来，任务一直被往后推。

**实测结果证明确实如此**：

| 指标 | TC1（无负载） | **TC3（IRQ 负载）** | 变化 |
|---|---|---|---|
| `irq delay` mean | 791 ns | 911 ns | **只涨 15%** |
| **`irq to sched` mean** | **2005 ns** | **9220 ns** | **涨 4.6 倍** |

**这个用例的意义**：模拟"系统里有一个高频中断源"的场景（比如高频率的 CAN 报文、以太网收包），**测 RTOS 在这种压力下还能不能保证调度实时性**。

## 二、CPU 性能 —— 吞吐类参数

### 2.1 整数吞吐（MOPS）

**是什么**：

**MOPS = Million Operations Per Second（每秒百万次操作）。**

测的是按顺序执行的整数运算（乘、加、移位、异或）**每秒能做多少次**。

**体现什么**：

**CPU 的通用计算能力。** 控制逻辑、状态机、协议解析这类"纯算"的活，速度直接由它决定。

**实测**：**1798 MOPS**（1800 MHz 下）。

**换算成周期**：每轮循环 3 个操作，1.66 ns/轮 × 1.798 GHz = **2.99 周期/轮** ——
也就是说**每 3 个周期做完一轮**，正好是一条乘法依赖链的长度。

> **一个要分清的细节**：这样测出来的是**"依赖链下的有效吞吐"**，不是 CPU 的峰值吞吐。
> 峰值要写多条彼此独立的运算链（让 CPU 的多发射单元并行工作）才能测到。
> **实测值低不代表 CPU 差，而是说明这个负载本身受依赖链限制** —— 真实程序里这种情况很常见。

### 2.2 浮点吞吐（MFLOPS）

**是什么**：

**MFLOPS = Million Floating-point Operations Per Second（每秒百万次浮点运算）。**

**体现什么**：

科学计算、控制算法（PID、滤波、坐标变换）的速度。

**实测**：**719 MFLOPS**。

**这个数偏低，原因要说清楚**：

程序里写的是**标量**运算（一次算一个数，`acc = acc * y + x`）。而 A55 有 **NEON SIMD** 单元，
能一次算 4 个单精度浮点数 —— **理论峰值能到 14 GFLOPS 量级，是实测值的 20 倍。**

**所以 `719 MFLOPS 是标量值，不是这颗 CPU 的浮点峰值。** 要拿峰值得写 NEON intrinsic。

### 2.3 为什么用 LCG 来测

**LCG 是什么**：Linear Congruential Generator（线性同余发生器），一个产生伪随机数的式子：

```c
a = a * 1664525 + 1013904223;
```

**为什么用它做基准**：**`a` 依赖上一轮的 `a`** —— 形成一条**依赖链**。

| 好处 | 说明 |
|---|---|
| **编译器不能并行化** | 下一轮必须等上一轮算完 |
| **编译器不能折叠循环** | 每轮结果不同，没法预先算出总和 |
| **和真实代码像** | 真实程序里也是到处都有前后依赖 |

**如果用互相独立的运算**（比如 `x1=a*b; x2=c*d; x3=e*f;`），CPU 的多发射单元会并行执行，
测出来的就不是单条链的速度了。

## 三、内存子系统

### 3.1 memcpy 带宽（三档）

**是什么**：

**单位时间能搬运多少字节**（GB/s）。

**为什么测三档**：**因为内存是有层级的，速度差很多。**

| 层级 | 典型容量 | 特点 |
|---|---|---|
| **L1 cache** | 几十 KB | 最快，和 CPU 同频 |
| **L2 cache** | 几百 KB 到几 MB | 次快 |
| **DDR 主存** | GB 级 | 慢得多 |

**测三档就是为了看出"数据在哪个层级"**：

| 大小 | 源+目标 | 落在哪 | 实测带宽 |
|---|---|---|---|
| 4 KB | 8 KB | L1 内 | 11.45 GB/s |
| **16 KB** | **32 KB** | **L1 内（正好装满）** | **12.36 GB/s** ← 最快 |
| 64 KB | 128 KB | 超出 L1，走 L2 | 8.08 GB/s |

**注意 4 KB 比 16 KB 慢** —— **不是 cache 问题，是函数调用开销占比大**（搬得太少，开销摊不薄）。
**这个容易误读，要留意。**

**体现什么**：

**数据密集型应用的能力上限** —— 图像处理、网络收发包、DMA 搬运、大数组运算。

**什么时候会变差**：数据超出 cache、和别的核抢内存带宽（比如 Linux 侧同时在大批量搬数据）。

### 3.2 访存延迟

**是什么**：

**CPU 发出一次读请求，到数据真正到手的耗时。**

```text
CPU: "我要读地址 X 的内容"  ──►  内存系统  ──►  数据回来
        │                                          │
        │◄────────── 访存延迟 ────────────────────►│
```

**和带宽的区别**：**带宽是"一次搬一大批有多快"，延迟是"搬第一个要等多久"。**

一个贴切的类比：**带宽是高速路的通行能力，延迟是从入口到出口要开多久。** 路再宽，你还是要开那么久。

**为什么用"指针追逐"来测**：

```c
p = &array[0];
for (...) { p = (uint32_t *)(*p); }   /* 取出的值当下一个地址 */
```

**每次的地址依赖上一次读到的内容** —— 形成一条**纯访存依赖链**，
CPU 的乱序执行和预取器都插不上手，**测到的就是单次访存的真实延迟**。

**实测**：**8.39 ns**（约 15 个周期）。

> **这个数有交叉验证**：在 500 MHz 和 1800 MHz 下各测一次，
> 换算成**周期数都是 14–15**（`28.08 ns × 0.5 GHz = 14.0`、`8.39 ns × 1.798 GHz = 15.1`）。
> **说明它是 L2 的物理特性，不随 CPU 频率变** —— 同时也反证了主频测的是对的。

**体现什么**：

**随机访问的性能** —— 链表、哈希表、树、以及任何"下一个访问地址由上一次结果决定"的代码。

**连续访问不受这个限制**（有预取和 cache line 帮忙），这也是为什么 memcpy 能跑到 12 GB/s 而单次随机读要 8 ns。

## 四、RTOS 内核开销

### 4.1 上下文切换（context switch）

**什么是"上下文"**：

**一个任务在某一刻的全部 CPU 状态** —— 通用寄存器、程序计数器（PC）、栈指针（SP）、状态寄存器。

**切换做了什么**：

```text
① 把当前任务的寄存器全存进它自己的栈
② 从下一个任务的栈把寄存器全恢复出来
③ 跳去执行下一个任务
```

**为什么会有开销**：几十条 load/store 指令，加上"该切给谁"的调度决策。

**怎么测**：两个同优先级任务互相让，数一定时间内让了多少次。

**★ 关键发现：这个开销分成两部分**

我们做了**三路对照** —— 同一个框架，只换中间的 IPC 机制：

| 路径 | 里面有什么 | 实测 |
|---|---|---|
| **纯 `taskYIELD()`** | **只有切换** | **202 ns（363 周期）** |
| 任务通知 | 通知 API + 切换 | 649 ns（1167 周期） |
| 二进制信号量 | 信号量 API + 切换 | 1150 ns（2068 周期） |

**读出来的东西**：

```text
纯切换            363 周期  ← FreeRTOS 的常规量级是 300–600，正常
任务通知额外 +804 周期
信号量额外   +1705 周期    ← 比通知贵一倍
```

**为什么信号量这么贵**（FreeRTOS 的设计）：**信号量是建在队列机制上的** ——
一个信号量本质就是"长度为 1、初始计数为 0 的队列"。
所以一次 `xSemaphoreGive` 要走完 `xQueueGenericSend` 的完整路径：
队列容量检查 → event list 操作 → 数据拷贝 → 唤醒任务。

**而任务通知直接挂在任务的 TCB 上，没有队列和 event list，路径短得多。**

**体现什么**：

**RTOS 在多任务之间切换的效率。** 切换越频繁的场合（高频 IPC、很多小任务），这个开销越重要。

**顺带**：**1148 ns 里只有 18% 是切换，82% 是信号量路径** —— 这条结论直接指导选型：
**高频 IPC 场景改用任务通知，能省 43%。**

### 4.2 tick 超调

**什么是 tick**：

FreeRTOS 的"心跳" —— 一个硬件定时器**每 1 ms 产生一次中断**（`configTICK_RATE_HZ = 1000`）。
系统的所有延时（`vTaskDelay`）、超时都基于它。

**`vTaskDelay(N)` 是怎么实现的**：

把当前任务放进"延迟列表"，标记"再过 N 个 tick 唤醒我"，然后让出 CPU。

**★ 这里有个容易搞错的地方**：

**`vTaskDelay(1)` 不是"等 1 毫秒"，而是"等到下一个 tick 边界"。**

```text
tick:      │         │         │
           ▼         ▼         ▼
时间:  ────┼─────────┼─────────┼────
           │         │
        在这里调用 vTaskDelay(1)
           │         │
           └─ 只等了 0.3 ms ─┘
```

**如果在 tick 前 0.3 ms 调用，它就只等 0.3 ms 就返回。** 这是**设计如此**，不是 bug。

**所以"超调"要看 `max - ideal`（比 1 ms 多等了多久），不是 `max - min`。**

**实测**：**666–708 ns 超调**。

**体现什么**：

**系统的定时精度上限。** 任何基于 tick 的延时，实际精度都不会好于这个值。

### 4.3 空载 CPU 负载

**是什么**：

**系统闲着的时候，CPU 有多少时间在忙。**

FreeRTOS 空闲时跑的是"空闲任务"（idle task）。测它的占比就知道还有多少余量。

**实测**：**1.83%**。

**换算**：5 秒里 1.83% ≈ 91 ms，每毫秒约 18 μs —— **差不多就是 tick 中断本身的开销**。

**体现什么**：

**系统的余量。** 空载负载越低，留给应用的空间越大。

## 五、测试方法（三个关键决定）

### 5.1 计时：用板子自己的硬件定时器

**用什么**：ARM **generic timer** 的 `cntvct_el0`（自由运行的计数器）+ `cntfrq_el0`（频率）。

**为什么选它**：FreeRTOS 的 tick 用的就是它，**cell 里已经能用，不用配任何东西。**

**它的天花板**：实测 **24 MHz**，一个刻度 = **41.7 ns**。

**这个限制很关键**：测"任务切换 202 ns"时，单次误差就有 20%。

**→ 所以所有结果都是几十万到两千万次操作的平均值。**

（rt_latency 用 **TPM** 硬件定时器，能测到更细的边沿，**所以延时类指标用它。**）

### 5.2 频率：必须钉住

**为什么**：A55 有 **500 / 900 / 1404 / 1800 MHz** 四个档，Linux 侧默认 `ondemand` 动态调。

**而 A55 是一个 cluster，六个核共用一个频率** —— Linux 在 CPU0–4，RTOS 在 CPU5，
**jailhouse 隔离了核和内存，但没隔离频率。**

**不钉住的话，同一份代码测出来差 3.6 倍。**

**→ 所以程序里每一项都实测并打印 CPU 主频，数据自带工况标注。**

### 5.3 主频怎么测（不用外部仪器）

**原理**：A55 上 `add` 指令的延迟是 **1 个周期**。
串 40 条**相互依赖**的 `add`，每轮循环正好花 40 个周期。

**为了消掉循环开销**，测两种展开长度（40 和 80）**做差**：

```text
(T80 - T40) 正好对应 40 × n 个 CPU 周期，常数项被减掉了
```

**准确性**：程序实测 **1798 MHz**，Linux 的 `scaling_cur_freq` 报 **1800000** ——
**两个完全独立的方法互相印证。**

## 六、测试用例怎么写

### 6.1 三条通用原则

| 原则 | 为什么 |
|---|---|
| **用依赖链，不用独立运算** | 独立运算会被 CPU 多发射并行掉，测不出单条链的速度 |
| **结果写进 `volatile`** | 否则编译器发现结果没用，会**把整个循环删掉** |
| **迭代次数要够多** | 计时器只有 41.7 ns 分辨率，单次测不准 |

### 6.2 每个用例的统一结构

```c
static void bench_xxx(void)
{
    say("-- [N] xxx --");
    mhz_line();              /* ★ 先打实测主频 */

    t0 = rd_cntvct();
    ... 被测操作循环 N 次 ...
    t1 = rd_cntvct();
    sink = 结果;             /* 防优化 */

    ns = 转换(t1 - t0);
    /* 打印 */
}
```

**`mhz_line()` 是加在每一项开头的** —— 这样每条数据自己会说明是在什么频率下测的。

### 6.3 ★ 对照实验的设计（最有价值的一条）

**任务切换那一组是最好的例子**：`[5]` `[8]` `[9]` 三个函数**框架完全一样**，
**只有中间那一句 IPC 调用不同**：

```c
/* [8] 纯切换 */
taskYIELD();

/* [9] 任务通知 */
xTaskNotifyGive(handle);

/* [5] 信号量 */
xSemaphoreGive(sem);
```

**只有"每次只换一个变量"，测出的差异才能归因到那个变量本身。**

最初只测了信号量，得到 1148 ns —— 比预期大 3 倍，**但不知道是切换慢还是信号量慢**。
三路一对照，**立刻看出切换只有 202 ns，问题在信号量路径。**

**这个套路可以复用**：以后测任何机制的开销，都拿"最简形式"当下界做对照。

### 6.4 几个具体用例的构造要点

| 用例 | 关键设计 |
|---|---|
| **整数 / 浮点** | LCG 造依赖链、结果写 volatile |
| **memcpy** | 三档大小对应三个存储层级，每档搬同样的总量 |
| **访存延迟** | 指针追逐 + **满周期 LCG 串成单环**（防止掉进短子环，那样测到的是 cache 命中而不是内存延迟）+ 相邻间隔 264 字节（防预取） |
| **任务切换** | 三路对照，同框架只换 IPC |
| **tick** | 看 `max - ideal`，不是 `max - min` |
| **CPU 负载** | 复用 harpoon-apps 现成的 `cpu_load_stats()` |
