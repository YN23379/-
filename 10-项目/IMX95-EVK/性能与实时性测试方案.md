## 二、测试方法

### 2.1 计时手段：为什么用 generic timer

```c
static inline uint64_t rd_cntvct(void)
{
    uint64_t v;
    __asm__ volatile("mrs %0, cntvct_el0" : "=r"(v));
    return v;
}
```

读数来自 ARM generic timer 的 **`cntvct_el0`**（计数器）和 **`cntfrq_el0`**（频率）。

**选它的原因**：FreeRTOS 的 tick 用的就是这个定时器（`common/freertos/FreeRTOS_tick_config.c:40` 里 `#define ARM_TIMER ARM_TIMER_VIRTUAL`），**cell 里已经能用，不用配任何东西**。

**实测 `cntfrq = 24 MHz`，分辨率 41.7 ns。** 这是它的天花板 —— 单次几百纳秒的操作测不准。

**所以所有结果都是 N 次平均**：
- 整数 2000 万次迭代
- 浮点 200 万次
- memcpy 每档搬 16 MB
- 指针追逐 200 万步
- 任务切换 20 万次

**这也是 rt_latency 用 TPM 而不是 generic timer 的原因** —— TPM 能测更细的边沿。**分工**：

| 测什么 | 用谁 |
|---|---|
| 中断延时、调度延时 | **rt_latency**（TPM 计时） |
| CPU 吞吐、任务切换、tick | **本程序**（generic timer 平均） |

### 2.2 CPU 主频实测

**这是本方案里最关键的一段。** 起因是同一块板子两次跑，整数吞吐差了 2.5 倍，而 memcpy 和访存延迟一模一样 —— 典型的"核频率变了"。

**原理**：A55 上 `add` 的延迟是 **1 个周期**。串 40 条**相互依赖**的 `add`，每轮循环正好花 40 个周期（`subs`/`bne` 那条链独立，能并行掉）。

**为消掉循环开销，测两种展开长度做差**：

```c
t40 = chain_ticks(n, 0);   /* .rept 40 */
t80 = chain_ticks(n, 1);   /* .rept 80 */
d = t80 - t40;             /* 正好对应 40 * n 个 CPU 周期，常数项被减掉 */
MHz = 40 * n * cntfrq / (d * 1e6);
```

**准确性和 `scaling_cur_freq` 相互印证**：程序实测 **1798 MHz**，Linux 报 **1800000 Hz**。

### 2.3 各项基准怎么写的

| 项 | 怎么写 | 怎么防优化 |
|---|---|---|
| **整数** | LCG：`a = a*1664525+1013904223`，加移位和异或，三个操作一组 | 结果写进 `volatile` |
| **浮点** | `acc = acc*y + x`，定点累加 | 同上 |
| **memcpy** | 4 KB / 16 KB / 64 KB 三档，每档搬 16 MB | 缓冲先 `memset` 成不同值 |
| **指针追逐** | 用**满周期 LCG `x→33x+1 mod 2^14`** 把 16384 个指针串成一个**单环**，相邻访问间隔 33 个元素（264 字节），预取器跟不上 | 最后写 `volatile` sink |
| **任务切换** | **三路对照**，同样结构只换 IPC：`[8]` 纯 `taskYIELD`、`[9]` 任务通知、`[5]` 二进制信号量 | 计数用 `volatile` |
| **tick** | 200 次 `vTaskDelay(1)`，记 min/mean/max | — |
| **CPU 负载** | 复用 harpoon-apps 现成的 `cpu_load_stats()`（在 `common/freertos/idle.c`） | — |

**指针追逐那个单环构造值得记一下**：`x → 33x+1 mod 2^14` 是**满周期 LCG**（`c=1` 与 `m` 互质；`a-1=32` 能被 `m` 的唯一质因子 2 整除；`a-1` 能被 4 整除），所以从任一元素出发都能走遍全部 16384 项，不会掉进短的子环。

## 四、实际结果

### 4.1 ★ 最大发现：DVFS 由 Linux 侧控制

**三个命令的结果**：

```text
scaling_governor        = ondemand
scaling_available_freqs = 500000 900000 1404000 1800000     ← 四档
scaling_cur_freq        = 1404000（改之前）
```

**程序实测主频 498 MHz，正好是最低档 500 MHz。**

**为什么 Linux 能影响 RTOS**：**A55 是一个 cluster，六个核共用一个频率。** Linux 在 CPU0–4，RTOS 在 CPU5，**jailhouse 隔离了核和内存，但没有隔离频率**。

```text
Linux 负载变化 → ondemand 调频 → 整个 cluster 频率变 → RTOS 性能跟着变 3.6 倍
```

**这个结论对项目的影响**：

1. 性能报告**必须**标注频率
2. rt_latency 之前的延迟数据也要补这个注，否则换工况不复现
3. 生产环境要么钉死频率，要么接受这个不确定性

## 五、逐项分析

### 5.1 整数 2.99 周期/次 —— 完美自洽

临界路径是 `a = a*1664525 + 1013904223`。实测 1.66 ns/次 × 1.798 GHz = **2.99 周期**。

**说明循环完全被依赖链限制，没有额外开销**（循环控制指令被 3 宽发射吃掉了）。这也反过来验证了主频实测是对的。

### 5.2 浮点 5.00 周期/次，但绝对吞吐偏低

719 MFLOPS 对 1.8 GHz 的 A55 来说**偏低** —— 理论峰值（NEON SIMD 4 路 FMA）能到 14 GFLOPS 量级。

**说明是纯标量运算，没有向量化。** 程序里写的就是标量 `acc = acc*y + x`，符合预期。

**要拿浮点峰值，得写 NEON intrinsic 或者让编译器自动向量化** —— 这是后续可以补的一项。

### 5.3 访存延迟 15.1 周期 —— 两次独立验证

| 频率 | ns/步 | 换算周期 |
|---|---|---|
| 500 MHz | 28.08 | 14.0 |
| 1800 MHz | 8.39 | 15.1 |

**两次都是 14–15 周期** —— 这证明访存延迟是 **L2 的物理特性，不随核频率变**。

**这个交叉验证同时证明了两件事**：主频测量是准的；dvfs 只改核频，不改访存路径。

### 5.4 memcpy 的趋势完全符合 cache 预期

| 大小 | 带宽 | 字节/周期 | 为什么 |
|---|---|---|---|
| 4 KB | 11.45 GB/s | 6.4 | 装得进 L1，但**函数调用开销占比大** |
| **16 KB** | **12.36 GB/s** | **6.9** | **源+目标 32 KB 正好装进 L1，开销也摊薄了** ← 最快 |
| 64 KB | 8.08 GB/s | 4.5 | 源+目标 128 KB **超出 L1**，每次访问走 L2 |

**4 KB 比 16 KB 慢是"开销占比"造成的，不是 cache 问题** —— 这个容易误读，要留意。

### 5.5 ★ 任务切换开销拆解：三路对照

最初只测了信号量路径，得到 1148 ns ≈ 2064 周期，比 FreeRTOS 在 A55 上的常规值（300–600 周期）大 3–4 倍，怀疑测量或端口有问题。**做了三路对照之后，疑点解除。**

**实验设计**：三条路径跑同样的 ping-pong，结构完全一样，只换 IPC 机制。

| 键 | 路径 | 包含什么 |
|---|---|---|
| `[8]` | **纯 `taskYIELD()`** | **只有上下文切换**，零 IPC 开销 |
| `[9]` | **任务通知** | `xTaskNotifyGive` + `ulTaskNotifyTake` + 切换 |
| `[5]` | **二进制信号量** | `xSemaphoreGive` + `xSemaphoreTake` + 切换 |

**实测结果**（1800 MHz，各跑 3 次）：

| 路径 | ns/次 | **周期数** | 3 次极差 |
|---|---|---|---|
| **`[8]` 纯切换** | **202.10 / 202.18 / 202.10** | **363** | **0.08 ns** |
| **`[9]` 任务通知** | **649.03 / 649.16 / 649.17** | **1167** | **0.14 ns** |
| **`[5]` 信号量** | **1150.26 / 1150.36 / 1150.36** | **2068** | **0.10 ns** |

**层次非常分明，三次跑几乎逐位一致。**

**拆解**：

| 路径 | 周期数 | 比纯切换多出的 |
|---|---|---|
| 纯切换 | 363 | — |
| 任务通知 | 1167 | **+804 周期**（通知路径开销）|
| 信号量 | 2068 | **+1705 周期**（信号量路径开销）|

**三条结论**：

**① `[8]` 363 周期，正好落在预期区间（300–600）里 —— 上下文切换本身完全正常。**

之前"任务切换偏大"的疑点解除：**问题不在切换，在信号量。**

**② 1148 ns 里只有 202 ns（18%）是切换，946 ns（82%）是信号量路径的开销。**

原因（`源码可确认`，FreeRTOS 的设计）：**FreeRTOS 的信号量是建立在队列机制之上的** —— 信号量本质是"长度为 1、初始计数为 0 的队列"。所以一次 `xSemaphoreGive` 要走完 `xQueueGenericSend` 的完整路径：队列容量检查、event list 操作、数据拷贝、`xTaskRemoveFromEventList`。

**而任务通知直接挂在 TCB 上**，没有队列和 event list，路径短得多。

**③ 信号量比任务通知贵 43%**（2068 vs 1167 周期）。

**对二阶段任务的意义**：老大要求"按键任务 → 二进制信号量 → 传感器任务"。实测两者差 501 ns，**但按键触发是低频事件（人按键），这个差异在实际场景里没有意义**。

**只在高频 IPC 场景（每毫秒多次）才值得改用任务通知。**

> **这个对照表本身也有方法论价值**：以后测任何 IPC 机制的开销，都可以用同一套 ping-pong 框架，对照"纯 taskYIELD"这个下界。

### 5.6 tick 超调 666–708 ns（约 1205 周期）

1 kHz tick 的完整 ISR + 调度路径。**偏大但可接受** —— 意味着 tick 中断本身占了约 0.07% 的 CPU。

### 5.7 空载 CPU 负载 1.83%

空闲任务在跑时的 CPU 占用。**换算下来每毫秒约 10–18 μs**，差不多就是 tick 中断的开销。

（`cpu_load_stats()` 的输出顺序不可靠 —— 它走 `hlog`，和程序里直接写 LPUART3 不是同一条路。**要读的是 `>>> WINDOW END` 和 `<<< DONE` 中间那个数。**）

### 6.3 踩过的坑

| 现象 | 根因 | 处置 |
|---|---|---|
| **按 `7` 之后整个 cell 卡死** | `ticks_to_ns()` 返回 `uint32_t`（封顶 **4.29 秒**），却拿去和 5 秒比较 → **恒为真，死循环** | 改成比 tick 数；`ticks_to_ns` 改成饱和不绕回 |
| 整数吞吐两次差 2.5 倍，其它指标不变 | **CPU 频率被 Linux 的 ondemand 改了** | 钉住 `scaling_governor=performance` |
| `CPU load` 读数对不上 | `cpu_load_stats()` 走 `hlog`，和程序直写 LPUART3 不是同一条输出路径，**串口上顺序会乱** | 用 `say()` 打标记对齐 |
| tick "抖动" 194–459 μs | **指标算错了** —— `vTaskDelay(1)` 是等到下一个 tick 边界，min 小于 1 ms 是**设计如此** | 改看 `max - ideal` |

## 九、附：FreeRTOS "跑通"的九级判据

> 这一节回答的是另一个问题：**现在算不算跑通了 FreeRTOS。**
> 结论：**跑通了 L1–L6（功能），没做 L7–L9（稳定性和边界）。**

| 级 | 要证明什么 | 判据 | 状态 |
|---|---|---|---|
| **L1** | 调度器活着 | 多个任务交替执行，`vTaskDelay()` 按 tick 返回 | ✅ |
| **L2** | tick 中断正常 | 输出节奏稳定；rt_latency 采样周期精确 100 μs | ✅ |
| **L3** | 中断能进、能唤醒任务 | `irq delay` / `irq to sched` 都测出来了 | ✅ |
| **L4** | 能改能部署 | 改代码 → 编译 → 部署 → 板上生效 | ✅ |
| **L5** | 外设驱动能用 | UART 收发、GPIO 输入输出 | ✅ |
| **L6** | 实时性达标 | 延迟数据和 UG10170 官方参考值最大偏差 25 ns | ✅ |
| **L7** | **长时间稳定** | **连续跑几小时/几天不崩、不漂** | ❌ |
| **L8** | **多任务 + 同步原语** | **队列、信号量、互斥量、事件组实测** | ❌ |
| **L9** | **资源边界** | **堆用满、栈溢出、优先级反转会怎样** | ❌ |

**L7–L9 的具体做法**：

- **L7**：循环跑 rt_latency 或本程序，观察 `xPortGetFreeHeapSize()` 是否随时间下降、`late alarm scheduling` 是否偶尔涨
- **L8**：SDK 里 `freertos_examples/` 下有 `freertos_queue` / `freertos_sem` / `freertos_mutex` / `freertos_event` / `freertos_swtimer` 五个现成示例（**CM7 版，要移植到 A55**）
- **L9**：`configTOTAL_HEAP_SIZE` 在哪、`configCHECK_FOR_STACK_OVERFLOW=2` 已开、`vApplicationStackOverflowHook` 已实现
