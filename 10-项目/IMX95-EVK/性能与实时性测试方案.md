## 一、"跑通"要分层看

**一句话：现在算跑通了"功能"，没跑通"稳定性"和"边界"。**

"跑通 FreeRTOS"不是一个是非题，得看**想证明什么**。按从易到难列成九级：

| 级 | 要证明什么 | 判据（怎么算过） | 状态 |
|---|---|---|---|
| **L1** | 调度器活着 | 多个任务交替执行，`vTaskDelay()` 按 tick 返回 | ✅ |
| **L2** | tick 中断正常 | 输出节奏稳定；定时器采样周期精确 | ✅ |
| **L3** | 中断能进、能唤醒任务 | 硬件中断 → handler → 任务被调度，链路通 | ✅ |
| **L4** | 能改能部署 | 改代码 → 编译 → 部署 → 板上生效 | ✅ |
| **L5** | 外设驱动能用 | UART 收发、GPIO 输入输出 | ✅ |
| **L6** | 实时性达标 | 延迟数据可复现，和官方参考值对得上 | ✅ |
| **L7** | **长时间稳定** | **连续跑几小时/几天不崩、不漂** | ❌ **没做** |
| **L8** | **多任务 + 同步原语** | **队列、信号量、互斥量、事件组实测** | ❌ **没做** |
| **L9** | **资源边界** | **内存用满、栈溢出、优先级反转会怎样** | ❌ **没做** |

### 1.1 前六级为什么算过了 —— 逐条给证据

| 级 | 证据 |
|---|---|
| **L1** | `hello_world` 的 `hello_func` 和 `tictac_func` 两个任务交替输出，`tictac_func` 里 `vTaskDelay(1 * configTICK_RATE_HZ)` 的节奏稳定 —— **tick + 调度器 + 上下文切换三者都在工作** |
| **L2** | `rt_latency` 的直方图每 10 秒整 **100,000** 个样本 → 每 100 μs 一次，和 UG10170 §4.6 说的采样周期分毫不差；`late alarm scheduling: 0` 全程为 0 |
| **L3** | `rt_latency` 的 `irq delay` 均值 791 ns（硬件中断→handler）、`irq to sched` 均值 2,045 ns（handler→任务）—— 这两段都测出来了，说明整条中断链路通 |
| **L4** | 改 `main.c` 打印 `Goodbye world`，编译 → scp → 重载 cell → COM9 出新输出 |
| **L5** | UART 收：终端敲键有回显；GPIO 输入：按住键读到 `samples==0 : 2768`、`edges : 84`；GPIO 输出：位翻转的 `[[GPIO-TX]]` 被 PC 正常收到 |
| **L6** | 六个 TC 的延迟值和 UG10170 Table 22 最大偏差 **25 ns**（IRQ 负载那行 9,189 vs 9,214） |

### 1.2 L7–L9 为什么不能省

**L7 长时间稳定**：现在所有测试都是几十秒量级。**跑一分钟不崩，和跑一天不崩，是两回事。** 要看的指标：

- 有没有内存泄漏（FreeRTOS 的 `xPortGetFreeHeapSize()` 随时间变不变）
- tick 有没有累积漂移（`rt_latency` 的统计计数器随时间的增长率稳不稳）
- 有没有偶发异常（几天里 `late alarm scheduling` 会不会偶尔涨一下）

**L8 多任务 + 同步原语**：现在只跑过"两个互不相干的任务"和 rt_latency 内部的任务。**队列、信号量、互斥量、事件组的实际行为没测过。** SDK 里有现成的 FreeRTOS 示例可以对照改：

```text
SDK_26_06_00_IMX95LPD5EVK-19/boards/imx95lpd5evk19/freertos_examples/
├── freertos_hello      任务创建（等价于现在跑通的）
├── freertos_generic    通用示例
├── freertos_sem        信号量
├── freertos_mutex      互斥量
├── freertos_queue      队列
├── freertos_event      事件组
└── freertos_swtimer    软件定时器
```

**注意这些是 CM7 版**（目录下只有 `cm7`），API 一样但要移植到 harpoon-apps 的 A55 工程里。

**L9 资源边界**：

- 内存：`configTOTAL_HEAP_SIZE` 在 `FreeRTOSConfig_Gen.h` 里（本地 SDK 里这个文件被改过，见 git status）
- 栈溢出：开 `configCHECK_FOR_STACK_OVERFLOW`，看 `vApplicationStackOverflowHook` 会不会被触发
- 优先级反转：这不是"能不能跑"的问题，是"设计对不对"的问题

## 二、性能 / 实时性测试：要测什么、用什么测

### 2.1 测试矩阵

| 想测什么 | 现成的手段 | 状态 |
|---|---|---|
| **中断延时**（硬件中断 → 进 ISR） | `rt_latency -r 1` 的 `irq delay` | ✅ 已测 |
| **任务调度延时**（ISR → 任务运行） | `rt_latency -r 1` 的 `irq to sched` | ✅ 已测 |
| **中断嵌套下的调度延时** | `rt_latency -r 3`（IRQ 负载） | ✅ 已测 |
| **Linux 重载下的实时性** | `rt_latency -r 5` + `stress-ng` | ✅ 已测 |
| **CPU 吞吐性能** | ❌ **没有现成的** | 要自己做 |
| **纯任务切换开销**（任务 → 任务） | ❌ rt_latency 测的是"中断→任务"，不是这个 | 要自己做 |
| **内存带宽 / 访存延迟** | ❌ | 要自己做 |
| **长时间稳定性** | 循环跑 rt_latency 或自写长跑程序 | 要自己做 |

**结论：NXP 只给了"中断/调度延时"这一类的现成工具（rt_latency），CPU 吞吐和内存性能要自己写。**

### 2.2 现成能用的：rt_latency

```bash
harpoon_set_configuration.sh freertos latency
systemctl start harpoon
harpoon_ctrl latency -r <1..6>
```

| TC | 测的是什么 |
|---|---|
| 1 | 基线：中断延时 + 调度延时 |
| 2 | CPU 负载下的（低优先级任务忙循环） |
| 3 | **中断嵌套下的调度延时** —— 唯一会让 `irq to sched` 数量级变差的一项（2 μs → 9 μs） |
| 4 | CPU + 信号量负载 |
| 5 | CPU + Linux 负载（**要手动压 Linux**） |
| 6 | CPU + cache flush（**只刷 I-Cache，D-Cache 是 TODO**） |

**测量原理**：用 **TPM 硬件定时器**（i.MX 9 上是 TPM，i.MX 8M 上是 GPT），每 **100 μs** 采一次样，相对硬件中断事件时刻计时，亚微秒精度。

### 2.3 CPU 吞吐性能：要自己写

**没有现成的。** NXP 的 SDK 里 `demo_apps` 只有 `hello_world` / `power_mode_switch` / `sai_low_power_audio` / `temperature_measurement`，**没有 benchmark**。

**标准做法是 CoreMark**，但这个 Harpoon A55 环境没有现成的移植，要自己做。

#### 自己写的话，测什么

| 项 | 怎么测 | 说明 |
|---|---|---|
| **整数吞吐** | 固定次数的乘加/移位循环，计时除次数 | 用 `volatile` 防优化掉 |
| **浮点吞吐** | 同上，用 float/double | 注意 A55 有没有开 NEON |
| **memcpy 带宽** | 固定大小、多次 memcpy，算 MB/s | 反映 DDR 带宽 |
| **访存延迟** | 指针追逐（pointer chasing） | 反映 cache 命中情况 |
| **任务切换开销** | 两个任务互相给信号量，测 N 次的总时间 / N | 这才是"纯切换"开销 |

#### 计时用什么

**用 ARM generic timer**：

```c
uint64_t cnt, freq;
__asm volatile("mrs %0, cntvct_el0" : "=r"(cnt));
__asm volatile("mrs %0, cntfrq_el0" : "=r"(freq));
/* 时间(ns) = (cnt2 - cnt1) * 1000000000ULL / freq */
```

**为什么用这个**：FreeRTOS 的 tick 用的就是它（`common/freertos/FreeRTOS_tick_config.c:40` 里 `#define ARM_TIMER ARM_TIMER_VIRTUAL`），**已经在 cell 里、已经能用**，不用额外配任何东西。

**别用 TPM 计时**：TPM 虽然精度更高，但会被 rt_latency 占着，而且要走 SCMI 配时钟。

### 2.4 具体要改哪些文件

| 改什么 | 文件 | 说明 |
|---|---|---|
| **程序逻辑** | `harpoon-apps/<应用>/freertos/main.c` | 加 benchmark 任务 |
| **计时** | 同上，用 `cntvct_el0` | **不用改配置** |
| **要用新外设**（如 TPM 输出 PWM） | `common/freertos/boards/imx95lpd5evk19/mmu.c` **或**应用目录下自己的 `app_mmu.h` | 一级页表白名单 |
| **链接新驱动** | `<应用>/freertos/boards/imx95lpd5evk19/armgcc_aarch64/CMakeLists.txt` | 加 `set(CONFIG_USE_driver_xxx true)` + `include(driver_xxx)` |
| **要新外设的 MMIO/中断** | `.cell` 文件 | 见路线 C |

#### CMakeLists 怎么看要加什么

`hello_world` 的 CMakeLists 里是这样的（`源码可确认`）：

```cmake
set(CONFIG_USE_driver_cache_armv8a true)
set(CONFIG_USE_driver_clock true)
set(CONFIG_USE_driver_common true)
set(CONFIG_USE_driver_iomuxc true)
set(CONFIG_USE_driver_lpuart true)
set(CONFIG_USE_driver_mu1 true)
...
include(driver_clock)
include(driver_common)
include(driver_lpuart)
```

**要加 TPM 就照格式加两行**：

```cmake
set(CONFIG_USE_driver_tpm true)
include(driver_tpm)
```

驱动本体在 `mcux-sdk/drivers/tpm/`（`fsl_tpm.c` / `fsl_tpm.h`），**A55 可用**（harpoon-apps 就是链 mcux-sdk）。

### 2.5 编译、部署

和改普通应用一模一样，**不用烧板子**：

```bash
# 编译
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh <应用名>

# 传板子
scp F:\project\Learning\RTOS\build\a55-bin\<应用名>.bin root@<板子IP>:/tmp/

# 板上重载
jailhouse cell shutdown freertos
jailhouse cell destroy  freertos
jailhouse cell create /usr/share/jailhouse/cells/imx95-harpoon-freertos.cell
jailhouse cell load freertos /tmp/<应用名>.bin -a 0xf0000000
jailhouse cell start freertos
```

### 2.6 配置要不要改

| 配置 | 要不要改 | 说明 |
|---|---|---|
| **U-Boot 的 `jh_root_dtb` / `jh_root_mem` / `jh_clk`** | ❌ | 和跑哪个应用无关 |
| **`.cell` 文件** | 看情况 | 用**已经在 cell 里**的外设（LPUART3、TPM2、TPM4、MU3）就不用改；用别的才要加 MMIO 段和中断 |
| **`app_mmu.h` / `mmu.c`** | 看情况 | 一级页表。**cell 里有不等于 inmate 能用** —— 这是第一次上板踩过的坑 |
| **SM 配置（`mx95rte.cfg`）** | ❌ **一般不用** | A55 non-secure 段本来就写了大部分外设的 `OWNER` |
| **`FreeRTOSConfig_Gen.h`** | 看情况 | 改 tick 频率、堆大小、开栈溢出检查时要动 |

**判断顺序**（三层，缺一层的现象都是"程序直接没了"）：

```text
① SM 层：这个外设归不归 A55？      → 看 mx95rte.cfg 的 A55 non-secure 段
② cell 层：MMIO 和中断给了吗？      → 用 pyjailhouse 解 .cell
③ MMU 层：一级页表里有吗？          → 看 mmu.c / app_mmu.h
```

## 三、建议的下一步顺序

按"投入产出比"排：

| # | 做什么 | 为什么先做这个 | 工作量 |
|---|---|---|---|
| **1** | **跑一次长时间稳定性** | 一个命令的事，能一次性回答 L7 | 很小 |
| **2** | **加一个纯任务切换开销的测量** | 补上 rt_latency 的盲区，几十行代码 | 小 |
| **3** | **加一个 memcpy 带宽测量** | 顺便就把"自己写 benchmark"这条路走通了 | 小 |
| **4** | **移植 SDK 的 freertos_queue / sem / mutex 示例** | 补 L8，而且这四个示例是现成的 | 中 |
| **5** | **TPM 输出 PWM** | 补"需要 GPIO/PWM 的功能"这块，见 [[10-项目/IMX95-EVK/UART与GPIO验证方案.md\|验证方案]] | 中 |
| 6 | CoreMark 移植 | 要做标准化对比时才需要 | 大 |
