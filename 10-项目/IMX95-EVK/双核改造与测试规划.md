# A55 inmate 从 1 核到 2 核：改造清单与测试规划

> **现状**：FreeRTOS inmate 只跑在 **CPU5 一颗核**上，全部性能数据都是单核的。
> **目标**：要用**两颗 A55 核**。
>
> 本文基于**源码核对**，不是推测。所有结论都标了文件路径。

---

## 零、先把几个概念弄清

### 0.1 "inmate" 是什么

**inmate 是 jailhouse 的术语**，指"跑在一个 cell 里的裸机程序"。

**在我们的项目里，inmate 就是那个 FreeRTOS 应用** —— 但它不是"一个文件"，而是**一整套编译产物**。

看 `CMakeLists.txt` 里实际链进去的东西：

```cmake
add_executable(hello_world.elf
    "${AppPath}/freertos/main.c"        ← ① 你改的应用代码
    "${AppPath}/src/hello_world.c"      ← ② 应用的其他源文件
    "${BoardPath}/board.c"              ← ③ 板级初始化（时钟/引脚）
    "${BoardPath}/mmu.c"                ← ④ 一级页表
)

include(rtos_abstraction_layer)                  ← ⑤ RTOS 抽象层
include(device_system_ca55)                      ← ⑥ ★ A55 的系统启动代码
include(common_freertos_core_armv8a)             ← ⑦ ★ startup.S / exception.c / system.c
include(middleware_freertos-kernel_aarch64)      ← ⑧ ★ FreeRTOS 内核 + A55 port
include(driver_lpuart) / include(driver_clock)   ← ⑨ MCUXpresso 驱动
include(component_lpuart_adapter) / ...          ← ⑩ 串口组件
include(lib_hlog) / include(utility_debug_console)  ← ⑪ 日志
```

**标 ★ 的三项（⑥⑦⑧）就是多核改造要动的地方** —— 它们不是"配置文件"，是**源码**。

| 层 | 在哪 | 单核还是多核 |
|---|---|---|
| **⑥⑦ 启动代码** | `harpoon-apps/common/freertos/core/armv8a/`（`startup.S` / `exception.c` / `system.c`） | **单核** |
| **⑧ RTOS 内核 + port** | `FreeRTOS-Kernel/` + `portable/GCC/ARM_AARCH64/` | **单核** |
| ① 应用代码 | `hello_world/freertos/main.c` | 和核数无关 |

**所以"改 cell 就够了"是不够的** —— cell 只管"允许用哪些核"，
**但程序本身不会因为被允许多用一个核就自动会用。**

### 0.2 SMP 是什么，为什么需要 port 支持

**SMP = Symmetric Multi-Processing（对称多处理）。**

**和它对立的是 AMP = Asymmetric Multi-Processing（非对称多处理）。**

| | **AMP（非对称）** | **SMP（对称）** |
|---|---|---|
| 结构 | **每个核跑一个独立的 RTOS 实例** | **一个 RTOS 实例管 N 个核** |
| 任务 | 固定在某个核上 | **可以在任意核上跑、可以迁移** |
| 内存 | 每个实例各自管理 | **共用一套内核数据结构** |
| 调度 | 各管各的 | **全局统一调度** |
| 核间通信 | 需要显式做（共享内存/消息） | 内核天然支持 |
| 类比 | 两个人各开各的车 | 一辆车两个司机轮班 |

**为什么 SMP 需要 port 支持**（关键）：

FreeRTOS 的**内核代码是共用的**，但**"怎么操作 CPU"这部分在 port 层**（汇编）。
单核 port 里有大量假设，在多核下全部不成立：

| 单核 port 的假设 | 多核下为什么不成立 |
|---|---|
| **只有一个"当前任务"**（`pxCurrentTCB` 是单个指针） | **每个核各有自己的当前任务**，必须变成数组 |
| **关中断就安全了** | 核 A 关中断，**核 B 照样在跑**，共享数据还是会被改 |
| **切任务就是改自己的寄存器** | 要能**中断别的核**让它也切（核间中断） |
| **tick 中断只有一个** | 得**只在一个核上开 tick**，否则计数重复 |
| 栈指针只有一个 | **每个核要有自己的栈** |

**所以这不是"配置改改"，而是 port 层（汇编 + GIC 操作）的实质移植。**

**NXP 论坛给的 A53 SMP 移植清单，一共 13 项**（原文：SMP Porting Checklist - A53 *4 as reference）：
配置宏 6 项、`xPortStartScheduler` 要唤醒其他核、`pxCurrentTCB` 改数组、
中断掩码的保存/恢复、**两个自旋锁**、`portGET_CORE_ID`（读 `MPIDR_EL1`）、
`portYIELD_CORE`（用 SGI 中断别的核）、GIC 集成、tick 只在主核……

**每一项都涉及 port 层的汇编和 GIC 操作。**

### 0.3 现成的 AArch64 SMP port 有没有

**查下来的结论**：

| 来源 | 状态 |
|---|---|
| **FreeRTOS 官方主仓库**（我们用的这份 V11.0.1） | `portable/` 树下**没有 AArch64 的 SMP port** |
| **官方有一个 PR 在做**（#1138 "Make ARM_AARCH64 Port SMP ready"） | **未合并** |
| **TI 的合作伙伴 port**：`CORTEX_A53_64-BIT_TI_AM64_SMP` | 存在，但是**给 TI AM64x 的**，而且**还没更新到 FreeRTOS v11**（官方论坛回复确认） |
| **NXP 的 harpoon-apps** | SMP **只在 Zephyr 侧**（`audio/zephyr/boards/*_smp.conf`、`build_smp.sh`），**FreeRTOS 侧没有** |

**所以：现成的、能直接用在 i.MX95 A55 上的 SMP port，没有。**

### 0.4 ★ NXP 回复：jailhouse 侧支持 SMP，卡点在 FreeRTOS

**2026-10-09 向 NXP 的 Dongbo Wang 确认，回复原文**：

> Harpoon/Jailhouse 本身支持SMP，修改配置文件就行，
> ```
> .cpus = {
>     0x6,    /* CPU1 + CPU2 */
> }
> ```
> 需要FreeRTOS也得支持SMP

**这两句话把问题定性了**：

| 层 | 支持情况 |
|---|---|
| **Jailhouse / Harpoon** | ✅ **支持 SMP**，**只要改 cell 配置** |
| **FreeRTOS** | ⚠️ **"也得支持 SMP"** —— 意思是这是个前提条件，**得先确认它支不支持** |

**他给的 `.cpus = { 0x6 }` 是 jailhouse cell 的 C 源码配置格式**（不是二进制 `.cell`）：

```text

```

**位图的约定和我们查到的一致**（一位对一个核）。**我们的 cell 现在是 `0x20`（只有 bit5 = CPU5），改成 `0x30`（bit4+bit5 = CPU4+CPU5）即可。**

**所以 cell 那层不是问题。真正的卡点是：这份 FreeRTOS 到底有没有 SMP port。**

### 0.6 链接脚本只有一套栈，影响什么

链接脚本里：

```ld
STACK_SIZE = 0x1000;      /* 4 KB */
...
__el1_stack = .;          /* 只有一套 */
__el0_stack = .;          /* 只有一套 */
```

**`startup.S` 里 `msr spsel, #1; ldr x0, =__el1_stack; mov sp, x0`** ——
**两个核都往同一个地址装栈指针。**

**后果**：

```text
核 A 压栈 →  写到 __el1_stack 附近
核 B 压栈 →  也写到 __el1_stack 附近
        ↓
    互相覆盖
        ↓
任务局部变量被踩、返回地址被改
        ↓
随机崩溃，而且现象不固定（很难查）
```

**这不是"性能下降"，是"根本跑不起来"。**

**改法**：每个核一套栈，比如：

```ld
__el0_stack_core0 = .;  . += STACK_SIZE;
__el0_stack_core1 = .;  . += STACK_SIZE;
__el1_stack_core0 = .;  . += STACK_SIZE;
__el1_stack_core1 = .;  . += STACK_SIZE;
```

然后 `startup.S` 里**先读 `MPIDR_EL1` 判核号，再选对应的栈**。

**这两个改动（`startup.S` 读 MPIDR + 链接脚本分栈）是 AMP 和 SMP 都要做的共同前提。**

## 一、现状：这套 inmate 是彻底单核的

四份源码证据：

### ① cell 只分配了一个核

解码 `imx95-harpoon-freertos.cell`（772 字节）得到：

```text
cpu_set_size   = 8B                    ← 8 字节的 CPU 位图（够 64 个核）
cpu_set        = 2000000000000000      ← 只有 bit5 置位
   -> assigned CPUs = [5]              ← 只给了 CPU5
cpu_reset_address = 0xf0000000         ← 所有核都从这个地址启动
```

**关键**：`cpu_reset_address` 是**一个**地址，不是每个核一个 —— 如果加了第二个核，**两个核都会从 `0xf0000000` 开始执行**。

### ② 启动代码完全不区分核

`common/freertos/core/armv8a/startup.S`（294 行）搜 `MPIDR` / `core` / `affinity` / `wfe` / `sev`：

```text
(无匹配)
```

**`Reset_Handler` 直接就开始配 `VBAR_EL1`、`SCTLR_EL1`、栈指针** ——
**没读 MPIDR、没判断自己是哪个核、没有从核等待逻辑。** 纯单核启动。

### ③ 链接脚本只有一套栈

`MIMX9596xxxxx_ca55_ddr_ram.ld`：

```ld
STACK_SIZE = 0x1000;      /* 4 KB */
...
__el1_stack = .;          /* 只有一套 EL1 栈 */
__el0_stack = .;          /* 只有一套 EL0 栈 */
```

**两个核跑同一个二进制会共用同一套栈 —— 必然踩踏。**

### ④ FreeRTOS 侧没有 SMP port

FreeRTOS-Kernel 版本是 **V11.0.1**（`include/task.h` 里的 `tskKERNEL_VERSION_NUMBER`），
内核里有 `#if ( configNUMBER_OF_CORES == 1 )` 的分支，**说明内核支持 SMP**。

**2026-10-09 复核（更硬的证据）**：

```text
grep -c configNUMBER_OF_CORES  FreeRTOS-Kernel/tasks.c   ->  196      ← 内核确实有 SMP 分支
grep -rl portGET_CORE_ID       FreeRTOS-Kernel/portable/ ->  （空）    ← 但没有任何 port 实现它
grep -rl portYIELD_CORE        FreeRTOS-Kernel/portable/ ->  （空）
```

`include/FreeRTOS.h:401-409` 把要求写死了：

```c
#ifndef portYIELD_CORE
    #if configNUMBER_OF_CORES == 1
        #define portYIELD_CORE( x )    portYIELD()
    #else
        #error configNUMBER_OF_CORES is set to more than 1 then portYIELD_CORE must also be defined.
    #endif
#endif
```

**也就是说：只要把 `configNUMBER_OF_CORES` 设成 2，编译会直接 `#error` 停下来** ——
这不是"配一下就能开"，是 port 层缺东西，编译器会明确告诉你。

> **补一处更正**：实际编译用的 port 是 **`portable/GCC/ARM_AARCH64_SRE`**
> （构建日志里是 `FreeRTOS-Kernel/portable/GCC/ARM_AARCH64_SRE/port.c`），
> 不是 `ARM_AARCH64`。两个都在树里、都是单核，但这一个才是当前生效的，改的时候别改错。

**但是**：`portable/` 树下**没有任何 AArch64 的 SMP port**：

| 路径 | 有没有 |
|---|---|
| `portable/GCC/ARM_AARCH64` | ✅（**当前用的，单核**） |
| `portable/GCC/ARM_AARCH64_SRE` | ✅（单核） |
| `portable/GCC/ARM_CA53_64_BIT` | ✅（单核） |
| **AArch64 的 SMP port** | ❌ **没有** |

而且 `common/freertos/FreeRTOSConfig.h` 里**没有定义 `configNUMBER_OF_CORES`**（取默认值 1）。

> **harpoon-apps 里的 SMP 只存在于 Zephyr 侧**
> （`audio/zephyr/boards/*_smp.conf`、`build_smp.sh`），**FreeRTOS 侧没有**。

## 二、要改什么（清单）

> **2026-10-09 复核修正**：第 3、4 两项**在 AMP 路线下都不需要做**，理由见下面两小节。
> 修正后 AMP 的实际工作量比原来估的小得多。

| # | 改什么 | 具体 | 难度 | 依据 |
|---|---|---|---|---|
| 1 | **cell 文件** | `cpu_set` 位图 byte0：`0x20`（bit5）→ **`0x30`（bit4+5）** | 🟢 小 | cell 解码 |
| 2 | **启动代码** `startup.S` | **读 `MPIDR_EL1` 判断核号**，从核跳到第二个镜像 | 🟡 中 | 现在完全没有 |
| ~~3~~ | ~~链接脚本每核一套栈~~ | **AMP 不需要**：两个镜像各自有自己的链接脚本和栈，天然不冲突。只有 SMP（一个镜像两核）才要分栈 | ✅ 免 | 见 2.2 |
| ~~4~~ | ~~主核用 SCMI `CPU_ON` / PSCI 拉起从核~~ | **不需要**：**jailhouse 在建 cell 时自己把所有核都复位启动**，两个核同时从 `cpu_reset_address` 进 | ✅ 免 | 见 2.1 |
| 3' | **第二个镜像** | 链接到另一个地址（现在一个镜像的链接脚本正好占满 16 MB，要另做一份紧凑的） | 🟡 中 | 见 2.2 |
| 4' | **两核的串口共用** | cell 里只有 LPUART3 一个串口，两核都要打印就得加自旋锁或走共享内存 | 🟡 中 | 新发现 |
| 5 | **RTOS 层** | 见第三节的路线选择 | 🔴 **看路线** | 无 SMP port |
| 6 | SM 配置 | 大概率**不用改** —— `mx95rte.cfg` 里 `A55C0`–`A55C5` 都在 A55 段 | 🟢 | 源码 |
| 7 | `app_mmu.h` | 从核要访问新外设时才加 | — | — |

### 2.1 为什么"第二核启动机制"不需要做（★ 修正）

原来第 4 项写的是"主核用 SCMI 的 `CPU_ON` 或 PSCI 把从核放出来"，**这是错的**。

**jailhouse 在 `cell start` 时会把 cell 里所有核一次性复位并启动**，
`hypervisor/control.c` 的 `cell_start()`：

```c
	pci_cell_reset(cell);
	arch_cell_reset(cell);

	for_each_cpu(cpu, cell->cpu_set) {
		public_per_cpu(cpu)->failed = false;
		arch_reset_cpu(cpu);        /* ← 对 cpu_set 里的每一个核都调一次 */
	}

	printk("Started cell \"%s\"\n", cell->config->name);
```

`arch_cell_reset()` 又把每个核的 `ELR_EL2` 设成 `cell->config->cpu_reset_address`。
所以：

```text
cell start
   ├── CPU4 ──┐
   └── CPU5 ──┴── 两个核同时从 0xf0000000 开始执行，都是"刚复位"状态
```

**没有"主核拉起从核"这一步** —— 两个核是对等的，同时起来。
**从核不是被谁唤醒的，是 hypervisor 直接放的。**

**这条修正意义很大**：原来把它当成"🟡 中 + 风险第一条（从核启动机制不明）"，
现在整个"要不要调 SCMI/PSCI 的 CPU_ON"这个问题消失了。
**唯一要做的就是让两个核在入口处分开**（第 2 项）。

代价是：原来担心的"从核启动机制不明"不再是风险。新的风险变成**"两个核同时初始化，共享的东西要小心"**
（栈、全局变量、外设）。

### 2.2 为什么 AMP 不需要"每核一套栈"（★ 修正）

原来第 3 项写的是"链接脚本每个核各自一套栈"。**这只在"一个镜像两核"（SMP）时才需要。**

如果走 AMP 用的是**两个独立镜像**（各自有自己的链接脚本、自己的 `__el1_stack`），
两个镜像的栈本来就在不同地址，**天然不冲突**。

链接脚本的实际布局（`MIMX9596xxxxx_ca55_ddr_ram.ld`）：

```ld
m_interrupts  (RX) : ORIGIN = 0xF0000000, LENGTH = 0x00002000   /*  8 KB  复位向量 */
m_text        (RX) : ORIGIN = 0xF0002000, LENGTH = 0x005FE000   /* ~6 MB */
m_data        (RW) : ORIGIN = 0xF0600000, LENGTH = 0x005FE000   /* ~6 MB */
m_stacks      (RW) : ORIGIN = 0xF0BFE000, LENGTH = 0x00002000   /*  8 KB  ★ 只有这一套 */
m_data_nc     (RW) : ORIGIN = 0xF0C00000, LENGTH = 0x00400000   /*  4 MB */
```

`0xF0000000 + 0x01000000 = 0xF1000000` —— **一个镜像的链接脚本正好把 cell 给的 16 MB 占满。**

所以第二个镜像要**另做一份紧凑的链接脚本**，把它的各段塞进这 16 MB 的剩余空间，例如：

```ld
m_interrupts  : ORIGIN = 0xF0800000   /* 注意：0x2000 对齐 */
m_text        : ORIGIN = 0xF0802000
m_data        : ORIGIN = 0xF0900000
m_stacks      : ORIGIN = 0xF0980000
m_data_nc     : ORIGIN = 0xF0A00000
```

（实际用到的只有几十 KB，6 MB 的 text 预留是虚的，压小没问题。）

**另一个选择：cell 给 32 MB**（把 `mem_regions` 里的 `0x1000000` 改成 `0x2000000`，
同时 `jh_root_mem` 要让 Linux 多让出 16 MB）。这样两个镜像都能用现有的链接脚本。
**代价是要动 U-Boot 的 `jh_root_mem`**，比改链接脚本麻烦。

**两种做法都比原来的"每核分栈 + 改 startup"简单**，因为不用碰共享的 `startup.S` 逻辑。

### 为什么从核也要从 `0xf0000000` 启动不是问题

`cpu_reset_address = 0xf0000000` 是**一个**地址给 cell 里所有核 ——
**这正是 FreeRTOS SMP 的标准做法**：所有核都从复位向量进来，
**第一条指令读 `MPIDR_EL1` 判断自己是谁**，主核继续初始化，从核跳到等待循环。

**所以第 2 项（读 MPIDR）是必须做的第一步。**

## 三、两条路线

### 路线 A：AMP（非对称多处理）—— 两个核各跑一个独立的 RTOS

```text
CPU4                                CPU5
  独立 FreeRTOS 实例                  独立 FreeRTOS 实例
  自己的栈、自己的任务                 自己的栈、自己的任务
        │                                  │
        └──── 通过共享内存 / RPMsg 通信 ────┘
```

**优点**：
- **现有单核 port 直接能用**，不用移植
- 一个核崩了不影响另一个
- **这是 10.30 "核间通信响应延时" 要测的场景**

**缺点**：
- 两个 bin / 两套链接地址（或者一个 bin 里放两份镜像、从核跳到第二份）
- 负载不能自动均衡

### 路线 B：SMP（对称多处理）—— 一个 RTOS 管两个核

**优点**：任务可以跑在任一核上，负载自动均衡。

**缺点**：**需要一个 AArch64 的 SMP port，而这份 FreeRTOS 里没有。**

**要做得自己移植** —— 参考 FreeRTOS 官方的 `ARM_AARCH64_SMP`（在更新的版本或官方仓库里），
工作量大，**不适合 10.30 这个时间点**。

> **建议先走路线 A。** 它能满足"用两颗核"的要求，而且**正好就是要测的核间通信场景**。

### 3.3 但先要确认一件事："两个核"这个要求到底指什么

**这是现在最该做的一步，而且不花时间 —— 去问老大，不要自己猜。**

理由是：**"SMP cell" 这个词在 jailhouse 里和"操作系统跑 SMP"根本不是一回事。**

| 说法 | 出处 | 实际含义 |
|---|---|---|
| **"multicore (SMP) cell"** | UG10170 §1.4 原文：`For a multicore (SMP) cell, two cores can be used. For instance, on i.MX 8M: .cpus = { 0b1100, }` | jailhouse 里 **"SMP cell" = "分了不止一个 CPU 的 cell"**。它讲的是 `.cpus` 位图，**完全没说细胞里的那个 OS 是不是 SMP** |
| **"两个核跑一个 FreeRTOS"** | 任务里可能的理解 | 需要 AArch64 SMP port（现在没有） |

**关键点**：UG10170 那句话讲的是 **jailhouse 的 `.cpus` 位图**（配置层面），
**不是"RTOS 要支持 SMP"**。所以如果要求是从这句话来的，**"两个核"= "cell 里给两个 CPU"，AMP 就满足。**

而且 —— **我们自己的计划里已经写了这个理解**。`A55-FreeRTOS任务与时间安排.md`
阶段三（10/8–10/21）原文：

```text
| 双核方案 | Jailhouse cell 扩到 2 个 A55 核（或两个 cell），与单核对比 | 8 后 |
```

**"（或两个 cell）"** —— 计划制定时就认为"两个 cell"是可选做法之一。

#### 所以去确认这三个问题

| # | 问题 | 为什么要问 |
|---|---|---|
| 1 | **"两个核"是"一个 FreeRTOS 用两个核"，还是"两个核都在跑 FreeRTOS"？** | 前者要 SMP port（数周），后者 1–2 周 |
| 2 | **验收看什么？** 是看"两个核都有 FreeRTOS 在跑 + 核间通信数据"，还是要求"任务能在两个核之间迁移"？ | **如果只看前者，AMP 就够** |
| 3 | **如果确实要 SMP，10/21 这个时间点做不到，是砍范围还是延后？** | 把选择权交回去，别自己扛 |

**带着这张表去问，比问"要不要 SMP"有效得多** —— 对方只需要回答"是/不是"。

> **同时可以并行做的**：把这个歧义也写进给 NXP 的问题清单（第七节已经在问"FreeRTOS 侧支不支持多核"），
> **两手准备**：老大说 AMP 够 → 走路线 A；老大说必须 SMP → 立刻问 NXP 要 port 并申请延期。

### 3.4 NXP 的回复（2026-10-09）★

问过去之后，王工回了三条：

```text
王工: freertos 用的啥版本？
王工: 你是想 freertos 跑 smp 吗？
王工: Harpoon/Jailhouse 本身支持SMP，修改配置文件就行，
      .cpus = { 0x6, /* CPU1 + CPU2 */ }
      需要FreeRTOS也得支持SMP
```

**三条各有含义：**

| 他说的 | 确认了什么 |
|---|---|
| "Harpoon/Jailhouse 本身支持SMP，**修改配置文件就行**" | **本文第二节的第 1 项（改 cell）就是全部**。jailhouse 侧不用做别的，`cell_start()` 自己会把 `cpu_set` 里的核都启动起来（和 2.1 的源码分析一致） |
| `.cpus = { 0x6, /* CPU1 + CPU2 */ }` | 位图规则："第 N 位 = 第 N 个核"。**这是 i.MX8M 的例子**。我们板子上是 **`0x30`**（bit4+bit5 = CPU4+CPU5） |
| **"需要FreeRTOS也得支持SMP"** | **卡点被官方确认在 FreeRTOS 侧** —— 和第四节 ④ 的结论完全一致。**这不是我们看错了源码** |

**所以问题的性质变了**：不再是"要怎么改 jailhouse"，而是**"从哪拿到 AArch64 的 FreeRTOS SMP port"**。
第二节的第 2 项（`startup.S` 读 MPIDR）和第 5 项（RTOS 层）**都要等这个 port 才能动**。

**下一步就看回复**：

| 对方的回复 | 我们怎么办 |
|---|---|
| **"有 port，给你"** | 走路线 B（SMP）。省掉整个 port 移植，工作量降到"接进来 + 调通" |
| **"没有，你自己做"** | SMP 是数周级 → **立刻和老大谈范围**（AMP 过渡 or 延期），别自己扛 |
| **不回复/含糊** | 按"没有"处理，先做 AMP 过渡 |

> 顺带一句：他问"**你是想 freertos 跑 smp 吗？**" —— 说明**他也需要我们明确表态**。
> 所以"两个核指什么"这件事（3.3 节）**不仅要问老大，也要明确回复 NXP**。

## 四、测试项规划

### 阶段 0：改之前先确认（★ 最省事的一步）

**这一步的目标不是"跑起来"，而是用一个最小的实验把三个未知一次问清**：

1. CPU4 到底能不能从 Linux 手里划给 cell
2. 两个核是不是真的都从 `0xf0000000` 同时开始执行
3. `MPIDR_EL1` 在两个核上分别读出来是什么（**不要猜哪个 bit 是核号**）

#### 具体做法（约 1 小时）

**① cell 改一个字节**：**产物已生成好** ——
`build\a55-bin\imx95-harpoon-freertos-2cpu.cell`（772 字节）。

生成工具：`build\tools\cell_set_cpus.py`

```bash
python build/tools/cell_set_cpus.py \
    <原始 cell> <输出 cell> 4,5
```

**它做了什么**（逐字节对比验证过）：

```text
偏移 0x084: 0x20 -> 0x30
CPU [5]  ->  [4, 5]
位图之外一个字节都没动
```

**位图的位置**（`jailhouse_cell_desc`，packed，revision 14）：

```text
0x00 signature[5] "JHCLL"   0x30 u32 cpu_set_size（位图字节数）
0x08 name[32]               0x54 u64 cpu_reset_address
---- sizeof = 0x84 ----
0x84 cpu_set[]              ★ 位图从这开始，一位对一个核
```

脚本自带三道自检：① 先验 `JHCLL` 魔数 ② 改完重解一遍确认 CPU 列表
③ 逐字节对比确认**只有位图范围内的字节变了**。

**② `startup.S` 在 `Reset_Handler` 的最前面插一段**（在动 VBAR/栈之前，只读寄存器、不碰内存）：

```asm
Reset_Handler:
	mrs	x9, mpidr_el1          /* 读本核的 MPIDR */
	and	x10, x9, #0xFF         /* Aff0 */
	cbz	x10, 1f                /* 是主核就继续原来的流程 */
	/* 从核：把自己的 MPIDR 写到一个固定地址，然后自旋 */
	ldr	x11, =0xF0BFF000       /* 16 MB 区里挑一个没人用的地址当信箱 */
	str	x9, [x11]
0:	wfe
	b	0b
1:	/* 主核：原来的 Reset_Handler 继续 */
	ldr	x0, =vectors
	msr	vbar_el1, x0
	...
```

**③ 主核那边读信箱并把结果打出来**：

```c
uint64_t *mailbox = (uint64_t *)0xF0BFF000;
log_raw_info("secondary MPIDR = 0x%llx\r\n", (unsigned long long)*mailbox);
```

#### 判据

| 看到什么 | 说明 |
|---|---|
| 打印出 `secondary MPIDR = 0x...` | **CPU4 划过来了，两个核都从 0xf0000000 起来了，MPIDR 读得到** —— 阶段 0 全过 |
| `cell create` 报 `Device or resource busy` | 见下面的坑 |
| 什么都没有、cell 挂了 | 说明从核的自旋地址选得不对（踩到主核在用的内存） |

#### 两个要提前知道的坑

**坑 1：`cell create` 可能报 `Device or resource busy`。**
jailhouse 的 `cell_create()` 里有这一条：

```c
	/* don't assign the CPU we are currently running on */
	if (cell_owns_cpu(cell, cpu_data->public.cpu_id)) {
		err = trace_error(-EBUSY);
```

**如果发起 `cell create` 的那个进程正好跑在 CPU4 上，就会 EBUSY**（概率约 1/5）。
**解法：把命令钉在 CPU0 上跑** —— `taskset -c 0 jailhouse cell create ...`。重试几次也行。

**坑 2：从核自旋时不能用 `wfe` 单独等，要确认它不占总线。**
`wfe` 会让核进入低功耗等待，这是对的；但**如果之后要唤醒它，得用 `sev` 或核间中断**。
阶段 0 只是验证，自旋不唤醒即可。

**阶段 0 只需要改 cell 一个字节 + `startup.S` 十来行汇编**，**不动 RTOS、不动链接脚本**，
做完就知道后面该怎么走。

### 阶段 1：两核各跑一个 FreeRTOS（路线 A）

| # | 测什么 | 判据 |
|---|---|---|
| 1.1 | 主核正常跑 FreeRTOS | 现有的 hello_world 输出 |
| 1.2 | 从核也能跑 FreeRTOS | 从核的 COM 口有输出 |
| 1.3 | 两核同时跑不互相踩 | 连续跑几分钟，两边的输出都正常 |

### 阶段 2：双核性能测试

#### 2.1 单核基线重测（看加核有没有副作用）

| 项 | 为什么测 |
|---|---|
| 全部 14 项 | 加一个核之后，**单核性能有没有变化**？（cache 竞争、内存带宽被分走） |
| **特别是 memcpy 带宽和访存延迟** | 这两项最可能被第二个核影响 |

#### 2.2 新增：多核相关指标（★ 这才是双核测试的重点）

| # | 指标 | 测什么 | 怎么测 | 为什么重要 |
|---|---|---|---|---|
| **M1** | **核间通信延时** | 一个核发、另一个核收，**往返要多久** | 两个核共用一个内存区放时间戳，核 A 写、核 B 读并回写，用 `cntvct_el0` 打时间 | **★ 10.30 要交的指标** |
| **M2** | **并行加速比** | 同样的计算量分到两核，快了多少 | 同一份计算分别用 1 核 / 2 核跑，比时间 | 看负载能不能真的分摊 |
| **M3** | **共享内存带宽** | 两个核同时读写内存，各自还能拿多少 | 两核同时跑 memcpy | 看内存带宽够不够分 |
| **M4** | **共享外设竞争** | 两个核同时访问同一外设，有没有冲突、慢多少 | 两核同时写同一个 UART（用互斥量保护） | 看资源划分是否合理 |
| **M5** | **核间中断延时** | 核 A 发 IPI（核间中断），核 B 多久响应 | 用 GIC 的 SGI（Software Generated Interrupt） | 是最轻量的核间通知机制 |

#### 2.3 复用现有测试项到双核

| 项 | 怎么改 |
|---|---|
| 任务切换开销 | 同优先级任务**被分到不同核** vs **同一个核**，对比 |
| 中断延时 | 中断投递到哪个核？两个核都测 |
| tick 超调 | 两个核各自的 tick 准不准 |

### 阶段 3：稳定性

| # | 测什么 | 判据 |
|---|---|---|
| 3.1 | 长时间双核运行 | 连续跑几小时，两核都不崩 |
| 3.2 | 负载不均 | 一个核满载、一个空闲，系统还稳不稳 |

## 五、风险和工作量

| 风险 | 说明 | 应对 |
|---|---|---|
| **从核启动机制不明** | 主核怎么把从核放出来？SCMI 的 `CPU_ON` 还是 PSCI？**要先查清** | 查 `scmi_cpu.c` 和 harpoon 的 `hal_power` |
| **两核共用一个二进制** | 链接地址、栈怎么分 | 要么分两个 bin，要么一个 bin 里两段镜像 |
| **cell 的 `cpu_reset_address` 只有一个** | 两核都从 `0xf0000000` 进 | 靠 `startup.S` 读 MPIDR 分流 |
| **cache 一致性** | 两核共享内存时的 cache 一致性 | A55 是硬件一致的（同一个 cluster），**但 inmate 关了 MMU 的 cache 属性要注意** |
| **SMP port 缺失** | 如果最后要求 SMP，要移植 | **先走 AMP，SMP 单独评估** |

**工作量粗估**：

| 阶段 | 工作量 | 说明 |
|---|---|---|
| **阶段 0** | **小** | cell 改一个字节 + 写个几行的从核程序 |
| 阶段 1 | 中 | 从核启动代码 + 链接脚本分栈 |
| 阶段 2 | 中 | 复用现有测试框架，加 5 个多核指标 |
| 阶段 3 | 小 | 跑着等 |

## 六、工作量评估（★ 关键）

### 6.1 三条路线的代价

| 路线 | 要做什么 | 估计 |
|---|---|---|
| **只改 cell 试试** | cell 的 `cpu_set` 改一个字节 | **几分钟**。但结果一定是：第二个核起来了、跑到 `Reset_Handler`、**然后和核 0 撞在一起** |
| **AMP 双核** | ① cell 加核 ② `startup.S` 读 MPIDR ③ 链接脚本分栈 ④ 从核启动机制（SCMI `CPU_ON`）⑤ 从核的代码 | **1–2 周**（含调试） |
| **SMP 双核** | 上面全部 + **port 层移植（13 项，汇编 + GIC）** | **数周到数月** |

**这不是"改配置"，性质上更接近"写一个新的 port"。**

### 6.2 和"Pro 板换 EVK"那次比

两次性质不同：

| | **Pro 板 → EVK** | **单核 → 双核** |
|---|---|---|
| 性质 | **硬件层面** —— 官方不支持那块板，只能换 | **软件架构层面** —— 要改 port 和启动代码 |
| 改动 | 搬迁 + 重新验证 | **动 RTOS 的 port 层源码** |
| 影响面 | 换板就完了 | 影响**所有** inmate 应用 |
| 可回退 | 换回来就行 | 要维护分支 |

**"换板"是选型问题，"改双核"是开发问题。** 后者风险和控制难度都更高。

### 6.3 但 AMP 那条路是可控的

| 项 | 说明 |
|---|---|
| 不用碰 FreeRTOS 的 port | **现有单核 port 直接用**，只动启动代码和链接脚本 |
| 两个核各自独立 | 一个核出问题不影响另一个，**调试简单** |
| 正好对上要测的指标 | **"核间通信响应延时"就是 AMP 场景下的典型指标** |
| 工作量可控 | 1–2 周 |

**建议先把 AMP 做出来** —— 它满足"两颗 A55 核"，而且能立刻出核间通信数据。
**SMP 单独评估**（要不要做、值不值得）。
