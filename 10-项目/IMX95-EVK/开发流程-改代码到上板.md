# 开发流程：改代码 → 编译 → 上板生效

> 这份文档回答一个问题：**拿到这块板子之后，我想改点东西，代码在哪、怎么编、编完怎么让板子跑起来。**
>
> 前面几篇笔记是"从零把系统跑起来"，这篇是"跑起来之后怎么改"。
> 操作手册见 [[10-项目/IMX95-EVK/Harpoon复现.md|Harpoon 复现]]，环境搭建见 [[10-项目/IMX95-EVK/A55交叉编译环境-WSL2.md|A55 交叉编译环境（WSL2）]]。
>
> **证据标注**：本文里凡是标 `源码可确认` / `官方文档` / `实机验证` 的都有出处；
> 标 `待验证` 的是**还没实际做过**的步骤，照做之前先留个心眼。

## 零、一句话说清

**这套系统从上到下分成七层代码，每层有自己的源码、自己的编译产物、自己的"送上板子"的方式。**

**改哪一层，就只需要重做那一层 —— 绝大多数日常改动（改 RTOS 应用）根本不用重新烧板子，`scp` 拷个文件 + 重启一个服务就完事。**

这一点和以前做 M7 裸机时完全不同：那时候改一行代码就要重编、用 imx-mkimage 合成启动容器、再用 UUU 烧一遍。**Harpoon 的 inmate 是系统跑起来之后由 Linux 侧动态加载的，不在启动链里。**

## 一、先建立"分层"的概念：改哪一层，重做哪一步

### 1.1 七层总表

从上到下（越往下越底层，改动代价越大）：

| #   | 层次                  | 源码在哪                                  | 编译产物                   | 怎么送到板子                                         | 要重烧吗    |
| --- | ------------------- | ------------------------------------- | ---------------------- | ---------------------------------------------- | ------- |
| 1   | **RTOS 应用**（inmate） | `harpoon-apps/<应用>/`                  | `<应用>.bin`             | `scp` 到 `/usr/share/harpoon/inmates/freertos/` | ❌ 不要    |
| 2   | **Linux 控制程序**      | `harpoon-apps/ctrl/`                  | `harpoon_ctrl`         | `scp` 到 `/usr/bin/`                            | ❌ 不要    |
| 3   | **cell 配置**         | 由 `.c` 或 pyjailhouse 生成               | `.cell`                | `scp` 到 `/usr/share/jailhouse/cells/`          | ❌ 不要    |
| 4   | **设备树 DTB**         | 内核源码 `arch/arm64/boot/dts/freescale/` | `.dtb`                 | 拷进 **boot 分区**                                 | ❌ 不要    |
| 5   | **Linux 内核**        | `real-time-edge-linux`                | `Image`                | 拷进 **boot 分区**                                 | ❌ 不要    |
| 6   | **U-Boot / ATF**    | `real-time-edge-uboot` / `imx-atf`    | 合进 `imx-boot` 容器       | **UUU 写裸区**                                    | ✅ **要** |
| 7   | **SM 固件**（M33）      | `imx-sm`                              | `m33_image.bin` → 合进容器 | **UUU 写裸区**                                    | ✅ **要** |

### 1.2 为什么 1–5 不用重烧，6–7 要

**关键区别：这段代码是"谁在什么时机加载的"。**

| | 1–5 层 | 6–7 层 |
|---|---|---|
| 谁加载 | Linux 内核 / jailhouse 服务，**系统已经跑起来之后** | **Boot ROM**，上电时 |
| 从哪读 | 文件系统（root 分区）、boot 分区（FAT） | 分区表之前的**裸区** |
| 怎么换 | 覆盖文件即可 | **必须重写裸区**，只能走 UUU/fastboot |
| 什么时候生效 | 重启对应服务 / 重启系统 | **必须重新上电** |

**Boot ROM 只会从固定位置读一个东西**：那个 `imx-boot` 容器（里面有 SPL、ATF、U-Boot）。容器里没有 SM，SM 是容器里的代码再去加载的。所以 U-Boot / ATF / SM 任何一个改了，都要重新合成容器、重新烧裸区。

### 1.3 系统在板子上长什么样（对照着看）

```text
SD 卡（mmcblk1）
├── 裸区（分区表之前）
│     └── imx-boot 容器 = SPL + DDR训练(OEI) + ATF + U-Boot + SM固件    ← 第 6、7 层
├── mmcblk1p1   256 MB   boot 分区（FAT）
│     ├── Image                        ← 第 5 层（内核）
│     ├── imx95-19x19-evk-harpoon.dtb  ← 第 4 层（设备树）
│     ├── imx95-19x19-evk-root.dtb
│     └── 几十个其它 .dtb / .dtbo
└── mmcblk1p2   ~11.1 GB root 分区（ext4）
      ├── /usr/share/harpoon/inmates/freertos/hello_world.bin   ← 第 1 层
      ├── /usr/share/harpoon/inmates/freertos/rt_latency.bin
      ├── /usr/bin/harpoon_ctrl                                 ← 第 2 层
      ├── /usr/share/jailhouse/cells/imx95-harpoon-freertos.cell ← 第 3 层
      ├── /etc/harpoon/harpoon.conf
      └── /lib/firmware/jailhouse.bin
```

**板子上的 boot 分区在 Linux 里挂在 `/run/media/boot-mmcblk1p1/`。**

## 二、VSCode 开发环境

### 2.1 用 WSL Remote，不要在 Windows 侧直接编

**源码放在 WSL 自己的文件系统里**（`~/hww`），不要放 `/mnt/f`。跨 `/mnt/f` 访问在 WSL2 里有几十倍性能损失，`west update` 和几千个文件的编译会慢到没法用。

#### 先装扩展（不装打不开 WSL 里的文件）

VSCode 里 `Ctrl+Shift+X` → 搜 `WSL` → 装 **`ms-vscode-remote.remote-wsl`**（微软官方）。

#### 打开文件夹

按 `F1`（或 `Ctrl+Shift+P`）→ 输入 **`WSL: Open Folder in WSL`** → 填：

```text
/home/chen/hww/harpoon-apps
```

打开后**左下角应显示 `WSL: Ubuntu`**，集成终端也自动是 WSL 里的。

> **不要用 `\\wsl$\IMX95A55\home\chen\hww\harpoon-apps` 这种 UNC 路径打开**。
> 那样是跨 Windows/WSL 文件系统编辑，很慢，而且**终端不在 WSL 里**，工具链变量全都读不到。

### 2.2 环境变量要能被 VSCode 读到

工具链路径写在 `/etc/profile.d/imx95a55.sh` 里（见 [[10-项目/IMX95-EVK/A55交叉编译环境-WSL2.md|A55 交叉编译环境]]）：

```bash
export ARMGCC_DIR=/opt/arm-gnu-toolchain-13.2.Rel1-x86_64-aarch64-none-elf
export PATH=$ARMGCC_DIR/bin:$PATH
```

**坑**：VSCode 的集成终端默认可能不是登录 shell，读不到 `/etc/profile.d/*`，`ARMGCC_DIR` 会是空的。
在 VSCode 设置里把默认 profile 指定成登录 shell：

```jsonc
// settings.json
"terminal.integrated.defaultProfile.linux": "bash",
"terminal.integrated.profiles.linux": {
  "bash": { "path": "/bin/bash", "args": ["-l"] }   // -l = 登录 shell
}
```

**判断方法**：开个终端敲 `echo $ARMGCC_DIR`，有输出就对了。

### 2.4 代码补全怎么配

`compile_commands.json` 是给 clangd / C/C++ 扩展用的编译数据库，有了它才能正确跳转和补全。

**harpoon-apps 默认不生成它**（`实机验证`：编译完 `armgcc_aarch64/` 下只有 `CMakeCache.txt`、`Makefile`、`output.map`，没有 `compile_commands.json`）。

在 `hello_world/freertos/boards/imx95lpd5evk19/armgcc_aarch64/CMakeLists.txt` 里加一行，再重编：

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

然后在 VSCode 的 `.vscode/settings.json` 里指给它：

```jsonc
{
  "clangd.arguments": [
    "--compile-commands-dir=${workspaceFolder}/hello_world/freertos/boards/imx95lpd5evk19/armgcc_aarch64"
  ]
}
```

**`待验证`**：这一步没实际做过，只是按 CMake 的通用做法给的。

## 三、源码从哪来

### 3.1 RTOS 应用和 Linux 控制程序 —— west

`west` 是 Zephyr 项目的多仓库管理工具，harpoon-apps 用它一次拉齐所有依赖。

```bash
cd ~
west init -m https://github.com/NXP/harpoon-apps --mr harpoon_3.3.0 hww
cd hww
```

**`west init` 只是建了个壳，真正拉代码是 `west update`。** 默认会把 `west.yml` 里列的全部项目拉下来，**包括我们用不到的 Zephyr（约 1GB）、GenAVB_TSN、rtos-abstraction-layer**。

**只拉 FreeRTOS 需要的**：

```bash
cd ~/hww
west update mcux-sdk FreeRTOS-Kernel CMSIS_5 heterogeneous-multicore \
            mcux-sdk-middleware-multicore rpmsg-lite
```

| 项目 | 要不要 | 说明 |
|---|---|---|
| `harpoon-apps` | ✅ | 应用本体（`west init` 已经拉下来了） |
| `mcux-sdk`、`CMSIS_5` | ✅ | 驱动和 CMSIS |
| `FreeRTOS-Kernel` | ✅ | 内核 |
| `heterogeneous-multicore`、`mcux-sdk-middleware-multicore`、`rpmsg-lite` | ✅ | RPMsg 核间通信 |
| `zephyr`、`hal_nxp` | ❌ | 另一个 RTOS，我们只用 FreeRTOS |
| `GenAVB_TSN`、`rtos-abstraction-layer` | ❌ | 只有 audio / industrial 应用要用 |

## 四、六条改动路线

### 路线 A：改 RTOS 应用代码（最常见，★ 已实测）

**场景**：改 `hello_world` 的打印内容、给 `rt_latency` 加个测试项、自己写一个新应用。

**状态**：`实机验证` —— 2026-09-22 把 `hello_world` 改成打印 `Goodbye world` + `0 1 0 1`，改完重新编译、传到板子、重新加载 cell，COM9 正常出新的输出。

#### 源码位置（实测路径）

```text
harpoon-apps/
├── <应用名>/                              ← 应用自己的代码
│   ├── freertos/
│   │   ├── main.c                         ← ★ 应用逻辑，入口在 main()
│   │   └── boards/imx95lpd5evk19/armgcc_aarch64/
│   │       ├── CMakeLists.txt
│   │       ├── build_ddr_release.sh       ← 编译入口
│   │       ├── build_ddr_debug.sh
│   │       └── clean.sh
│   └── zephyr/
├── common/                                ← ★ 所有应用共用的板级代码
│   ├── freertos/boards/imx95lpd5evk19/
│   │   ├── board.c / board.h              ← 板级初始化
│   │   ├── mmu.c                          ← ★ MMU 映射
│   │   ├── memory.h                       ← 内存布局
│   │   ├── hal_config.h                   ← HAL 配置
│   │   ├── sm_config.h                    ← SM 接口配置
│   │   └── armgcc_aarch64/
│   │       ├── MIMX9596xxxxx_ca55_ddr_ram.ld   ← ★ 链接脚本（地址就是这里定的）
│   │       ├── MIMX9596xxxxx_ca55_ram.ld
│   │       └── flags.cmake
│   └── boards/imx95lpd5evk19/
│       ├── rpmsg_config.h                 ← RPMsg 核间通信
│       └── gen_sw_mbox_config.h
└── ctrl/                                  ← Linux 侧控制程序（路线 B）
```

**两个容易踩的点**：

1. **应用代码和板级代码是分开的**。`main.c` 在应用目录下，但**板级代码全在顶层 `common/` 里，所有应用共用一份**。`hello_world/freertos/boards/imx95lpd5evk19/armgcc_aarch64/` 里**只有 CMake 和编译脚本，没有板级 `.c` 文件**。改 `common/` 里的东西会影响所有应用。
2. **UG10170 §6.3 里写的 `app_board.h` / `app_mmu.h` / `pin_mux.c` 是 audio 应用的文件名**，i.MX95 上 hello_world / rt_latency 用的是上面这套 `board.c` / `mmu.c`。别照着文档找文件，找不到。

#### 改哪几个文件

| 想改什么 | 改哪个文件 |
|---|---|
| **应用逻辑**（最常改） | `<应用>/freertos/main.c` |
| 板级初始化（时钟、引脚、内存） | `common/freertos/boards/imx95lpd5evk19/board.c` |
| **MMU 映射**（要用新外设时） | `common/freertos/boards/imx95lpd5evk19/mmu.c` |
| 内存布局 | 同目录 `memory.h` + `armgcc_aarch64/MIMX9596xxxxx_ca55_ddr_ram.ld` |
| 串口 / SM 接口 | 同目录 `hal_config.h`、`sm_config.h` |
| RPMsg 通信 | `common/boards/imx95lpd5evk19/rpmsg_config.h` |

#### `main.c` 长什么样（hello_world 原文）

```c
__WEAK void BOARD_InitClocks(void) {}
__WEAK void BOARD_InitPlatform(void) {}

int main(void)
{
    BaseType_t xResult;

    BOARD_InitMemory();          /* 内存 */
    BOARD_InitPlatform();        /* 平台 */
    BOARD_InitClocks();          /* 时钟 */
    BOARD_InitDebugConsole();    /* 调试串口 */

    xResult = xTaskCreate(hello_func,  "Hello_task",  ..., hello_task_PRIORITY,  NULL);
    xResult = xTaskCreate(tictac_func, "Tictac_task", ..., tictac_task_PRIORITY, NULL);

    vTaskStartScheduler();       /* 启动调度器，不返回 */
    for (;;);
}
```

`BOARD_InitClocks()` / `BOARD_InitPlatform()` 在 `main.c` 里是 **`__WEAK` 空实现**，真正的实现在 `common/freertos/boards/imx95lpd5evk19/board.c` 里，链接时把弱符号覆盖掉。

**改应用就是改 `hello_func` / `tictac_func`，或者自己 `xTaskCreate` 加任务。**

#### ★ 链接地址 `0xf0000000` 是哪来的

**它是链接脚本里 `m_interrupts` 段的起始地址**（`MIMX9596xxxxx_ca55_ddr_ram.ld`）：

```ld
ENTRY(Reset_Handler)

MEMORY
{
  itcm          (RX) : ORIGIN = 0x203C0000, LENGTH = 0x00020000  /* 128 kB */
  dtcm          (RW) : ORIGIN = 0x20400000, LENGTH = 0x00020000  /* 128 kB */
  ocram_text    (RX) : ORIGIN = 0x20480000, LENGTH = 0x00030000  /* 176 kB */
  ocram_data    (RW) : ORIGIN = 0x204B0000, LENGTH = 0x00030000  /* 176 kB */
  m_interrupts  (RX) : ORIGIN = 0xF0000000, LENGTH = 0x00002000  /*   8 kB */  ← ★
  m_text        (RX) : ORIGIN = 0xF0002000, LENGTH = 0x005FE000  /*  ~6 MB */
  m_data        (RW) : ORIGIN = 0xF0600000, LENGTH = 0x005FE000  /*  ~6 MB */
  m_stacks      (RW) : ORIGIN = 0xF0BFE000, LENGTH = 0x00002000  /*   8 kB */
  m_data_nc     (RW) : ORIGIN = 0xF0C00000, LENGTH = 0x00400000  /*   4 MB */
}
```

**所以 `cell load -a 0xf0000000` 不是随便定的，它必须等于链接地址。** 程序按这个地址编好了绝对跳转和符号地址，加载到别处就飞。

**三处必须一致**：

| 位置 | 值 |
|---|---|
| 链接脚本 `m_interrupts` 的 ORIGIN | `0xF0000000` |
| cell 文件里带 `LOAD` 标志的内存区 | `0xf0000000` |
| `jailhouse cell load ... -a` 的参数 | `0xf0000000` |

**每次编完核对一下**：

```bash
aarch64-none-elf-readelf -h ddr_release/<应用名>.elf | grep "Entry point"
# 应该输出：Entry point address: 0xf0000000
```

**改了链接脚本，cell 文件和 `-a` 参数都要跟着改。**（`源码可确认`）

#### 编译

**方式一：用封装脚本（推荐）**

```bash
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh [应用名] [debug|release]

# 例：
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh                # 默认 hello_world release
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh rt_latency     # 编 rt_latency
bash /mnt/f/project/Learning/RTOS/build/tools/build_a55.sh hello_world debug
```

脚本做四件事：设工具链变量 → `cd` 到应用目录 → 跑 `build_ddr_release.sh` → **把 bin 拷到 Windows 侧的 `F:\project\Learning\RTOS\build\a55-bin\`**，最后打印入口地址检查。

**方式二：手动**

```bash
export ARMGCC_DIR=/opt/arm-gnu-toolchain-13.2.Rel1-x86_64-aarch64-none-elf
export PATH=$ARMGCC_DIR/bin:$PATH

cd ~/hww/harpoon-apps/<应用名>/freertos/boards/imx95lpd5evk19/armgcc_aarch64
./build_ddr_release.sh
# 产物：ddr_release/<应用名>.bin
```

- **`imx95lpd5evk19` 就是本板的板名**；15x15 那块是 `imx95lp4xevk15`
- 两个编译脚本：`build_ddr_release.sh`（代码跑在 DDR）、`build_ddr_debug.sh`（带调试信息）

#### 工具链注意

FreeRTOS 侧用 **`aarch64-none-elf`**（**bare-metal** 版本），不是 `aarch64-linux-gnu`。

原因：inmate 跑在裸核上，不链接 Linux 的 glibc。工具链名三段含义：

| 段 | 值 | 含义 |
|---|---|---|
| 架构 | `aarch64` | ARM 64 位 |
| 系统 | `none` | **无操作系统** |
| ABI | `elf` | 裸机 ELF |

#### 部署 + 跑起来（★ 实测流程）

**① 传到板子**（在 Windows 的 PowerShell 里，不是 WSL 里）

```powershell
scp F:\project\Learning\RTOS\build\a55-bin\<应用名>.bin root@<板子IP>:/tmp/
```

板子 IP：板子上敲 `ip -brief addr`。（RTE 系统从 SD 启动，`eth1` 上通常是 `169.254.x.x` 链路本地地址）

**② 板上跑起来**

```bash
modprobe jailhouse                                   # 还没启用才要
jailhouse enable /usr/share/jailhouse/cells/imx95.cell

```


#### 另一条路：走 systemd

```bash

systemctl start harpoon
```

**区别**：systemd 方式读 `/etc/harpoon/harpoon.conf` 决定加载哪个 cell、哪个 bin；手工方式可以随时指定任意 bin 和地址。

**手工方式改完立刻能试，不用动配置；systemd 方式更接近产品形态。** 两条都通，日常调代码用手工更快。

| | |
|---|---|
| ❌ imx-mkimage 打包 | inmate 不在启动链里 |
| ❌ UUU 烧录 | 同上 |
| ❌ 重启板子 | 重启 jailhouse cell 就够 |
| ❌ 重新让内存 | 内存是 U-Boot 阶段让的，和改应用无关 |

#### 自己新建一个应用

复制一个现成的应用目录改名，改这几处：

| 要改的 | 改什么 |
|---|---|
| 目录名 | 就是应用名 |
| `<应用>/freertos/main.c` | 入口和任务 |
| `<应用>/freertos/boards/imx95lpd5evk19/armgcc_aarch64/CMakeLists.txt` | 列出要编译的源文件、要链的 MCUXpresso 驱动 |
| `common/freertos/boards/imx95lpd5evk19/mmu.c` | **★ 新用到的外设寄存器，必须在这里加 MMU 映射** |

**`mmu.c` 是最容易漏的**：inmate 是裸机程序，**没有内核替它管页表**。它要访问哪块外设寄存器，就得自己建映射。这和写 Linux 驱动完全是两回事 —— Linux 驱动里 `ioremap()` 一下就完事，裸机得手写页表项。

> **注意**：`mmu.c` 在 `common/` 下，**是所有应用共用的**。给新应用加映射会同时影响其它应用。
> 如果只是试验，可以先加着；要长期共存就得改成按应用区分。

**新应用还要配一份 cell 文件**（cell 里要写清这个应用能用哪些 MMIO 和中断），见路线 C。

### 路线 C：改 cell 配置（外设 / 中断划分）

**场景**：新应用要用一个现有 cell 里没有的外设；或者要调整分配给 RTOS 的内存、中断。

#### cell 文件里写了什么

| 内容 | 作用 |
|---|---|
| **内存区域** | 这个 cell 能访问哪些物理地址范围，每个范围的权限（R/W/X）和标志（`LOAD` = 代码加载区） |
| **中断** | 这个 cell 能用哪些 GIC 中断号 |
| **虚拟 PCI 设备** | 用于 RPMsg / ivshmem 通信 |
| **CPU** | 分配给这个 cell 的核 |

之前用 pyjailhouse 解出来的 demo cell 就是这样：

```text
0x00ff900000  0x1000    R|ROOTSH        GIC 相关
0x0044380000  0x1000    R|W|IO|ROOTSH   LPUART1
0x00ff600000  0x100000  R|W|X|LOAD      inmate 代码区（1 MB）
```

harpoon 的 freertos cell 里，`LOAD` 区是 `0xf0000000`（就是 `cell load -a` 那个地址）。

#### 文件格式

**`.cell` 是 jailhouse 的二进制格式，不能直接改文本。** 生成方式有两条：

**方式一：从 `.c` 源文件编译**（jailhouse 官方做法）

jailhouse 源码树里 `tools/` 下有 cell 配置生成工具，把 `struct jailhouse_cell_desc` 写成的 `.c` 编译成 `.cell`。

**方式二：用 pyjailhouse 解析现有 cell，改完再序列化**

板上自带 pyjailhouse：

```text
/usr/lib/python3.13/site-packages/pyjailhouse/
├── config_parser.py     ← 解析
└── ...
```

关键结构定义（`config_parser.py`，`源码可确认`）：

```python
CellConfig._HEADER_FORMAT = '=5sBH32s4xIIIIIIIIIIQ8x32x'
Irqchip._IRQCHIP_FORMAT   = 'QIIQQ'    # 32 字节
```

**`待验证`**：**方式二没有实际做过**。序列化回去能不能被 jailhouse 接受，没验证过。真要改 cell，建议用方式一 —— 拉 jailhouse 源码，用它的工具重新生成。

#### 部署

```bash
scp <新cell>.cell root@<板子IP>:/usr/share/jailhouse/cells/
systemctl restart harpoon
```

#### 重要提醒

**cell 文件只管"jailhouse 允不允许访问"，不管"硬件允不允许"。** 这两件事是分开的：

| 层 | 谁在管 | 改哪里 |
|---|---|---|
| hypervisor 层 | jailhouse | `.cell` 文件 |
| **硬件层** | **SM 的 TRDC/RDC 配置** | **SM 的 `.cfg` 文件（路线 E）** |

**LPUART3 就是活例子**：cell 文件里把 LPUART3 的 MMIO 划给了 inmate，但 SM 把它分给了 M7，结果 inmate 一写串口就撞总线错误（SIGBUS）。**两层都要放行，缺一个都不行。**

### 路线 E：改 SM 配置（资源归属）

**场景**：要把某个外设从 M7 挪给 A55 / RTOS 用。**这是最底层、代价最大的一条路。**

#### 先理解 SM 在干什么

**SM（System Manager）** 跑在 **AON Cortex-M33** 上，是这块 SoC 上**第一个跑起来的软件**（Boot ROM 之后）。

它做三件事：

1. 配置硬件隔离机制（**TRDC / RDC**，基于总线 requester 的 DID 做访问过滤）
2. 启动其它核（A55、M7）
3. 进入服务模式，通过 **SCMI**（System Control and Management Interface）对外提供时钟、电源、传感器、引脚控制

**为了做隔离，SM 把 SoC 分成若干 "logical machine"（LM，逻辑机器），每个 LM 对硬件和 RPC API 有静态配置的访问权。**

（`源码可确认`：`imx-sm/README.md` 原文 —— *"the SM partitions the SoC into logical machines (LM) which have statically configurable access rights to both hardware and RPC API calls"*）

**LPUART3 的归属就是在这里定的，不在 jailhouse 层。**

#### 源码位置和现有的 LM 划分

```bash
git clone https://github.com/nxp-imx/imx-sm
cd imx-sm/configs/
```

现成的配置：

| 配置文件 | 用途 |
|---|---|
| `mx95evk.cfg` | **i.MX95 EVK，Linux + M7 系统测试**（我们的板子对应这个） |
| `mx95alt.cfg` | i.MX95，MCUXpresso 测试用 |
| `mx952evk.cfg` / `mx952alt.cfg` | i.MX95 **2**（另一个型号） |
| `mx94evk.cfg` / `mx94alt.cfg` | i.MX94 |

**`mx95evk.cfg` 里的 LM 划分**（`源码可确认`）：

| 行号 | 声明 |
|---|---|
| 115 | `LM0  name="SM", rpc=none, boot=1, did=2` |
| 343 | `LM1  name="M7", rpc=scmi, boot=2, skip=1, did=4` |
| 443 | `LM2  name="AP", rpc=scmi, boot=3, skip=1, did=3, default` |

后面还有一段 **A55 非安全 EENV**（`DFMT0: sa=nonsecure`），那才是 Linux 实际运行的环境。

#### ★ LPUART3 在哪一行

**这就是 SIGBUS 的源码级根因：**

| 行号 | 内容 | 属于哪个 LM |
|---|---|---|
| 245 | `LPUART2 OWNER` | LM0（SM 自己） |
| **407** | **`LPUART3 OWNER, test`** | **LM1（M7）** ← **问题就在这一行** |
| 512–517 | `PERLPI_LPUART1 / 4 / 5 / 6 / 7 / 8  ALL` | LM2（AP）的 SCMI API 白名单 —— **没有 LPUART3** |
| 792–797 | `LPUART1 / 4 / 5 / 6 / 7 / 8  OWNER` | A55 非安全 EENV 的资源表 —— **没有 LPUART3** |

**M7 段里有 LPUART3，A55 的两处（API 白名单、资源表）里都没有。** 所以 A55 域碰不到它，一读就 SIGBUS。

**对比 `mx95alt.cfg`**（643–649 行）：LPUART1 和 LPUART3–8 全在一个 LM 里。**说明"把 LPUART3 给 A55"这件事在配置上是做得到的，只是 `mx95evk.cfg` 没这么配。**

#### 要改什么

**如果要把 LPUART3 从 M7 挪给 A55**，改 `mx95evk.cfg` 三处：

```diff
  # ── LM1（M7）段 ──
- LPUART3             OWNER, test        # 第 407 行，删掉

  # ── LM2（AP）段的 API 白名单 ──
+ PERLPI_LPUART3      ALL               # 插在 513 行附近，按字母序

  # ── A55 非安全 EENV 的资源表 ──
+ LPUART3             OWNER             # 插在 793 行附近，按字母序
```

**每行的作用**：

| 段 | 作用 |
|---|---|
| **Resources** | **决定硬件访问权**（TRDC/RDC 按 DID 过滤）。这一项是 SIGBUS 的直接原因 |
| **API** | 决定这个 LM 能调哪些 SCMI 服务。少了它，Linux 侧管不了这个外设的时钟/电源/引脚 |

**注意顺序**：`Resources` 段里 CPU 必须放最前面（原文件有注释 `# CPUs must be first`）。

#### 编译 SM

**工具链是 `arm-none-eabi`（AArch32 裸机），不是编 A55 用的 `aarch64-none-elf`。** 两个工具链不能混。

```bash
# 依赖
sudo apt -y install make gcc g++-multilib srecord
export TOOLS=~/tools      # arm-none-eabi 工具链所在目录
export SM_CROSS_COMPILE=/usr/bin/arm-none-eabi-
```

**自定义配置要放在 `configs/other/` 下**，然后用 `configtool.pl` 生成配置目录：

```bash
cd ~/imx-sm
cp <你的配置>.cfg configs/other/
./configs/configtool.pl -i ./configs/other/<你的配置>.cfg -o ./configs/<配置名>
make config=<配置名> all
```

产物：**`build/<配置名>/m33_image.bin`**

（`源码可确认`：SM 的 `README.md` 给的是 `make config=mx95evk cfg` + `make config=mx95evk all`；
`configtool.pl` 那一步来自本项目之前做 M7 实验时实际用过的脚本 `tools/build-sm-m7gpio.sh`。）

#### 关于 RTE 用的那份配置

RTE 系统用的是 **`mx95rte`** 这个配置名（在 `imx-boot` 容器里能扫到这个字符串，`实机验证`）。

**公开的 `imx-sm` 仓库里没有 `mx95rte.cfg`** —— 只有 `mx95evk` / `mx95alt` / `mx952evk` / `mx952alt` / `mx94evk` / `mx94alt`。

**所以自己定制要从 `mx95evk.cfg` 出发改。** 这也意味着**没法直接看 RTE 那份配置是怎么写的**，只能从现象反推。

## 五、烧录：什么情况下要烧，烧什么

### 5.1 决策表

| 改了什么 | 要重新烧吗 | 怎么做 |
|---|---|---|
| RTOS 应用（inmate） | ❌ | `scp` + `systemctl restart harpoon` |
| `harpoon_ctrl` | ❌ | `scp` + 重新执行命令 |
| `.cell` 文件 | ❌ | `scp` + `systemctl restart harpoon` |
| 设备树 `.dtb` | ❌ | 拷进 boot 分区 + **重新上电** |
| 内核 `Image` | ❌ | 拷进 boot 分区 + **重新上电** |
| **SM 固件** | ✅ **要** | **重新合成容器 + UUU 烧** |
| **U-Boot** | ✅ **要** | 同上 |
| **ATF** | ✅ **要** | 同上 |

### 5.2 重新合成启动容器

**四个输入**（都放进 `imx-mkimage/iMX95/`）：

| 文件 | 从哪来 |
|---|---|
| `m33_image.bin` | SM 编译产物（路线 E） |
| `u-boot.bin` / `u-boot-spl.bin` | U-Boot 编译产物 |
| `bl31.bin` | ATF 编译产物 |
| `oei.bin`（可选） | DDR 初始化固件，默认不用 |

**合成命令**（`源码可确认`：`imx-mkimage/Readme.imx95`）：

```bash
cd imx-mkimage
make SOC=iMX95 flash_lpboot_sm_a55
```

**`flash_lpboot_sm_a55` 这个名字拆开看**：

| 段 | 含义 |
|---|---|
| `flash` | 生成可烧写的镜像 |
| `lpboot` | **low-power boot**，即 A55 由 SM 启动（不是单核 boot） |
| `sm` | **带 System Manager 固件** |
| `a55` | **A55 从 sd/emmc 启动**（相对的是从 flexspi nor） |

**其它可选目标**（同一份 Readme）：

| 目标 | 用途 |
|---|---|
| `flash_singleboot` | **不带 SM**，单核启动 |
| `flash_lpboot_sm` | 只有 SM，不带 A55 |
| `flash_lpboot_sm_a55` | **SM + A55 从 SD/eMMC 启动** ← **本板用这个** |
| `flash_lpboot_sm_all` | SM + A55 + M7（TCM） |
| `flash_lpboot_sm_m7_ddr` | SM + M7 在 DDR 里跑 |
| `flash_lpboot_sm_a55_flexspi` | A55 从 flexspi NOR 启动 |

**常用附加参数**：

| 参数 | 作用 |
|---|---|
| `LPDDR_TYPE=lpddr4` | 默认是 LPDDR5，换 LPDDR4x/LPDDR4 要加 |
| `MSEL=m` | 传给 SM 的 mode select 值，用来在运行期选不同启动配置（启动哪些核等） |
| `OEI=YES` | 启用 OEI 镜像（DDR 初始化固件） |
| `UBOOT_LOAD_ADDR=...` | **i.MX95 默认 `0x90200000`**，U-Boot 版本不对的话要改 |

**产物**：`flash.bin`（或按目标命名的变体），大小约 2.7 MB。

### 5.3 用 UUU 烧

#### 进串行下载模式

**硬件动作**：断电，把启动模式开关 **SW7** 拨到 USB 串行下载位，接 USB 线到 **J8**，上电。

> **注意 EVK 上两个开关容易混**：
> **SW7 = 启动模式开关**，**SW4 = 电源开关**。
> （Pro 板的 SW4 才是启动开关，别搞混。）

#### 执行烧写

```powershell
.\tools\uuu-1.5.243\uuu.exe -b sd_all `
  ".\Real-time_Edge_v3.3_IMX95-19X19-LPDDR5-EVK\real-time-edge\imx-boot-imx95-19x19-lpddr5-evk-sd.bin-flash_a55" `
  ".\Real-time_Edge_v3.3_IMX95-19X19-LPDDR5-EVK\real-time-edge\nxp-image-real-time-edge-imx95-19x19-lpddr5-evk.rootfs.wic.zst"
```

#### `sd_all` 到底做了什么

（`源码可确认`：从 `uuu.exe` 里提取出的脚本原文）

```text
SDP: boot -f _flash.bin                                    ← 把 bootloader 下载进 RAM 并跳转
...
FB: ucmd setenv fastboot_dev mmc
FB: ucmd setenv mmcdev ${sd_dev}
FB: ucmd mmc dev ${sd_dev}
FB: flash -raw2sparse all _image                           ← 写 wic 整盘（分区表 + p1 + p2）
FB: flash -scanterm -scanlimited 0x800000 bootloader _flash.bin   ← 写 bootloader 到裸区
FB: done
```

**关键点**：**UUU 一开始不是在烧写，是先把 bootloader 塞进内存跑起来**（`SDP` = Serial Download Protocol），拿到一个能用的 U-Boot 之后，真正的写入交给 U-Boot 的 fastboot 做。

**两个文件的分工**：

| 文件 | 写什么 | 写到哪 |
|---|---|---|
| wic（第二个参数） | 分区表 + boot 分区 + root 分区 | SD 卡偏移 0，整盘 |
| `imx-boot`（第一个参数） | **启动容器**（SPL + DDR 训练 + ATF + U-Boot + SM） | **分区表之前的裸区** |

**顺序不能反**：脚本先写 wic（`all` 会覆盖整盘），最后才写 bootloader。**如果反过来，写 wic 会把刚烧好的 bootloader 盖掉。**

#### 只想改 bootloader / SM，不想重烧 rootfs

如果这次只改了 SM 或 U-Boot，**wic 不用重写**（1.8 GB，要 5 分钟）。用只写 bootloader 的脚本：

```powershell
.\tools\uuu-1.5.243\uuu.exe -b spl ".\路径\imx-boot-...-flash_a55"
```

`待验证`：`spl` 脚本只下载 bootloader 并跳转、不落盘，**不能用来更新板子上的 bootloader**。要只更新裸区，得用 fastboot 单烧：

```text
FB: flash -scanterm -scanlimited 0x800000 bootloader <文件>
```

**这个没实际做过，要试的话先确认 U-Boot 里的分区别名。** 保险做法还是老老实实跑 `sd_all`。

### 5.4 烧完之后的收尾

**硬件动作**：断电，把 **SW7** 拨回 SD 启动位（`x011`），重新上电。

**软件动作**：在 U-Boot 里让出内存（这一步每次冷启动都要做，除非固化）：

```text
u-boot => setenv jh_root_dtb imx95-19x19-evk-harpoon.dtb
u-boot => run jh_mmcboot
```

**想省掉每次手敲**（`官方文档` UG10170 §4.2）：

```text
u-boot => setenv bootcmd 'run jh_mmcboot'
u-boot => saveenv
```

> ⚠️ **`saveenv` 会写 U-Boot 环境区。** 之前做 A 方案时特意强调过"绝对不要跑 saveenv"，
> 那是为了保持零足迹。**现在系统已经在 SD 卡上了，固化反而是推荐做法** —— 但要知道这一条会持久化。
