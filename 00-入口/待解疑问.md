## Harpoon / Jailhouse 类

### Harpoon 方案先要"把 Linux 的硬件资源分隔"，这一步的对象和边界是什么

**问题**：Harpoon 方案里，需要先把 Linux 的硬件资源分隔开。但"分隔"具体指哪几类资源、
在哪一步做、由谁做（U-Boot 还是 Jailhouse），还需要理清。

**已有的部分答案**：

- 内存：U-Boot 阶段改（`jh_root_mem`），因为内存必须在 Linux 建立页表前就限定
- CPU、外设：`jailhouse enable` 时由 hypervisor 按 root cell 配置接管
- 外设的最终归属还受 SM 配置约束，改外设要重编 SM 并重烧启动容器

**还缺什么**：root cell 配置里到底把哪些资源"留给 Linux"，哪些"抽走"，完整的资源清单。

**怎么才能答上**：解 root cell（`imx95.cell`）的完整内容，和普通 Linux 设备树做对比。

**2026-09-22 进展**：结构位置已经探到一部分（`JHSYS` 头，`platform_info.arm` 在 `0x138`，
`gicd_base=0x48000000` 在 `0x13c`、`gicr_base=0x48060000` 在 `0x15c`，与 GICv3 布局对得上），
但按 `cell-config.h` 算 `root_cell` 的起点（应为 `0x160` 或 `0x164`）和实测的第一段内存区（`0x1f0`）
差了 4~12 字节，**没对上**。工具在 `build\tools\syscfg.py`，还没解出来。

### inmate 的 GPIO 从 cell 到物理引脚要过哪几关

**问题**：cell 里加一段 RGPIO 之后，是否就等于"能改引脚电平"？中间还有几层。

**已有的部分答案**（`源码确认`，2026-09-22）：

| 层 | 现状 |
|---|---|
| SM 资源表（TRDC/RDC） | `mx95rte.cfg` 的 A55 non-secure 段已有 `GPIO2..5 OWNER`，**已放行** |
| jailhouse cell | **缺 RGPIO 的地址段**，要自己加，`.cell` 要重新生成 |
| IOMUX 引脚归属 | A55 non-secure 段里 `PIN_GPIO_IO14/15` 是 `ACCESS`，其余 `PIN_*` 是 `OWNER`。**`ACCESS` 够不够申请改复用功能，不清楚** |
| RGPIO 内部 `PCNS`/`PCNP` | BL31 会写 `0xffffffff`。A55 是非安全态，**预计**不撞（Pro 板上 M7 是安全特权态才撞的），未实测 |
| 观察手段 | EVK **没有用户 LED、没有用户 GPIO 按键**，J37 排针默认不焊 |

**还缺什么**：`dup=2` 的 SCMI agent 是否完整继承权限；`ACCESS` 与 `OWNER` 的行为差别；
自造 `.cell` 会不会被 jailhouse 以"与 root cell 重叠"为由拒绝。

**怎么才能答上**：先只验 UART 收（不用改配置），确认 cell/SCMI/引脚这条链是通的；
再改 cell 加 RGPIO2，用 `GPIO_IO14/15` 做回环或多用表实测。

**2026-09-22 进展**：产物已做好，等上板——
带 RGPIO2 的新 cell `build\a55-bin\imx95-harpoon-freertos-gpio.cell`（17 段，name `freertos-gpio`）、
测试程序 `build\a55-bin\hello_world.bin`（菜单：读寄存器 / UART 收 / GPIO 输入 / GPIO 输出）。
步骤见 [A55 inmate 的 UART 收发与 GPIO 验证方案](../10-项目/IMX95-EVK/UART与GPIO验证方案.md) 第五节。
测试程序第一件事就是直读 `RGPIO2` 的 VERID，**能读出来就说明 cell 改动生效**，这是最先能判定的一个问题。

## 启动类

### 一个只有硬件的芯片，软件是怎么从 0 进去并跑起来的

**问题**：

1. 单片机上，CubeMX 配好、业务代码写完，点"下载"这一步**到底发生了什么**？
   - 文件是怎么被写进 Flash 的、写到了哪个地址
   - 写完以后芯片怎么知道该从哪儿开始执行
   - 那个"地址"是编译器定的还是烧录器定的
2. **同一件事在 Linux 上是怎么做的？**
   - 一块完全没有系统的板子，Linux 是怎么进去的
   - 内核那么大，它是被谁搬到内存里的
   - 搬进去之后，谁告诉 CPU "从这儿开始跑"
3. i.MX95 这种多核板子上，**打包在一起的那"一个大文件"里到底是什么**？

**已有的部分答案**（2026-09-21 抽容器字符串确认）：

多核板子的 `flash.bin` 里不止一个 bin，实测抽出的文件包括
`oei-m33-ddr.bin`、`m33-oei-ddrfw.bin`、`lpddr5_imem/dmem_v202311.bin`、
`gpd.tee.*.bin`、`imx95-19x19-frdm-pro.dtb`、`setup.bin`、`os_cntr_signed.bin`。
每个核（M33/M7/A55）都有各自的固件，按约定格式打包，由 Boot ROM 分发。
Linux 不是"一个 bin"，是内核 `Image` + `.dtb` + rootfs 三部分，且内核和 rootfs
不在这个容器里（单独放 boot 分区，U-Boot 运行时读）。

**还缺什么**：单片机的"下载"机制、容器格式的具体定义、Linux 首启动的完整链条。

**怎么才能答上**：
- 看 `imx-mkimage` 怎么把镜像拼成容器（工作区 `tools\imx-mkimage`）
- 看 AN14748（M7 镜像生成）、UUU 手册（下载协议）
- 对照 STM32 的 Flash loader 理解"下载"这一步
