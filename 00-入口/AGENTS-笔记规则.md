# 工作笔记记录规则

所有已经完成的操作、查到的资料、理解的知识点和实际遇到的问题都要及时记录到本目录。记录时按主题分类，不把不同层次的内容全部写在同一篇笔记中。

- 开发板接线、启动、串口、下载命令和现场日志记录到 `10-项目/<项目名>`。
- FreeRTOS、uC/OS-II、任务、调度器和实时性原理记录到 `20-领域/RTOS`。
- 处理器架构、多核启动、内存、System Manager和芯片资源记录到 `20-领域/芯片与平台-i.MX95`。
- 原理图、元器件、电源、接口电路和通用调试方法记录到 `20-领域/嵌入式通用`。
- 工具安装、编译器、SDK获取和命令使用方法记录到 `20-领域/工具与环境`。
- 启动镜像、Bin/ELF、Boot ROM、UUU、SD/eMMC和remoteproc记录到 `20-领域/芯片与平台-i.MX95/启动与烧录`。

本目录另外区分两类笔记：

- `项目档案`：只记录某个项目的实际过程，包括日期、板卡版本、接线、命令、日志、失败现象、排查和最终结果。项目结束后仍保留原貌，便于追溯，不要求写成通用教材。
- `知识库`：从项目中提炼出来、以后换板子或换芯片仍可能复用的知识。这里不按日期写流水账，而按概念组织内容，必须写清适用范围、原理、判断方法和来源。i.MX95专属知识可以保留，但要明确它是芯片/板卡特性，不能误当成所有嵌入式平台的通用规则。

从项目记录提炼知识时，不能直接整篇复制。先回答“这个知识离开当前项目后还能解决什么问题”，再保留原理、方法和证据；当前项目的路径、COM号、SW4状态和临时命令放在项目档案中，知识库只保留必要示例。

知识库建议按以下层次组织：

1. 嵌入式通用：启动、镜像、Bin/ELF、内存、调试、串口和下载的通用概念。
2. 芯片与平台：i.MX95的多核、System Manager、LM/TRDC、时钟、IOMUX和资源模型。
3. 启动与烧录：Boot ROM、SDP/SDPS、UUU、启动容器、SD/eMMC和remoteproc的工作机制。
4. RTOS：FreeRTOS任务、调度、通信、内存、移植和实时性测试。

项目档案中的结论只有在完成资料核对并标注适用范围后，才提炼到知识库；未经验证的猜测、特定板卡临时修改和失败命令不直接进入知识库。

每次记录区分已经完成、资料中看到但尚未验证、后续待处理三种情况。涉及实际硬件时，记录接线方式、开关状态、工具参数、现象和错误信息。不要把计划写成已经完成的结果。

进行新开发或使用新的芯片、开发板、SDK和工具前，先查找并阅读厂家官方资料。资料优先级为开发板用户手册和快速入门、芯片参考手册、SDK示例自带说明、官方应用笔记、BSP文档、工具官方文档，最后再参考社区经验。笔记中注明结论依据和适用板型，区分官方明确说明、根据源码得到的结论和仍需实机验证的判断。

## 演讲稿写作规范

以后写汇报稿、讲解稿、演讲稿时，遵守以下要求。完整流程见技能 `my_speech`（`C:\Users\chen\Desktop\资料\My_skill\my_speech`）。

1. 一次汇报产出两份文档。一份是稿子，用于口述；一份是知识梳理，逐条解释稿中出现的名词、因果和可能被追问的问题，用于应对提问。两份分开保存，不混在一篇里。
2. 先列主链再写稿。稿子只讲主链、关键动作和前因后果，细节放到知识梳理。
3. 稿子只用逗号和句号，不使用破折号、双引号、单引号、分号、冒号、括号等书面符号，方便口述。
4. 语言精简，删掉只为衔接和转折的冗余句。
5. 第一次出现的专有名词必须当场用一句话解释，并交代它的来源和前因后果。不能让听众靠猜。例如提到 Quick Boot 数据，要说明它来自原厂启动镜像、缺了会怎样。
6. 保留讲述者本人的语气、叙述顺序和用词习惯，不改成书面报告腔。
7. 事实以项目档案、源码和实机结果为准，区分已验证、资料确认和推测。
