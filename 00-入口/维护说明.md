# 维护说明（每周 10 分钟）

本库结构：**PARA 顶层分区 + 数字前缀排序 + Diátaxis 作为属性**。结构只分到二级，
再往下按主题自由建目录，别为了"整齐"把笔记切碎。

## 属性字段（每篇笔记的 frontmatter）

| 字段 | 含义 | 取值 |
|---|---|---|
| `type` | 这篇属于哪一层 | 项目档案 / 知识库 / 参考 / 索引 / 归档 / 学习方法 / 视频蒸馏 |
| `scope` | **适用范围** | 项目名、领域名或"全库" |
| `doc_type` | Diátaxis 文档类型 | 教程 / 怎么做 / 原理 / 参考 / 复盘 / 未分类 |
| `status` | 整理状态 | 待整理 / 已整理 / 待验证 / 进行中 / 已归档 |
| `evidence` | **结论的依据等级** | 见下表六档 |
| `tags` | 自由标签 | 数组 |
| `updated` | 最后整理日期 | YYYY-MM-DD |

`evidence` 的完整取值（`type` / `status` 的取值以本表为准，写别的值体检脚本会报错）：

| 取值 | 含义 |
|---|---|
| 官方资料 | 来自原厂手册、数据手册、应用笔记、板级 UM |
| 源码确认 | 读源码读出来的结论 |
| 实机验证 | 在本项目硬件上实测得到 |
| 教材课程 | 来自教材、课程、培训资料 |
| 个人观点 | 自己的判断或外部视频/他人的说法，尚未核实 |
| 推测 | 自己的推断，还没找到出处 |
| 不适用 | 索引、导航、计划这类无结论的页面 |
| 待标注 | 还没判断依据等级（**待办**） |

> 自动生成时 `doc_type` 和 `status` 多数是初判，`evidence` 一律先标 `待标注`——
> 这是故意留的**待办**，不是最终值。用 `看板-待整理.base` 逐个过。

## 每周 10 分钟做什么

1. 先跑一次体检脚本，看有没有新引入的断链或字段问题：

   ```powershell
   & "D:\笔记\99-模板\check_vault.ps1"
   ```

   输出里 `断链`、`链接内反斜杠`、`frontmatter 字段问题` 三项应当是 0；
   `缺一级标题` 只应统计到 `40-归档/`（归档不改）。

2. 打开 `00-入口/看板-待整理.base`，把 `status` 从"待整理"改成"已整理"或"待验证"。
3. 对本周新结论，把 `evidence` 从"待标注"改成实际等级（见上表）。
4. 项目笔记里冒出来的通用原理，提炼一份到 `20-领域/`，两边互相加链接。
5. 新增笔记从 `99-模板/` 起步，不要手写 frontmatter。

## 写作与整理的硬约定（2026-09-21 定）

这几条是踩过坑之后定的，改笔记时照做：

1. **表格里的内链，管道符要转义**。Markdown 表格用 `|` 分列，链接别名前必须写成 `\|`：
   `| [[路径/笔记.md\|别名]] | 一句话 | 依据 |`。
   漏了反斜杠，Obsidian 会把别名当成新的一列，整行错位。
2. **链接里不要出现反斜杠路径**。统一用 `/`，例如 `[[20-领域/Linux/Linux内核.md]]`，
   不要写 `[[20-领域\Linux\Linux内核.md]]`——后者 Obsidian 解析不了，是断链。
3. **跨文件跳转优先写库内绝对路径**（与 Obsidian 的 `newLinkFormat=absolute` 一致），
   短名只在同一目录内使用。
4. **一篇文章只留一个 H1**，与文件名主题一致；章节用 `##` 起。不要出现两个同级标题重复表达同一件事。
5. **不要留自动生成的"相关/同目录"区块**。链接必须有理由，
   "因为它在同一个文件夹"不构成理由。要链就写清两篇是什么关系。
6. **删掉没有信息量的句子**：空泛的引导语（"需要注意的是""关键在于"）、
   与正文重复的"一句话总结"、对话残留（"你说的""我们之前"）一律删。
7. **正文精简不等于内容少**。语言要短、要直，但该有的来龙去脉、
   依据、对比、取舍、排查过程都要写全（见 `AGENTS-笔记规则.md`）。
8. **结论与依据分开标**。区分"官方资料明确说明""源码可以确认""实机验证得到""推测"，
   不把推测写成事实。

## `evidence` 到底要标什么（这是唯一需要你动手的事）

每篇笔记都有一行 `evidence: 待标注`。它问的**不是**"这篇写得好不好"，
而是：**这篇笔记里的结论，是靠什么得出来的？**

四条可选值，对应四档依据强度（从强到弱）：

| 填什么 | 什么情况下填 | 例子 |
|---|---|---|
| `官方资料` | 结论来自 NXP/ARM 的官方文档：参考手册、数据手册、应用笔记（AN）、板级用户手册（UM）、SDK 文档 | "LPUART1 基地址 0x44380000" 来自 i.MX95 RM |
| `源码确认` | 结论是**读源码**读出来的：TF-A、U-Boot、imx-sm、FreeRTOS、驱动源码 | "BL31 把 GPIO2 的 PCNS/PCNP 写成全 1" 来自 TF-A 源码 |
| `实机验证` | 结论是**在这块板子上实测/实测日志**得到的 | "GPIO14 有波形、OUT=1/IN=1 同步" 是串口+引脚实测 |
| `推测` | 还没找到出处，是你自己的推断，或者只是"应该是这样" | 还没验证的猜想 |

> 一篇笔记里依据可能不止一种。**填最强的那一档**；如果同一篇里既有官方文档又有实机验证，
> 填 `实机验证`（因为实机验证最直接）。
> 有争议或自己也不确定的，填 `推测` —— 标成"推测"不丢人，**把推测当事实写下来才是问题**。
> 这就是 `AGENTS-笔记规则.md` 第 7 条的要求。

### 具体怎么做（每篇 10 秒）

1. 打开 `00-入口/看板-待整理.base`，它会列出所有 `status=待整理` 或 `evidence=待标注` 的笔记。
2. 点开一篇，看它的结论从哪来，把 `evidence:` 改成上面四档之一。
3. 顺手把 `status:` 从 `待整理` 改成 `已整理`（内容已经靠谱）或 `待验证`（还缺验证）。
4. 存盘即可，不用改别的地方。

**不用一次做完。** 每周维护时处理看板上前 10 篇就行；`20-领域/` 里的知识笔记优先，
`10-项目/` 的日志类可以最后做。

### 为什么值得做

半年后你再翻到一篇笔记，如果不知道"这是官方文档写的，还是我当时猜的"，
就**没法判断能不能拿它当依据**——严重的话会把一个猜的结论用到新项目上。
标了 `evidence`，你一眼就知道哪些能直接信、哪些要重新查。

## 看板（.base 文件）怎么用

`00-入口/` 下的 `.base` 文件不是普通笔记，是 **Obsidian Bases**（数据库视图），
用 Obsidian 1.9+ 打开即可，你库里核心插件 `bases` 已启用。

- **打开**：在左侧文件列表直接点 `.base` 文件，它就渲染成活表格。
- **新建**：`Ctrl+P` → `Bases: Create new base`；或右键文件夹 → `New base`。
- **嵌进笔记**：写 `![[00-入口/看板-全部笔记.base]]`，要指定视图就
  `![[00-入口/看板-全部笔记.base#领域知识]]`。
- **改列/改筛选**：不用手改文件，用表格工具栏的 **Properties** / **Filter** 菜单即可。

| 看板 | 用途 |
|---|---|
| `看板-全部笔记.base` | 4 个视图：全部 / 领域知识 / 项目档案 / 参考资料 |
| `看板-待整理.base` | 筛出 `status=待整理` 或 `evidence=待标注` 的笔记，每周过一遍 |

> 不想要看板就直接删掉 `.base` 文件，没有任何东西依赖它们。

## 哪些内容**不该**放进知识库

本库只放两类东西：**项目档案**（本项目的路径/命令/接线/日志/失败与验证）
和**知识库**（离开本项目仍可复用的原理与方法）。

**工作汇报类产物不放这里**，已经移到库外的 `D:\工作汇报\`：

```
D:\工作汇报├─ FRDM-IMX95-PRO│   ├─ 日报\              每日总结（领导要求的工作汇报）
│   ├─ 汇报稿\            口头汇报稿、主链、知识梳理
│   └─ 进度汇报\          阶段性进度汇报
└─ 个人\                  薪资与制度等个人信息
```

判断标准：**写给领导看的、按天/按阶段交差的 → 放库外；写给以后自己查的 → 放库里。**
汇报稿里真正可复用的技术结论，已经在 `10-项目/FRDM-IMX95-PRO/` 的
技术笔记和 `20-领域/芯片与平台-i.MX95/` 里有对应正式笔记，不会因为移走汇报稿而丢。
